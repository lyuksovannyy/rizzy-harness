# OpenHands (Agent Canvas): Round 2 source study, agents and sessions

Short answer first: the repository `OpenHands/OpenHands` at the pinned commit is **only the Agent Canvas web client and its launchers**. The agent loop, condensers, stuck detector, security analyzers, tools, ACP host, delegation tools, event persistence, the OpenAI-compatible endpoint, the resolvers and the enterprise server are **not in this repository**. What the code does show, precisely, is the client side of every one of those: the wire protocol between browser and Agent Server (a resume-by-sequence-number WebSocket), the start-conversation request (which is where the agent, its confirmation policy, its tools and its skills are actually specified), browser-executed "client tools", the backend registry, and how credentials move. That is the part worth copying.

## 3. Findings

### Sessions: the client and server split

#### The session socket is an envelope protocol with a per-conversation URL and no handshake
- What the code does: the browser opens `ws(s)://<host>[/<proxy-prefix>]/sockets/session/<conversationId>` per conversation. The frames are a closed set: `sync` (range about to be replayed), `durable` (one persisted event plus its `seq`), `transient` (published but never persisted, no `seq`), `item_started` / `delta` / `item_aborted` (streaming-text progress keyed by the id the durable event will later carry), and `error`. The file says "The URL is the protocol version — there is no handshake" and "Unknown frame types must be ignored", and `asSessionFrame` drops anything not in the set. The `durable` frame wraps the event untouched; protocol fields live on the envelope.
- Trace:
  1. Frame types and the rule that the envelope may grow: [session-frames.ts L1-L79](https://github.com/OpenHands/OpenHands/blob/d7293dfd671e23dab182fe71c247ff05f48e780b/src/types/agent-server/session-frames.ts#L1-L79).
  2. Closed set and unknown-frame drop: [session-frames.ts L81-L107](https://github.com/OpenHands/OpenHands/blob/d7293dfd671e23dab182fe71c247ff05f48e780b/src/types/agent-server/session-frames.ts#L81-L107).
  3. URL construction, including the proxy path prefix and `wss` only when the page or target is https: [websocket-url.ts L87-L115](https://github.com/OpenHands/OpenHands/blob/d7293dfd671e23dab182fe71c247ff05f48e780b/src/utils/websocket-url.ts#L87-L115).
  4. Routing: deltas go to a batcher, everything else flushes it first so nothing overtakes streamed text; `durable` advances the cursor and stamps `seq` onto the event: [conversation-websocket-context.tsx L208-L261](https://github.com/OpenHands/OpenHands/blob/d7293dfd671e23dab182fe71c247ff05f48e780b/src/contexts/conversation-websocket-context.tsx#L208-L261).
- Edge cases and failure handling: a rejected inbound message gets an `error` frame and the socket stays open ("not worth dropping over"), so the client must surface it itself ([L254-L260](https://github.com/OpenHands/OpenHands/blob/d7293dfd671e23dab182fe71c247ff05f48e780b/src/contexts/conversation-websocket-context.tsx#L254-L260)). Progress frames are never replayed, so on every (re)open the client discards open streaming slots and waits for the durable event ([L1305-L1312](https://github.com/OpenHands/OpenHands/blob/d7293dfd671e23dab182fe71c247ff05f48e780b/src/contexts/conversation-websocket-context.tsx#L1305-L1312)).
- Round 1: `new (not documented)`. Round 1 said only "HTTP plus WebSocket" and that the architecture page "does not state auth or transport details".
- For rizzy-harness: this is the closest published design to our "UI is a fold over the log" rule. Copy the split between durable (sequenced, replayable) and transient/progress (never replayed, never sequenced); our UI protocol needs exactly that distinction for streaming text.
- Confidence: traced end to end (client side). The server's `session_protocol.py` is not in this repository. (checked in review)

#### Resume is "everything after seq N", with a gap-tolerant cursor
- What the code does: the first connect asks `after_seq=<n>` where `n` comes from the REST event count read before the history page (so nothing appended in between is lost, and nothing older than the page is replayed); `-1` means the whole log. After that each socket keeps its own cursor. The cursor is not "highest seq seen" because durable frames can arrive out of order (a state update can overtake the message persisted just before it); it is the highest seq with nothing missing below it, and it steps over a hole after more than 1,024 later seqs have been seen because the server skips unreadable events and that seq never arrives. A captured wire fixture (`__tests__/fixtures/session-socket/reconnect-mid-stream.agent-server-1.47.0.json`, not line-citable) shows seq 2 delivered before seq 1, a `sync` frame with `from_seq`/`through_seq` equal to the resume point, and a `full_state` snapshot sent as a `transient` frame after `sync`.

#### The session API key travels as the first WebSocket message, never in the URL
- What the code does: local backends authenticate HTTP with `X-Session-API-Key`; Cloud uses `Authorization: Bearer` (or cookies when locked to a cloud host). On the WebSocket the key is sent as the first frame `{"type":"auth","session_api_key":...}` right after `onopen`, so it never appears in a URL or access log.

#### Sending is socket-first with an HTTP fallback when the socket has not been "served" yet
- What the code does: a message goes over the open socket as JSON with `run: true`. If the socket is closed, or open but has delivered no frame yet, it is posted over HTTP instead (`sendEvent(..., {run: true})`). The comment explains why: the server subscribes a new session socket only after the running step releases the conversation lock, so a message written to an unserved socket can be lost if the tab navigates away. On Cloud, when the sandbox is paused or starting (no runtime URL), the message is held in memory and flushed later, not an error.

#### Several backends: one active backend per tab, everything keyed by it, credentials in localStorage
- What the code does: a registry of backends (`local` or `cloud`) is stored in `localStorage` under `openhands-backends`, including each backend's `apiKey` in plain text. Exactly one backend is active per browser tab (sessionStorage first, localStorage as the fresh-tab fallback, and a `?backend=<id>&org=<id>` URL pin so a link opened in a new tab lands on the backend that owns the conversation). Services build their client from the active backend on every call; a cloud selection is forbidden from borrowing another registered local backend. Long-lived queries include the backend id and org id in their cache keys, so a switch re-fetches without a blanket invalidate. Health of every backend is polled (30 s local, 5 min cloud) and polling stops after 5 consecutive failures until the host or key is edited.

## 5. In the code but not in the documentation

- The session-socket envelope, its resume cursor (`after_seq`, highest contiguous seq, 1,024-hole step-over), the `sync` boundary and the transient `full_state` snapshot (above).
- First-message WebSocket authentication, and the one place a key is still in a URL (the bundled editor).
- Browser-executed client tools with a `localStorage` replay ledger and a result channel that is a hidden, prefixed user message.
- Plan mode as a separate read-only sub-conversation, enforced by tool set, plus the "never fall back to the parent in plan mode" send guard.
- The skill allow-list/deny-list split and the slash-command attach rule that bypasses the allow-list.
- ACP login probes executed through the generic bash endpoint, and credentials delivered as `LookupSecret` self-callbacks carrying the backend's own key.
- Backend-served JavaScript executed in the Canvas origin; the hooks file read from the project without a prompt; the `/launch?plugins=` deep link behind a trust checkbox.
- The model router: classifier prompt and score/price table shipped in the client.
- Metadata (repository, branch, profile, plugins, planner id) kept in browser `localStorage` and mirrored into server conversation tags so other browsers can recover it.
- A `/goal` loop that cancels on any inbound message, so no client-tool result is posted while it runs.
