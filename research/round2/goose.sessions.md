## 2. Architecture as it bears on this cluster

- Rust workspace; the engine is crate `goose`, the binary is `goose-cli`, the desktop client is Electron/TypeScript under `ui/desktop`. Everything a UI does goes through ACP: the desktop opens a WebSocket to `/acp` ([acpConnection.ts L136-L140](https://github.com/aaif-goose/goose/blob/14bf51817b79f6e98ca73c6eda61c11d9d5cc892/ui/desktop/src/acp/acpConnection.ts#L136-L140)).
- `AcpServer` owns one lazily built `StateMachineServices` (session manager, scheduler, providers, extension manager) that every connection shares; each client connection is an `AcpConnection` wrapping that shared state ([server_factory.rs L51-L80](https://github.com/aaif-goose/goose/blob/14bf51817b79f6e98ca73c6eda61c11d9d5cc892/crates/goose/src/acp/server_factory.rs#L51-L80), [L90-L112](https://github.com/aaif-goose/goose/blob/14bf51817b79f6e98ca73c6eda61c11d9d5cc892/crates/goose/src/acp/server_factory.rs#L90-L112)). There is no per-user or per-connection tenancy.
- Transport entry points: `goose acp` (stdio), `goose serve` (HTTP + WebSocket on `/acp`, default 127.0.0.1:3284, [cli.rs L860-L905](https://github.com/aaif-goose/goose/blob/14bf51817b79f6e98ca73c6eda61c11d9d5cc892/crates/goose-cli/src/cli.rs#L860-L905)), and the optional `roaming` feature (iroh QUIC streams handed to the same `acp::server::serve`, [server.rs L2611-L2630](https://github.com/aaif-goose/goose/blob/14bf51817b79f6e98ca73c6eda61c11d9d5cc892/crates/goose/src/acp/server.rs#L2611-L2630)).
- Persistence is one SQLite file (`sessions.db`) accessed through `SessionManager`; the agent loop is a state machine that is a fold over the stored conversation ([ops_toolcalling.rs L987-L1010](https://github.com/aaif-goose/goose/blob/14bf51817b79f6e98ca73c6eda61c11d9d5cc892/crates/goose/src/agents/state_machine/ops_toolcalling.rs#L987-L1010)).
- The agent loop runs inside the same process as the ACP server (and the shell tools run in-process or as MCP children). There is no master/worker split: the "remote" model is a client dialing a server that owns the code.

#### Schema: a conversation table, not an event log
- What the code does: four live tables. `sessions` (id, name, `session_type`, `working_dir`, token counters, `recipe_json`, `provider_name`, `model_config_json`, `goose_mode`, `parent_session_id`, `container_id`, `system_prompt_override`, ...), `messages` (autoincrement `id`, `message_id`, `role`, `content_json`, `created_timestamp`, `metadata_json`), `usage_ledger` (per-call usage rows with a compaction flag) and `session_tags` (key/value labels). #### Session ids and append path
- What the code does: ids are `YYYYMMDD_<n>` where `n` is `MAX(n)+1` computed in SQL inside the insert, or a caller-chosen id of 1-128 `[A-Za-z0-9_-]` characters (a caller id that looks like a date-prefixed number of 10+ digits is rejected so it cannot collide with the counter). `add_message` runs in a `BEGIN IMMEDIATE` transaction, clamps the new message's `created_timestamp` up to the session's current maximum (so a message prepared early and filled in later never sorts before what is stored), writes it, drops resolved "advertised tools" metadata, and bumps `updated_at`.

#### One run per session, attach/detach of connections, run cancelled when the connection drops
