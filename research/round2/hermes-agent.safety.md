## 2. Architecture as it bears on this cluster

- **Language and process model.** A large Python monorepo. One `AIAgent` process runs the loop, the tool registry and every approval decision; it always runs on the host. A "terminal backend" decides only where shell commands (and the file tools' I/O for non-local backends) run. The loop head is a `while` over `api_call_count < max_iterations` and the per-agent `IterationBudget` (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/conversation_loop.py#L1748-L1753: the loop condition), with one tool round per model response (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/conversation_loop.py#L1781-L1798: `run_tool_round` when the reply has tool calls, else `finish_text_response`).
- **Tool dispatch.** `agent/tool_executor.py` runs relay middleware, then scope block, `pre_tool_call` plugin hooks, a pruned-argument check and guardrails, then the one real dispatch (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L679-L752: `_dispatch_authorized_once`). Command approval is not in this path: it lives inside the `terminal` tool and `execute_code`.
- **Approval.** `tools/approval.py` is the gate; floors and the allowlist are in `tools/approval_floors.py`; the regex detectors (hardline and dangerous) in `tools/approval_detection.py`; the LLM "guardian" in `tools/approval_smart.py`; who-can-answer logic in `tools/approval_context.py`. The combined entry point is `check_all_command_guards` (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L1276-L1323).
- **Backends.** `BaseEnvironment.execute()` wraps every command (snapshot, cwd marker, sudo rewrite, timeout backstop) and each backend implements `_run_bash` (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/environments/base.py#L263-L282: the contract; only Local sets `uses_host_filesystem`). Local spawns `bash -c` directly; Docker uses `docker exec` into a long-lived container; SSH spawns `ssh ... bash -c` per call; Modal and Daytona use their SDKs.
- **Secrets.** Child envs are built in `tools/environments/local.py` from a blocklist in `local_env_policy.py`; `execute_code` uses a separate allowlist scrub in `code_execution_env.py`; output redaction is `agent/redact.py`; the egress proxy is `agent/proxy_sources/iron_proxy.py` plus `tools/environments/docker_egress.py`.
- **Compaction** is out of this cluster's scope (see the agents file); it is entered from the same loop.

#### Parallel tool batches: 8 workers, serialized prompts, interrupt cancels only unstarted calls
- What the code does: several tool calls in one response run on a daemon thread pool capped at 8 workers. An authorization gate serialises approval prompts so they do not interleave, and human-wait time is excluded from the batch deadline. On interrupt, pending futures are cancelled, running tools get 3 s to notice a per-thread interrupt, and tools without interrupt checks run to completion. If an interrupt is already set when the batch starts, every call gets a "skipped" result.
- Trace: `_MAX_TOOL_WORKERS = 8` (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L136-L136) → pre-batch interrupt skip (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L1578-L1596) → wait loop with interrupt and deadline (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L1439-L1495) → serialised prompts with a bounded lock (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L479-L497, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L526-L545).

### Approvals and permission rules

#### The order of command checks in code
- What the code does: for a terminal command, `check_all_command_guards` runs: (1) the container fast path, which on isolated backends returns after the user deny globs only; (2) floors: hardline patterns, runtime self-delete, the `sudo -S` guard, user deny globs; (3) a prepared batch verdict; (4) YOLO or `approvals.mode: off` → approve; (5) the permanent `command_allowlist` by exact text or glob; (6) if no human can answer, the unattended modes; (7) the dangerous-pattern findings minus session or permanent grants; (8) the smart guardian, then the human.

#### The hardline floor: what it matches and what "fails closed on unparseable quoting" means
- What the code does: hardline is a regex list: recursive `rm` of `/` (including `//`, `/.`, `/..`), system roots and `$HOME`; `mkfs`; `dd of=/dev/sd*`; redirect to a raw block device; the fork bomb; `kill -1`; shutdown, reboot, halt, poweroff, `init 0/6`, `systemctl poweroff`, `telinit`. Command-name rules are anchored to command position (start, newline, backtick, `$(`, after optional `sudo`, `env`, `exec`, `nohup`, `setsid`, `time`). Positionless rules match a quote-masked copy unless a shell carrier (`sh`, `bash`, `eval`, `source`) is present. It also blocks when a parser limit is crossed (over 128,000 chars, over 4,096 chars with no separator, or 25,000 or more separators) and when a `grep` operand cannot be lexed (an unterminated quote or a dangling backslash). That is the "unparseable" case.
- Trace: `_CMDPOS` (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L99-L103) → patterns (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L124-L157) → limits (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L933-L948) → `detect_hardline_command` (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L365-L390) → malformed lexing returns `None` (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L1016-L1021) and grep parse failures fail closed (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L1027-L1041).
- Edge cases: each rule runs over several "variants": normalised, quote-aware command-start-marked, `-c` payloads extracted from interpreters, Windows backslash paths, and deobfuscated command words (`r\m`, `r''m`) (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L1667-L1745). A parser-limit block saves the payload to `~/.hermes/cache/blocked-scripts/` and tells the agent to run `bash <file>`, which then goes through normal approval (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_floors.py#L54-L85, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_floors.py#L94-L118). The comments record real false-positive storms (118 of 125 hardline blocks in one week were benign greps).
- Round 1: `corrected`. "Piping untrusted URLs into sh" is not hardline: it is the approvable dangerous pattern "pipe remote content to shell" (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L301-L324). Shutdown, reboot and `kill -1` are hardline and Round 1 did not list them.
- For rizzy-harness: a regex floor on a string is defeatable (for example `python -c` with an encoded payload); Hermes says the matcher is not an interpreter. Treat it as a speed bump. The variant set and the "save the oversized payload as a script" recovery are worth copying.
- Confidence: `traced end to end` (checked in review).

#### The hardline floor does not run on container backends
- What the code does: `_should_skip_container_guards` returns early for `docker` without host access, and always for `modal`, `daytona`, `vercel_sandbox` and plugin backends flagged `skip_container_guards`. On that path only `_user_deny_block` runs, so hardline, the sudo guard and dangerous-pattern prompts are all skipped. The docstring states the reason: the container is the boundary.
- Trace: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L1161-L1175 → https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L1282-L1287 → deny globs only (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L1178-L1186).
- Edge cases: "host access" means `docker_mount_cwd_to_workspace` with a host cwd, or a `docker_volumes` entry starting with `/`, `~`, `./`, `../` or a drive letter (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/terminal_tool.py#L145-L162). A `-v /:/host` placed in `docker_extra_args` is not inspected by this check (confirmed in review: `_docker_has_host_access` reads only `host_cwd`/`docker_mount_cwd_to_workspace` and `docker_volumes`; extras are only appended and collision-checked for env and `--network`), and the persistent sandbox bind mounts under `~/.hermes/sandboxes` are not counted either (read from the predicate in review; not tested). Plugin backends that raise fall back to guards on.
- Round 1: `corrected`. Round 1 said the hardline floor is "refused even under YOLO/off" and implied it applies everywhere. In code it does not apply on isolated backends, and Docker loses the skip once host paths are bind-mounted.
- For rizzy-harness: if we add container sessions, do not drop the floor inside them. A container with network access can still push to a remote or exfiltrate; the floor costs almost nothing.
- Confidence: `traced end to end` (checked in review).

#### User deny globs: fnmatch over executable projections, before YOLO and on every backend
- What the code does: `approvals.deny` is a list of case-insensitive `fnmatch` globs. Each is matched against every detection variant plus, per command word in each segment, the executable (and its basename) followed by the whitespace-collapsed tail. `env` payloads and `-c` style execution-flag payloads are pushed back onto the work list and projected again. That is how `sudo`, `env`, `nohup` and `sh -c` are seen through.
- Trace: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_floors.py#L23-L42 → https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_detection.py#L1623-L1664 → block message (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_floors.py#L45-L51).
- Edge cases: an unreadable config returns no rules (fail open) (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_floors.py#L30-L33). Globs anchor at the start of the candidate, so `git push --force*` matches only where `git` is a command word.
- Round 1: `confirmed`.
- For rizzy-harness: per-segment executable projection is a good model for our `node.toml` deny list. Fail closed on an unreadable policy file instead.
- Confidence: `traced end to end` (checked in review).

#### Approvals are bound to a pattern class, not to the command, and "always" persists the class in config
- What the code does: findings are `(pattern_key, description)` pairs, where the key is the rule's description string ("recursive delete"). "session" adds the key to an in-memory per-session set; "always" also adds it to `command_allowlist` in `config.yaml`. Later commands are checked by key, so one "always" on `rm -r build` approves every future recursive delete in every session. Content rules (credential upload, invisible Unicode) need their own consent even when the first match is approved.
- Trace: findings (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L731-L740) → scope lookup by key (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L432-L445) → persistence (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L474-L487) → disk merge (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L543-L574).
- Edge cases: hand-removing an entry from `command_allowlist` takes effect on the next check (on-disk delta sync, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L414-L429). Manual allowlist entries are command text or globs, and compound commands never match them: a quote-aware scan refuses `;`, `|`, `&`, `$(`, backticks, and quoted control characters when a `-c`/`-e` option is present (https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval_floors.py#L140-L200). Session state lives in process memory and is lost on restart.
- Round 1: `new (not documented)`.
- For rizzy-harness: do not copy class-level "always". Bind a standing grant to the exact argv (or a narrow rule the owner writes) and store it in `node.toml`, not in agent-writable state.
- Confidence: `traced end to end` (checked in review).

#### The smart approver: prompt, inputs, timeout and failure path
- What the code does: the guardian runs only for commands the regexes already flagged. #### iron-proxy: how tokens map to keys, how it starts, what it binds

### Prompt injection in context and tool output

#### Threat-pattern scan: blocks project context files, warns on the user's own, tags untrusted tool output
- What the code does: one regex library has three cumulative scopes. `all` covers classic "ignore previous instructions", hidden HTML comments or divs, and curl/wget with secret variables. `context` adds role hijack, C2 vocabulary and anti-forensics. `strict` adds `authorized_keys`, `~/.ssh` writes, edits to AGENTS.md or config, and hardcoded secrets.
