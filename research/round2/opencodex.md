## 2. Architecture as it bears on this question

- **Language and process model.** TypeScript on Bun. One long-running process (`Bun.serve`) that can open up to four listeners from one `serveOptions.fetch`: the public listener, an optional unauthenticated loopback listener, a hub-management listener bound to 127.0.0.1, and link/relay listeners. Which listener a request arrived on is an `ingress` value that selects its route allow-list and its auth policy. https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/index.ts#L603-L609 (`ingressForServer`: public, unauthenticated-loopback, hub-management) and https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/index/serve-options.ts#L330-L364 (per-ingress route filtering before any handler runs).
- **One internal protocol.** Every inbound wire (Responses, Chat Completions, Anthropic Messages) is converted to an internal Responses request and run through one pipeline, `handleResponsesInner`, then converted back (findings 2 and 3).
- **A second, separate relay for "keys off the worker".** `Remote Link` (Home computer serves a Child computer through an SSH tunnel) is implemented partly in a small Rust binary, `ocx-child`. It is a different feature from Remote Workspace (finding 17, finding 37).
- **No agent loop of its own**, with exactly three bounded exceptions that run inside a request: the web-search loop, the compaction summariser turn, and the vision description call (findings 26 to 28). Remote Workspace hosts an agent only by spawning the Codex app-server (finding 29).
- Key types: `RequestPolicyView` and `DataPlaneAdmission` (auth), `TranslatorBudget` (per-request memory accounting), `OcxProviderConfig` with `apiKey` holding a literal, `${ENV}` or `keychain:<provider>` reference, `NormalizedComboConfig`/`ComboPick` (routing), `RemoteWorkspaceHub`, `RemoteWorkspaceExecutor`, `RemoteControlCipher` (Remote Workspace).

## 3. Findings

### A. The request path of a proxied model call

#### 1. Three inbound protocols, three auth rules, one admission gate
- What the code does: `POST /v1/responses`, `POST /v1/messages` and `POST /v1/chat/completions` are separate branches of one `fetch`. Each checks "draining", then resolves the caller's credential, then checks the request `Origin`, then calls `runAdmittedHttpTurn`. The Responses and Chat branches use `resolveResponsesApiAuth`, which accepts `x-opencodex-api-key` or `Authorization: Bearer` and deliberately refuses `x-api-key`; the Messages branch uses `resolveApiAuth`, which also accepts `x-api-key` (what the Anthropic SDK sends).
- Trace: `/v1/responses` auth and origin check https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/index/serve-options.ts#L1478-L1486 ; `/v1/messages` https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/index/serve-options.ts#L1570-L1580 ; `/v1/chat/completions` https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/index/serve-options.ts#L1610-L1620 ; credential header precedence https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/auth-cors.ts#L652-L691 .
- Edge cases and failure handling: a cross-origin browser request gets 403 `origin_rejected` even with a valid key. The 401 body is shaped per protocol (Anthropic error envelope for Messages).
- Round 1: `confirmed` (accepts the three wires). The per-protocol header difference is `new (not documented)`.
- For rizzy-harness: if the master proxies model calls, decide early which headers carry the node credential and refuse the others; this code keeps a Codex client's own bearer and a gateway key distinguishable only by that rule.
- Confidence: traced end to end. (checked in review)

#### 2. Translation pivots on a synthetic `http://localhost/v1/responses` request
- What the code does: the Messages handler converts the Anthropic body into a Responses body, builds `new Request("http://localhost/v1/responses", ...)` in process, and calls `handleResponses` on it; the reply stream is converted back with `responsesSseToAnthropicSse`. Chat Completions does the same. The request copy is charged to the translator budget as 3x the body bytes while the UTF-16 string and the UTF-8 request body coexist, then the body size stays charged.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/claude-messages.ts#L1240-L1262 (budget reservation and synthetic request) ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/claude-messages.ts#L1268-L1268 (`handleResponses` call) ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/claude-messages.ts#L1432-L1432 (stream converted back) ; Chat: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/chat-completions.ts#L555-L563 .
- Edge cases and failure handling: a request that exceeds the budget returns 413 `translation_buffer_limit` in Anthropic form. A non-stream JSON upstream answering a streaming client is expanded into a minimal synthetic Anthropic stream, so that path is fully buffered: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/claude-messages.ts#L1537-L1556 .
- Round 1: `confirmed` ("validated, lowered to an internal request"); the in-process loopback Request is `new (not documented)`.
- For rizzy-harness: one internal canonical request shape is what keeps three inbound wires tractable; the cost is that every wire inherits the Responses vocabulary's quirks.
- Confidence: traced end to end for Messages; read the call site for Chat.

#### 3. The pipeline has fixed phases and a passthrough shortcut
- What the code does: `handleResponsesInner` runs: prepare request, prepare transport (routing, auth), sidecar auth, effects, send budget, then either a native passthrough (OpenAI-Responses style targets, no translation), or the sidecars, then either an adapter that owns the whole turn (`runTurn`) or the generic prepare-exchange/deliver path. Admission leases are released in a `finally`.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/responses/core-pipeline.ts#L47-L49 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/responses/core-pipeline.ts#L86-L142 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/responses/core-pipeline.ts#L150-L161 .
- Edge cases and failure handling: any phase may return a `Response` instead of a state object, which short-circuits; a thrown retained-compaction error becomes 502 `invalid_compaction_summary`.
- Round 1: `confirmed` (passthrough with targeted rewrites versus adapters).
- For rizzy-harness: phase functions that return either state or a finished `Response` are a cheap way to keep one entry point honest.
- Confidence: read the definition.

#### 4. Streaming back is pull-driven; at the SSE bridge the only buffer is the default queue of one
- What the code does: `bridgeToResponsesSSE` returns a `ReadableStream` whose `pull()` calls `step()`; `step()` awaits one upstream adapter event, emits that event's frames, and stops as soon as it has emitted at least one frame. The code comment states the default queue strategy (high-water mark 1) is the only buffering layered on top of the bridge ("no custom FIFO or queuing strategy"). This is a statement about `bridgeToResponsesSSE` only: other paths do buffer (the combo preflight up to 4 MiB, the web-search loop whole iterations (findings 24, 26), and the Cursor adapter's live transport up to 32 MiB, `CURSOR_TRANSPORT_MAX_BUFFERED_BYTES` in `src/lib/translator-budget.ts` L8, used at `src/adapters/cursor/live-transport.ts` L816). So a slow client stops the upstream read; the cost per live stream is one in-flight event plus the bookkeeping the translator retains for the terminal snapshot (finished output items), each charged to a `TranslatorBudget`. The outermost wrapper on the inbound-body lease uses `highWaterMark: 0`.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/bridge/sse.ts#L902-L912 (`step`) ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/bridge/sse.ts#L1600-L1606 (HWM comment) ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/bridge/sse.ts#L1670-L1686 (`pull`/`cancel`) ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/bridge/sse.ts#L310-L330 (frame charged and released around `enqueue`) ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/inbound-body-admission.ts#L73-L134 .
- Edge cases and failure handling: client disconnect calls `cancel()`, which sets `closed`, clears the heartbeat timer, calls `cancelUpstreamOnce()` and disposes the budget, so the upstream fetch is aborted rather than drained. Budget limits (found in `translator-budget.ts`): 2 MiB per tool-call argument, 32 MiB per turn, 32 MiB per SSE event; an SSE frame is capped at 4 MiB. Exceeding one terminates the stream with `translation_buffer_limit`.
- Limits source: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/lib/translator-budget.ts#L3-L6 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/sse-frame-buffer.ts#L4-L4 .
- Round 1: `corrected` in detail. Round 1 listed a "32 MiB native-compaction body ceiling" and a "WebSocket relay 4 MiB/frame"; the 32 MiB compaction ceiling is real (finding 29), but the 4 MiB value in code is the SSE frame cap, and the live-sideband WebSocket frame cap is 50 MiB (`MAX_WS_FRAME_BYTES`, https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/index/live-sideband.ts#L24-L24 ). I did not find a 4 MiB WebSocket frame limit.
- For rizzy-harness: build back-pressure by making the response a pull stream and cancelling the upstream on drop; budget the translator state per stream, not per process.
- Confidence: traced end to end. (corrected in review: scoped the "only buffer of one" claim to the generic SSE bridge; other paths buffer more)

#### 5. Heartbeats and the stall watchdog are one timer
- What the code does: a 2-second interval does two jobs. If upstream (adapter) activity was seen since the last tick it resets the stall counter; if not it increments it, and at `ceil(stallSec*1000/heartbeatMs)` ticks (300 s on public upstreams by default) it ends the turn with `response.incomplete` and reason `upstream_stall_timeout` and cancels upstream. Independently, if nothing was written to the client for a tick it enqueues a heartbeat frame. The default frame is a typed `event: response.heartbeat`, because Codex's idle timer is armed at the SSE event level and an SSE comment line would not re-arm it; a `comment` style exists for a strict decoder (grok).
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/bridge/sse.ts#L294-L305 (why typed) ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/bridge/sse.ts#L373-L376 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/bridge/sse.ts#L1606-L1662 ; defaults https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/stall-timeout.ts#L1-L1 and https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/stall-timeout.ts#L29-L36 .
- Edge cases and failure handling: an unset budget resolves to disabled (0) for a loopback/private/`.local`/`.lan` upstream so a slow local model is not cut off; an explicit value always wins. The stall kill is synchronous and does not wait for the durability barrier (comment at line 1629). Connect (header-arrival) deadline defaults to 200 s on public upstreams: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/stall-timeout.ts#L48-L75 .
- Round 1: `confirmed` ("300 s upstream stall deadline for public upstreams", "SSE heartbeat comment every 2 s"). Corrected detail: the default heartbeat is a typed `response.heartbeat` event, not a comment; comment style is opt-in per surface.
- For rizzy-harness: an SSE keep-alive must be an event the client's parser counts, not a comment; make the stall limit depend on whether the upstream is local.
- Confidence: traced end to end.

#### 6. Inbound bodies are admitted against a shared byte budget, and 256 turns is the hard concurrency ceiling
- What the code does: the default per-request body cap is 256 MiB (decompressed); an opt-in `maxInboundBodyBytes` can raise it to 512 MiB, but only requests that raise it above 256 MiB take a reservation from a global FIFO byte budget (default 512 MiB, hard max 2 GiB). The queue holds at most 32 waiters for at most 120 s; beyond that the caller gets 503 `server_busy` with `Retry-After: 1`. The lease is shrunk to the measured body size and held until the response body finishes or is cancelled. Separately a turn gate allows 256 concurrent active turns; the 257th gets `server_busy` for "active turns".
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/request-decompress.ts#L25-L39 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/lib/inbound-body-policy.ts#L2-L3 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/inbound-body-budget.ts#L3-L4 and https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/inbound-body-budget.ts#L63-L69 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/inbound-body-admission.ts#L143-L193 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/lifecycle.ts#L33-L36 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/admitted-http-turn.ts#L26-L30 .
- Edge cases and failure handling: a declared `Content-Length` above the cap bypasses the queue and gets the normal 413 from the bounded reader; a client abort while queued removes the waiter and drains the next. The code comment on `MAX_CONFIGURABLE_INBOUND_BODY_BYTES` says the body is materialised several times (bytes, decoded bytes, string, measurement string, object) so peak RSS is a multiple of what is admitted; the budget is admission accounting, "these values do not cap RSS".
- Round 1: `new (not documented)` (Round 1 documents the 300 s deadline and sidecar caps, not the body budget or the 256-turn gate).
- For rizzy-harness: size the master's proxy against "bytes admitted", not request count; give a queue a bound and a timeout, and shed with 503 plus `Retry-After`.
- Confidence: traced end to end. (checked in review)

#### 7. Retry and send budgets bound what one logical request may spend upstream
- What the code does: one logical request carries a send budget; transient 5xx retry is capped at 3 attempts per request including recovery legs, reduced by sends already used; a combo child inherits the parent's spend; every send is also charged to a workflow-root counter keyed by `x-codex-parent-thread-id` so a fan-out cannot multiply sends.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/lib/upstream-retry.ts#L175-L175 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/responses/request-send-budget.ts#L36-L48 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/responses/request-send-budget.ts#L62-L75 .
- Edge cases and failure handling: exhausted budget raises `SendBudgetExhaustedError`; a configured `transientRetryOn5xx.attempts` is treated as the total including the first send (the comment cites an amplification bug, #4893/#4546).
- Round 1: `new (not documented)`.
- For rizzy-harness: put retry accounting on the logical request, not on each hop, from the start.
- Confidence: read the definition.

### B. Credentials, client authentication, listeners

#### 8. Provider keys are plaintext in `config.json` by default; the OS keychain is an explicit, per-provider move
- What the code does: `apiKey` holds one of three things: a literal (store kind `file`), a `$VAR`/`${VAR}` environment reference, or `keychain:<provider>[/<pool id>]`. Moving a provider to the keychain is an API action (`POST /api/providers/keychain` with `store`/`restore`) that first probes the keychain (write, read back, delete), writes and read-back-verifies each secret, and only then rewrites `config.json` with references; on failure it deletes what it wrote and leaves config untouched. Reads fail closed: an unreadable reference yields no key and a warning, "no plaintext fallback". The keychain service name is `opencodex.provider-api-key.v1`.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/providers/api-key-resolve.ts#L26-L29 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/providers/api-key-resolve.ts#L106-L125 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/providers/api-key-resolve.ts#L147-L155 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/providers/key-store.ts#L75-L121 ; route https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/management/oauth-account-routes.ts#L1180-L1192 ; env reference grammar https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/config/proxy-env.ts#L74-L80 .
- Edge cases and failure handling: a headless service or locked session returns 503 "OS keychain unavailable" and nothing moves.
- Round 1: `corrected`. Round 1 said keys are `${ENV_VAR}` references or pasted and that OAuth tokens are "kept in separate credential stores, not `config.json`"; true for OAuth tokens, but a pasted API key lands in `config.json` as plaintext unless the user opts into the keychain.
- For rizzy-harness: a master that holds provider keys should default to a secret store or an env reference, not a file; copy the verify-then-rewrite migration.
- Confidence: traced end to end. (checked in review)

#### 9. OAuth tokens and the Codex account pool are plaintext JSON files under a 0700 directory
- What the code does: `auth.json` (OAuth accounts by provider, multi-account shape) and `codex-accounts.json` (Codex pool credentials) are written through `atomicWriteFile`, which opens a temp file `wx` with mode 0600, `fchmod`s it to 0600 on POSIX, asserts the descriptor, writes, and renames. The config directory is `chmod 0700`; on Windows NTFS ACLs are applied instead. Nothing is encrypted at rest. A one-time `auth.json.pre-multiauth` backup exists and is pruned of a provider's entry when that credential is deleted.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/oauth/store.ts#L2-L19 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/codex/account-store.ts#L45-L47 and https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/codex/account-store.ts#L200-L200 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/config/atomic-write.ts#L238-L262 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/config/paths.ts#L33-L46 .
- Edge cases and failure handling: refresh is serialised with per-account lock files and an intent file so a crash mid-refresh is detected; the refresh-token rotation case is handled by a compare-and-swap on a file snapshot (see `OAuthRefreshIntent` in `oauth/store.ts`).
- Round 1: `confirmed` ("OAuth tokens kept in separate credential stores, per-account file locks"); the plaintext-at-rest fact is `new (not documented)`.
- For rizzy-harness: refresh-token rotation needs a lock and an intent record; mode 0600 plus a 0700 directory is the whole protection here, so say so in your threat model.
- Confidence: read the definition. (checked in review)

#### 10. In memory, a key lives in a per-request copy of the provider config; keychain reads are cached for the process lifetime
- What the code does: `routedProviderConfig` copies the provider row and replaces `apiKey` with the resolved value (env or keychain) for that request; the Chat adapter then builds `Authorization: Bearer <key>` from that copy. Keychain values are held in a module-level `Map` (`resolvedCache`) until a write-path invalidation; a secret replaced by another process is seen only after this process re-resolves it.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/providers/routed-config.ts#L103-L113 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/providers/routed-config.ts#L133-L135 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/adapters/openai-chat/wire.ts#L32-L33 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/providers/api-key-resolve.ts#L45-L69 .

#### 11. Logs refuse to echo a configured credential
- What the code does: before an upstream diagnostic is kept, the request log checks it against a set built from every configured credential: each provider `apiKey` and pool key (keychain and env references resolved), every credential-named field, every configured header value, and every OAuth token in `auth.json`. The set is rebuilt when the bytes of `config.json` or `auth.json` change (content digest, not mtime), values stay in memory only, and if any store or keychain reference cannot be read the set is marked incomplete and the check fails closed.
- Trace: https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/configured-credentials.ts#L1-L30 ; https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/configured-credentials.ts#L38-L38 and https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/server/configured-credentials.ts#L124-L124 ; name pattern https://github.com/lidge-jun/opencodex/blob/ddee2c20030c1f0ec852202256be877397e8f396/src/lib/redact.ts#L10-L10 .
- Edge cases and failure handling: motivated by gateways that echo a credential learned earlier; incomplete set retried after 30 s.
- Round 1: `new (not documented)`.

#### 38. Telemetry is a daily, enum-only aggregate with a daily-rotating hash; it is effective only after a notice was shown or a decision made
- What the code does: the payload (validated against a strict contract before sending) holds: schema version, a batch UUID, the day, `SHA-256(installId:day)` (the id changes every day, so days are not linkable by the hash alone), a first-report flag, version, release channel, OS, arch, install channel (npm-global, docker, desktop, ...), active minutes, request outcome counts (completed, failed, incomplete, aborted), up to 64 rows of `providerKind` (a fixed enum of about 26 kinds), `modelFamily` (fixed enum) with request and token counts (input, cache read/write, output, reasoning), and failure-cause counts from a fixed list. It is POSTed to `https://telemetry.opencodex.me/v1/events` with redirects disabled and a 10 s timeout, with jittered startup and interval timers. Consent resolution: `OCX_TELEMETRY=0/false/off/no` or `DO_NOT_TRACK=1/true/yes` wins; then an explicit `declined`/`accepted`; then, with no decision, telemetry is effective only if `noticeShownAt` is set (`default-on`), otherwise `awaiting-notice` and nothing is sent. The interactive prompt defaults to Yes; agent-driven, non-TTY or `OCX_SERVICE` starts print a notice and record neither a notice nor a decision, so they stay off. Declining deletes the install id file. A telemetry decision through the HTTP API needs a human dashboard session.
