# Group 01: the agent loop, tool dispatch and durability

Research date 2026-11-10. Synthesis of Round 2 source-code findings. No finding here is new: everything below comes from the Round 2 input files, and every permalink is copied from them. Terms used: a **turn** is one user request run to its end; a **step** is one model call plus the tool calls it asked for; **steering** is user input that arrives while a turn runs and is fed into that turn; a **follow-up** is such input held until the turn ends; **intent** is the record "this tool call is about to run with these arguments"; **replay policy** is what a restart does with a tool call that may have started.

Trust labels: `checked in review` (an independent reviewer opened the cited code and agreed), `corrected in review` (the text uses the reviewer's corrected version), `unchecked` (traced by the Round 2 author, not re-opened by a reviewer), `inferred` (the author's inference from code, not stated by it), `absence confirmed` (a reviewer searched for the thing and did not find it). Where a project subsection says "read the definition" or "traced end to end", that is the author's confidence and the review status is given beside it.

## 1. Scope

**Group:** how one step is driven; where tool calls are validated, authorised and executed; parallel calls; step, turn and time limits; stuck-loop detection; cancel and interruption; steering and queueing; output truncation; crash safety (intent before effect, flush-before-effect, replay policy, a turn running when the process dies); unattended and scheduled runs as far as they change the loop.

**Read:** for each of the 13 repositories, the findings in the safety, agents and sessions files (or the single file for Zed, Warp, OpenCodex) that belong to this group, plus each file's section 8 (Review). Findings were read wherever they sit, including headings that are not named after this group: the loop sits in "safety" files (3.1 "agent loop and tool dispatch") for most repositories, and in "agents" files (retry, stuck-loop, output limits) and "sessions" files (durability, resume, headless) for the rest. Compaction, edit tools, sandboxing, approvals rules and MCP were not read except where they change the loop (for example, the approval wait and the retry rules around a failed step).

**Not available:**
- OpenHands: the agent loop, tool dispatch, stuck detector, iteration enforcement, event persistence and Automation Server are in other repositories (`OpenHands/software-agent-sdk`, `OpenHands/automation`) that were not cloned. Only the client's request to the server and its reconnect logic were read.
- Warp: the agent loop, prompt and model calls run on Warp's server; the repository holds the client that executes tools. The self-hosted worker is a separate Go repository.
- OpenCodex: a proxy, no agent loop of its own; only three bounded helper loops and the Remote Workspace tool channel exist.
- Zed: the input file covers permissions, sandboxing, ACP and compaction; it has no finding on step caps, loop detection, steering or crash recovery.
- No clones were opened for this synthesis, so one contradiction (goose tool batches) was resolved by comparing two input files rather than reading code (see Section 7).

## 2. Implementations by project
### Codex

Rust, one process family: a TUI or `codex exec` runs the engine in process through an app-server client, or a long-lived `codex app-server` daemon serves clients over a socket or WebSocket. The loop is `run_turn` in `codex-rs/core/src/session/turn.rs`. Files read: `codex.agents.md` (3.6), `codex.safety.md` (3.1), `codex.sessions.md` (3.1, 3.3, 3.6).

**One step, in order** (checked in review unless noted).
1. `run_turn` loops until a sampling request needs no follow-up, there is no pending input, and no stop hook blocks it. There is no iteration counter. Loop and drain: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L536-L554; follow-up decision: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L690-L691 and https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L805-L806.
2. Each tool call starts executing as soon as its output item completes while the model stream continues (a `FuturesOrdered` of in-flight futures). Results are recorded in order after the stream ends: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L3330-L3334, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L3791-L3802, `drain_in_flight` https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L2852-L2870.
3. Authorisation is inside the executor: `ToolOrchestrator::run` computes the `ExecApprovalRequirement`, asks for approval if needed, runs a first attempt under the selected sandbox, and only on `SandboxErr::Denied` considers a retry without the sandbox. The retry needs a fresh approval unless the first approval came from the user or a hook; a model-reviewer ("Guardian") approval never pre-approves the retry. Requirement and first approval: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L164-L233; sandbox selection: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L333-L360; denial handling: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L446-L480; retry pre-approval scope: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L491-L501. "Denied" is a heuristic: exit codes 0, 2, 126, 127 are never denials, Linux 128+SIGSYS is, otherwise a stderr keyword match: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/sandboxing/src/denial.rs#L13-L72 (checked in review). Whether a failed bubblewrap start can yield a retry offer was not traced (inferred).
4. Session-scoped approvals are keyed on environment id, executable, canonical argv, cwd, tty flag, sandbox permissions and extra permissions; MCP calls, network and `request_permissions` are never cached: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/runtimes/unified_exec.rs#L87-L98, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/approvals.rs#L282-L322, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/sandboxing.rs#L72-L117 (read the definition, unchecked).
5. Argument validation and unknown-tool handling were not described in the input files for Codex.

**Parallel calls.** `ToolCallRuntime` holds a `RwLock<()>`. A tool whose `supports_parallel_tool_calls()` is true takes the read lock; every other tool takes the write lock. Trait default is `false`. Declared parallel: `exec_command`, `write_stdin`, `view_image`, MCP resource tools, tool search, `list_agents`, dynamic tools, MCP tools only if the server opted in or the tool has `readOnlyHint`. Exclusive: `apply_patch`, `spawn_agent` and agent-control tools. The request sets `parallel_tool_calls: true`. Lock: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/parallel.rs#L183-L183, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/parallel.rs#L292-L304; trait default https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/tools/src/tool_executor.rs#L122-L124; cancellation aborts the admission wait and the handler https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/parallel.rs#L282-L284 (checked in review). Note: this is per-tool opt-in, not a read-only classification; shell is parallel-capable, file edits are not.

**Limits.** No step cap and no stuck-loop detector (absence confirmed in review: ripgrep for `max_steps`, `max_iterations`, `stuck`, `doom`, `loop_detect` in `core/src/session` and `core/src/config`). The only brakes: an optional rollout token budget (`SessionBudgetExceeded`, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/rollout_budget.rs#L61-L72), the Guardian reviewer's denial circuit breaker (`TooManyDenials`, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/agent/control/completion.rs#L91-L95), cancel, and stop hooks. Provider stream idle timeout 5 minutes; stream retry budget 5, request retry 4, both capped at 100; backoff 200 ms doubling with plus or minus 10% jitter (corrected in review); pure connection failure retries forever (5 s to 60 s) with a "waiting for network" notice when `unbounded_connection_retries` is on (default on). Never retried: auth denials, interrupts, invalid requests, context-window-exceeded, quota. Classification https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/protocol/src/error.rs#L445-L511; backoff https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/async-utils/src/backoff.rs#L7-L17; defaults https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/model-provider-info/src/lib.rs#L73-L75; driver https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/responses_retry.rs#L58-L167; unbounded retries https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/responses_retry.rs#L94-L117. Completed items before a stream break were already recorded; an item still streaming is lost (inferred). There is no model fallback chain (absence confirmed in review).

**Input during a turn.** `turn/steer` queues a user message (and mailbox mail from sub-agents). It is drained at the top of the next loop iteration, that is after all in-flight tool calls of the current step finished, except right after a compaction where the drain is deferred once. After an interrupted sampling, pending input is drained even if the context is still over the limit: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L774-L785. Whether the steered text is written to the rollout before the acknowledgement was not established in the input files (unchecked; the queue is not described as durable). A separate SQLite-backed queue (`codex queue --thread`, max 100 per thread, 10 s poll of SQLite `data_version`, dispatches to idle threads) is durable and lets another process enqueue work: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/ext/queue/src/service.rs#L90-L105, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/state/src/lib.rs#L122-L122 (checked in review; corrected: no scheduler in the engine, but a desktop-app automation flag and thread source exist).

**Cancel.** `turn/interrupt` is a protocol method (https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/app-server-protocol/src/protocol/common.rs#L522-L530). Cancellation aborts waits and handlers; interrupts are never retried as errors.

**Output truncation (enforced by the tool and by the recorder).** Unified exec: each `exec_command`/`write_stdin` call returns at most `max_output_tokens` (default 10,000), truncated in the middle with a marker; each process buffers at most 1 MiB (head and tail kept); at most 64 processes, LRU pruning protecting the 8 most recent; yield 250 ms to 30 s per call; background terminals default 300 s max. Constants https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/unified_exec/mod.rs#L68-L77; pruning https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/unified_exec/process_manager.rs#L1729-L1805 (checked in review). Old tool output is truncated when recorded (`record_item_with_metadata`), never pruned later (checked in review). In paginated history mode, command output and MCP results are cut to 64 KiB for persistence: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/policy.rs#L231-L287 (unchecked).

**Crash safety.**
- Durable format: `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<thread>.jsonl`, one JSON line `{timestamp, ordinal?, type, payload}`; the writer stamps and flushes after every line: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/recorder.rs#L2034-L2074. A missing final newline (torn tail) is repaired before appending: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/recorder.rs#L2019-L2032. A write error drops the handle, reopens and retries once, keeping unwritten items in memory: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/recorder.rs#L1786-L1830 (unchecked, read the definition).
- What is not durable: `persisted_rollout_item` drops deltas, begin/updated events, approval requests, errors, warnings, `ExecCommandEnd`, `McpToolCallBegin`: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/policy.rs#L16-L52 and https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/policy.rs#L136-L165. So an "intent to run this tool" record is not a separate durable event; the `ResponseItem` for the model's tool call is recorded when its output item completes (https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L360-L362). No flush-before-effect rule is described (not found in the input files).
- File creation is deferred until the first `persist()`: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/recorder.rs#L1004-L1015.
- One writer: advisory file lock `<CODEX_HOME>/thread-writer-locks/<thread>.lock` plus a `.coordination.lock`, 30 s bounded wait; second writer gets `WouldBlock`: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/writer_lock.rs#L45-L95, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/rollout/src/writer_lock.rs#L137-L158 (checked in review).
- Resume: `ContextManager::reconstruct_rollout` picks the newest compaction with `replacement_history` as a base and scans the suffix backwards; rollback markers skip N user turns: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/rollout_reconstruction.rs#L205-L260, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/rollout_reconstruction.rs#L300-L306. The input files describe no handling of a turn that was running when the process died (no synthetic "interrupted" results, no re-run); for an unmatched tool call in the log nothing was reported (not found).
- Planned daemon restart is the one explicit recovery: the daemon writes `loaded-threads.json` (loaded thread ids plus interrupted-turn metadata) on a plain thread so a forced exit does not wait for the Tokio blocking pool; the next generation consumes and deletes it and restores runtimes, and only local-environment turns can auto-continue: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/app-server/src/daemon_thread_recovery.rs#L9-L50, https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/app-server-transport/src/daemon_recovery.rs#L12-L32 (unchecked). This covers a planned restart, not a crash.
- Resume of a running thread rejoins it instead of failing: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L340-L374.

### OpenCode

TypeScript (Effect library, Bun) in one server process per machine ("V2" engine under `packages/core`); the TUI, web app and `opencode run` are clients over HTTP and SSE. The loop is `drain` in `packages/core/src/session/runner/llm.ts`. Files read: `opencode.safety.md` (loop and dispatch), `opencode.agents.md` (step limit, stuck loop, output limit, goal reviewer), `opencode.sessions.md` (event log, resume, headless).

**One step.**
1. `drain` promotes queued inbox input, then loops `advanceToStep` (handles queued compaction and move controls, promotes input or steering) and `runStep` until a step reports no continuation: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/llm.ts#L61-L75, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/llm.ts#L214-L222 (checked in review).
2. `runStep` compacts if needed, builds the request, and calls the model. Each `tool-call` event from the provider stream is forked at once into its own fiber (`Effect.forkScoped`): tools run in parallel and before the stream ends, with no concurrency cap: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/step.ts#L133-L161 (checked in review).
3. Dispatch: `Tool.snapshot(permissions)` hides a tool only when the last matching rule has resource `*` and effect deny. `execute` runs the `tool.execute.before` plugin hook (which may rewrite input and tool name), resolves the tool, decodes input against its schema, then calls the tool's own `execute`. The registry never calls `Permission`; each built-in tool calls `permission.assert` itself, and a plugin tool that omits it runs unchecked: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/tool.ts#L389-L392, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/tool.ts#L305-L327, schema decode https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/tool/runtime.ts#L30-L46. The repository's own design note says so: "Tool filtering is catalog visibility, not execution authorization" https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/tool/AGENTS.md#L51-L55 (checked in review).
4. A plain user decline is thrown as a defect so no tool can catch it and turn "no" into model-visible output; the step ends as interrupted. A decline with feedback stays a typed failure and the model continues: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/model-request.ts#L418-L436, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/permission.ts#L271-L284 (checked in review).

**Limits.** `agent.steps` has no default, so a session is unbounded unless configured. When the step number reaches it, the request gets an extra assistant message `CRITICAL - MAXIMUM STEPS REACHED ... Respond with text only` with `toolChoice: "none"`; tool definitions stay in the request to keep the provider's cached prefix; a tool call that still arrives is refused with "Tools are disabled after the maximum agent steps": https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/llm.ts#L259-L281, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/max-steps.ts#L1-L16, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/step.ts#L116-L118 (corrected in review of Round 1: tools are not removed). Step numbering resets to 1 when new user input is promoted, so the cap is per user turn. Output limit: catalog limit (fallback 32,000, ceiling 256,000) fitted to the room left in the window, never below 1,024; a `length` finish injects a synthetic nudge and continues; three `length` finishes in a row fail the step: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/model-request.ts#L49-L103, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/llm.ts#L343-L373. Provider retry: 10 retries, 2 s doubling to 10 s with jitter, honours retry-after up to 15 minutes, plus a separate one-hour "no network" budget (checked in review, from `opencode.agents.md`). No wall-clock turn limit was reported.

**Loop detection.** None in the step loop (absence confirmed in review: only the V1 `doom_loop` config key exists). The `/goal` plugin has `MAX_ROUNDS = 50` and `MAX_STALLS = 3`; a round counts as a stall if the reviewer's `continue` reason repeats or the model used no tool since the last continuation: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/plugin/goal.ts#L15-L19, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/plugin/goal.ts#L140-L203. The reviewer is the session's own model asked for one line of JSON in the same cache prefix: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/plugin/goal.ts#L104-L136, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/plugin/goal/judge.txt#L1-L20 (checked in review).

**Input during a turn.** The input files say only that `drain` and `advanceToStep` "promote" queued inbox input or steering at step boundaries. Where the inbox is stored and whether it is written before the HTTP reply was not described (not found in the input files). Cancel: a user stop first asks tools that support cooperative cancel (`context.cancel`), waits `COOPERATIVE_STOP`, then interrupts the remaining fibers: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/runner/step.ts#L104-L115 (checked in review).

**Output truncation.** Bounded once at call time; V2 has no later pruning of old tool output (from `opencode.agents.md`, unchecked here). Tool-output and shell-output files age out through `FileRetention.cleanup`.

**Crash safety.**
- Every durable event is committed by `Bus` under a per-aggregate keyed mutex inside an `immediate` SQLite transaction: read latest `seq`, take `latest + 1`, run the projectors, run an optional caller `commit` hook (used to set or clear the execution claim atomically), upsert `event_sequence`, and, only if persistence is on, insert the `event` row: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L372-L412, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L417-L434 (checked in review).
- The durable event log is opt-in: `persist` defaults to false; the shipped CLI server never sets it; only the workerd profile forces it: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L186-L192, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L214-L214, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/workerd.ts#L69-L73. Truth locally is the projection tables (messages, parts), not the log. The review notes that the workerd comment says boot-time resume replays the log, but `restart.ts` resumes from the claim, not from the log.
- Write-ahead execution claim: when a turn starts, `Execution.Started` and `store.claim` (`time_suspended = now`) commit in one transaction; terminal events release the claim in the same transaction as the event; a graceful shutdown keeps the claim. At boot `resumeSuspendedSessions` finds top-level sessions with a claim, increments a durable `resume_attempts`, and either publishes the synthetic message "The server restarted while you were working. Continue from where you left off without repeating completed work." and drains the session again, or after more than 10 attempts terminalises the turn with an `aborted` error. Background shell and image jobs are marked cancelled. Recovery is explicitly at-least-once: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/execution.ts#L73-L82, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/execution.ts#L130-L151, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/store.ts#L218-L261, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/execution/restart.ts#L16-L34, https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/execution/restart.ts#L76-L99, boot call https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/process.ts#L246-L252 (checked in review).
- No lease or fencing token: the sweep assumes every orphaned claim's owner is dead, guaranteed only by the managed-server protocol (registration lock, successor spawned after the old pid is confirmed dead). Two server processes on one database would break it (checked in review).
- No "intent before effect" record for individual tool calls was reported; recovery re-asks the model to continue, so a tool that had started may run again.
- `Bus.replay` (exact-seq re-apply, "Replay diverged", "Sequence mismatch") and `claim` have no non-test caller: machinery for future replication: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L329-L378 (checked in review).

### Hermes Agent

Python. One "gateway owner" process per profile home runs the agent in process; the CLI, TUI, messaging platforms, cron and a kanban "worker" are clients or admitted callers of it. State is SQLite (`state.db`, a relational transcript, not an append-only event log). **One step and dispatch.**
1. `pre_tool_call` plugin hooks may return `block`, `approve` (escalate to the human gate) or `modify` (shallow-merge args). Precedence block over approve. A hook exception is swallowed and the call runs with the original args (fail open); an `approve` whose gate raises, denies or times out blocks: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L662-L676, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_cli/plugins.py#L1118-L1170, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_cli/plugins.py#L1198-L1227, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/approval.py#L1246-L1271 (checked in review). The dangerous-command check is inside the terminal tool, not in the executor, so approval is per tool, not at the dispatch boundary. A `modify` hook rewrites args before that check, so the rewritten command is what is checked.
2. Parallel batches: several tool calls from one response run on a daemon thread pool capped at 8 workers (`_MAX_TOOL_WORKERS`). An authorisation gate serialises approval prompts; human-wait time is excluded from the batch deadline; if the gate lock is not acquired in time the worker prompts unserialised. On interrupt, pending futures are cancelled, running tools get 3 s to notice a per-thread interrupt, tools without interrupt checks run to completion, wedged workers are left detached. If an interrupt is already set when the batch starts every call gets a "skipped" result: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L136-L136, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L1578-L1596, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L1439-L1495, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L479-L497, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L526-L545, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_executor.py#L1497-L1516 (traced end to end, unchecked by review for this finding).
3. Foreground shell calls asking for more than `FOREGROUND_MAX_TIMEOUT` (600 s default) are promoted to a tracked background job with `notify_on_complete` instead of being refused; a trailing `&` becomes `background=true`: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/terminal_tool.py#L78-L78, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/terminal_tool.py#L1240-L1266, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/tools/terminal_tool.py#L1512-L1519 (checked in review; corrected from Round 1: promotion is triggered by an over-cap timeout, not by an interrupt).

**Loop detection.** Per turn the controller records `(tool, args hash, result)` signatures. Identical consecutive calls get a notice at the 3rd repeat; from the 2nd byte-identical result over 512 characters the payload is replaced by a reference stub; cycles of 2 to 4 calls are detected over a 64-entry history. Failure counters: exact-args failure warn at 2 and block at 5; same-tool failure warn at 3 and halt at 8; idempotent no-progress warn at 2 and block at 5. `hard_stop_enabled` is false on attended platforms (cli, tui, desktop, acp, subagent, api_server) and forced on for gateway and cron. `terminal` and `execute_code` never halt on different commands. A successful mutating call resets failure counts. Hashes mean raw arguments do not leave the controller: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_guardrails.py#L26-L66, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_guardrails.py#L81-L108, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_guardrails.py#L113-L145, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/agent/tool_guardrails.py#L149-L162. Confidence: read the definition; the enforcement call site was not traced (not stated as checked by review).

**Input during a turn.** Each inbound message is first committed as a `session_admissions` row `(principal, target_session, request_id)` with a unique key (a retried delivery is an exact replay; a changed payload under the same key raises `admission_conflict`), a payload digest, an intent (`queue`, `steer`, `redirect`) and a status `queued -> started -> terminal | unknown`. At most 32 inputs may be queued per session. This is a durable per-session FIFO, and the row exists before the work starts: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_state_common.py#L597-L615, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_state_runtime.py#L126-L177. How a `steer` row is injected into a running turn was not read for this synthesis.

**Cancel.** Per-thread interrupt flag (see parallel batches); a `steer` handed to a lost claim is settled `interrupted`, not replayed.

**Crash safety.**
- `claim_session_input` takes the FIFO head in one write transaction: it refuses (`unknown_execution`) if any admission or worker for the session is `unknown`, does nothing if one is still `started`, bumps `runtime_generation`, and marks the row `started` with `(owner_epoch, generation)`. `settle_session_input` accepts a row only if status, epoch and generation match (`stale_generation` otherwise): https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_state_runtime.py#L206-L242, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_state_runtime.py#L245-L274.
- At gateway start `begin_runtime_epoch` increments a singleton epoch under the profile ownership lock; `recover_session_inputs` marks every `started` admission from an earlier epoch `unknown` and every non-terminal worker execution `unknown`, and never requeues them ("Never replay started work"): https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_state_runtime.py#L453-L464, boot order https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/gateway/session_authority.py#L1450-L1467.
- Only an explicit `resolve_unknown_session_input` (the person's Discard, or boot-time unattended settlement) settles an `unknown` row, and never back to `queued`: the outcome is `interrupted`, except that if the same owner epoch captured the finished result before its settlement write failed, it resolves as `completed` or `failed` with the stored answer. It writes a transcript boundary in the same transaction so the FIFO cannot advance past an unclosed turn: https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_state_runtime.py#L657-L694, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/hermes_state_runtime.py#L663-L694 (corrected in review; the epoch and generation fence, never-requeue rule and the cap of 32 were checked).
- Unattended turns (cron principal, principals starting `automation:`, payload markers `local_automation_v1`, `kanban_card_v1`, webhook marker) that end `unknown` settle themselves as interrupted at boot, so a queue does not stall behind nobody; a person's `unknown` still pauses the session (the code comment records a chat stuck for ten hours): https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/gateway/session_unattended_unknown.py#L23-L38, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/gateway/session_unattended_unknown.py#L41-L66 (checked in review).

- Outbound replies: `delivery_obligations` row written `pending` then immediately `attempting` before the send; on boot `sweep_recoverable` claims rows whose owner process (pid plus start time) is dead, abandons rows with 3 attempts or older than 24 h, and redelivers with an explicit "may be a duplicate" prefix. Ledger errors are swallowed (best effort, at-least-once): https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/gateway/delivery_ledger.py#L368-L446, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/gateway/platforms/base.py#L4136-L4168, https://github.com/NousResearch/hermes-agent/blob/95fc3e668fc1e13ad05d22a4f02fccc6a6d6ce02/gateway/delivery_ledger.py#L33-L36 (checked in review).

### Oh My Pi

TypeScript plus Rust native crates, one process per session (interactive, `-p` print mode, `--mode json`, RPC over stdio, or in-process SDK). The loop is `packages/agent/src/agent-loop.ts`; approvals and extensions wrap tools in `packages/coding-agent/src/extensibility/extensions/wrapper.ts`. There is no server and no node split. Files read: `oh-my-pi.safety.md` (loop, running commands, headless), `oh-my-pi.sessions.md` (crash discipline, large content, headless), `oh-my-pi.agents.md` (retry, fallback, TTSR, child budgets).

**One step and dispatch.**
1. In the loop, a `beforeToolCall` result can block, add context or replace arguments; replaced arguments go back through schema validation and are baked into the message so history shows one version. A throwing `beforeToolCall` becomes a tool-error result for that call without aborting the batch: https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/agent/src/agent-loop.ts#L3204-L3234.
2. In the wrapper, `deny` is checked once on the original input, then `tool_call` extension handlers run (they may block or rewrite), then the full approval gate is re-resolved against the effective input, so a handler cannot rewrite a call into something that skips a prompt or deny: https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/coding-agent/src/extensibility/extensions/wrapper.ts#L265-L291, https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/coding-agent/src/extensibility/extensions/wrapper.ts#L306-L342, https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/coding-agent/src/extensibility/extensions/wrapper.ts#L355-L374 (checked in review). A non-`Error` thrown by a handler becomes "Extension failed, blocking execution" (fails closed; 30 s default handler timeout from `oh-my-pi.safety.md`).
3. Speculative execution: while the model still streams, a speculation host may start a call early, only if no extension lifecycle handler is loaded and `resolveApproval` would return `allow`, and only for a single `local_read` effect on an absolute path; a later block discards the candidate: https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/coding-agent/src/speculation/host.ts#L216-L235, https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/coding-agent/src/speculation/host.ts#L246-L254 (checked in review).

**Parallel calls.** Each tool declares `concurrency` (`shared` or `exclusive`, or a function of args); unset is shared; a throwing resolver is treated as exclusive. Queued steering or a peer message aborts only tools flagged `interruptible` (pure waits); every other tool, bash included, gets a cooperative `steeringSignal` it may honour (for example auto-backgrounding) and sees only the external abort: https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/agent/src/agent-loop.ts#L113-L129, https://github.com/can1357/oh-my-pi/blob/e325ffc73ab86e03bdd20a91b77d8e2b3964c906/packages/agent/src/agent-loop.ts#L3360-L3374 (checked in review; the steering lines were not re-read). ### Pi

### DeepSeek harness

TypeScript, a composition of plugins (Cordis) in one host process; interactive TUI, a web profile (the loop and web server share a process), and a headless profile. The session is an append-only typed event log, one file per session, and the model request is derived from it by a fold. Files read: `deepseek-harness.safety.md` (loop and dispatch), `deepseek-harness.agents.md` (stuck loop, loop mechanics), `deepseek-harness.sessions.md` (durability, resume, prompt admission, schedule, headless).

**One step.** `Agent.turn()` appends `turn/start`, then repeatedly runs `preStep` (claim inbox messages, resolve the tool set, assemble the prompt, run the `agent/pre-step` waterfall, which may rewrite messages or reject; a reject ends the turn as `blocked`), appends `step/start`, runs `step()`, appends `step/end`. `step()` loops over request attempts, so retry and overflow recovery re-enter without a new step: it re-prepares the request, appends prompt and user events, streams, settles the assistant message durably, then executes the tool calls. A request failure is first recorded as an `assistant/attempt` event; the `agent/request-error` waterfall decides retry, or the turn ends `error`. Turn end reasons: completed, aborted (with cancel cause), blocked, error, max-tokens (sticky): https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/core/agent-loop/src/agent.ts#L327-L433, https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/core/agent-loop/src/agent.ts#L283-L317, https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/core/agent-loop/src/agent.ts#L584-L610 (traced end to end; the mechanics finding is not listed in review).

### goose

Rust (`crates/goose-agent` for the state machine, `crates/goose` for operations, tools and the ACP server). A session is a row set in one SQLite database; the loop runs in the process that serves the session (the desktop's own server, `goose serve`, or the CLI). It is a conversation table, not an event log: state is re-derived from the stored messages on every pass. Files read: `goose.safety.md` (loop, shell), `goose.agents.md` (retry, stuck loop, spill), `goose.sessions.md` (resume, one run per session, scheduler).

## 4. Patterns and trade-offs

### 4.1 Where authorisation sits in dispatch

| Approach | Projects | What it costs or fails to cover |
|---|---|---|
| One pipeline at the dispatch boundary: freeze args, policy waterfall, approval, guards, body; a throwing listener denies | DeepSeek harness (`pipeline.ts`), Pi (find, repair, validate, hook, execute), OpenClaw (`before_tool_call` chain fails closed), Oh My Pi (deny, handlers, re-resolve on the effective input) | DeepSeek validates arguments after policy (a policy sees raw strings); Pi lets a hook mutate args after validation with no re-check; DeepSeek's shipped waterfall has no asking listener (the ask lives inside bash, fs and plugin tools) |
| Authorisation inside each tool | OpenCode (`permission.assert` in each tool), Cline (each tool validates its own input after approval), Hermes (dangerous-command check inside the terminal tool) | A new or plugin tool that forgets the check runs unchecked; OpenCode's own note says "catalog visibility, not execution authorization" |
| Approval keyed to the call id, persisted, expiring with the process | goose (`goose.executable` flag in stored metadata; approvals expire with the extension lease) | Binds to the call id, not a hash of arguments; works because state is re-derived from stored messages |
| Approval bound to "whatever is pending" | OpenHands client (`{accept, reason}` only) | A stale or double click answers the wrong action (corrected in review: only client-side de-duplication) |

Common good rule: policy runs after the last mutation of the call. Oh My Pi re-resolves approval on the effective input after extension handlers run; Hermes' `modify` hook runs before the terminal tool's own check, so the rewritten command is what is checked.

### 4.2 Parallelism

- **Per-tool flag to a shared lock** (Codex): reads share, everything else is exclusive; the flag is set per tool (shell is parallel-capable; `apply_patch` is not). Cost: the flag is easy to set wrongly for shell.
- **Fail-closed classifier per call** (DeepSeek `isConcurrencySafe(args)` exactly `true`, max 10; Oh My Pi unset is shared but a throwing resolver is exclusive). Cost: in DeepSeek a tool that does not say it is safe runs alone; in Oh My Pi an unset tool runs shared, so a forgotten declaration means parallel.
- **Serial preparation, parallel execution** (Pi, Cline, Hermes, OpenClaw): all approval prompts appear one at a time, then approved tools run together; Hermes also serialises prompts and excludes human-wait time from the batch deadline.
- **Unbounded fork per call** (OpenCode): each call starts while the model still streams, no cap.
- **Speculative pre-execution** (Oh My Pi): only auto-allowed `local_read` effects, and only when no extension lifecycle handler is loaded.
- **Sequential** (Rizzy on main; goose dispatches in order and merges result streams).

### 4.3 Stuck loops

Five distinct designs exist, and the cost of each is visible in the code:

| Design | Projects | Cost |
|---|---|---|
| None | Codex, Pi, OpenCode (outside `/goal`), Oh My Pi (outside edits), Zed, Warp (client) | A looping model runs until the user aborts or the context fills. Codex and Pi say so (`agent-loop.ts`: "nothing in the loop counts calls or cost") |
| Hash of tool plus arguments, consecutive repeats, notice only | DeepSeek (3, 5, 8, never blocks), Cline (3rd call notice) | A looping call is not stopped; A, B, A, B is missed |
| Hash of outcome too, thresholds, block | OpenClaw (rolling, off by default; error breaker on) | Heuristic that can block good work, hence off; the always-on breaker covers only identical errors |
| Attended warns, unattended stops | Hermes (`hard_stop_enabled` forced on for gateway and cron) | Needs a notion of "attended" per run |
| Dead code | goose (`RepetitionInspector` on a clone, no limit, flag not passed) | The lesson is that the counter must live where it persists across steps: a fold over the log, not a local object |

Cline's detector runs from the `tool-started` event, so the repeated call has already begun when the stop fires; OpenClaw's runs at admission, before dispatch.

### 4.4 Step and time limits

- **No cap, rely on the user** (Codex, Pi, DeepSeek, OpenClaw, Hermes, Cline by default): all state it, and Pi, DeepSeek, Codex notes call it a runaway risk.
- **Hard cap plus a canned stop message** (goose 1000; also a half-budget `<turn-budget>` hint to the model).
- **Cap that keeps the cache and is enforced** (OpenCode): keep tool schemas, send `toolChoice: none` with an instruction, refuse any late call at dispatch. Reviewed and corrected from Round 1 ("tools are removed").
- **Client-set cap** (OpenHands Canvas sends 500): the server enforces; the client can change it.
- **Idle rather than total timeouts** (OpenClaw 120 s model idle plus 48 h run; Hermes cron 600 s of inactivity; Codex 5 min stream idle; OpenCodex 300 s stall): these catch a hung provider without capping honest long work.
- **Timeouts as metadata nobody reads** (Cline `timeoutMs`): the dispatcher does not wrap the call.
- **Model-set timeouts**: goose lets the model set `timeout_secs` with 0 meaning none; Hermes promotes an over-limit foreground call to a tracked background job instead of refusing it (to avoid retry loops).

### 4.5 Steering and queueing

| Approach | Projects | Cost |
|---|---|---|
| Reject while a turn runs | goose (`AgentRunExists`), Cline (`run()` throws), Pi core (`prompt()` throws, the session layer converts to steer or follow-up), Rizzy on main | No loss of accepted input, but the user waits; a UI must hold the text |
| Queue and deliver at a step boundary, never kill a tool | Codex (`turn/steer`), Pi, Oh My Pi, OpenClaw (default), DeepSeek (inbox claimed at pre-step), OpenCode | Coarse: in parallel batches steering waits for the whole batch (OpenClaw, Pi). Pi's repository doc says only "enters after the current assistant turn"; Round 1's "interrupts remaining tools" was wrong |
| Steer with fallback to follow-up, collect, interrupt as separate modes | OpenClaw (`steer` default, 500 ms debounce, cap 20, `summarize`, a durable "dropped" receipt per dropped input) | The most complete policy; also the most configuration |
| Interrupt the turn | OpenClaw `interrupt` (abort and wait for the writer to settle); Oh My Pi cooperative `steeringSignal` aborts only `interruptible` tools | Aborting a half-done edit loses work; omp and Pi deliberately avoid killing side-effecting tools |
| Durable queue with idempotent admission | Hermes (`session_admissions`, 32 per session, `queue`, `steer`, `redirect` intents), OpenClaw (`session_pending_inputs` with request hash), DeepSeek (client `requestId` in the logged message), Codex queue extension (SQLite, 100 per thread) | More schema; the payoff is a retried HTTP call is an exact replay and an accepted message survives a crash |
| In-memory queue | Pi, OpenClaw's in-flight steering list | Only protects against a failed run, not a process crash (corrected in review for OpenClaw) |

A reliability lesson from OpenHands: a message written to a socket that the server has not yet subscribed can be lost; the client falls back to HTTP, and holds messages in browser memory when the sandbox is paused. Acknowledging only after a durable append removes the window.

### 4.6 Crash safety: four families

1. **Write intent first, replay by policy** (pi-durable): a checkpoint `{phase: execute, arguments, replay: safe|unsafe}` is committed before the tool runs; on resume only `safe` tools re-run; a restart counter per task, reset on progress (default limit 5). Cost: only experimental, only in a separate package, and every tool must declare a policy; built-in file and shell tools do not.
2. **Flush the log, then close the turn with "outcome unknown"** (DeepSeek, Rizzy on main): fail-closed flush before each model request and each top-level tool body; on resume synthetic error results ("outcome is unknown ... do not retry blindly") and `turn/end` with reason `interrupted`; tools are never re-run. Cost: up to 200 ms of events can be lost on a hard crash; a tool that ran and whose result was lost is reported as unknown.
3. **Re-drive the turn**: OpenCode re-drains with "continue without repeating completed work" (at-least-once, abort after more than 10 attempts); OpenClaw injects a fixed prompt to check state first; goose re-derives from the stored conversation and continues an unanswered approval. Cost: the model decides what is safe to repeat, and a started shell command may run again.
4. **Fence the claim** (Hermes epoch plus generation on every settle; OpenClaw `activeWriterRunId` checked in the write transaction; Codex and DeepSeek use a file lock and flock with no expiry; OpenCode relies on "the old owner is dead"; goose has none). Cost: OpenClaw's fence is skipped when a write carries no expected writer (corrected in review); the file locks assume one host.

Hermes alone separates an `unknown` execution from `interrupted`, and never requeues it. A person's unknown turn pauses the session until a decision; an unattended one settles itself so the queue does not stall.

### 4.7 Output truncation: who enforces it

| Layer | Projects |
|---|---|
| Each tool (loop applies nothing) | Pi: an extension or MCP tool returning 10 MB goes straight into context |
| Tool plus recorder | Codex (tool yields and caps; recorder truncates old output at record time); goose (shell cap, plus a 200,000 character per block backstop in dispatch) |
| Dispatcher, proportional to context | OpenClaw (30% of window and 16k, 32k, 64k characters per result) |
| Executor cap plus request-build cap plus recoverable cache | Cline (48,000 at executor, 8,000 or 50,000 at request, `cline://cache` URI the model can page; stale re-reads rewritten) |
| Spill to a file or artifact with head and tail preview | Oh My Pi (50 KiB spill), DeepSeek (12,500 tokens, fails open), goose (slot files, can be overwritten), Pi bash (temp file) |

Collection must be bounded while reading: goose holds a gigabyte-printing command in memory before truncating; Codex keeps 1 MiB per process with head and tail; OpenClaw bounds sandbox bridges at 100 MB.

### 4.8 What changes in unattended runs

- **Same engine, a client that cannot answer approvals** (Codex `exec`: approvals become errors; DeepSeek headless: `ask` with no answerer fails closed; Oh My Pi: fails closed only when a prompt would be needed).
- **Permissive defaults that make a headless run never prompt** (Oh My Pi `yolo`, Cline cron `yolo`, goose forced `Auto`).
- **Deny by default for unattended** (Hermes `cron_mode: deny`, a toolset denylist, loop hard-stop forced on).
- **Schedule semantics**: Hermes advances `next_run_at` before dispatch (at-most-once); OpenCode and DeepSeek skip or collapse missed slots; goose skips and lets runs overlap; OpenClaw retries an interrupted turn only if delivery had not started, with no attempt count (a repeat crash qualifies again).
- Warp reports every unattended refusal as `Denylisted`, hiding the actual reason from the model.

Our state, from `research/round1/own-rizzy-harness.md` (as of `main`): one native loop in `crates/agent-native/src/lib.rs`; a fixed cap of 50 model calls per turn, not configurable; tool calls run one after another (only `delegate` runs in parallel); a prompt sent while a turn runs is rejected ("a turn is already running", `crates/node/src/session.rs:297-299`); a restart mid-turn closes the turn as `interrupted`, denies pending approvals and closes interrupted tool calls synthetically (`session.rs:154-191`); 600 s per tool call; no loop detector; no provider retry (pull request 7 adds it); cancel does not abandon a tool future that ignores the token (fixed only on `integration/gate3`); routines run agentic only in `ask` or `ask_all`. Feature freeze applies until Gate 3 of `FIX_PLAN.md`: items marked "fix" below are repairs of the loop's safety; items marked "feature" cost against the plan and need the owner's decision to break the freeze.

Ranked by importance. Each point is stated as a verdict.

### 6.1 Do: make the order "append, flush, then act" a tested rule (fix)

- **Copy from DeepSeek harness** (`packages/session/session-checkpoint-policy/src/index.ts`, `packages/core/agent-loop/src/index.ts` `interruptedTurnClosers` in `packages/core/session/src/repair.ts`): an awaited, fail-closed flush before each model request and before each top-level tool body; a failed flush means the tool never runs.
- **Check in our code:** is the event that records "tool call X with arguments A is about to run" committed (not just sent down the node link) before the tool body starts? Our log is written by the node's session actor; the master persists via the link. Name the exact point (the `approval_requested` or the tool-start event in `session.rs` around `:955-1012` and the loop call site `agent-native/src/lib.rs:744-870`). If the append is queued behind the back-pressure channel (pull request 4's bounded link) the flush rule is false.
- **Test that fails first:** kill -9 the node while a `bash` call is running; assert the log holds the call's arguments and, after restart, a closing event.
- **Closing wording:** copy DeepSeek's synthetic result ("outcome is unknown ... retry only if read-only or idempotent ... do not retry blindly") and OpenClaw's restart text (check files, processes and external actions before repeating). ### 6.2 Do: a default-on repeated-call guard, checked before dispatch (fix)

Evidence that the gap is real: Codex and Pi have none and say so; goose's is dead code; OpenCode has none outside `/goal`.
- **Copy from Hermes** (`agent/tool_guardrails.py`): tool plus arguments hash, a result hash (so a changing timestamp does not hide a loop, as OpenClaw masks volatile tokens in `tool-loop-detection.ts`), warn at the 3rd repeat, block at 5, and `hard_stop` on for routines and off for attended chats. Hash arguments so the guard cannot leak them.
- **Copy from OpenClaw** (`tool-loop-admission.ts`): decide at admission, before the call runs; if the guard itself errors, block. Cline runs its detector from `tool-started`, after the call was issued: do not do that.
- **Copy from Cline** (`mistake-tracker.ts`): a turn where every tool call failed is a "mistake"; any success resets it.
- **Where the state lives:** derive it from the event log fold, not an object local to the loop (goose's `RepetitionInspector` counts on a clone and never accumulates). The node can then rebuild it after a restart.
- **Do not copy** DeepSeek's notice-only reminder as the only guard: it never stops a loop. Add it as the warning stage, with the block after it.
- **Test:** a scripted provider issuing the same failing `read` call; assert the 5th call is refused with a visible reason and the 3rd carried a warning.

### 6.3 Do: step, time and tool limits in `node.toml`, enforced in the dispatcher (fix)

- The cap of 50 is hard-coded; the node is the authority, so move the cap and a per-turn wall-clock into `node.toml` `[limits]` (today only `tool_stream_bytes`) with defaults, as Hermes does for routines (a finite default per routine) and goose does with `GOOSE_MAX_TURNS` plus a half-budget `<turn-budget>` hint.
- **Copy from OpenCode** (`session/runner/llm.ts`, `step.ts`): at the cap, keep tool schemas in the request, set `tool_choice: none`, append an instruction, and refuse any late tool call at dispatch. It keeps the provider cache and is enforced, not requested.
- **Enforce each tool's deadline in the dispatcher, once** (Cline's `timeoutMs` metadata is never read; goose lets the model set `timeout_secs` and 0 disables). Clamp any model-supplied timeout to a `node.toml` maximum; never let 0 mean infinite. Our bash cap of 3600 s is the model-visible ceiling: check it is a node setting.
- Prefer idle limits to total limits for the provider stream (OpenClaw 120 s, Codex 5 min, OpenCodex 300 s), which pull request 7 should set.

### 6.4 Do: never run tool calls from a response that stopped on the length limit (fix)

Pi fails every tool call in a `length`-stopped message ("was not executed: the response hit the output token limit, so its arguments may be truncated") because streamed arguments are completed by a JSON salvage parser (`packages/agent/src/agent-loop.ts` L273-L279, L488-L513, checked in review). OpenCode separately fails the step after three consecutive `length` stops. A truncated `write` or `bash` argument is a data-loss and safety hazard.
- **Check in our code:** how does `agent-native` assemble arguments from stream chunks, and what does it do with a `length` finish? Test: a provider fixture ending a `write` mid-JSON.

### 6.5 Do: provider retry rules (pull request 7), from Codex and others (fix, already in flight)

- Copy Codex's single error-to-policy function (`protocol/src/error.rs` classification; `core/src/responses_retry.rs`): never retry context overflow, auth, model-not-found, quota; server advice before local backoff; `Retry-After` cannot extend the configured count.
- **Add the rule Cline and Oh My Pi have and Codex only implies:** never retry a turn after it already streamed visible output, or after a tool ran ("no replay-unsafe committed output unless every tool call provably never ran", `turn-recovery.ts`). Check that PR 7's retry cannot re-run a step whose tool calls were already issued.
- Cap provider-requested waits (Oh My Pi `maxDelayMs` 300 s): a three-hour sleep in a node is a stuck session.
- OpenCodex's rule fits master-side proxies: charge retries to the logical request, not each hop.

### 6.6 Do: fence every settle with a claim generation (fix, ties to the nodes design note)

The invariant is "events are appended only by the owning node's session actor". Nothing in the files read shows a design that survives a stale node better than Hermes: `claim_session_input` bumps a per-session `runtime_generation`; `settle_session_input` accepts only a matching epoch and generation (`hermes_state_runtime.py` L206-L274); at start a global epoch is incremented and every `started` row of an earlier epoch becomes `unknown` and is never requeued (L453-L464). OpenClaw's `activeWriterRunId` compared inside the write transaction (`session-accessor.sqlite-scope.ts` L79-L97) does the same at the storage level, but is skipped when a write carries no expected writer: make the unfenced path impossible. OpenCode has no fence and says its sweep "assumes every orphaned claim's owner is dead"; Codex and DeepSeek use file locks that only protect one host.
- **For us:** when a workspace node reconnects or a session is moved to another node (the design note's worktree-per-session and node-per-workspace), give each claim a generation; the master rejects an append that names an old one. Test: two nodes append to one session; the older one is refused and the log stays contiguous.
- Also copy the OpenClaw lost-worker message: "tool effects may be unknown"; never auto-continue a turn after a lost node.

### 6.7 Do: unattended runs close themselves and record why (fix, routines)

- **Copy from Hermes** (`gateway/session_unattended_unknown.py`, `cron/scheduler_tick.py`, `cron/scheduler_authority.py`): advance the routine's next-run time before dispatch (at-most-once), write an idempotency key for each fire before it runs, pause the routine when the outcome is unknown, and settle a crashed routine turn as `interrupted` with a reason so the next run is not blocked; a person's own crashed turn waits for a decision. OpenClaw's cron retry has no attempt counter (a run that crashes again before delivery qualifies again): store an attempt count on the receipt.
- **Default for unattended:** keep our "routines run agentic only in `ask` or `ask_all`" rule; Hermes' `cron_mode: deny` is the same idea. Do not follow Oh My Pi, Cline or goose (default `yolo` or `Auto` for scheduled runs).
- **Return the real refusal to the model** on unattended runs (Warp tells the model "denylisted" for every denial, which misleads it).
- Skip-not-burst on catch-up (OpenCode, DeepSeek's latest-only) and an explicit overlap rule (goose lets a job overlap itself).

### 6.8 Do: a dispatcher-level ceiling on every tool result (fix, small)

Pi enforces truncation per built-in tool; an extension tool returning 10 MB goes straight into context. Our shell filter and the 2 MB `tool_output` store exist; pull request 4 adds capped file tools. **Check:** `web_fetch` (2 MiB body cap, 20,000 characters), MCP results and any future tool pass through one cap in the dispatcher, ideally proportional to the context window (OpenClaw: 30% of the window and 16k, 32k or 64k characters), with a recoverable handle (Cline's `cline://cache` URI; our `tool_output` id is the equivalent). Cap while reading, not after (goose holds a gigabyte in memory first; our idle RSS budget makes this mandatory).

### 6.9 Do: cancel and orphan processes (fix; mostly gate3)

- Cancel semantics to copy: Goose's "every open tool call gets a terminal result" on cancel (`machine.rs` L250-L285); OpenCode's cooperative cancel, grace, then interrupt, and its "decline is a defect, feedback is a failure" split so a tool cannot swallow a refusal (`model-request.ts`, `permission.ts`).
- Kill: Oh My Pi re-walks the process tree between SIGTERM and SIGKILL (`proctree.rs`); a cgroup or pid namespace is stronger (goose and Cline children that call `setsid` escape a group kill).
- **Node crash leaves children running** (goose: shells get no `PR_SET_PDEATHSIG`). Check what our node does with a `bash` child when the node is killed; with the Landlock launcher in pull request 4, test that a restarted node does not leave an earlier shell running against the same worktree.

### 6.10 Decide, feature (freeze): input during a turn

Today: reject. That is safe; no accepted input is lost. If the owner breaks the freeze, the evidence says:
- Persist the message as an event or row with an idempotency key before acknowledging (Hermes `session_admissions`, OpenClaw `session_pending_inputs`, DeepSeek's `requestId` in the logged message). Pi's and OpenClaw's in-memory queues do not survive a crash.
- Deliver at a step boundary and never kill a running tool (Codex, Pi, Oh My Pi). In parallel batches this waits for the batch; if we stay sequential it is fine. Make interrupt a separate explicit action.
- When a queued message is dropped, write an explicit receipt (OpenClaw).
- Avoid the OpenHands shape: a message written to a socket the server has not subscribed, or held in browser memory, can be lost; the node should append the user message to the log before any "run" decision.
- Cost against the plan: a new event type, a node protocol message and UI state (not in `Shell.tsx`). I would not do it before Gate 3.

### 6.11 Avoid

- Per-tool authorisation (OpenCode `permission.assert`, Cline per-tool validation after approval): one forgotten check is an unchecked tool. Our dispatcher should authorise once, with tools declaring resources.
- Validation after policy (DeepSeek): validate arguments before policy so a reviewer sees a normalised shape, and re-validate after any hook mutates them (Pi does not).
- Tool results as user-role text (OpenHands client tools): results are events written by the owning node.
- Persistence as an option (OpenCode's durable log is off in the shipped server): our log is the truth.
- Parallelism by name ("read-only"): Codex's lesson is that a shell command can write. If we add parallel execution, key it on declared effects, serialise authorisation and parallelise execution (Pi, Cline), and keep shell exclusive.
- Resume cost growing with age: DeepSeek reads the whole log (`read(0)`). Codex's rule (latest full-history compaction is a base, replay only the suffix) makes resume independent of session age; our fold needs the same checkpoint record. This ties to pull request 7's compaction.
