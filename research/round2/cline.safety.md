## 2. Architecture as it bears on this cluster

**Languages and layout.** TypeScript on Bun/Node (`AGENTS.md`: Bun 1.4.2, Node >= 22). The monorepo has an SDK (`sdk/packages/{shared,llms,agents,core,sdk,ui}`, layered `shared <- llms <- agents <- core`, see `sdk/ARCHITECTURE.md`) and apps on top (`apps/cli`, `apps/vscode`, `apps/cline-hub`, `apps/examples/desktop-app` which is the Tauri + Bun-sidecar desktop app). There is no Rust, no container code and no OS sandbox code in the product path.

**Process model.**

The CLI's default `backendMode` is `"auto"` (hub if available), forced to local for `--yolo` and the `--data-dir` "sandbox" ([run-agent.ts L173-L176](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/runtime/run-agent.ts#L173-L176)).

## 3. Findings

### 3.1 The agent loop and tool dispatch

#### The loop is a plain while loop with no iteration cap unless the host sets one
- What the code does: `execute()` loops `while (maxIterations === undefined || iteration < maxIterations)`. Each turn issues one model request (with provider-error retry), records the assistant message, runs all tool calls the message holds, pushes the tool-result messages and loops. The run ends when a turn has no tool calls (after "completion reminders"), when a tool marked `completesRun` succeeds, on abort, or on an exception. `maxIterations` is optional. The CLI sets none by default (only the schedule wizard exposes `maxIterations`), so an interactive CLI run is bounded only by the mistake limit, loop detector, `--timeout` and the user.
- Trace: `while` header [L849-L866](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L849-L866); tool execution and message push [L987-L996](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L987-L996); completing-tool exit [L1018-L1035](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L1018-L1035); cap error [L1038-L1040](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L1038-L1040); `--timeout` is a host timer calling abort ([run-agent.ts L319-L330](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/runtime/run-agent.ts#L319-L330)).
- Edge cases and failure handling: an exception, abort or controlled stop is caught at the end of `execute`, mapped to status `failed` or `aborted`, `afterRun` hooks still run, and a result object is returned instead of a throw ([L1041-L1102](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L1041-L1102)). A second `run()` while running throws ([L803-L805](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L803-L805)).
- Round 1: `not in code` for a documented iteration limit (Round 1 only noted `--retries`); `new (not documented)` that CLI iteration count is unbounded.
- For rizzy-harness: set a default iteration and wall-clock cap in the node, not in the UI. Cline's lack of one is a cost-runaway risk.
- Confidence: traced end to end (cap absence in the CLI is inferred from grep: `maxIterations` appears in `apps/cli/src` only in the schedule wizard). (checked in review)

#### Dispatch order: JSON parse, `beforeTool` hooks, policy, approval, execute, `afterTool` hooks
- What the code does: for each tool call, `prepareToolExecution` (1) takes a skip reason if the streamed arguments were invalid JSON or the tool is provider-executed, (2) runs every `beforeTool` hook in order (a hook can rewrite `input`, set a `policy` override, append context, `skip` with a reason, or `stop` the run), (3) merges `toolPolicies["*"]`, `toolPolicies[name]` and the hook's override, (4) skips if `enabled === false`, (5) calls `requestToolApproval` only if `autoApprove === false`. `executePreparedTool` then calls `tool.execute`, then the `afterTool` hooks (which can replace the result). Unknown tool names produce an error result, not an exception. All tool calls of one assistant message are prepared (so all approval prompts happen) before any runs.
- Trace: input-parse skip [L2445-L2447](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2445-L2447) (set by [parseToolInput L2872-L2903](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2872-L2903)); hooks [L2469-L2500](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2469-L2500); policy and approval [L2502-L2524](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2502-L2524); prepare-all-then-execute [L2370-L2408](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2370-L2408); execute [L2574-L2630](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2574-L2630); `afterTool` [L2635-L2660](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2635-L2660).
- Edge cases and failure handling: a thrown error in `tool.execute` becomes `{error, isError:true}` in the tool result ([L2622-L2629](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2622-L2629)). A `beforeTool` hook that throws is not caught here, so it propagates to the run-level catch and fails the run; the plugin wrapper and the file-hook runner swallow errors before they get here (see 3.6). Schema validation is not central: each built-in tool validates its own input (for example `validateWithZod` in [definitions.ts L731](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/definitions.ts#L731), `normalizeRunCommandsInput` in the shell tool [L536-L539](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/definitions.ts#L536-L539)).
- Round 1: `new (not documented)`.
- For rizzy-harness: Cline's order (hooks before policy before approval) is a good one: a deny hook short-circuits a prompt. Validate tool input once, centrally, before any hook sees it.
- Confidence: traced end to end. (checked in review)

So `spawn_agent`'s declared `timeoutMs: 300000` is not enforced anywhere I found.
- Trace: defaults [create.ts L141-L143](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/tools/create.ts#L141-L143); the call site without a timeout [agent-runtime.ts L2600-L2629](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2600-L2629); declared and unused [spawn-agent-tool.ts L201-L202](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/team/spawn-agent-tool.ts#L201-L202); plugin reader [plugin-registry.ts L991-L1020](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/plugin/plugin-registry.ts#L991-L1020).

#### Cancel is one AbortController whose signal reaches the shell and kills the process group
- What the code does: `abort()` records a `TASK_CANCELLED` event and aborts one `AbortController`; the signal is passed in the tool context. The shell executor listens on it, kills the whole process group with `SIGKILL` (`taskkill /T /F` on Windows) and rejects.  A pending approval is not tied to the signal in the runtime; hosts must resolve it (the hub cancels pending approvals on abort, VS Code `clearPending`).
- Trace: [agent-runtime.ts L650-L666](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L650-L666); signal into tools [L2608](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2608-L2608); kill [bash.ts L773-L817](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/bash.ts#L773-L817), abort listener [L819-L848](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/bash.ts#L819-L848); hub cancel [approval-handlers.ts L99-L121](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hub/server/handlers/approval-handlers.ts#L99-L121).
- Edge cases and failure handling: the shell is spawned `detached` (own process group) so a grandchild that setsid()s away survives; `-pid` SIGKILL only reaches the group.
- Round 1: `new (not documented)`.
- For rizzy-harness: copy "kill the group, not the pid". Add a cgroup or a pid namespace if you want orphans gone.
- Confidence: traced end to end.

#### Provider errors: three retries with 1 s, 2 s, 4 s backoff (cap 15 s), only for transient errors
- What the code does: a turn that fails with a retryable provider error and produced nothing but reasoning is re-issued up to `PROVIDER_ERROR_MAX_RETRIES = 3` (four requests total), waiting `min(1000 * 2^(attempt-1), 15000)` ms, abortable. Auth and context-window errors are never retried (context overflow goes to compaction recovery). There is no jitter. Separately, an output-limit cut-off with no tool call is nudged up to 3 times (`MAX_TOKENS_RECOVERY_LIMIT`).
- Trace: constants [agent-runtime.ts L72-L91](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L72-L91); retry loop [L1255-L1293](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L1255-L1293); retryability [L1308-L1337](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L1308-L1337).
- Edge cases and failure handling: no retry if any text or tool call had already streamed, to avoid duplicate UI output; no retry after provider-executed tool activity, to avoid repeating side effects.
- Round 1: `confirmed` (3 model-request retries); the CLI `--retries` flag is a different thing (see next entry).
- For rizzy-harness: copy the "do not retry if output already streamed or side effects ran" rule; add jitter.
- Confidence: traced end to end. (checked in review)

#### Two stuck-loop guards: consecutive failed turns (default 6 in the SDK, 3 in the CLI) and identical consecutive tool calls (warn at 3, stop at 5)
- What the code does: `SessionRuntime` counts a "mistake" when a turn has failed tool calls and no successful ones, and resets on any productive turn. At the limit it asks the host callback (`onConsecutiveMistakeLimitReached`); the CLI answers "stop" automatically when auto-approve is on (message: "in yolo mode") and otherwise asks the user. The CLI default limit is 3 (`--retries`), the SDK default 6. Loop detection compares tool name plus key-sorted JSON input of consecutive calls: the 3rd identical call appends a user-role notice, the 5th forces the mistake counter to the limit, which calls the same host callback (no callback: stop; CLI in yolo or without a TTY: stop; interactive CLI: asks the user, so the run is not necessarily aborted).
- Trace: limit default [session-runtime-orchestrator.ts L474](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L474-L474); per-turn bookkeeping [L1415-L1437](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L1415-L1437); loop inspection [L1524-L1554](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L1524-L1554) and abort [L1567-L1591](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts#L1567-L1591); thresholds [loop-detection.ts L113-L116](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/runtime/safety/loop-detection.ts#L113-L116); CLI values [defaults.ts L6-L9, L15](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/runtime/defaults.ts#L6-L15), [main.ts L1079-L1081](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/main.ts#L1079-L1081); CLI resolver [mistakes.ts L9-L21](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/runtime/interactive/mistakes.ts#L9-L21).
- Edge cases and failure handling: loop inspection runs from the `tool-started` event (after approval), so it never blocks the repeated call itself and also counts denied or skipped calls; the abort is enqueued on a promise chain and lands after the 5th call has started. A shell command that exits non-zero returns `success:false` inside a normal result and is not an error turn, so a model looping on a failing command is only caught by the identical-call detector.
- Round 1: `corrected`: Round 1 says "`--retries` = consecutive mistakes allowed before exit (default 3)": true for the CLI, but the SDK default is 6 and the same counter is also fed by the loop detector.
- For rizzy-harness: copy both guards; make the repeat guard check before dispatch so the 5th call does not run.
- Confidence: traced end to end. (corrected in review: the hard escalation goes through the host callback and does not always abort)

### 3.2 Approvals and permission rules

#### There is no rule grammar: the whole model is `{enabled, autoApprove}` per tool name, default allow
- What the code does: a tool call is gated by `toolPolicies[name]` merged over `toolPolicies["*"]`. Missing policy means enabled and auto-approved. `autoApprove:false` calls the host's `requestToolApproval`. If a tool needs approval and the host gave no callback, the call is denied; if the callback throws, it is denied. Nothing in the SDK is bound to a command string, a path or a command prefix; there is no "always allow this command" store; an approval answers exactly one `toolCallId`. `policyDependencies` lets one tool inherit `enabled:false` or `autoApprove:false` from others.
- Trace: [resolveToolPolicy L216-L234](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L216-L234); gate [L2502-L2524](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2502-L2524); no callback and callback failure [L2539-L2571](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2539-L2571).
- Edge cases and failure handling: closed on failure for the approval path (deny), open for the missing-policy path (allow). A hook can force a prompt for one call by returning `policy:{autoApprove:false}`, but not the file-hook path (see 3.6).
- Round 1: `confirmed` ("tools with no policy are enabled and auto-approved by default").
- For rizzy-harness: this is the weakest part to copy. A rule grammar with precedence, bound to the parsed command, is the part Cline lacks.
- Confidence: traced end to end. (checked in review)

#### Defaults by surface: CLI on, Desktop on, VS Code per category, cron yolo, ACP off

The Desktop sidecar uses `autoApprove: config.autoApproveTools !== false`, i.e. on unless the UI sends an explicit false. Scheduled runs (below) are on. The VS Code extension has its own category table (next entry).
- Trace: CLI default and policy [main.ts L885-L895](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/main.ts#L885-L895); precedence [startup-settings.ts L21-L31](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/utils/startup-settings.ts#L21-L31); flag parsing [program.ts L145-L161](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/commands/program.ts#L145-L161); ACP [main.ts L802-L811](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/main.ts#L802-L811); Desktop [chat-session.ts L853-L861](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/examples/desktop-app/sidecar/chat-session.ts#L853-L861).
- Edge cases and failure handling: with `--auto-approve false` in a non-TTY (CI, pipe) the terminal approver denies every call ("requires approval in a TTY session"), so a headless run with approvals on does nothing useful ([approval.ts L69-L77](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/utils/approval.ts#L69-L77)). The CLI help text for `--auto-approve` literally says "(default: true)".

#### VS Code: four categories plus MCP, defaults read, edit, browser and MCP on, commands off; one toggle covers every command
- What the code does: the extension sets `autoApprove:false` on every read, edit, command, web and MCP tool, so the SDK always calls the extension's callback, which re-evaluates the live settings (`isToolAutoApproved`) and either approves silently or shows buttons. ### 3.11 Hub authentication and workspace scope

#### The hub has a random per-start token and also accepts any loopback `Origin` header without it
- What the code does: the daemon binds `127.0.0.1` by default, mints `randomBytes(32).hex` per start, writes it to a discovery file created with mode 0600, and checks it (constant-time compare) from the `Sec-WebSocket-Protocol` value `cline-hub-auth.<token>` or a Bearer header on HTTP endpoints. For the WebSocket upgrade it authorises a connection if the token is valid or if the bind host is local and the `Origin` header's hostname is `localhost`, `127.0.0.1` or `::1`. `Origin` is a client-supplied header: any local process can set it, and any page served from a local port in a browser sends it. Connections authorised only by origin are marked `tokenAuthenticated:false`: they are refused `providers.*` and `mcp.*` commands, cannot use cross-workspace or local-git cloud operations, and register pinned to the hub's workspace root. Session creation, run, send-input and approval commands do not look at that flag.
