## 2. Architecture as it bears on this cluster

- **Process model.** One HTTP server process per machine ("the managed service", `opencode serve --service`) owns sessions, plugins, tools and the SQLite database. TUI, web app, desktop, `opencode run` and the SDK are clients of its HTTP API. Three server modes exist: `default` (foreground), `service` (shared background), `stdio` (private, lives as long as the parent's stdin pipe). Type and branches: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/server-process.ts#L23-L23 and https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/server-process.ts#L87-L96 .
- **API definition.** `packages/protocol` declares the HTTP API once (Effect `HttpApi`, groups under `packages/protocol/src/groups/*`); `packages/server` implements the handlers; `packages/client` has generated Promise and Effect clients; `packages/protocol/openapi.json` is the emitted spec. Example endpoint declarations: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/protocol/src/groups/server.ts#L56-L79 .
- **State.** One SQLite file (`opencode.db` in the data dir) in WAL mode: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/database/database.ts#L42-L46 and https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/database-path.ts#L4-L13 . Sessions are an **event-sourced aggregate**: every durable event goes through `Bus` (`packages/core/src/bus.ts`), is given a per-aggregate `seq`, is applied by projector functions to ordinary tables (`session_v2`, `session_message`, `session_part`, `session_inbox`, ...) inside the same transaction, and is (optionally, see finding "Durable log is opt-in") written to an `event` table. Table definitions: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/session/sql.ts#L28-L80 and https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/event/sql.ts#L4-L26 .
- **Location.** Most API calls are scoped to a "Location" (a project directory, optionally a workspace); per-location services (tools, plugins, MCP, snapshot, skills) are built per Location.

## 3. Findings

### Client and server split

#### One shared background service per machine, found through a registration file
- What the code does: the server writes `service.json` (url, pid, version, **password**, instance id) under the user state dir with mode 0600 and re-checks every 5 s that the file still names it; if replaced it shuts itself down. A client reads that file as "the complete discovery contract", health-probes `GET /api/info` with Basic auth, checks pid and version match, and otherwise spawns `opencode serve --service` "contenders" until one answers. The server itself, at boot, looks for an incumbent on its port and exits if one is healthy; on `EADDRINUSE` it polls up to 15 s for the incumbent.

#### Other connection modes: `--server URL`, `--standalone`, private stdio server
- What the code does: `--server` connects to an explicit URL with Basic auth from `OPENCODE_PASSWORD` and only warns on a version mismatch. `--standalone` (or `service disabled`) starts a private child server with `--stdio --port 0`; the parent generates a random password and passes it in the child's environment; the child prints `{"url":...}`, deletes the password variables from its own environment so tools cannot inherit them, and exits when stdin reaches EOF.
- Trace: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/services/server-connection.ts#L27-L66 ; child command and lease comment: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/services/standalone.ts#L11-L27 ; env scrub and stdin wait: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/server-process.ts#L87-L90 and https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/server-process.ts#L233-L245
- Edge cases and failure handling: pipe EOF as lease means a killed parent cannot orphan the server ("The OS closes it even when the TUI is killed"). `opencode run` uses `autostart: false`: it attaches to an already-running service, otherwise starts a private one and never leaves a new service behind (https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/commands/handlers/run.ts#L9-L13).
- Round 1: `confirmed` (`--standalone`, `opencode serve`); `new (not documented)`: the stdio lease.
- For rizzy-harness: stdin-EOF as lifetime lease for a private child is a good trick for tests and one-shot headless runs.
- Confidence: traced end to end (checked in review).

#### Server authentication: one shared secret, three ways to present it
- What the code does: the server will not start without a password (`Missing server password`), and the outer dispatcher requires credentials for everything except `/auth/connect/:code` and three ticketed WebSocket upgrade routes. Credentials are Basic auth with the fixed user `opencode`, or a session cookie, or `?auth_token=` (a base64 `user:password` blob in the URL). The raw-password comparison is a plain `===` (not constant time); only the session-token HMAC compare uses `timingSafeEqual`. A service password is generated once (32 random bytes) and persisted in the service config (0600). Foreground `serve` prints `server password ...` to stdout when no env password was given.

#### Per-session data is not scoped to a credential
- What the code does: authorization yields a boolean only. There is one fixed username and one secret; handlers do not receive an identity. Sessions are addressed by id plus a Location (directory/workspace) for routing, not for access control.
- Trace: `Info` has only `password` and `username`: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/auth.ts#L11-L14 ; `authorized` returns a boolean: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/auth.ts#L33-L37
- Edge cases and failure handling: none to speak of; a stolen pairing session equals the password.
- Round 1: answers the open question "whether per-session data is scoped to the cookie or visible to anyone with the shared password": visible to anyone with any valid credential.
- For rizzy-harness: confirms rizzy's multi-user plus private-chat invariant is a real differentiator; do not copy this model for the master.
- Confidence: read the definition (negative claim: I found no per-user identity type in `packages/server/src`) (checked in review).

### Pairing links and tunnelled remote access

#### Pairing code: 16 random bytes, 5 minutes, single use, in memory
- What the code does: `POST /api/pair` (authenticated) mints `randomBytes(16)` base64url, stores it in an in-memory cache (capacity 1000, TTL 5 min) and returns `{code, expires_in}`. `GET /auth/connect/:code` is unauthenticated; it atomically removes the code (`Cache.invalidateWhen`), and on success issues a session token. Browsers (Accept: text/html) get a 302 to `/` with an `httpOnly`, `sameSite=lax`, 30-day cookie named `opencode_session_<port>`; JSON clients get `{token}` to use as the Basic-auth password. The cookie has no `Secure` attribute.
- Trace:
  1. Code store, TTL, issue and consume: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/pairing.ts#L7-L34
  2. Handlers for pair and connect: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/handlers/server.ts#L31-L55
  3. Route is exempt from credential checks: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/middleware/authorization.ts#L87-L94
  4. CLI: `opencode pair` prints the link(s), expiry and a QR code of `{code, urls}` (non-loopback only): https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/commands/handlers/pair.ts#L28-L54
- Edge cases and failure handling: codes are lost on restart (memory only) and a restart does not revoke issued sessions. An expired or used link returns 401 text. Over SSH the CLI prints an `ssh -L` hint and tells the user to set `hostname 0.0.0.0` for other devices (https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/commands/handlers/pair.ts#L56-L68).
- Round 1: `confirmed` (single-use, 5 minutes, 30-day cookie).
- For rizzy-harness: single-use in-memory code, atomic consume, redirect-with-cookie for browsers and token for API clients is a sound small design. Consider adding `Secure` and per-device records (below).
- Confidence: traced end to end (checked in review).

#### What a pairing session grants and how it expires or is revoked
- What the code does: the token is `"<expiry-unix-seconds>.<HMAC>"` where the HMAC key is derived from the **server password**. It is accepted anywhere the password is. There is no per-token identity, no list, no individual revocation; the only revocation is changing the password (comment: "rotating the password revokes every session"). Expiry is fixed 30 days from issue.
- Trace: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/auth.ts#L16-L16 , https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/auth.ts#L39-L55 , https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/server/src/auth.ts#L63-L66
- Edge cases and failure handling: stateless, so nothing to clean up, but a leaked cookie cannot be revoked short of rotating the password for everyone. Because the token is valid as a Basic password, a paired phone can also drive the HTTP API and mint further pairing codes (`/api/pair` needs only normal auth).
- Round 1: `confirmed` ("30-day cookie"); `new (not documented)`: no revocation granularity, tokens are password-derived.
- For rizzy-harness: store pairing sessions server-side (id, device label, last seen, scopes) so a lost phone can be revoked alone; make "can mint pairing codes" a separate capability.
- Confidence: traced end to end (checked in review).

#### `--remote`: OpenTunnel, a secret subdomain, and what could not be verified
- What the code does: `opencode pair --remote` asks once for consent, sets the service config `remote` (a random 16-hex-char route), restarts the service and waits up to 3 minutes for the tunnel URL to appear in `server.info`. Inside the service, `@opentunnel/client` (npm 0.6.1) opens a tunnel from the machine to a relay and maps `https://<route>.<tunnel-hostname>` to the local server. The comment says the hostname appears in public certificate logs but the certificate covers subdomains by wildcard, so the random route is what keeps the address unguessable. The route is treated as secret as the password ("The route is as sensitive as the password"). The password is still required on that URL.
- Trace: consent and flow https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/commands/handlers/pair.ts#L20-L31 ; tunnel run, retry, fatal classification https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/services/remote-tunnel.ts#L7-L47 ; route generation https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/services/service-config.ts#L171-L173 ; target selection (wildcard bind tunnels to loopback) https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/cli/src/server-process.ts#L190-L206
- Edge cases and failure handling: setup failures retry with exponential backoff capped at 30 s; a rejected token, failed certificate issuance or an unsupported proxy scheme (socks5) stops it for good with a log line. The tunnel and relay are outside this repo.
- Round 1: `confirmed` that `--remote` exists. **Not settled**: "end-to-end encrypted" cannot be confirmed from this repository, because all encryption lives in the external `@opentunnel/client`/`@opentunnel/protocol` packages (pinned 0.6.1 in `bun.lock`). The repo comments suggest the device obtains its own certificate for the tunnel hostname (consistent with TLS terminated on the user's machine), but this is inferred from comments only.
- For rizzy-harness: relies on a third-party relay; the in-repo security is "unguessable subdomain plus password". If rizzy wants remote access, the hop-by-hop trust question has to be answered from the tunnel's own source.
- Confidence: read the definition (client side); the tunnel itself not read.

#### Remote machines over SSH (desktop "Add SSH server")
- What the code does: the desktop plugin runs `ssh` to the remote host, runs a script that finds the `opencode` binary, runs `opencode service status`, then `cat`s `service*.json` back over the SSH channel to learn the loopback URL and the password. If no matching version is present it downloads `@opencode/cli-<os>-<arch>` from `registry.npmjs.org` on the remote (or uploads the tarball over stdin as a fallback), checks only that `--version` equals the expected string, starts the service, and opens `ssh -L 127.0.0.1:<local>:<host>:<port>` with ControlMaster off. The URL must be `http` on a loopback host or bootstrap is rejected. SSH options are filtered to a short allow-list (`-p -l -i -F -J -o` with a fixed set of `-o` keys; newline, CR and NUL in the target are refused).

### Durable per-session event log

#### Event-sourced writes: per-aggregate contiguous `seq` under a lock and a transaction
- What the code does: every durable event is committed by `Bus` under a per-aggregate keyed mutex inside an `immediate` SQLite transaction. It reads the latest `seq` from `event_sequence`, takes `latest + 1`, runs the projectors (which update the session and message tables), runs an optional caller `commit` hook (used to set or clear the execution claim atomically), upserts `event_sequence`, and, only if persistence is on, inserts the row into `event` (unique on `(aggregate_id, seq)`, id unique). Subscribers waiting on the aggregate are woken after commit.
- Trace:
  1. Commit path (seq assignment, projectors, hook): https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L372-L412
  2. Event-table insert and `immediate` transaction: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L417-L434
  3. Per-aggregate lock: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L470-L470
  4. Wake of durable subscribers after commit: https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L438-L444
  5. Schema (sequence table with `owner_id`, event table): https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/event/sql.ts#L4-L26
- Edge cases and failure handling: `replay(event)` re-applies a serialized event at an exact `seq`: equal id, type, time and payload is a no-op, a different payload at the same seq dies with "Replay diverged", a gap dies with "Sequence mismatch", and an aggregate with a different `owner_id` is rejected (strict) or ignored (https://github.com/anomalyco/opencode/blob/05d347d75054bf27778750ad5f2cd30336e81d8f/packages/core/src/bus.ts#L329-L378). I found no non-test caller of `replay` or `claim` in `packages/*/src`, so this is machinery for future replication, not an active feature.
- Round 1: `confirmed` in outline ("durable per-session event log with sequence numbers"); detail is new.

#### The log read contract: exclusive cursor, replay then marker then follow
- What the code does: `GET /api/experimental/session/:id/log?after=<seq>&follow=<bool>` streams SSE. `after` is exclusive (default -1, i.e. from the start). #### Guards against cost in large repositories
- What the code does: the shadow store sets `fsmonitor=false`, `untrackedCache=true`, `feature.manyFiles=true`, index v4 and threaded index, and no split index. #### MCP client: transports, auth, limits, and how tool lists stay out of context
- What the code does: local servers use stdio, spawned through the location's `Environment` (so they run wherever the rest of the execution happens); remote servers use Streamable HTTP, OAuth on by default (code in `mcp/oauth.ts`), with a `protocol` setting (`legacy` default, `auto` or a pinned 2026-07-28 revision) and optional `pool: true` to share one connection across directories with identical config (only for the 2026-07-28 revision; key includes URL, header fingerprint, OAuth config and credential). Timeouts default to 30 s startup, 30 s catalog and 12 h per call; stdio frames are capped at 16 MiB. Each MCP tool is registered under a namespace named after the server and every call first asserts a permission with action `<server>_<tool>`.
- Keeping lists out of context: a tool is "Code Mode" by default (`codemode !== false`). The model gets one `execute` tool plus a **catalog** in its instructions: every namespace is always listed, and tool signatures are added round-robin, one per namespace per round, in path order, until a budget of 2000 tokens (estimated as chars/4, description cut to 120 characters) is spent; the prompt then tells the model the catalog is partial and to find tools with a global `search(...)` function inside `execute`. Core built-ins (`read`, `edit`, `patch`, `shell`, `grep`, `skill`, subagent, todo...) are marked `codemode:false` and stay direct tools; a few `opencode` namespace tools are pinned into the listing. If the `execute` tool is denied by permission rules, all Code Mode tools become direct tools. Catalog changes are sent to the model as deltas with a fixed update budget.
