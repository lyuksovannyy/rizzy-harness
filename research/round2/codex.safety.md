## 2. Architecture as it bears on this cluster

- **Process model.** One Rust binary hosts the agent loop (`core`) behind the JSON-RPC app-server (stdio, WebSocket or a WebSocket-over-Unix-socket daemon). Commands are executed either locally or by an `exec-server` (local or remote, reached over a Noise channel). Sandboxed commands on Linux run through a helper (`codex-linux-sandbox`, re-entered via `arg0`) that execs bubblewrap and then re-enters itself inside the sandbox to apply seccomp.
- **Loop.** `run_turn` loops over sampling requests; each call to `run_sampling_request` builds a `ToolCallRuntime` and streams the model response, dispatching tool calls as they arrive: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L647-L690 (one sampling step, then follow-up decision from `needs_follow_up` or pending input).
- **Tool dispatch and parallelism.** A per-turn `RwLock<()>` gates admission: tools that declare parallel support take a read lock, all others a write lock, so mutating tools are serialised against everything: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/parallel.rs#L292-L304 (read vs write lock by `supports_parallel`).
- **Where safety decisions live.**
  - Command rules: `core/src/exec_policy.rs` (turns a command into an `ExecApprovalRequirement`) on top of the `execpolicy` crate (Starlark).
  - Approval flow and sandbox retry: `ToolOrchestrator::run`: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L164-L233 (Skip / Forbidden / NeedsApproval / NeedsHumanApproval).
  - Sandbox selection and command wrapping: `sandboxing/src/manager.rs`; Linux enforcement in `linux-sandbox`.
  - Model-based approver: `core/src/guardian/` (host side) plus `ext/guardian-reviewer` (routing, circuit breaker, completion).
  - Hooks and their trust: `hooks/src/engine/discovery.rs`.
  - Network egress: `network-proxy` (opt-in), with a Linux bridge in `linux-sandbox/src/proxy_routing.rs`.
- **Compaction** lives in `core/src/compact*.rs` and is triggered from `run_turn` (`run_auto_compact` around turn.rs L740-L790); it belongs to the `agents` cluster and was not traced here.

## 3. Findings

### 3.1 Agent loop and tool dispatch

#### Approval happens before the first attempt; a sandbox denial triggers a second, separately approved attempt
- What the code does: `ToolOrchestrator::run` computes the tool's `ExecApprovalRequirement` (or a default from the approval policy), asks for approval if needed, runs a first attempt under the selected sandbox, and only if the result is `SandboxErr::Denied` considers a retry without the sandbox. The retry requires a fresh approval unless the first approval came from the user or a hook and the policy allows bypass; a Guardian approval never pre-approves the retry, and the retry is always re-reviewed under strict auto-review.
- Trace:

  - Sandbox selection for the first attempt: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L333-L360 (`should_sandbox`, `select_initial`, `ensure_native_sandbox`).
  - Denial handling and "never retry" policies: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L446-L480 (no unsandboxed retry under `OnRequest`/`Never`, or when denied reads exist).
  - Retry pre-approval scope: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/orchestrator.rs#L491-L501 (only `User` or `Hook` approvals carry over).
  - `wants_no_sandbox_approval`: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/sandboxing.rs#L349-L356 (`OnRequest` and `Never` never offer the unsandboxed retry; `UnlessTrusted` does; `Granular` per config).
- Edge cases: "denied" is a heuristic: exit code 0, 2, 126, 127 are never denials; on Linux 128+SIGSYS is; otherwise stderr/stdout keyword matching (`permission denied`, `sandbox`, `seccomp`, ...): https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/sandboxing/src/denial.rs#L13-L72 (exit codes plus keyword list). ### 3.2 Approvals, command rules and shell parsing

#### The rule engine: Starlark `prefix_rule`, most restrictive decision wins
- What the code does: `.rules` files are evaluated as Starlark (extended dialect, f-strings) with three builtins: `prefix_rule(pattern, decision, match, not_match, justification, canonical_matching)`, `network_rule(host, protocol, decision)` and `host_executable(name, paths)`. A pattern is a list of tokens (a token may be a list of alternatives); the first token keys the rule. Matching is an exact token-by-token prefix match on argv (optionally Unicode case-folded). All matching rules are collected and the decision is the maximum of `Allow < Prompt < PromptUser < Forbidden`. A rule file cannot express `prompt-user` (only `allow|prompt|forbidden` parse).
- Trace:
  - Builtins: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/parser.rs#L347-L410 (`prefix_rule`, default decision `allow`).
  - Prefix matching: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/rule.rs#L46-L73 (`matches_prefix`).
  - Decision order and parse: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/decision.rs#L7-L30 (derive `Ord`; `prompt-user` not parseable).
  - Aggregation: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/policy.rs#L577-L595 (`max()` over matches).
  - Host-executable fallback: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/policy.rs#L397-L424 (exact rules first, then absolute-path rules by basename, else heuristics).
- Edge cases: when no rule matches, a heuristic fallback decides per command segment (next finding). Loading: rule files come from `rules/` under every enabled config layer, low to high precedence, and the managed `requirements` policy is merged on top: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/exec_policy.rs#L746-L806 (layer folders, skip user/project when required, `merge_overlay`).
- Round 1: `confirmed` ("most restrictive decision wins").
- For rizzy-harness: an argv-prefix matcher with a strict decision lattice is small and auditable; copy it. Do not use Starlark unless we need computed rules; a TOML list gets the same matcher.
- Confidence: traced end to end (checked in review)

#### Inline `match`/`not_match` tests run at load, and one failing file silently drops every user and project rule
- What the code does: each `prefix_rule` call queues its examples; after the file is evaluated, `validate_pending_examples_from` builds a policy from just that call's rules and checks every `not_match` example matches nothing and every `match` example matches something. Example strings are split with `shlex`. On the core side, any `ParsePolicy` error (which includes a failed example) makes `load_exec_policy_with_warning` return only the managed requirements policy (or an empty one) plus a warning.
- Trace: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/parser.rs#L57-L79 (parse, then validate) ; https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/parser.rs#L133-L152 (per-call validation) ; https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/execpolicy/src/rule.rs#L258-L319 (match / not-match checks) ; https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/exec_policy.rs#L729-L744 (parse error falls back to requirements-only policy).
- Edge cases: a typo or a stale example in one file removes the user's own `forbidden` rules too, for the whole session, with only a warning. That is fail-open for user denials.
- Round 1: `confirmed` (tests at load) and `corrected`: the failure mode was not documented.
- For rizzy-harness: copy inline examples; on a broken rule file, keep the other files and fail closed (treat the broken file's commands as `prompt`), never drop denials.
- Confidence: traced end to end (checked in review)

#### How a shell command is split before matching, and when it refuses
- What the code does: only `[bash|zsh|sh, -c|-lc, script]` is unpacked. tree-sitter-bash parses the script; the parse is rejected if it has any error node, any named node outside `program, list, pipeline, command, command_name, word, string, string_content, raw_string, number, concatenation`, or any operator other than `&&`, `||`, `;`, `|`. Words containing `{ } * ? [ ] \ ~ ^ # $` or a backtick, or starting with `=` (zsh), are rejected; double-quoted strings are accepted only if they contain no expansion and no escape of `$ \` " \\` or newline. Variable assignments (`FOO=1 cmd`), redirections, substitutions, subshells, functions and control flow therefore all refuse to split. When splitting succeeds, each segment is checked separately; when it refuses, the whole argv `["bash","-lc","<script>"]` is matched as one command (so only a rule whose first token is `bash` can match it).
- Trace: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/shell-command/src/bash.rs#L29-L98 (allow-listed node kinds and operators) ; https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/shell-command/src/bash.rs#L106-L127 (only `-c`/`-lc` of bash/zsh/sh) ; https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/shell-command/src/bash.rs#L260-L301 (literal-word and double-quote checks) ; https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/exec_policy.rs#L971-L1001 (split, PowerShell on Windows, else whole argv).
- Edge cases: a second, looser parser (`parse_shell_lc_literal_commands`) walks every command node even in complex syntax, but is used only to find dangerous literal commands, never to prove safety: https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/shell-command/src/bash.rs#L129-L160 (documented "must not be used to prove that a command is safe").
- Round 1: `corrected`. "Opaque invocation" means the full `bash -lc` argv is prefix-matched on its first token, not an exact-string match; assignments and quoting escapes are also refused.
- For rizzy-harness: this is the design to copy for our approval path: an allow-list of syntax node kinds, fail-to-opaque, and a separate deny-only scanner. Write a test for each refused construct.
- Confidence: traced end to end (checked in review)

#### Unmatched commands: the heuristic is almost only "forced rm"
- What the code does: if no rule matches a segment, `render_decision_for_unmatched_command_for_platform` decides. #### The prompt and what the reviewer sees
- What the code does: the reviewer's base instructions are a bundled Markdown template with two slots (`tenant_policy_config`, `extra_policy`) filled from managed `guardian_policy_config` or local policy; the model catalog can replace the template and policy text unless managed policy is set, in which case the bundled template is forced. #### Fail-closed paths, timeout and the denial circuit breaker
- What the code does: prompt-build, session, parse and stale-authorization errors become a denial with "automatic approval review failed" ("FailedClosed"). A timeout is a separate `TimedOut` decision whose instructions tell the agent the action is not presumed unsafe and it may retry once or ask the user. Cancellation aborts. Exceeding the reviewer's input budget yields no decision (falls back to the normal approval path) unless Guardian review is mandatory, in which case it fails closed. A cached low-risk async score can approve without a synchronous review. The circuit breaker counts per turn: 3 consecutive denials, or 10 denials among the last 50 reviews of that turn, interrupt the turn once; for cyber-specialty models the limits are 1 and 1.

#### Linux: bubblewrap for the filesystem view, seccomp for sockets, two-stage helper

#### Seccomp filter per mode: what "network off" really blocks

### 3.7 Hooks and trust

#### What is hashed for hook trust
- What the code does: each hook's trust identity is a version hash of a normalised TOML value of `{event, matcher, the single handler config}` (so a hook in `hooks.json` and the same hook in `config.toml` share trust). For plugin hooks, a SHA-256 over the plugin directory tree (names, types, sizes, bytes; skipping `__pycache__`, `.venv`, `*.pyc`, `*.egg-info`; any other entry type fails) is appended. Trust is stored as `hooks.state."<key>".trusted_hash` (and `trusted_content_hash`) in the user config; a mismatch is `Modified`, a missing record is `Untrusted`, and only `Managed`/`Trusted` hooks are registered. Plugin contents are re-hashed before each execution.

### 3.8 App-server listener authentication
