## 2. Architecture as it bears on this scope

**The agent loop is not in this repository. The client is a tool executor plus UI plus policy gate.** Every model turn is one HTTP request from the client to Warp's server (`POST {server}/ai/multi-agent`, protobuf, answered as an SSE stream of base64 protobuf `ResponseEvent`s). The server holds the system prompt, the model call, the tool-call decisions, model routing and summarisation. The wire schema is a separate repo, `warpdotdev/warp-proto-apis`, pinned by git rev. The client then executes the returned tool calls locally (in the user's terminal PTY, local file APIs, local MCP servers), applies its permission policy, collects results and sends the next request. So "what the client decides locally" is: whether a tool call may run without asking (permissions), how it runs, secret redaction of what it sends, which tools it advertises, and orchestration plumbing.

## 3. Findings

### 3.1 Where the loop runs

#### The agent loop and model call are server-side; the client advertises tools and executes them
- What the code does: the client builds one `Request` containing task context, input, model ids, a long list of capability flags and the `supported_tools` list, and streams the response. A tool call arrives as a `ResponseEvent`; the client turns it into an `AIAgentActionType`, runs it, then sends the result as the next request's input. Which tools exist for a session is decided client-side from session type (local, remote SSH host, none) and feature flags. The prompt, tool descriptions and model calls are not in the repo.
- Trace: (1) request built with `supported_tools`: https://github.com/warpdotdev/warp/blob/4b790f5fac9a2cc637c865aacbfa4f2cf64f6c39/app/src/ai/agent/api/impl.rs#L65-L121; (2) tool set by session type: https://github.com/warpdotdev/warp/blob/4b790f5fac9a2cc637c865aacbfa4f2cf64f6c39/app/src/ai/agent/api/impl.rs#L225-L303; (3) stream opened and cancellable with `take_until(cancellation_rx)`: https://github.com/warpdotdev/warp/blob/4b790f5fac9a2cc637c865aacbfa4f2cf64f6c39/app/src/ai/agent/api/impl.rs#L152-L168; (4) results drained into the next request: https://github.com/warpdotdev/warp/blob/4b790f5fac9a2cc637c865aacbfa4f2cf64f6c39/app/src/ai/blocklist/controller.rs#L2154-L2200 and follow-up trigger https://github.com/warpdotdev/warp/blob/4b790f5fac9a2cc637c865aacbfa4f2cf64f6c39/app/src/ai/blocklist/controller.rs#L1642-L1673.
- Edge cases and failure handling: `ContextWindowExceeded` is surfaced as an error, not handled by client-side compaction https://github.com/warpdotdev/warp/blob/4b790f5fac9a2cc637c865aacbfa4f2cf64f6c39/app/src/ai/blocklist/controller.rs#L4108-L4120. I found no client-side maximum of turns or tool calls (searched `controller.rs`, `action_model.rs`, `conversation.rs`, `agent_sdk/driver.rs` for max turns, iterations, steps, tool-call limits). Retry is covered in the next entry.
- Round 1: `new (not documented)`. Round 1 could not say where the loop runs. It runs on Warp's server; every local-agent model call is proxied through it (see 3.6).
- For rizzy-harness: the opposite split. Warp's client trusts a remote brain; ours has the brain on the node. Copy only the idea that tool availability is a function of session type and is advertised to the model each turn.
- Confidence: traced end to end for the client side; server behaviour not in this repository. (checked in review)

#### Retry budget per request
- What the code does: one counter of recovery attempts (retries and resumes) per request, `MAX_RECOVERY_ATTEMPTS = 3`; each tool-result round trip starts a fresh budget. Auto-resume waits for backoff, for the network to be online, and for a modal to close.

#### Allow and deny lists: anchored regex over decomposed sub-commands
- What the code does: entries are regexes wrapped in `^...$` and matched against each sub-command. The command string is first normalised (backslash-newline or backtick-newline joined), then `decompose_command` yields the sub-commands including those inside `$( )` and `( )`, concatenations, and each recomposed level; leading `KEY=VAL` env assignments are stripped before the denylist test. Redirection (`>`/`<`) is reported as a flag. The default denylist is wider than Round 1 said: `bash`, `fish`, `pwsh`, `sh`, `zsh`, `curl`, `eval`, `exec`, `source`, `wget`, `dig`, `nslookup`, `host`, `ssh`, `scp`, `rsync`, `telnet`, `rm`; the CLI default allowlist is `cat`, `echo`, `find .*`, `grep`, `ls`, `which .*`.

#### The model supplies `is_read_only` and `is_risky`, and the client trusts them
- What the code does: for `RunShellCommand` the tool call carries `is_read_only` and `is_risky` booleans produced by the server-side model. With `execute_commands = AgentDecides`: after the denylist, if the `AgentDecidesCommandExecution` flag is on and `is_risky == Some(false)`, the command is allowed, skipping both the redirection check and the allowlist; otherwise a redirection denies, an allowlist match allows, and finally `is_read_only` (model supplied) allows. The flag is in the app crate's default feature set, so it is on in normal builds.

#### "Run until completion" and the denylist: exact conditions

Then only the organisation denylist is evaluated, the user and default denylist entries are skipped, and every other command returns `Allowed(RunToCompletion)`. Round 1's description is right but incomplete: the same override also auto-allows file reads and writes (except MCP config paths), all MCP calls and writes to a running command's PTY, and it suppresses ask-user questions unless that setting is "always ask".

#### `--sandboxed` is a self-declared flag, not a mechanism
- What the code does: `is_sandboxed` comes from a hidden CLI flag `--sandboxed` (or the cloud-standby command). When true the client builds the CLI default profile with an empty denylist, skips the user denylist, and allows reads and writes (including MCP config writes). It does not drop every denylist: `team_autonomy_settings` swaps in the organisation's separate "sandboxed agent" denylist (`sandboxed_agent_execute_commands_denylist_for_scope`, permissions.rs L233-L243), which is still evaluated (and is the only list left when run-to-completion is on). If the organisation configures none, nothing is denylisted. The client does not create any OS sandbox itself; the protection is whatever environment the run was launched in.

## 5. In the code but not in the documentation

- The model's `is_risky` and `is_read_only` flags decide auto-execution (3.2).
- `--sandboxed` is a hidden self-declaration that empties the denylist (3.2).
- ACP policy auto-approves everything but denylisted commands and protected writes; `read_text_file` is unchecked (3.3).
- Claude and Codex children run with their permission systems disabled and trust pre-seeded (3.3).
- Local Docker sandbox via `sbx` behind a dogfood flag (3.2).
- Autonomous runs return `Denylisted` for any denial (3.2).
- The PTY-plus-socket bridge for ACP agents (3.3).
- Handoff derives files from the last 500 tool calls' writes (3.5).
- MCP tool lists are all sent each turn (3.7).
