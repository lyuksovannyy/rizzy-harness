## 2. Architecture as it bears on this cluster

- Language and shape: one Rust workspace (`codex-rs/Cargo.toml`), roughly 120 crates. The agent loop lives in `core` (`core/src/session/turn.rs`, 3,843 lines). Tools are `ToolExecutor` implementations registered per step in a `ToolRegistry`. Compaction, AGENTS.md loading and sub-agent control are modules of `core`. Memories are split across `memories/{read,write}` and `ext/memories`. The patch engine is its own crate, `apply-patch`.
- Process model relevant here: a `Session` (one per thread) owns history (`ContextManager`) and an `input_queue`; `run_turn` is a `loop` of "drain pending input, capture a `StepContext`, record world-state diff, sample, run tools, decide follow-up" (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L543-L554`). A sub-agent is another `Session` (thread) in the same process, owned by `AgentControl` (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/agent/control/spawn.rs#L740-L775`).
- Model-visible context has two layers. (1) `Prompt.base_instructions`, sent as the Responses `instructions` field, taken from the model catalog (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/turn.rs#L1841-L1875`). (2) A set of typed "world state" sections (permissions, collaboration mode, AGENTS.md, environment, multi-agent, memory, plugins and so on), each rendered into history as developer or user messages, with a persisted snapshot per section so that later steps emit only a diff (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/world_state.rs#L75-L90`, `https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/context/world_state/mod.rs#L340-L349`, `https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/session/mod.rs#L4180-L4207`).
- Per-model behaviour is data, not code: `ModelInfo` (from `models-manager/models.json`, refreshable from a backend, 300 s cache TTL) carries `apply_patch_tool_type`, `shell_type`, `tool_mode`, `multi_agent_version`, `truncation_policy`, `context_window`, `auto_compact_token_limit`, `instructions_template` (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/models-manager/models.json#L4-L36`, `https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/models-manager/src/manager.rs#L42-L42`).

### 3.2 Edit tool: `apply_patch`

#### A freeform, grammar-constrained tool, with a lenient hand-written parser behind it
- What the code does: on models that set `apply_patch_tool_type`, `apply_patch` is a Responses "custom"/freeform tool whose input is constrained by a Lark grammar shipped in the tool spec. The grammar: `*** Begin Patch`, then hunks `*** Add File: p` (lines prefixed `+`), `*** Delete File: p`, `*** Update File: p` with optional `*** Move to:` and chunks introduced by `@@` or `@@ <context line>`, lines prefixed space/`+`/`-`, optional `*** End of File`, then `*** End Patch`. The parser is more lenient than the grammar: it trims whitespace around markers and, for gpt-4.1 compatibility, strips a `<<'EOF' ... EOF` heredoc wrapper (strict mode is hard-coded off).
- Trace:
  1. Spec: `create_apply_patch_freeform_tool` with description "This is a FREEFORM tool, so do not wrap the patch in JSON" (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/handlers/apply_patch_spec.rs#L9-L28`); grammar (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/assets/tools/apply_patch.lark#L1-L19`); multi-environment adds an `*** Environment ID:` line (`https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/core/src/tools/handlers/apply_patch_spec.rs#L10-L14`).

#### Matching is line-based, four tiers of tolerance, first match after a cursor wins
- What the code does: for each `@@` chunk the engine (1) finds the optional context line with `seek_sequence`, advancing a cursor past it, then (2) finds the chunk's old lines (context + `-` lines) starting at the cursor. `seek_sequence` tries exact, then trailing-whitespace-insensitive, then trim-both-sides, then a final pass that also folds Unicode dashes, curly quotes and exotic spaces to ASCII. If the old lines end with an empty line and no match is found, it retries without that last line (and drops the matching trailing empty line from the new side). `*** End of File` makes the search start at the end of the file first. There is no uniqueness requirement: each tier scans from the cursor and the first match at or after the cursor is used (tiers are tried in order, so an exact match later in the file beats an earlier fuzzy one), and chunks must appear in file order.

#### Verify all hunks first, then apply one by one; not atomic, no staleness check
- What the code does: the handler first runs `verify_apply_patch_args`, which reads every target file and computes every update's new content and unified diff in memory; any parse or match failure returns `apply_patch verification failed: <error>` to the model with nothing written. ### 3.3 Compaction

#### Triggers: pre-turn, mid-turn, post-turn, plus model-change; default threshold is 90% of the window
- What the code does: after each sampling step the loop computes `ContextWindowTokenStatus`. `token_limit_reached` is true when the auto-compact scope usage reaches the buffered limit or the full window (window x `effective_context_window_percent`, serde default 95, `https://github.com/openai/codex/blob/82e6bacb9c6950d3b56cb153847fa80bdd698053/codex-rs/protocol/src/openai_models.rs#L413-L415`) is reached. The default auto-compact limit is 90% of the context window, or the smaller of that and `model_auto_compact_token_limit`. Scope `total` counts all active tokens; scope `body_after_prefix` counts active tokens minus the window's prefill baseline (`window.prefill_input_tokens`), i.e. what was added after the injected prefix. Pre-turn: compaction runs before the new user input is recorded. Mid-turn: when the model needs a follow-up (tool calls pending) and the limit is hit. Post-turn: only when `model_post_turn_compact_threshold_percent` > 0 (default 0 = off) and usage is at or above that percent of the usable window.
