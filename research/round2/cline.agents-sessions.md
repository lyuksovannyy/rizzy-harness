## 2. Architecture as it bears on this cluster

- **Layers**: `@cline/shared` (types, prompt builder, hub protocol types), `@cline/llms` (providers), `@cline/agents` (one stateless loop class, `AgentRuntime`), `@cline/core` (sessions, tools, compaction, checkpoints, hub, MCP, plugins, SSH remote), then apps. The architecture note says the same (`sdk/ARCHITECTURE.md`).
- **The loop** is `AgentRuntime.execute`: a `while` over turns, one model call per turn, tool calls then prepared (hooks, policy, approval) and executed, ending when a turn has no tool call or a completion tool succeeded (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L849-L1040). `SessionRuntime` in `core` wraps it with conversation state, hooks, mistake tracking and loop detection.
- **Runtime hosts** (`RuntimeHost`): `LocalRuntimeHost` runs the loop in the calling process; `HubRuntimeHost` talks to a hub daemon over WebSocket; `RemoteRuntimeHost` is a `HubRuntimeHost` pointed at a user-supplied endpoint with a token. `createRuntimeHost` picks one by `backendMode` (`local|hub|remote|auto`, `auto` prefers a discovered local hub and falls back to local) (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/runtime/host/host.ts#L137-L260).
- **The hub** is one WebSocket + HTTP server per user and owner context, hosting a `LocalRuntimeHost` in its own process (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hub/server/hub-server-transport.ts#L334-L343). There is no separate "spoke" process in the code (see finding "The hub runs the loop in-process").
- **Storage**: per-session directory of JSON files plus a SQLite index (`sessions.db`), a separate SQLite event log for the hub, and a git-ref based checkpoint store inside the user's own repository.
- **Per-surface wiring**: the CLI turns on checkpoints, compaction, loop detection, auto-approve and a mistake limit of 3 itself (`apps/cli/src/runtime/defaults.ts`, `main.ts`); the SDK core leaves most of them off unless the host enables them. The VS Code extension builds its own session config (`cline-session-factory.ts`) and turns spawn_agent off.

## 3. Findings

### Agents: system prompt and tool definitions

#### There is no per-model-family system prompt; two templates, filled by string replacement
- What the code does: `buildClineSystemPrompt` picks one of two constant templates (`ACT` for plan and act modes, `YOLO` for yolo) and replaces `{{PLATFORM_NAME}}`, `{{CWD}}`, `{{CURRENT_DATE}}`, `{{IDE_NAME}}`, `{{CLINE_RULES}}` and `{{CLINE_METADATA}}`. Plan mode is the ACT template plus a plan-mode block appended to the rules slot. A caller-supplied `overridePrompt` replaces the whole template. Nothing branches on model or provider except the workspace-metadata slot.
- Trace: builder and mode switch (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/prompt/cline.ts#L152-L213); the two templates (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/prompt/system/act.ts#L1-L36), (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/prompt/system/yolo.ts#L1-L40); the registry (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/prompt/system/index.ts#L1-L9); core fallback (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/services/local-runtime-bootstrap.ts#L167-L186); CLI (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/runtime/prompt.ts#L14-L38); VS Code (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/vscode/src/sdk/cline-session-factory.ts#L1034-L1077).
- Edge cases and failure handling: the git remote, branch and commit block (`{{CLINE_METADATA}}`) is filled only when `isClineProvider(providerId)` is true, so it goes to Cline's own gateway for observability and never to other providers (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/prompt/cline.ts#L205-L209); remote URLs have credentials stripped first (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/prompt/cline.ts#L55-L77). If building the prompt throws, VS Code falls back to a one-line prompt. Sub-agents on non-Cline providers get the model-written prompt verbatim, with no environment block (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/team/subagent-prompts.ts#L23-L38).
- Round 1: `not in code`. Round 1 did not claim per-model prompts, but the task brief expected "per model family"; the old extension had them, the SDK does not. The per-model difference is in the tool set (next finding), not the prompt.
- For rizzy-harness: a single template with a small number of slots is easy to reason about and keeps the cache prefix stable; keep per-model differences in the tool list, as Cline now does.
- Confidence: `traced end to end`.

#### Mode is carried twice: appended plan block in the system prompt, and a tag on every user message

YOLO omits all of it.

- Round 1: `confirmed`. Round 1: plan mode removes edit tools; the code adds the per-message tag, which Round 1 did not describe.
- For rizzy-harness: tagging each user message with its mode survives resume and compaction better than relying on the system prompt alone. Worth copying.
- Confidence: `read the definition`.

#### The tool set is chosen by mode preset and a model-family routing table
- What the code does: each mode has a preset of enabled tools (act: read, search, bash, web fetch, editor, skills, ask, spawn, teams; plan: the same minus the editor, bash stays; yolo: read, bash, editor, `submit_and_exit`, no spawn). A routing table then flips tools per model: in act mode, provider `openai-native` or any model id containing `codex` or `gpt` swaps `editor` for `apply_patch`. Plan mode never gets either edit tool. Callers can pass their own rules.
- Trace: presets (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/presets.ts#L25-L37), (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/presets.ts#L45-L57), (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/presets.ts#L98-L110); routing rules and resolver (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/model-tool-routing.ts#L60-L75), (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/model-tool-routing.ts#L105-L134); applied at (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/runtime/orchestration/runtime-builder.ts#L158-L163).
- Edge cases and failure handling: matching is case-insensitive substring on the model id, so any model whose id merely contains "gpt" gets `apply_patch`. Mode switches rebuild the runtime and its tool list.
- Round 1: `confirmed` (the `editor` vs `apply_patch` routing and "plan mode offers neither").
- For rizzy-harness: per-model edit formats are worth having because models are trained on one; but match on a model-family field, not a substring of the id.
- Confidence: `traced end to end`.

#### Tool inputs are accepted leniently, validated inside each tool, after approval
- What the code does: the runtime only normalises JSON-like strings against the schema before the policy check; real validation (`validateWithZod`) happens inside each tool's `execute`. Input schemas are broad unions on purpose: `read_files` accepts about a dozen shapes (a string, an array of strings, `file_path` and `filePath` aliases, `paths`, `file_paths`), `run_commands` accepts strings, argv objects and arrays of both. Argument text that does not parse becomes `inputParseError` and the call is skipped with that message. `editor` caps `old_text` and `new_text` guidance at 6,000 characters in the schema text.
- Trace: pre-policy normalisation and parse-error skip (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2432-L2467); unions (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/schemas.ts#L19-L106), (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/schemas.ts#L149-L176); per-tool validation (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/definitions.ts#L731-L733).
- Edge cases and failure handling: an invalid input is therefore shown to the user in an approval prompt before it is rejected; a malformed call costs an approval click.
- Round 1: `not in code` (Round 1 has no claim here).
- For rizzy-harness: validate against the schema before asking for approval, and be tolerant on shape only where you have seen real models fail (Cline's unions come from field reports).
- Confidence: `traced end to end`.

### Agents: edit tools

#### `editor` is exact, unique, whole-string replacement with no staleness check
- What the code does: `editor` has three modes chosen by input. `insert_line` inserts before a one-based line. Otherwise, a missing file is created from `new_text`; an existing file needs `old_text`. The replace reads the file, counts occurrences of `old_text` (after converting its line endings to the file's), fails on zero or more than one, and writes `String.replace` with a replacer function so `$` sequences stay literal. The result returned to the model is a prefix and suffix trimmed diff, capped at 200 lines.
- Trace: replace path (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/editor.ts#L162-L192); executor and create/insert branching (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/editor.ts#L221-L267); insert (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/editor.ts#L194-L216); schema text (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/schemas.ts#L198-L233).
- Edge cases and failure handling: no whitespace fuzz, no similarity matching and no "read before write" or modification-time check; a stale `old_text` simply fails as "text not found". A null `old_text` on an existing file produces an explicit "do not re-send unchanged" error aimed at models that fill optional fields with null. `restrictToCwd` applies only to relative paths: an absolute path anywhere on disk is accepted (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/editor.ts#L42-L65). There are no post-edit diagnostics or formatter (a search of the tools directory found none). Failures return as tool errors and count toward the consecutive-mistake limit only when every tool in the turn failed.
- Round 1: `new (not documented)`. Round 1's edit-format rows are `-` (undocumented).
- For rizzy-harness: this is the simplest correct design, and its failure mode (stale text fails loudly) is fine. The absolute-path escape is the part to not copy: bind edits to the node's allowed roots, as the node-decides invariant requires.
- Confidence: `traced end to end`. (checked in review)

#### `apply_patch` has a four-step fuzz ladder, but rejects the whole patch if any hunk fails to anchor
- What the code does: it parses the Codex-style grammar (`*** Begin Patch`, `*** Update File:`, `@@`, move, add, delete) and tolerates shell wrappers (`%%bash`, `apply_patch`, `EOF`, a code fence). For each hunk it looks for the context lines in the file by trying, in order: exact; trailing-whitespace-insensitive (fuzz 1); fully trimmed (fuzz 100); then a similarity score of at least 0.66 (fuzz 1000). Text is first canonicalised (Unicode NFC, smart quotes and dashes to ASCII, non-breaking spaces to spaces, escaped quotes). A hunk anchored at end-of-file gets an extra 10,000 fuzz penalty if it cannot match at the end.
- Trace: canonicaliser (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/apply-patch-parser.ts#L58-L82); ladder (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/apply-patch-parser.ts#L347-L430); unmatched hunk becomes a warning (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/apply-patch-parser.ts#L236-L250); any warning aborts before writing (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/apply-patch.ts#L374-L396); the success message reports the fuzz (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/apply-patch.ts#L399-L426).
- Edge cases and failure handling: the whole patch is computed in memory and rejected if any hunk failed, with a per-hunk message and the first 200 characters of context. The write phase then applies files one by one and is not transactional: a failure midway leaves earlier files written (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/tools/executors/apply-patch.ts#L316-L372). Same cwd restriction as `editor`. CRLF files keep their line endings.
- Round 1: `confirmed` for the model routing; the fuzz ladder is `new (not documented)`.
- For rizzy-harness: the "reject the whole patch before writing, report which hunk" rule is the right failure mode. Similarity matching at 0.66 will apply a patch to the wrong place on repetitive code; tell the model when fuzz was used (Cline does, in the result text) or disable the last rung.
- Confidence: `read the definition`. (checked in review)

#### The VS Code diff view is a cosmetic preview opened at approval time
- What the code does: the extension wraps the SDK editor and patch executors. It opens a read-only diff of two virtual documents when the approval prompt appears (the SDK exposes full tool input only after the stream ends, so there is no streaming diff), then delegates the real write to the SDK's disk executor. Auto-approved edits show the preview for 1.5 s. Opening the preview has a 5 s timeout, after which the edit proceeds without it.
- Trace: design comment (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/vscode/src/sdk/sdk-diff-edit-coordinator.ts#L59-L77); constants (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/vscode/src/sdk/sdk-diff-edit-coordinator.ts#L18-L30).
- Edge cases and failure handling: a wedged workbench cannot block the loop. The file the user rejected is never touched, because the preview never opened the real file.
- Round 1: `new (not documented)`. Round 1 had "the diff view" only as a UI feature.
- For rizzy-harness: previews must be best-effort and bounded in time; do not let a UI stall hold a tool call.
- Confidence: `read the definition`. (checked in review)

### Agents: loop control

#### One step per iteration; no default iteration cap; approvals are serial and happen before any tool runs
- What the code does: `execute` loops `while (maxIterations === undefined || iteration < maxIterations)`. Neither the core nor the CLI sets a default and VS Code passes `maxIterations: undefined` (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/vscode/src/sdk/cline-session-factory.ts#L1175-L1175), so an unconfigured run is unbounded; the only stops are abort, the mistake limit, loop detection, an error or a turn with no tool call. After the model turn, **all** tool calls are prepared first (hooks, policy, approval, one after another), and only then executed: adjacent `parallel` tools in a `Promise.all` group, `sequential` tools one at a time. A tool absent from the registry returns "Unknown tool". Approval is requested only when the resolved policy has `autoApprove === false`; **no policy at all means run without asking**.
- Trace: loop condition and end (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L849-L853), (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L1037-L1040); scheduling (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2370-L2408); hooks, policy and approval (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2432-L2532); execution and error capture (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2574-L2660); the policy merge (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L216-L233).
- Edge cases and failure handling: no approval callback configured means the tool is rejected, not run; a callback that throws is a rejection (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/agents/src/agent-runtime.ts#L2534-L2572). `beforeTool` hooks run before the policy and can skip, rewrite input, force approval, append context or stop the run. The tool-declared `timeoutMs`, `retryable` and `maxRetries` fields (defaults 30 s, true, 3 in `createTool`) have no consumer in the runtime; timeouts exist only where an executor wraps itself in `withTimeout` (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/shared/src/tools/create.ts#L120-L145). The CLI defaults `autoApprove` to true (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/apps/cli/src/main.ts#L884-L895).
- Round 1: `confirmed` for "CLI auto-approve default is ON"; `new (not documented)` for "no policy means no approval" and the unused tool timeout fields.
- For rizzy-harness: make the default deny, not allow; an absent policy must not mean auto-approve. Keep the step cap.
- Confidence: `traced end to end`. (checked in review)

#### Provider errors, output-limit cut-offs and context overflow have three separate bounded recoveries

### Agents: compaction

#### Compaction is opt-in in the core, on by default in the CLI, triggers at 90% of an estimated budget, and self-corrects its estimator
- What the code does: the compaction hook runs before each model request. It estimates the request tokens (about 3 characters per token plus image costs), derives the model's input limit from model info, and compacts when the estimate reaches 90% of that limit. When the model reports only a context window and no `maxInputTokens`, the limit is itself 0.9 of the window, so the effective trigger is about 81% of the window ([compaction-shared.ts L65-L82](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/extensions/context/compaction-shared.ts#L65-L82)). If the provider's real count for the previous request exceeded the estimate, the budget is scaled down by that ratio, capped at 4x. When the model's limit is unknown, automatic compaction does not run (an unknown limit is not evidence the request is full); manual compaction and overflow recovery fall back to a 128,000-token budget. The target after compaction is 70% of the trigger, or 50% of the input limit for conversations of 5 or more user and assistant pairs on models whose output cap is below their input limit.

### Sessions: checkpoints

#### Checkpoints are `git stash create` commits in the user's own repository, kept alive by private refs; there is no shadow repository
- What the code does: at the first model call of a user's run, the checkpoint hook builds a stash-shaped commit with `git stash create`; if there are untracked, non-ignored files it adds them as a **third parent** built with a private index file (`GIT_INDEX_FILE`) and `commit-tree`. The commit is kept reachable under `refs/cline/checkpoints/<sessionId>/<runCount>`, which does not show in `git stash list`. The private index lives under `~/.cline/data/checkpoint-scratch/<hash of cwd and session>` (mode 0700), persists across turns so git's stat cache skips unchanged files, and is reaped after 14 days idle. A clean tree with no untracked files records `HEAD` as a `commit`-kind checkpoint.
- Trace: hook (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hooks/checkpoint-hooks.ts#L535-L649); stash with untracked parent (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hooks/checkpoint-hooks.ts#L349-L429); untracked tree and index maintenance (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hooks/checkpoint-hooks.ts#L249-L338); pinned git config for the private index (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hooks/checkpoint-hooks.ts#L169-L184); scratch dir and reaper (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hooks/checkpoint-hooks.ts#L19-L78); a search for "shadow" in the SDK and apps found only unrelated hits.
- Edge cases and failure handling: **non-git folders get no checkpoint from the built-in snapshotter** (the probe `rev-parse --is-inside-work-tree` fails and the hook returns nothing; a host-supplied `createCheckpoint` callback, which hub clients can contribute, bypasses that probe: [checkpoint-hooks.ts L538-L544](https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hooks/checkpoint-hooks.ts#L538-L544)), contrary to the Round 1 comparison table's "working on non-git folders". Our latest-10 cap is better than nothing here: Cline's refs are removed only when the session is deleted (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/session/services/persistence-service.ts#L600-L626).

#### Restore is a transaction with a snapshot of the current tree, a HEAD guard and a compare-and-swap
- What the code does: before restoring, it stashes the **current** worktree including untracked files, moves that object behind `refs/cline/restore-transactions/<uuid>`, and drops it from the visible stash list; the ref is deleted only on commit. Restore then refuses if `HEAD` is not the commit the checkpoint was taken on (commits were added, or the branch changed), to avoid silently moving the branch pointer. It moves `HEAD` to the base with `git update-ref HEAD <new> <old>` (a compare-and-swap), runs `git reset --hard`, then `git clean -fd` **only** for checkpoints that captured untracked files (third parent), then `git stash apply <checkpoint>`. Checkpoints without the third parent leave untracked files alone, because they could not be rebuilt.
- Trace: transaction (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/session/checkpoint-restore.ts#L50-L154); apply with guards (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/session/checkpoint-restore.ts#L376-L478); orchestration, rollback and cleanup of the started session (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/session/session-versioning-service.ts#L278-L375).
- Edge cases and failure handling: if both the capture and its rollback fail, it throws an `AggregateError` ("Workspace snapshot and rollback both failed"). #### SSH remote uploads the CLI binary, starts a loopback hub on the host and tunnels to it
- What the code does: `RemoteEnvironmentService.connect` (1) inspects the host with `ssh ... sh -c 'uname -s; uname -m; $HOME'`; (2) picks the local CLI binary for that platform and architecture (no network installer, by design) and uploads it by `ssh ... 'umask 077; cat > <tmp>'` into `~/.cline/remote/cline-<os>-<arch>-<hash16>` after `chmod 700`, skipping the upload if the hash-named file exists; (3) runs `cline hub ensure --json --host 127.0.0.1 --port 0 --no-connectors ...` remotely with a discovery file under `~/.cline/data/remote/`; (4) reads the hub's port, path and **auth token** from that command's stdout; (5) reserves a random local port and starts `ssh -N -L 127.0.0.1:<local>:127.0.0.1:<remote>`; (6) waits for the tunnel and returns a `ws://127.0.0.1:<local>/hub` endpoint plus the token to the client.
- Trace: constants (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L177-L183); connect (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L325-L400); helper (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L530-L600); remote command (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L1018-L1054); result parsing, loopback-only check (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L1436-L1490).
- Edge cases and failure handling: SSH options are `BatchMode=yes`, `StrictHostKeyChecking=yes`, `ConnectTimeout=30`, and an optional pinned `UserKnownHostsFile`; the tunnel adds `ServerAliveInterval=15` and `ServerAliveCountMax=3`, which is the "about 45 s of network loss" in the docs (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L713-L757). The 40 s `DEFAULT_TUNNEL_TIMEOUT_MS` is the startup wait, a different thing. A failed connect runs a remote `hub stop`; if that also fails, a cleanup record is persisted (mode 0600) and retried on the next connect (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L399-L430), (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/remote/remote-environments.ts#L821-L840). The remote hub must report a loopback URL or the connect fails. The local port is picked by binding and releasing, so another local process could take it before `ssh -L` binds (`ExitOnForwardFailure` is not set; the code says `waitForTunnel` verifies the forward).
- Round 1: `confirmed` for key-based non-interactive login, strict host-key checking, a helper under `~/.cline/remote/`, a loopback hub reached by `ssh -L` to a random local port, the 45 s figure, and ProxyJump via the user's ssh config. The helper is the full CLI binary (the "~30 MB" is the Round 1 reviewer's figure; the code has no size). "Provider key is sent over the tunnel per session and not written to host settings": the session config carries `apiKey` in `session.create` (https://github.com/cline/cline/blob/500a40e7b76692153906b44dd68732520a966663/sdk/packages/core/src/hub/server/handlers/session-handlers.ts#L497-L520); I did not trace whether it can reach the remote's on-disk manifest (the manifest stores `metadata`, not the config), so this is `confirmed in part`.
- For rizzy-harness: the hash-addressed, 0700-directory, 0077-umask upload and the explicit "no network installer" rule are good. Note that the hub token is returned on SSH stdout and then used over a loopback tunnel; any user on the remote host who can read the 0600 discovery file or connect from loopback with a local Origin gets the same powers. Our node-dials-master design avoids opening a listener on the worker at all.

#### The core/host split in the standalone build is gRPC on loopback; the host bridge has a per-spawn token, the core's own server has none
- What the code does: for JetBrains and the CLI-hosted build, the extension code runs as a standalone "core" process. ## 5. In the code but not in the documentation

- A **four-rung fuzzy match** for `apply_patch` (exact, trailing whitespace, trim, 0.66 similarity), with the fuzz reported to the model, and all-or-nothing rejection if any hunk cannot anchor.
- **Estimator self-correction** for compaction: the provider's real input token count of the previous request scales the budget down (up to 4x), and automatic compaction is skipped entirely when the model's limit is unknown.
- A **deterministic compaction fallback** that is the only strategy allowed after a context-overflow error, and a custom compactor that must return something strictly smaller or lose to it.
- **Stale-read rewriting and a tool-result cache** (`cline://cache/...` URIs, 16 MiB, 5-iteration idle eviction, 8,000-character cap per result) in the message builder.
- A **repeated-call detector** (3 soft, 5 hard) that is on by default despite comments saying it is off.
- **Checkpoint restore transaction**: snapshot of the present tree behind a private ref, `HEAD` guard, compare-and-swap `update-ref`, and the rule that untracked files are only cleaned when the checkpoint recorded them.
- **Tool executors contributed by clients** over the hub (`tool_executor.bash` and friends): the loop can run in the hub while the shell runs in the IDE or CLI process.
- A **hub auth token and two trust tiers** (token versus Origin-only), and an `approval.respond` that is not bound to a responder.
- A **hub event log** with global sequence numbers, 7-day retention and replay on reconnect.
- **Cross-tool session import** (Claude Code, Codex, OpenCode) with a one-time summary at resume.
- **Named sub-agents** loaded from `.cline/agents/*.md` as `subagent_<name>` tools, each with its own optional provider and model.
- A **spawn-secret scrub** (`CLINE_CORE_CONNECTION_TOKEN` deleted from `process.env` before any child process starts) in the standalone core.
- The system prompt's **workspace metadata is sent only to Cline's own provider**.
