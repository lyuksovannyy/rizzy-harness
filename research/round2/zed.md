## 2. Architecture as it bears on this scope

- Language and process model: Rust, one GUI process (GPUI). The Zed Agent runs **inside the editor process** as a GPUI entity (`Thread`), not a separate server. External ACP agents are child processes over stdio JSON-RPC, spawned by the editor (or over an SSH remote). Everything is one process boundary plus the ACP wire.
- Crates: `agent` (the native agent: thread, loop, tools, permission decisions), `acp_thread` (the UI-facing thread model that both the native agent and external agents feed, plus `read_text_file`, `write_text_file`, terminals and `rewind`), `agent_servers` (the ACP client: v1 and v2 connections), `project::agent_server_store` and `agent_registry_store` (finding and installing external agents), `sandbox` (Seatbelt, Bubblewrap, WSL wrappers) with `http_proxy` (host allowlist proxy), `action_log` (per-thread tracking of agent edits for review), `shell_command_parser` (brush-parser based command splitting), `agent_settings` (settings types, compaction prompt).
- The agent loop is `Thread::run_turn` and a per-request loop that calls compaction first, then the model, then tools. Compaction is checked before **every** model request: [thread.rs L2959-L2990](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/agent/src/thread.rs#L2959-L2990) (loop head, cancel check, then `perform_compaction_if_needed`).
- Both the native agent and external agents surface into `AcpThread`; the native agent is wired through `AgentConnection` like any ACP agent: [connection.rs trait with `truncate`](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/acp_thread/src/connection.rs#L296-L302) (default `None`, so only the native agent supports rewind).
- Feature flags matter for what is on: `SandboxingFeatureFlag` is `enabled_for_all = true`, `AcpBetaFeatureFlag` has no such override: [flags.rs L22-L28](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/feature_flags/src/flags.rs#L22-L28) and [flags.rs L107-L121](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/feature_flags/src/flags.rs#L107-L121).

#### The surviving checkpoint recipe shows the likely cost shape
- What the code does: `create_archive_checkpoint` runs `git rev-parse HEAD`, `git write-tree` on the real index (staged state), `commit-tree` with message "WIP staged", then in a **temporary copy of the index** runs `git add --all`, `write-tree`, and `commit-tree` ("WIP unstaged") parented on the staged commit. No branch ref moves; author is fixed to `Zed <hi@zed.dev>`. Restore is `git read-tree --reset -u <unstaged>` then `git read-tree <staged>`. The temp index is a copy of the current index "so Git doesn't have to rebuild the whole index".
- Trace:
  1. [repository.rs L3085-L3135](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/git/src/repository.rs#L3085-L3135): the create sequence (`write-tree`, `commit-tree`, `with_temp_index`, `add --all`).
  2. [repository.rs L3138-L3165](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/git/src/repository.rs#L3138-L3165): restore via `read-tree --reset -u` then index-only `read-tree`.
  3. [repository.rs L3715-L3745](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/git/src/repository.rs#L3715-L3745): `with_temp_index` copies `.git/index` to a UUID-named file and deletes it afterwards.
  4. The commits are anchored by a ref so they are not garbage collected: [thread_worktree_archive.rs L590-L600](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/agent_ui/src/thread_worktree_archive.rs#L590-L600) (`update_ref`).
- Edge cases and failure handling: `git add --all` has to stat every tracked file and walk untracked directories on each call, so cost scales with repository size and not with what changed. That is the likely reason a per-message version hung in large repositories (inference; no profile or comment in this tree says so). Restore requires HEAD to already be at the original commit (documented at L1079-L1082). Failures bubble as `Result` context strings; there is no timeout around the git calls in this function.
- Round 1: `new (not documented)`.
- For rizzy-harness: if you keep a shadow repo, do not `add --all` per turn. Use the agent's own edit tracking (paths the tools wrote) to build the tree, or cap by a changed-file count or time budget and fall back to per-file undo. The temp-index trick (never touch the user's index) is worth copying.
- Confidence: `read the definition`. (checked in review)

#### What replaces checkpoints: an in-memory action log with per-buffer baselines, and `rewind` that rejects everything unreviewed
- What the code does: `ActionLog` keeps, per buffer the agent has read, edited or created, a `diff_base` rope (the text when the agent first touched it) plus a patch of `unreviewed_edits`. Accept ("keep") folds edits into the base; reject writes base text back into the buffer and saves. User edits made later are also tracked and folded in. Rewinding a thread (editing an earlier message and resubmitting) truncates the model messages, kills the terminals that those entries created, then calls `reject_all_edits` on the **whole** log, not only on the edits after that message.

### 3.2 Tool permissions

#### Rule evaluation and precedence
- What the code does: `ToolPermissionDecision::from_input` is the single decision function. Order: (1) hardcoded security denies (terminal only); (2) if any regex in the tool's rules failed to compile, deny the whole tool; (3) for the terminal tool, parse-validate the command and deny if it contains substitutions or cannot be parsed, unless the tool is effectively "allow everything"; (4) per-tool rules: any `always_deny` match denies, any `always_confirm` match confirms, `always_allow` allows only if every sub-command matches an allow pattern, then the tool `default`, then the global `default`. The global default is `confirm` in shipped settings. Regexes are case-insensitive by default.
- Trace:
  1. Entry and doc comment of the precedence: [tool_permissions.rs L208-L260](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/agent/src/tool_permissions.rs#L208-L260).
  2. Body (hardcoded, invalid-regex deny, substitution deny, no-rules path): [tool_permissions.rs L253-L306](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/agent/src/tool_permissions.rs#L253-L306).
  3. Rule evaluation per sub-command: [tool_permissions.rs L378-L431](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/agent/src/tool_permissions.rs#L378-L431) (deny short-circuits, confirm is remembered, allow needs all sub-commands covered and `allow_enabled`).
  4. Shipped default `"default": "confirm"`: [default.json L1259-L1264](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/assets/settings/default.json#L1259-L1264).
  5. File tools match the path both raw and lexically normalised and take the more restrictive result: [tool_permissions.rs L514-L560](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/agent/src/tool_permissions.rs#L514-L560).

#### Splitting a terminal command into sub-commands (and what it does not do)
- What the code does: `extract_commands` parses the string with `brush-parser` (a POSIX shell parser) into an AST and flattens it into a list of normalised sub-command strings: each pipeline element, each `&&`/`||`/`;` branch, subshell and brace-group bodies, and nested command substitutions. Quotes are stripped so `rm -rf '/'` and `rm -rf /` match the same patterns; redirects other than `/dev/null` become extra pseudo-commands such as `> out`, which an allow list must also match. If any word cannot be normalised or the parse fails, `extract_commands` returns `None`, the raw string is matched, and **allow is disabled** (deny and confirm still apply).

#### What an approval is bound to, and how long it lasts

While a prompt is open the code subscribes to settings changes and auto-resolves a pending prompt if a sibling approval makes it allowed or denied. ### 3.4 The ACP client

#### How external agents are found, installed and launched
- What the code does: the registry index is fetched from `https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json` (30 s timeout, refreshed at most hourly, cached on disk). ### 3.5 Edit tools and how agent edits are reviewed

#### `edit_file`: search and replace with a fuzzy line matcher, applied to the buffer, then saved
- What the code does: `edit_file` takes `path` and a list of `{old_text, new_text}`. The `old_text` is documented as "matched using fuzzy matching to handle minor differences in whitespace or formatting". A `StreamingFuzzyMatcher` consumes the model's streamed `old_text` line by line against a snapshot of the buffer: first exact matching (stops after two matches since that already proves ambiguity), otherwise a dynamic-programming alignment with costs replace 1, insert 3, delete 10, and a per-line similarity threshold of 0.8 normalised Levenshtein (`fuzzy_eq`, L368-L379, which also pre-rejects on length difference); a candidate range is then kept only if matched query lines divided by max(matched buffer lines, query lines) is at least 0.8 ([L254-L256](https://github.com/zed-industries/zed/blob/3def8bad0b62dbda02d5b67b00df96fe8d3957bd/crates/agent/src/tools/edit_session/streaming_fuzzy_matcher.rs#L254-L256)). With several candidates a line hint (tolerance 200 lines) picks one; if still ambiguous the edit fails listing the line numbers. Edits apply to the open buffer as the model streams and a diff is shown live, then the buffer is optionally formatted (format-on-save setting) and **saved to disk** when the tool completes, also on failure of a later edit in the same call.

### 3.6 Compaction and context limits

#### Auto-compaction: threshold, model, prompt, what survives
- What the code does: before every model request in the turn loop, `compaction_message_target_ix` checks the last reported usage (`input + cache creation + cache read + output` tokens) against a threshold computed from the model's input capacity: percentage (default 90%), tokens used, or tokens remaining. If at or above threshold it runs a compaction request on the compaction model (`agent.compaction_model`, else the thread's own model), which is the whole history up to that point plus a fixed prompt asking for a handoff (goal, state, context, next steps, pitfalls). The summary is inserted as a `Message::Compaction(Summary)`; all earlier messages stay in the thread for the UI but are no longer sent. When building later requests, the last **80,000 bytes** of earlier user messages (about 20k tokens) are re-sent verbatim before the summary, the oldest one truncated to fit; agent messages and tool results are dropped. Auto-compaction is only enabled when the model's input capacity is at least 80,000 tokens; smaller models get a UI warning instead. Capacity is `min(input_limit, combined_limit - output_limit)`.
