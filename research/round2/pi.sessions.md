## 3. Findings

### Session storage: format, tree, compaction, migration

#### One JSONL file per session; append-only tree via `id` and `parentId`
- What the code does: a session is a file `<timestamp>_<uuidv7>.jsonl` in a per-cwd directory `~/.pi/agent/sessions/--<cwd with separators replaced by "-">--/`. Line 1 is a `session` header `{type, version, id, timestamp, cwd, parentSession?}`; every later line is an entry with an 8-hex-character `id` (collision-checked against the in-memory map, falling back to a full UUID) and a `parentId` (null for a root). Entries are appended with `appendFileSync` one line at a time; nothing is edited in place during normal operation.
- Trace: header and entry types https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L41-L62; id generation https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L276-L284; directory name https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L590-L595; file name https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1058-L1084; append https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1173-L1190.
- Edge cases: the file is not created until the session holds a user or assistant message (`_hasConversation`); at that point the header plus buffered entries are written with `wx` (fail if exists) and later entries are appended. If the write throws, the entry is popped from memory so a lost entry cannot become a parent (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1192-L1207). Malformed lines are skipped on load (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L617-L625); a file without a valid first-line header loads as empty and opening a non-empty non-session file throws instead of overwriting (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1030-L1047). If the file does not end in a newline, loading appends one (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L662-L670). No file lock and no `fsync` appear in this file: two processes appending to one session are not guarded (searched `session-manager.ts` for lock/flock/fsync; the only lock in the package is for `trust.json`).
- Round 1: `confirmed` (JSONL, id/parentId, in `~/.pi/agent/sessions/` grouped by directory).
- For rizzy-harness: a tree needs only `id` + `parentId` on each event; pi's 8-hex ids are fine for one file but you have a per-session `seq` already. Decide whether a fork is a parent pointer or a copy (pi does both, see below).
- Confidence: traced end to end. (checked in review)

#### The active leaf is not stored: it is "the last entry in the file"
- What the code does: on load `_buildIndex` sets `leafId` to the id of the last non-header entry in file order. `branch(id)` and `resetLeaf()` only change the in-memory `leafId`; nothing is written. The next appended entry gets `parentId = leafId`, which is what actually persists the branch choice.
- Trace: `_buildIndex` https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1104-L1123; `branch`/`resetLeaf` https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1590-L1604; `navigateTree` without a summary calls `branch()`/`resetLeaf()` and nothing else (a label, if requested, is appended and so persists the position) https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L4286-L4297.
- Edge cases: consequence (inferred from the two pieces above, not from a test): after `/tree` to an older node with "No summary" and a restart before sending anything, the session reopens on the most recently written entry, which is on a different branch. With a summary the `branch_summary` entry is appended with `parentId = target`, so the new leaf persists. Entries written for other reasons while you sit on a moved leaf (a `session_info`, a label, a `usage` entry) are children of the moved leaf too.
- Round 1: `new (not documented)` (docs say "the current leaf is the active branch" and do not say it is derived).
- For rizzy-harness: if you add forking over an event log, store the active head explicitly (a `head` event or a column) or accept this derived-head behaviour knowingly; pi's variant makes "navigate and quit" lossy.
- Confidence: traced end to end (the restart consequence is inferred). (checked in review)

#### Rebuilding the current path and the model context
- What the code does: `buildSessionPath` walks `parentId` from the leaf to the root and reverses. `buildContextEntries` then applies the latest compaction on that path: the compaction entry first, then the path entries from `firstKeptEntryId` up to the compaction entry (system messages dropped), then everything after it. `buildSessionProjection` additionally applies `context_edit` entries (replace the content of an earlier entry or omit it) and extracts the current model and thinking level by scanning the path.
- Trace: path https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L390-L416; compaction-aware list https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L476-L512; context edits and projection https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L520-L574; the agent's message array is replaced from the projection after navigation/compaction https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L999-L1005.
- Edge cases: an unknown leaf id falls back to the last entry; a dangling `parentId` simply ends the walk (path begins at the orphan) (`buildSessionPath`, lines above). `getTree()` treats orphans and self-parented entries as roots and sorts children by timestamp (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1540-L1578). Context is rebuilt from the whole entry list on each projection (`getEntries()` copies the array), so cost is linear in session size per call; there is a note in `getSessionName` that the footer avoids `getEntries()` for this reason.
- Round 1: `confirmed`.
- For rizzy-harness: your fold-over-log already does this; the transferable part is that the path is a pure function of (entries, leaf) and compaction is just another node on the path, so branches can compact independently.
- Confidence: traced end to end.

#### Compaction and branch summaries are ordinary entries on the path
- What the code does: `CompactionEntry` holds `summary`, `firstKeptEntryId`, `tokensBefore`, optional `details`, `usage`, `fromHook`, and a `systemMessage` snapshot (the full system prompt and tool state at that point). `appendCompaction` writes it as a child of the leaf. `BranchSummaryEntry` holds `fromId` (the abandoned leaf), `summary`, `details`, `usage`, `fromHook`, and is written as a child of the navigation target. Old entries are never removed; they are just not on the compacted path. Trigger test: `contextTokens > contextWindow - reserveTokens`.
- Trace: entry types https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L91-L116; `appendCompaction` https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1272-L1298; `branchWithSummary` https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1611-L1636; threshold https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/compaction/compaction.ts#L267-L270; the session appends after summarizing then refreshes the projection https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L3330-L3335.
- Edge cases: when a branch is forked into a new file, a compaction whose `firstKeptEntryId` pointed at a dropped label entry is remapped (see the fork finding). Compaction does not store per-file read/modified state outside `details` (extensions can add anything there). The summarizer and its prompt belong to the agents cluster; not traced here.
- Round 1: `confirmed` (compaction and branch_summary entries, original entries stay in the tree); Round 1's remark that the tokens reserve for branch summary is 16384 is `confirmed` (`reserveTokens = 16384` default, https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/compaction/branch-summarization.ts#L320).

#### Branch summary on `/tree`: what is summarized, prompt, where it lands
- What the code does: `collectEntriesForBranchSummary` finds the deepest common ancestor of the old leaf and the target and collects entries from the old leaf back to it. `prepareBranchEntries` walks newest to oldest within `contextWindow - reserveTokens`, skips tool results (the assistant's tool call carries the context), applies context edits, and gathers read/edited file lists (including from earlier branch summaries' `details`). The model is asked with a fixed structured prompt (Goal, Constraints, Progress, Key Decisions, Next Steps) over a serialized `<conversation>` block, no tools allowed (a response with a tool call is an error). The text is prefixed with a preamble and suffixed with file lists, and stored via `branchWithSummary(newLeaf, ...)`.
- Trace: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/compaction/branch-summarization.ts#L115-L153 (collect), https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/compaction/branch-summarization.ts#L203-L261 (budgeted walk), https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/compaction/branch-summarization.ts#L272-L299 (prompt), https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/compaction/branch-summarization.ts#L379-L397 (tool-call rejection, preamble, file lists).
- Edge cases: summarization is cancellable; an abort returns `{cancelled, aborted}` and the TUI returns to the selector; errors throw. No model: throws "No model available for summarization" before anything is written (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L4146-L4149). Navigation is refused while streaming or compacting (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L4130-L4137).

- For rizzy-harness: the summary is a node placed at the target, so the returning branch carries the memory of the abandoned one. File state is not touched (see checkpoints).
- Confidence: traced end to end.

#### `/tree` semantics: user messages become "re-edit", other nodes are "continue after"
- What the code does: `navigateTree(targetId)`: selecting a user message (or a custom message) sets the leaf to its parent and returns the text to put in the editor; selecting anything else sets the leaf to that node. Extensions can veto (`session_before_tree` returns `cancel`), supply their own summary, or change the instructions and label. Afterwards the tool loadout is re-derived from the branch and `session_tree` is emitted.
- Trace: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L4187-L4214 (extension hook), https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L4251-L4311 (leaf choice, summary entry, label, refresh, event); the interactive prompt "No summary / Summarize / Summarize with custom prompt" https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/modes/interactive/interactive-mode.ts#L5751-L5852.
- Edge cases: navigating while a response streams makes the TUI abort it first (restoring queued messages to the editor) (interactive-mode lines above); navigating to the current leaf is a no-op (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L4141-L4144). No working-tree change happens: nothing in `navigateTree` touches files.
- Round 1: `confirmed` (selecting a user message loads it into the editor). The Round 2 question "what happens to file state" answer: nothing.
- For rizzy-harness: copy the user-message-as-edit-point rule; it makes "edit and resubmit" a navigation, not a mutation.
- Confidence: traced end to end.

#### Fork, clone and "continue from another cwd" produce new files; `/tree` stays in one file
- What the code does: `AgentSessionRuntime.fork(entryId, {position})`. Position `before` (the default, for the `/fork` command) requires a user message and forks at its parent, returning the text for the editor; `at` (used by clone) forks at the entry itself. For a persisted session with a non-root target, `SessionManager.createBranchedSession(leaf)` writes a new file containing only the root-to-leaf path (labels removed and re-created, parent links re-chained, `firstKeptEntryId` remapped), with a new header whose `parentSession` is the old file path. For a root target it creates an empty session with `parentSession`. Separately `SessionManager.forkFrom(source, targetCwd)` copies the whole entry list into a new file in another project's directory (used by `--fork` and "session found in a different project").
- Trace: runtime https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session-runtime.ts#L262-L350; path extraction and re-chaining https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1643-L1738; `forkFrom` https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1826-L1882; CLI selection https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/main.ts#L415-L460; RPC `fork` and `clone` https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/modes/rpc/rpc-mode.ts#L632-L650.
- Edge cases: forking an unsaved session throws "has not been saved yet" (runtime line 312-314); the other branches of the original are not copied into the fork (only the chosen path), so a fork loses sibling branches; `forkFrom` copies everything including all branches. The old runtime is torn down first (abort, `session_shutdown`, dispose) and the new one built by the same factory; if creation fails the error propagates and no session is active (class comment, https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session-runtime.ts#L67-L72). `session_before_fork` handlers can cancel.
- Round 1: `confirmed` (`/fork` creates a new file from an earlier user message; `/clone` copies the active branch). New detail: the fork copies a path, not the tree, and the parent link is a file path in the header.
- For rizzy-harness: two cheap designs side by side: pi's in-file branching (leaf pointer) and out-of-file fork (copy path, record `parentSession`). The `parentSession` is a path, so renaming or deleting the parent silently orphans the lineage.
- Confidence: traced end to end.

#### Format versioning and migration: rewrite on load
- What the code does: `CURRENT_SESSION_VERSION = 3`. A missing `version` means 1. v1 to v2 adds `id` and `parentId` (a linear chain in file order) and converts `firstKeptEntryIndex` into `firstKeptEntryId`; v2 to v3 renames the message role `hookMessage` to `custom`. Migrations mutate entries in memory; if any ran, the whole file is rewritten with `openSync(..., "w")`.
- Trace: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L286-L347 (migrations), https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1086-L1102 (migrate and rewrite on load), https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1125-L1135 (`_rewriteFile`).
- Edge cases: the rewrite truncates then writes sequentially with no temp file and rename, so a crash during migration can leave a truncated session (inferred from the code: `openSync(path, "w")` then loops writes). Newer files read by an older pi are not rejected: only `version < CURRENT` triggers work; a higher version loads as is (`migrateToCurrentVersion` returns false when `version >= CURRENT`). Entries are parsed without schema validation, and `sessionEntryToContextMessages` patches null content (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L439-L451).
- Round 1: `confirmed` (v1 linear, v2 tree, v3, old files auto-migrate); the "append-only" claim is true except for migration and fork-file creation.
- For rizzy-harness: if you need migrations after the first tag, prefer an upcasting reader to rewriting the file, and write via temp file and rename.
- Confidence: traced end to end. (checked in review)

#### The system prompt and the tool declarations are stored in the transcript as deltas
- What the code does: a `system` role message carries `content`, named `sections`, and `toolsAdded` / `toolsRemoved`. `getCurrentSystemMessage(messages)` replays every system message in order: contents appended, sections patched by name (null deletes), tools resolved as a map. The coding agent persists system messages as ordinary `message` entries. On `/tree`, resume and fork, `_restoreToolsFromTranscript` replays the branch's system messages to restore the active tool loadout (including tools loaded later by `tool_search`), and tools recorded for servers not yet connected stay pending until they register.
- Trace: replay https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/ai/src/utils/transcript.ts#L57-L96; restore https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L1900-L1929; persistence at `message_end` including `system` https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L1212-L1233; compaction snapshots the replayed system message https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/session-manager.ts#L1281-L1294.
- Edge cases: a branch with no recorded loadout keeps the current tools (line "No recorded loadout" in `_restoreToolsFromTranscript`). Tools that were registered after the branch recorded its loadout are activated like new tools.
- Round 1: `new (not documented)`; Round 1 only knew `context_edit`.
- For rizzy-harness: this is a clean way to make "what the model was told" an event-log fact, so forks and resumes reproduce tool sets and prompt-cache-friendly prefixes. Cost: prompt and tool JSON schemas are stored in the log (large).

### Remote workers and executors

#### pi-env: the controller dials over SSH; the daemon is a framed-stdio tool server
- What the code does: the host side runs `ssh` with `BatchMode=yes`, `ClearAllForwardings=yes`, `ForwardAgent=no`, `ControlMaster=no`, strict host-key checking against an application-owned known-hosts file and a fixed alias. The protocol (version 1) is length-prefixed binary frames (u32 length, u8 type, u32 request id, JSON, raw payload; max 16 MiB) on the process's stdin/stdout: request, result, error, event, cancel, ping. The `--token` is only a sync marker printed as `PI-ENV <token>` so the client can skip shell startup noise; it is not an authentication secret. Authentication and confidentiality are SSH's.
- Trace: SSH flags https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/env/src/ssh.ts#L88-L111; hash-verified deployment https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/env/src/ssh.ts#L381-L420; framing and sync https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/env/docs/protocol.md#L1-L35.

### pi-durable (a second, experimental session model)

#### Durable harness: forks as parent pointers over linear conversations; restart limit per task
- What the code does: `packages/durable` is a separate harness (README: "Experimental"). ## 5. In the code but not in the documentation

- The active leaf of a session file is never written; it is recomputed as the last entry (section 3, leaf finding).
- The system prompt, tool declarations and tool loadout are delta entries in the transcript, which is how `tool_search` loads and `/tree` branches restore a tool set (3.1 and the tool-search finding).
- Compaction entries snapshot the replayed system message (`systemMessage` field).
- Fork copies only the root-to-leaf path with label entries re-created and compaction `firstKeptEntryId` remapped; `forkFrom` (cross-project) copies everything.
- The `mcp_servers` system prompt section (4096 characters, 250 per server description) is how the model learns about servers whose tools are hidden.
- Stdio MCP servers inherit the whole process environment; there is no scrub.
- `apps/p2`: a web UI with sign-in token, Fetch-Metadata origin checks, per-session worker processes, SSH environments and Gondolin sandboxes with a secret-substituting proxy.
- `packages/env`: the SHA-256 content-addressed remote daemon and its frame protocol with stdin-EOF liveness.
- `trust.json` writes use `proper-lockfile`; trust keys are canonical paths with nearest-ancestor lookup.
- RPC mode has no `navigate_tree`.
