## 2. Architecture as it bears on this cluster

- Language and layout: a TypeScript monorepo. Three packages matter here. `packages/ai` (provider streaming, retry classifier, overflow classifier, model catalogue and thinking levels), `packages/agent` (the stateless-ish loop `agent-loop.ts` plus the `Agent` class with the two message queues), and `packages/coding-agent` (the product: `AgentSession` wraps the `Agent`, owns the session tree, compaction, retry, model cycling, system prompt assembly, tools, extensions).
- The decisions live in three places. The turn loop is `runLoop` in `packages/agent/src/agent-loop.ts`. Everything product-specific (compaction trigger, retry, prompt assembly, steering UI queue) is in the ~4,500-line `packages/coding-agent/src/core/agent-session.ts`, which hooks the loop through `prepareRequest`, `prepareNextTurnWithContext` and `finishTurn`. Compaction maths is pure functions in `core/compaction/compaction.ts`.
- Process model: one Node process per session, in-process extensions. There is no separate engine and no master/node split in this cluster. Sub-agents exist only as an example extension that spawns another `pi` process.
- Key architectural fact for the cluster: the system prompt and the tool declarations are not request-time strings. They are **system messages inside the transcript** (`SystemMessage` with `sections`, `toolsAdded`, `toolsRemoved`), so a mid-session change is an appended patch message, not a rewrite of the head of the prompt (see finding 1.2).
  - https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/ai/src/types.ts#L559-L585 defines the type and its replay semantics.

### 3.3 Edit tool

#### 3.1 The edit tool: multi-edit, exact match with a quiet fuzzy fallback, unique-in-original, all-or-nothing
- What the code does: the schema is `{ path, edits: [{ oldText, newText }] }`. Every `oldText` is matched against the ORIGINAL file content (not incrementally), must be non-empty, must occur exactly once, and must not overlap another edit. Matching is `indexOf` exact first. If any edit fails the exact match, the whole operation switches to a "fuzzy" space: both file and `oldText` are normalised (Unicode NFKC, trailing whitespace stripped per line, curly quotes to ASCII, Unicode dashes to `-`, special spaces to space) and matched there. After matching, all replacements are applied in reverse order; if no text changed, it is an error. The file is written once, after the diff has been computed, so a failure leaves the file untouched.
- Trace:
  - schema and model-facing rules: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/tools/edit.ts#L18-L38
  - exact-then-fuzzy search: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/tools/edit-diff.ts#L250-L288
  - normalisation: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/tools/edit-diff.ts#L77-L98

  - assembly of the multi-edit, overlap and no-change checks: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/tools/edit-diff.ts#L343-L406

#### 3.2 Fuzzy matches preserve untouched lines byte-for-byte, but rewrite touched lines from the normalised text
- What the code does: when fuzzy matching is used, offsets are in normalised space. `widenReplacementsToLines` widens every replacement to the whole lines it touches, rewrites those lines from the normalised text with the replacement applied, and leaves all other lines as the original bytes. It requires the normalised and original text to have the same line count (otherwise it throws). So a fuzzy edit that touches a line with a curly quote or trailing space silently converts that whole line to its ASCII/trimmed form, and a further edit in the same call that matched exactly is also applied in normalised space.
- Trace:
  - widening: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/tools/edit-diff.ts#L176-L214
  - switch to normalised base if any edit needed fuzzy: https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/tools/edit-diff.ts#L359-L361
- Edge cases and failure handling: NFKC can change string length, which is the reason the algorithm works in normalised space and maps back by line; the guard "different line count" would throw for a normalisation that merges or splits a newline. The tool reports `Successfully replaced N block(s)` with no flag that fuzzy matching was used (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/tools/edit.ts#L204-L212).

- For rizzy-harness: if you copy a fuzzy fallback, tell the model and the user that it was used and what was normalised; Pi's silent rewrite of a whole line can change content the model did not mention.

#### 3.3 Line endings and BOM are preserved; no staleness check; per-file write queue; no post-edit diagnostics
- What the code does: the BOM is split off before matching, text is normalised to LF for matching, and the result is spliced back into the original text with the line ending of the line where each replacement begins, so untouched lines keep their CRLF. Edits and writes to the same real path (symlinks resolved) are serialised by `withFileMutationQueue`; different files run in parallel. There is NO "file changed since read" check: the tool reads the file at execution time and applies the edits to whatever is on disk, and it does not require a prior `read`. ### 3.4 Compaction

#### 4.1 Trigger: estimated context over (context window minus 16,384), checked at three moments

#### 4.4 Overflow recovery: one compact-and-retry, the failed attempt is hidden by `context_edit` entries
- What the code does: after a run, `_checkCompaction` classifies the last assistant message. A context-overflow error (regex table over provider error text, a 413 rule, plus "silent overflow" where input tokens exceed the window and a "length stop with zero output filling the window" rule) or a `length` stop below the model's desired output limit selects recovery. Before compacting it appends `context_edit` entries (replacement null) that hide the failed assistant message and its tool results from the model projection while the raw log keeps them (`_omitRecoveryAttempt`). It then compacts with reason `overflow` and, if it succeeds, the session continues (`agent.continue()`), so the model re-answers the last input. The flag `_overflowRecoveryAttempted` allows exactly one such attempt per run; a second failure emits "Context overflow recovery failed after one compact-and-retry attempt. Try reducing context or switching to a larger-context model." and stops. A successful response that nevertheless exceeded the window (silent overflow) compacts without retrying.

### 3.5 Retry and backoff

#### 5.1 Two layers: agent-level retry (3 tries, 2,000 ms doubling, 60,000 ms cap, no jitter) and provider-level retry (default 0)

The agent layer is in `AgentSession`: when a run ends with an assistant message with `stopReason: "error"`, `_isRetryableError` (not a context overflow, matches the retryable regex, does not match the non-retryable limits regex) and `_prepareRetry` increment `_retryAttempt`, emit `auto_retry_start`, hide the failed attempt with `context_edit` omissions, sleep `baseDelayMs * 2^(attempt-1)` capped at 60,000 ms (attempt delays 2 s, 4 s, 8 s), and the post-run loop calls `continue()`. Abort during the sleep cancels the retry and emits `auto_retry_end` with "Retry cancelled" (L3908-L3918). A retried attempt that follows a failed request is routed with `reason: "retry"` for virtual-model routers (see 6.4). The agent-level backoff ignores any `Retry-After` header; the provider layer honours `retry-after-ms`/`retry-after` but refuses to wait when the server asks for more than `maxRetryDelayMs` (error text "Server requested Ns retry delay"), and that message matches the retryable "retry delay" pattern so it then flows into the agent-level backoff (https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/ai/src/utils/provider-retry.ts#L39-L69). The provider layer's own backoff is `min(0.5*2^n, 8) s` with up to 25% downward jitter. All of the provider-layer behaviour in this paragraph is dormant by default: `provider.maxRetries` is unset (0), so `retryProviderRequest` rethrows at once and never reads `Retry-After` (corrected in review).

Corrected nuance: "60,000 ms maximum" names two different caps, the agent-level delay cap (`maxAgentDelayMs`) and the provider layer's cap on SERVER-REQUESTED waits (`maxRetryDelayMs`). Round 1's open question about how the two interact on a streamed response is answered: provider layer only wraps the request until the response object exists (retry of the HTTP call), mid-stream failures surface as an error assistant message and go through the agent layer. The agent-level schedule has no jitter despite the doc comment.

### 3.8 Message queueing and steering

#### 8.1 Two queues in the `Agent` class: steering (after the current turn) and follow-up (when otherwise done), one-at-a-time by default

#### 9.1 Parallel tool execution by default, sequential opt-out per tool, `terminate` only if every result says so
- What the code does: `executeToolCalls` runs the batch in parallel unless `config.toolExecution === "sequential"` or any call's tool has `executionMode: "sequential"`. In the parallel path, each call is prepared one after another (argument repair, schema validation, `beforeToolCall` hook) and the permitted ones then execute under `Promise.all`; results are returned in the order of the calls. The batch ends the run's tool loop only if every finalised result has `terminate: true`. Same-file edits are serialised by the file mutation queue, not by the loop.
- Trace:

### 3.10 Output truncation

#### 10.1 Truncation is enforced by each built-in tool, not by the loop
- What the code does: `truncate.ts` defines `DEFAULT_MAX_LINES = 2000` and `DEFAULT_MAX_BYTES = 50 KB`. `read` (head), `ls`, `find`, `grep` (head, plus 500 chars per match line) and `bash` (tail) apply them themselves. Bash streams into an `OutputAccumulator` that keeps a bounded tail in memory and spills the FULL output to a temp file when truncation occurs, then tells the model the path (`[Showing last ... Full output: <path>]`). The loop (`agent-loop.ts`) and the extension wrapper apply no generic cap: an extension tool that returns 10 MB goes straight into context unless it truncates (the docs only recommend it).
- Trace:

## 5. In the code but not in the documentation (Round 1)

- The system prompt is transcript state with section patches and tool declarations as `toolsAdded`/`toolsRemoved` system messages (finding 1.2).
- The edit tool silently falls back to a Unicode/whitespace-normalised search and rewrites whole touched lines in normalised form (3.2); `prepareArguments` repairs mis-shaped arguments from specific models (3.4); no staleness check, no formatter or diagnostics step (3.3).
- Compaction: iterative "update" prompt using the previous summary; `Additional focus` suffix; summaries are never persisted if truncated (`length`) or errored; one compaction call per split turn; `cacheRetention: "none"` for summary calls; no staged fallback and no input-size guard on the summariser (4.3).
- Overflow handling uses a large provider-error regex table with a non-overflow exclusion list, "silent overflow" detection, and `context_edit` omissions that hide the failed attempt from the model while keeping it in the log (4.4).
- Retry: two layers with different caps; a quota/billing non-retryable regex evaluated first; agent-level retry has no jitter and ignores `Retry-After` (the provider layer honours it with a refusal threshold); summaries share the policy (5.1, 5.2).
- Truncated tool calls (`length` stop) are never executed; they come back as error results asking the model to re-issue (4.4).
- Virtual models (a per-request router with reason, previous model and failure info) as the only fallback mechanism (6.4).
- Instruction files are loaded up to the filesystem root with no size cap; worktree shadowing prevents double load (2.1).
- Skill discovery is trust-gated for project directories, and the SDK-only `includeDefaults: true` path has the opposite precedence from the CLI path (2.3).
- Sub-agent example: no depth limit, no env scrubbing, no worktree isolation; only the last text returns (7.2).
