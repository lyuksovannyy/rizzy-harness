## 2. Architecture as it bears on this cluster

- Language and layout: a TypeScript npm monorepo plus one Rust crate. `packages/agent` is the provider-agnostic loop (`agentLoop`, `Agent` class). `packages/coding-agent` is the CLI product: tools, sessions, settings, trust, extensions, built-in extensions for MCP, codemode and tool search. `packages/codemode` is the QuickJS-in-WebAssembly script runner. `packages/durable` is an experimental second harness (task scheduler over a transactional store) that does not share the loop with the CLI. `packages/env` holds `pi-env`, the Rust daemon plus its SSH client, implements the `ExecutionEnv` interface of `durable` (`pi-env` depends on `pi-durable`, not the reverse) and is depended on only by `apps/p2` (`apps/p2/package.json` line 30; no `coding-agent` or `durable` manifest lists it) (corrected in review).
- Process model of the CLI: one Node (or Bun) process runs the TUI or RPC front end, the agent loop, all tools and all extensions. Shell commands are `spawn`ed as children of that process. Extensions are TypeScript modules loaded into the same process (so they hold the process's full authority). There is no separate server, no tool broker, no sandbox process.
- Where the decisions live:
  - Loop and tool pipeline: [`packages/agent/src/agent-loop.ts`](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L172-L330) (`runLoop`) and [`#L718-L787`](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L718-L787) (`prepareToolCall`).

## 3. Findings

### The agent loop and tool dispatch

#### Two nested loops, no turn cap, three ways to stop
- What the code does: `runLoop` has an inner loop (runs while the last assistant message had tool calls or steering messages are pending) inside an outer loop (re-enters when follow-up messages exist). It stops when a turn ends with no tool calls and no queued messages, when `finishTurn` returns `{action: "end"}`, when every tool result in a batch sets `terminate: true`, or on an `error`/`aborted` stop reason. A grep for `maxTurns|max_turns|maxSteps` in `packages/agent/src` and `packages/coding-agent/src` returns nothing: the only loop bound is model behaviour, user abort and (in durable) a restart limit.
- Trace: `agentLoop` / `runAgentLoop` emit `agent_start`, then `runLoop` ([agent-loop.ts#L172-L192](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L172-L192)); stream one assistant message ([#L250-L252](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L250-L252)); error/aborted exits at once ([#L254-L265](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L254-L265)); tool calls are executed and results pushed ([#L267-L287](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L267-L287)); `finishTurn` decides end/continue and steering is polled ([#L295-L308](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L295-L308)); follow-ups re-enter the outer loop ([#L310-L317](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L310-L317)).
- Edge cases and failure handling: a model that keeps emitting tool calls loops until the user aborts or the context fills; nothing in the loop counts calls or cost.
- Round 1: `confirmed` (Round 1 described the turn loop and `agent_settled`; no cap was claimed).
- For rizzy-harness: add an explicit per-run step and spend ceiling on the node side; Pi has none, and a hostile or confused model can loop for hours.
- Confidence: traced end to end. (checked in review)

#### Tool call pipeline: find, repair, validate, hook, execute, hook, settle
- What the code does: for each call the loop looks the tool up by name in `context.tools`; unknown tool gives an error result. Then `tool.prepareArguments` (optional repair), `validateToolArguments` (schema), then `beforeToolCall`, which may return `{block: true, reason}` (and `terminate`). Only then `tool.execute(id, args, signal, onUpdate)`. Any thrown error in preparation or execution becomes an `isError` tool result, never a loop crash. After execution `afterToolCall` may replace content, details, `isError` and `terminate`; a throwing `afterToolCall` turns the result into an error result.
- Trace: lookup and `prepareToolCall` ([agent-loop.ts#L718-L787](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L718-L787)); `executePreparedToolCall` with try/catch ([#L831-L867](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L831-L867)); `finalizeExecutedToolCall` ([#L869-L920](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L869-L920)); result message built with `durationMs` ([#L940-L954](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L940-L954)).
- Edge cases and failure handling: `beforeToolCall` throwing is caught by the `try` at [#L735-L786](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L735-L786) and returned as an error result, so a failing gate fails closed (the tool does not run). The abort signal is checked after the hook and again before returning "prepared" ([#L748-L773](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L748-L773)).
- Round 1: `confirmed` (Round 1: "runs every tool call and records results"); the validate-then-hook-then-execute order and fail-closed hook were not documented.
- For rizzy-harness: the same ordering is right (validate before authorise, so the approver sees normalised arguments). Pi's hook can mutate `args` afterwards with no re-validation (see the hook finding).
- Confidence: traced end to end. (checked in review)

#### Parallel batches: preparation is serial, execution is concurrent
- What the code does: if the config says `toolExecution: "sequential"` or any call in the batch is a tool with `executionMode: "sequential"`, calls run one at a time. Otherwise `executeToolCallsParallel` loops over calls in order, emits `tool_execution_start`, runs `prepareToolCall` (including `beforeToolCall`) for each call one after another, and queues the execute-and-finalise closures; the closures then run under `Promise.all`. So an approval prompt in a `tool_call` hook is shown one call at a time, but approved tools then run concurrently. Results are emitted in the model's call order. `terminate` only stops the loop when every finalised call in the batch sets it.
- Trace: [agent-loop.ts#L518-L533](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L518-L533) (selection), [#L596-L670](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L596-L670) (parallel), [#L700-L702](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L700-L702) (`shouldTerminateToolBatch`).
- Edge cases and failure handling: on abort mid-preparation the for-loop `break`s ([#L623-L625](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L623-L625), [#L651-L653](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L651-L653)), so later calls in that batch get no result message from this function; closures already queued return "Operation aborted" ([#L629-L638](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L629-L638)). What the provider layer does with the unmatched tool calls was not traced.
- Round 1: `confirmed` (parallel by default, per-tool sequential opt-out, `terminate` only if all set it) and answers the Round 2 question on `terminate`.
- For rizzy-harness: serialising authorisation while parallelising execution is a good shape for approvals; copy it.
- Confidence: traced end to end. (checked in review)

#### A response cut off by the token limit never executes its tool calls
- What the code does: if the assistant message's `stopReason` is `"length"`, every tool call in it is failed with "was not executed: the response hit the output token limit, so its arguments may be truncated", because streamed arguments are completed by a best-effort JSON salvage parser and could be silently incomplete.
- Trace: [agent-loop.ts#L273-L279](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L273-L279) selects the path; [#L488-L513](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L488-L513) fails each call.
- Edge cases and failure handling: results are marked `isError` and the loop continues so the model can re-issue.
- Round 1: `new (not documented)`.
- For rizzy-harness: copy. A truncated `write` or `bash` argument is a data-loss and safety hazard; refuse to run any call from a length-truncated message.
- Confidence: traced end to end. (checked in review)

#### Cancel: one AbortSignal, process-tree kill, no steering interrupt
- What the code does: `Agent.abort()` aborts the active run's `AbortController`; the signal reaches the stream function, hooks and `tool.execute`. The shell tool kills the whole process tree on abort. Steering messages do not interrupt running tools: they are polled only after `finishTurn`, that is after the whole tool batch.
- Trace: [agent.ts#L350-L352](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent.ts#L350-L352) (abort); signal wiring into the loop [#L522-L536](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent.ts#L522-L536); sequential path stops after the first aborted call ([agent-loop.ts#L585-L587](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L585-L587)); steering polled at [#L304](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L304).
- Edge cases and failure handling: tools that ignore the signal keep running; the loop awaits them.
- Round 1: `corrected`. Round 1 reported the homepage claim that a steering message is "delivered after the current assistant turn, interrupting remaining tools". The code at the agent-core level does not interrupt remaining tools; the repository's own `how-pi-works.md` says only that steering "enters after the current assistant turn" ([docs/how-pi-works.md#L13](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/docs/how-pi-works.md#L13)). Abort is the only interrupt.
- For rizzy-harness: decide deliberately whether a user message should cancel in-flight tools; Pi chose "no".
- Confidence: traced end to end (core loop); the TUI layer was not read for extra interrupt logic. (checked in review)

### Approvals and permission rules

#### There is no permission system: the only gate is an extension hook
- What the code does: nothing in `packages/agent` or `packages/coding-agent/src` implements modes, rules, allowlists, approval prompts, a classifier or a model-based approver. A grep over `coding-agent/src`, `agent/src`, `durable/src`, `env/src` for `approver|autoApprove|dangerously|yolo|landlock|seatbelt|bubblewrap|sandbox-exec` returns no files; the only files matching `permission|approv` in `coding-agent/src` concern file-lock errors, MCP UI text, the trust flags (`--approve`) and the codemode tool's description. What exists instead is one event: extensions register `tool_call` handlers, and the loop's `beforeToolCall` is bound to them.
- Trace: hook installed at [agent-session.ts#L714-L715](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L714-L715); `_beforeToolCall` emits `tool_call` only if handlers exist ([#L719-L743](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L719-L743)); runner iterates handlers in load order and returns at the first `block` ([runner.ts#L1256-L1274](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/extensions/runner.ts#L1256-L1274)).
- Edge cases and failure handling: with no extension loaded, every tool call runs unprompted. A handler that throws propagates (re-thrown as "Extension failed, blocking execution" for non-Error values) and the loop turns it into a blocked error result, so a crashing gate fails closed. A handler returning a non-block value does not stop later handlers; only `block` short-circuits.
- Round 1: `confirmed` (no built-in permission system; extensions can block or mutate; "a failing `tool_call` handler blocks that tool call").
- For rizzy-harness: Pi shows that a clean hook seam is cheap, but the default is "allow everything". Keep your node-side policy as the default and make the hook seam additive (can only restrict).
- Confidence: traced end to end. (checked in review)

#### `tool_call` handlers may mutate arguments after validation with no re-check
- What the code does: the event's `input` is the same validated args object; handlers can patch it in place and the loop executes the patched object. The docs state "No re-validation is performed after your mutation".
- Trace: `input: args` at [agent-session.ts#L728-L735](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/agent-session.ts#L728-L735); the loop then returns `args: validatedArgs` as prepared ([agent-loop.ts#L774-L779](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/agent/src/agent-loop.ts#L774-L779)); documented at [docs/extensions.md#L981-L986](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/docs/extensions.md#L981-L986).
- Edge cases and failure handling: a buggy or hostile extension can make a tool receive arguments that violate its own schema.
- Round 1: `new (not documented)` (Round 1 said extensions "can block or mutate tool calls").
- For rizzy-harness: if you allow hooks to rewrite arguments, re-run schema validation and re-authorise after the rewrite.
- Confidence: read the definition. (checked in review)

#### The shipped example gates are advisory text matching
- What the code does: `permission-gate.ts` blocks a bash command only if one of three regexes matches (`rm -rf`, `sudo`, `chmod/chown ... 777`), asks through `ctx.ui.select`, and blocks by default when there is no UI. `protected-paths.ts` blocks `write`/`edit` whose `path` string contains `.env`, `.git/` or `node_modules/`. Neither parses shell, resolves paths or follows symlinks, and neither covers `bash` for the path rule.
- Trace: [permission-gate.ts#L10-L33](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/examples/extensions/permission-gate.ts#L10-L33); [protected-paths.ts#L10-L30](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/examples/extensions/protected-paths.ts#L10-L30).

- Confidence: read the definition. (checked in review)

### Project trust gate

#### Resolution order, as implemented
- What the code does: `resolveProjectTrusted` returns the CLI override if given (`--approve` / `--no-approve`). If the folder has no trust-requiring resource it returns the saved decision or true. Otherwise it first lets user-level and CLI extensions answer through the `project_trust` event (first yes/no wins, `undecided` falls through, a throwing handler is skipped with a warning), then the saved decision for the folder or its nearest saved parent, then `defaultProjectTrust` (`always` true, `never` false, `ask` prompts). With no UI and `ask`, the answer is false.
- Trace: [project-trust.ts#L47-L97](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/project-trust.ts#L47-L97); handler loop [runner.ts#L302-L329](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/extensions/runner.ts#L302-L329); default `"ask"` at [settings-defaults.ts#L30](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/settings-defaults.ts#L30); `defaultProjectTrust` read from the global settings only ([settings-manager.ts#L1020-L1023](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/core/settings-manager.ts#L1020-L1023)); the UI flag is true only for the initial runtime in interactive mode ([main.ts#L819-L833](https://github.com/earendil-works/pi/blob/91d9719b4123a83816249d7a7917c75126bb55af/packages/coding-agent/src/main.ts#L819-L833)).
- Edge cases and failure handling: extension errors leave the decision to the later steps, so the failure outcome is "ask" (or deny headless) unless the user set `always`. An extension handler can return `remember: true` to persist its answer.
- Round 1: `confirmed` (order: CLI override, extensions, saved decisions, `defaultProjectTrust` default `ask`; headless `always` loads, `ask`/`never` skip).
- For rizzy-harness: the decision lives entirely on the local machine and project-controlled settings cannot set `defaultProjectTrust`; copy that property (a repo must not be able to relax its own trust prompt).
- Confidence: traced end to end. (checked in review)

#### What trust gates, and what it does not
- What the code does: "trust-requiring" means `.pi/{settings.json,mcp.json,extensions,skills,prompts,themes,SYSTEM.md,APPEND_SYSTEM.md}` under the working directory, or a `.agents/skills` directory in the cwd or any ancestor (the user's own `~/.agents/skills` excluded). ### The codemode sandbox

#### Isolation mechanism: QuickJS compiled to WebAssembly, one worker thread and one wasm instance per script
- What the code does: model-written JavaScript is evaluated by `quickjs-wasi` (pinned `3.6.2`) in a fresh worker thread. The WASI imports the VM gets are replaced by `discardOutput` (engine writes to fd 1/2 are swallowed) and, in deterministic mode, virtual clock and PRNG functions; no file, socket or environment imports are supplied in this code. The only host functions are the `bridge` calls `call`, `global`, `output`, `done`. All data crosses as JSON strings. Before the script runs, the prelude freezes every object reachable from the built-ins (`Object.freeze`, read-only globals, "override mistake" accessors), so a script cannot patch `Array.prototype.toJSON` to corrupt what is reported to the host. The host stops a script by setting a shared interrupt flag the VM polls (also between batches of 50 promise jobs) and then calling `worker.terminate()`.

### Remote execution: pi-env

#### Process model and wire protocol: a stdio daemon started over SSH, framed binary protocol, no authentication layer

### pi-durable: crash-surviving runs

#### What is persisted and how a run resumes
- What the code does: every conversation entry, model turn, task state and tool call is a transactional commit to a storage back end (memory, IndexedDB, JSONL, SQLite, "store"). Work is modelled as tasks with a checkpoint state (`pending`, `running`, `waiting`, terminal). On `open()` the scheduler scans all live tasks, marks each as resumed and, for tasks whose state was `running` (cut off by a crash), rewrites them to `pending` with `restarts + 1` in one transaction. `resume()` (or any submit/wait) enables scheduling. A close is not counted as a crash: closing returns running tasks to `pending` without incrementing `restarts`. A read-only open recovers nothing.
