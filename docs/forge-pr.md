# Opening a pull request in a project's forge repository (X.27)

Status: built (branch `feat/pr-create`, 2026-11-24).
Row: [`plan/X.27.md`](plan/X.27.md). Threat row: [T102](threats/T102.md). It builds on the push tool ([`forge-push.md`](forge-push.md), T101) and the repository listing (T83).

## 1. Tool or button

The owner approved "the push and open-PR tool". Before building, the question the brief asked: is a button the person presses after a push the better product?

What the others do (research `round1/claude-code.md`): Claude Code's terminal agent opens pull requests itself with `gh pr create` or `glab mr create`, under its permission rules (auto mode allows pull requests on the working repository); its web client has "Create PR" and "Create draft PR" buttons on the session's changes card; its Slack app ends with a "Create PR" button that opens the forge's compare page. Codex's desktop diff pane commits, pushes and opens pull requests by the person's hand (`round1/codex.md`).

A button would be simpler and safer: the person's own request would carry the title and description they see and edit, so there is no agent-written request to bind to a card and no click-binding class to get right (four findings on push's card came from that class). Its cost: the person writes or edits the description, or the agent's draft has to reach the form some other way (a message they copy, or a draft-only tool, which is a tool again).

The tool is still worth it here, because what it adds is the point: the agent writes the description from the work it just did and opens the pull request in the same flow as its push, and the person approves one card that shows exactly what will be sent. The binding it needs is small on top of push's: the master creates the pull request from the input of the one `tool_call_started` the approval names in its own mirror, and the page draws that same event. So the tool is built; a button ("Open pull request" in the side panel after a push, with an editable form) is a possible addition, not a replacement.

## 2. Decisions (the session lead's of 2026-11-24; each may be overruled by the owner)

1. It runs on the master as a built-in service: the node shows the card and files `forge.pull_request` with the approval id only; the master takes the scope from the session (the owner, the project's `source`, the target it named for the turn: the owner's newest connection for that host), makes the forge calls with the sealed token through the listing's client, and answers. The token never goes to the node for this tool.
2. The click approves the content: the master acts only against an Allow it relayed itself from the signed-in owner, for an approval id that is unique in the chat's log, within the id rule, whose one call is a `pull_request` call, once; and it creates the pull request from that call's input as its own mirror holds it, not from the approval event's own `input` field (which a node can set apart from what the page draws) and not from anything the node sends after the click (the request carries nothing else).
3. Only the project's recorded source repository: head and base are branches of it (no forks, no other repository). Branch names by `valid_branch` (push's rule). A missing base is the forge's default branch, asked with one GET after the Allow; no network call before it.
4. Bounds: title 1 to 256 characters, one line; body up to 20,000 characters; no control characters but newline and tab in the body; hidden and bidirectional characters are shown on the card (the page's `showHidden`) and sent as they are; 5 per chat per hour; one request at a time per chat (shared with push).
5. Who: as push. Only the chat's own agent in a turn its signed-in owner started; never a sub-agent, a routine, a callback turn, a forked, temporary or foreign-marked chat, or an API-token or webhook turn; refused in plan mode. The node's say: node.toml's `[forge] push = false` withholds pull requests too (it is the operator's "this node sends nothing to a forge"; the session lead's decision of 2026-11-24, overridable by the owner), and `denied_tools = ["pull_request"]` withholds only this tool; either way the node does not announce `forge-pr` and the tool is not offered.
6. Forges: GitHub `POST /repos/{owner}/{repo}/pulls`, GitLab `POST /projects/{id}/merge_requests`, Gitea and Forgejo `POST /repos/{owner}/{repo}/pulls`, at the host entry's `api_base`. A draft is GitHub's `draft`; GitLab's `Draft: ` and Gitea's and Forgejo's `WIP: ` title prefix. The draft prefix is not added when the title already starts with a draft mark, and a title that would then pass the forge's 255 characters is refused, not cut. The forge's refusal (`message`, `errors[].message`) is returned cleaned, without the token, cut to 300 characters; an "already exists" answer says so, with the open pull request's number and address from one bounded lookup (GitHub `GET /repos/{o}/{r}/pulls?head={owner}:{head}&base={base}&state=open`, GitLab `GET /projects/{id}/merge_requests?source_branch=&target_branch=&state=opened`; none for Gitea and Forgejo, whose API this server does not query that way: the number only when the text names one). The address is passed on only when it is https, with no user name or password, on the project's own source host as the URL parser writes it (lower case; a trailing dot is another name), on the default port or the port the host entry's `api_base` names on that same host (`[forge] hosts` names carry no port; a self-hosted forge on `:3000` serves its pages there too), and at most 300 bytes as written (so the cleaning of the answer, which cuts at 300, never cuts it); otherwise the result names the number only. The result goes to the model as text and to the page through the tool card, which draws it as plain text (`<pre>`, no link is made).
7. Its own per-agent switch, "Open pull requests", on for Software Developer and Senior Teamlead, by explicit name for others, never through `tools: all`.
8. No schema change, no new dependency, no `unsafe`, no event kind change.

## 3. What was generalised from push

`crate::forge_push::release` (master) is now the one set of checks for both master-released forge actions: the node runs the session and announced the tool's capability; a top-level, non-temporary chat; one request of the chat at a time; the relayed Allow once; the approval and its one call both naming the tool, each id unique and within the rule; the chat's target and owner unchanged; the open turn not a callback, the tool not withheld, the agent's switch on; no one else acted in the chat; the owner's account, level and membership now; the project's source, the host and the connection unchanged; the hourly room per tool. Push then opens the token; the pull request reads the call's input. The click record (`note_push_click`) takes either tool's card; the per-turn target (`MasterContext::push`) is named when the agent may use either tool on a node that offers it, and says `pull_requests: true` only when the master offers this tool (the node announced `forge-pr` and the agent names `pull_request`). In `release` the card's tool is checked against the request's before the click is taken, so a request for the other tool spends no click (review R1). On the node, the target is kept when either tool is allowed and each tool not allowed is withheld (`forge_for_turn`); `pull_request` needs the target's `pull_requests`.

## 4. The card

Each part and where it comes from:

- **Destination line**, from the master (`GET /api/sessions/{id}/push-target`, the project's recorded source and the connection it named for the turn): "Opens a pull request in `host/owner/name` as `login` (as the server knows it)"; without it only Deny.
- **Base**: when the call names none, "Into the repository's default branch (asked from the forge after you allow)", drawn by the page from the call's input (no `base` key); the master asks the forge after the Allow.
- **head, base, title, body, draft**: the call's own input, the `tool_call_started` the master reads to make the request, drawn by the page's generic call fields as raw text (hidden characters shown as codes). The body is Markdown the forge will render (mentions, `Closes #n`, images fetched by each viewer); the card does not render it.
- **Not drawn**: the approval's `reason` and `preview` and anything else the node wrote (review R6, the session lead's decision): the card says what it does from the master's record and the call's input.
- **Collapsed text**: a long field is cut in the middle; while any cut part has not been shown once, the card offers "Show all to allow" in Allow's place (a focusable button described by a note saying how many characters are collapsed); pressing it shows them, and the Allow that appears waits the card's 700 ms guard so the same click doubled does not answer. Deny never waits for it. The same holds for push's card.

Invalid cards (mismatched tools, reused or out-of-rule ids) offer only Deny, as for push. Seen in a real browser: `web/e2e/forge-card.cjs` (seeded source and connection rows, the demo provider's scripted call, Deny only: no forge is contacted).

## 5. The wire with older masters and nodes

- **New node, older master.** A node sends `forge.pull_request` only from `run_pr`, which runs only when the turn's target says `pull_requests: true`; only a master with this service writes that field (`forge_push::decide`, when the node announced `forge-pr`). An older master's target has no such field, so the tool is withheld for the turn (`forge_for_turn`) and refused at `run_pr`: an older master never sees the message. Test: `a_target_without_pull_requests_offers_none` (node).
- **Older node, new master.** An older node does not announce `forge-pr`, so the master never sets the field, and `skip_serializing_if` leaves it out of the target: the older node's `PushTarget` (`deny_unknown_fields`) reads the target as before. It has no `pull_request` tool and its push is unchanged. Should one send `forge.pull_request` anyway, `release` refuses it (no `forge-pr` capability). Tests: `the_target_says_whether_pull_requests_are_offered`, `a_node_that_did_not_announce_the_tool_gets_nothing` (master).

## 6. What remains

A compromised node that runs the chat can still make the agent's request say what it likes; the person sees exactly that on the card, and the master sends exactly that. The forge's default branch and the existence of the head branch are the forge's word. The pull request's address is shown as text. The node's `[forge] hosts` list does not limit pull requests (the master makes the call to the project's source host, which the server's own host list allows); the node's say is `push = false` and `denied_tools`. Gitea and Forgejo's "already exists" gives no number (their text names internal ids). The GitLab and Gitea/Forgejo request shapes are tested against a stand-in written from their API documentation as known, not against the real forges. No fork pull requests, no reviewers or labels, no update of an open pull request.
