## Change

**Done (branch `feat/A.21-control-under-load`; PLAN.md T9, `node/src/outbox.rs`): parts (a) to (d) as written, and a fifth the row did not have.** (a) The command loop never waits on the link: the acks of its inline commands are queued without waiting. (b) Those acks, and only those, go in a lane ahead of the queued output (at most 64 kept, past that dropped; at most 8 in a row while output waits, so a flooding master cannot starve it); every lane command's ack, a create's among them, stays in order behind its events. (c) The ordered queue is 256 messages and 1 MiB (a larger message goes alone); a feeder hands one message at a time to the link's channel of one, so ahead of an ack there is at most the message in that slot and the frame being written; `session.snapshot` batches are cut at 512 KiB instead of 2 MiB for the same reason. (d) `coalesce_led` keeps polling the tool and the cancel while a batch's append waits, and reads no more output meanwhile. (e, new) The node's socket holds at most 128 KiB unsent (`TCP_NOTSENT_LOWAT` through `socket2`, already in the tree with that feature through tokio): without it the kernel's autotuned send buffer is ahead of every ack whatever the node's queue does (up to `tcp_wmem`'s maximum, 4 MiB here, 16 s at 256 KiB/s; measured with the lane alone: 8.9 s, with the cap 1.0 s).
Also: the command loop never waits for the store: it acts, acks, then hands the audit line to one writer task (a queue of 1,024; past it, or when the store refuses a write, lines are counted and the count is recorded as one `audit.not_recorded` line), an inline command for a session with neither a session nor a lane is refused at once, and at most 256 sessions have a lane, the refusals past it (and past a lane's depth) going ahead of the queued output (review A21-1, A21-2, re-check D-1: the first version wrote audit lines in the command loop past 64 pending, so a Stop waited for a slow store, and a cancel for an unknown session cost a task each).
Rejected: making appends never wait and the link a reader of the log (the store as the overflow): it removes the back-pressure that keeps an agent within the queue of what the person sees, so a Stop would stop something minutes ahead of the screen; it needs per-session catch-up ordering against lane acks and replays; and it does not touch the kernel's buffer, which the target needed.
Differs from the done-when: the timeout test uses the node's ceiling of 15 s (the default 60 s made it a 66 s test) and "full" is read from the node's log, not the channel, whose depth (c) changes.
Tests (each failed on the code before, run 2026-11-14, except B.7's control, which passed then too): `node/tests/control_under_load.rs` (B.7's three and their control, un-ignored; a trickling uplink; the create's order and the Stop's lane; a flooding master) and `control_over_link.rs` (the link test, rebuilt on the real node over the real link at 256 KiB/s: Stop and approval answer acked after 1.0 s, before A.21 20.1 s).
Residual in T9: a stopped turn's end still waits behind its session's queued output (about 4.5 s at 256 KiB/s); one large event or the master's own slowness can still hold an ack; acks that stay in order (create, prompt, delete, restore) pass the 15 s `ACK_TIMEOUT` below about 75 KiB/s (review A21-5); a frame the uplink cannot carry in 60 s now drops the link (A21-6).
After the independent review of `8c28173` (findings A21-1 to A21-9): the command loop no longer waits for the store (one audit writer), inline commands for unknown sessions are refused at once and lanes are capped at 256, output piled up behind a waiting append goes out in batches, `Store::call` returns `StoreError::Stopped` instead of panicking at shutdown, `control_over_link` holds the acks under 3 s and `link/tests/unsent_limit.rs` reads the socket option back, and the tests read "full" from `NodeRuntime::backlog`.
**Follow-up, not built:** the back-pressure is node-wide, not per session; a per-session round-robin ordered lane would keep it and give fairness to normal events and creates.**
**A Stop, an approval answer and `stop_background` take effect on the node and are acknowledged within the grace, whatever the uplink carries.** (a) The node's command loop never waits for room in the out queue before it reads the next command. (b) The acks of the inline commands (cancel, approval answer, `stop_background`) go ahead of queued output, and only those: `create_session` relies on a create's ack arriving after its `session_created`. (c) The out queue is bounded in bytes as well as messages. (d) (The builder's addition, for the owner to confirm: (a) to (c) do not reach the first test below, whose hold is in the agent loop.)
The agent loop keeps polling the tool, the cancel and the timeout while an emit waits for room (fix sketch part 1 in B.7's result), so a Stop and a timeout end a streaming command whatever the out queue holds.
