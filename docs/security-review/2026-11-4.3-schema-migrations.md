## 2. Findings

### R43-1 (high): Foreign keys are ON while a migration runs, so a table-rebuild migration silently deletes every row that references the table

Bundled SQLite is compiled with SQLITE_DEFAULT_FOREIGN_KEYS=1 (libsqlite3-sys
0.39.1 build.rs:171), and migrate() runs before Store::init sets anything, so
foreign keys are enforced inside the migration transaction. A migration cannot
turn them off: the pragma is a no-op inside a transaction. The first post-tag
migration that changes a table the way SQLite documents it (create new, copy,
DROP old, rename), for example adding a UNIQUE or NOT NULL to `users`, runs an
implicit DELETE on the old table. That cascades through every ON DELETE
CASCADE child: ui_sessions, workspaces.personal_owner, workspace_members,
blobs, artifacts, media_items (crates/store/src/lib.rs:366-408, blobs.rs:17,
artifacts.rs:19, media.rs:17). The migration reports success, bumps the
version and commits. No test catches it, because check_recorded only migrates
empty databases. rusqlite_migration, the crate that was rejected, documents
this trap and ships `foreign_key_check()`; the own runner dropped it.

Proof: sh crates/cli/tests/support/review_4_3/run_rust_proofs.sh finding_f1
(log: target/tmp/review_4_3_proofs.log) -> `F1: foreign_keys on a fresh
connection, before migrate = 1` / `F1: after migration 2: version 2, users 1,
blobs 0 (was 2)`; test
finding_f1_a_table_rebuild_migration_deletes_the_rows_that_reference_it
passes, i.e. the child rows are gone and migrate() returned Ok.

Asked for: In migrate(): read `PRAGMA foreign_keys`, set it OFF before BEGIN
IMMEDIATE, run `PRAGMA foreign_key_check` before the version bump and return
Failed if it yields a row, then restore the previous value after commit or
rollback (SqliteMemory::init never sets it, so the runner must restore it
itself). Add two tests: a rebuild migration keeps its child rows; a migration
that leaves a dangling reference fails and leaves the file byte-identical.

### R43-2 (medium): Version 1 is a stamp, not a fact: stale and edited-in-place schemas pass as version 1, and at the tag they are indistinguishable from a released version 1

Three cases, one cause: the runner trusts the number and never looks at the
schema. (a) Regression against main: until the tag, PLAN.md §0 says migration
1 is edited in place. On main an added table or index reached every dev
database on the next open through IF NOT EXISTS. Now a database stamped 1 gets
nothing and no message, and the first sign is `no such table` at some query or
a silently missing index. Task 4.5 is next and edits the schema. (b) A
version-0 file with old-shaped tables is stamped 1 whatever it contains (the
builder's own weak spot). (c) At the first tag every pre-tag directory,
including any pulled pre-release image's, carries version 1 with whatever
schema its commit had. The tagged build accepts it as release v1 and later
runs migration 2 on top of it. The runner has no floor and no way to say 'pre-
release database, wipe it', and the T39 residual mentions only version 0, not
the version-1 files this change creates. On the builder's question: refusing
version 0 with tables buys nothing by itself while migration 1 is still edited
in place; the check has to be against the schema.

Proof: run_rust_proofs.sh finding_f3 -> `F3: objects of the edit present: 0 of
2; first use: no such table: added` (running the same statements main's way
then succeeds). run_rust_proofs.sh finding_f4 -> `F4: version 1 ; schema
equals schema/1.sql: false` (Store::open accepted a file whose `nodes` table
has one column and stamped it 1).

Asked for: Smallest acceptable: PLAN.md §0, T39 and the README say that from
this change on every pre-tag schema edit, additive ones included, needs a
wipe, and that the tag commit must make pre-tag files refusable; give the
runner a way to do that (an oldest-supported floor with its own error, raised
at the tag). Better, and it uses what was already built: on open, and inside
the migration transaction after migration 1, compare schema_text(conn) with
the recorded schema/<version>.sql (include_str!) and refuse a mismatch with
'does not match schema version N (a pre-release database or another file); not
changed'. That closes (a), (b), (c) and the T39 residual about a memory.db
copied over a node.db, with no upgrade code. FTS5 shadow tables should be left
out of that comparison.

### R43-3 (medium): Nothing half-applied holds per file, not per data directory: one database migrates, the next fails, and then neither the new nor the old build starts

`serve` opens master.db (main.rs:300), node.db (:632), memory.db
(master/src/providers.rs:366) and chat.db (:353) one after another, each
migrating and committing on its own. If master.db migrates and node.db or
chat.db then fails (a full disk, or a migration that trips on that file's
data), the new build fails on every start and the previous build now refuses
master.db as newer. The builder's 'impossible to half-apply' and T39's 'leaves
the file as it was' are true per file and silent about the directory. Related,
on the real binary: a newer chat.db is refused only after master.db, node.db
and memory.db were created or migrated and the local node's runtime had
started on node.db. The version check comes late and one file at a time.

Proof: run_rust_proofs.sh finding_f2 -> new build: `chat.db: migrating the
schema from version 1 to 2 failed in migration 2; nothing was changed: UNIQUE
constraint failed: t.a`; old build: `master.db was written by a newer rizzy-
harness (schema version 2; this build knows up to 1)`; versions (master, chat)
= (2, 1). Real binary: sh
crates/cli/tests/support/review_4_3/real_binary_refusal.sh target/debug/rizzy-
harness (log target/tmp/review_4_3_binary.log) -> with only chat.db at version
2: exit 1, chat.db sha256 unchanged, but `master.db: user_version 1`,
`node.db: user_version 1`, `memory.db: user_version 1` all newly written, plus
sandbox-tmp and artifacts-stage.

Asked for: A preflight right after the data directory lock: read user_version
of every database this role opens and refuse on any newer one before anything
is created, migrated or swept. T39 residual and the Failed message state that
the databases migrated earlier in the same start stay migrated and the
previous build will refuse them. Note on FIX_PLAN 4.4 that a copy before
migrating is what makes a failed upgrade reversible. No cross-file atomicity
is asked for: SQLite cannot give it in WAL mode.

### R43-4 (low): A migration runs without a word in the log

The moment a data directory becomes unreadable to the previous build is not
logged: migrate() has no logging and returns (), and neither Store::open nor
the CLI says anything. A long migration of a large event log holds start-up
with no output and looks like a hang; a person who kills it loses nothing, but
they are never told what it was doing or that a downgrade is now refused.

Proof: by reading only: `git grep -n "tracing\|info!" --
crates/store/src/migrate.rs crates/store/Cargo.toml` returns nothing; the
real-binary log shows no migration line when master.db, node.db and memory.db
went from absent to version 1.

Asked for: migrate() returns the (from, to) it applied, and the callers log
one info line before and after, naming the file and both versions, when from
!= to and from != 0.

### R43-5 (low): 'A second process waits and then finds it migrated' holds only inside the 5 s busy timeout; the claim is untested and failed when measured

The second opener waits at most busy_timeout (5 s) for the write lock and then
fails with `reading or writing the schema version: database is locked`. It
fails closed and nothing is damaged, and the data directory lock is the real
guard, but T39 and migrate.rs:17-21 state the wait as a property. Any real
migration of a large log takes longer than 5 s, and so did plain commits on
this machine's disk under load (1.7 to 3.5 s each). The message also blames
the schema version for what is lock contention. It is still far better than
main's order, which failed 60 of 72.

Proof: run_rust_proofs.sh race_taken_apart (log
target/tmp/review_4_3_race.log) -> `[fresh file, staged, WAL after]: 10 failed
opens of 72`, all `BEGIN IMMEDIATE: database is locked`; `[fresh file, main's
Store::open]: 60 failed opens of 72`. run_rust_proofs.sh race_timed -> `BEGIN
IMMEDIATE failed after 5003ms` for 5 of 6 openers on a fresh file and 4 of 6
on a WAL database one version behind, next to `COMMIT Ok(()) 3536ms`.

Asked for: Reword T39 and the module comment: a second opener waits up to 5 s
and is then refused unchanged; the data directory lock is what keeps a second
process away. Give a failed BEGIN IMMEDIATE its own message (another process
holds the database).

### R43-6 (low): HARNESS_WRITE_SCHEMA=1 rewrites every recorded file, released ones included, and the recorded text contains DDL that SQLite generates

Write mode overwrites 1.sql..N.sql in one go, so after the tag the guard for a
released migration is one environment variable away from being reset together
with the new version's file, and the diff is hidden among 600 lines. The files
also record FTS5 shadow tables (crates/store/schema/1.sql:5-15, `CREATE TABLE
'artifact_fts_config'(k PRIMARY KEY, v) WITHOUT ROWID`), text that the bundled
SQLite produces, not the migrations. A rusqlite bump that changes it fails the
guard with no migration changed, and the only remedy offered is rewriting a
released file. The check also compares schema only: a released migration whose
data statements change (a backfill UPDATE) passes.

Proof: by reading only (migrate.rs:155-163: `if write { ...
std::fs::write(&file, &now) ...; continue; }` for every k;
crates/store/schema/1.sql lines 1-15).

Asked for: Write mode creates only files that do not exist and compares the
rest; rewriting 1.sql before the tag means deleting it first. Leave SQLite-
made shadow tables out of schema_text, or record a hash of each migration's
SQL beside the schema.

### R43-7 (low): Tests: one half cannot fail, the 'before any write' order is not pinned, and three 'failed on the old code' claims are misreported

(1) The 'migrating matches fresh' half of
every_version_matches_its_recorded_schema_and_migrating_matches_fresh runs
zero times today (`for k in 1..steps.len()`, migrate.rs:179) and, once it
runs, compares two replays of the same list on empty databases. It cannot fail
unless a migration is non-deterministic, yet the FIX_PLAN row's 'done when'
leans on it. (2) T39 says the check runs before any pragma writes, but every
refusal test builds its newer file through Store::open, so it is already WAL:
main's order (journal_mode=WAL first) would pass them all. Only my real-binary
run covers a rollback-mode newer file. (3) The report says the newer-build and
failing-migration runner tests failed on 7d663a2 because the file 'was opened,
not refused' and 'no error was returned'. The builder's own
target/tmp/fail.log shows all three (lines 74, 94, 111) failed on `table t
already exists`, because the placeholder re-ran V1, which has no IF NOT
EXISTS. They did fail first, but not for the property they name. The Store-
level and memory tests failed for the right reason. (4) migrations.rs:3 points
at crates/memory/tests/memory.rs; the tests are in schema.rs.

Proof: target/tmp/fail.log (builder's): `panicked at
crates/store/tests/migrations.rs:111:18: Sqlite { db: "test.db", source:
SqlInputError { ... msg: "table t already exists"` and the same at 74:5 and
94:5. Rest by reading only. Tests unchanged between 7d663a2 and HEAD (`git
diff 7d663a2 HEAD --stat -- crates/store/tests crates/memory/tests` is empty).

Asked for: Rename the test to what it checks, or drop the loop. Add one
refusal case whose newer file is in rollback-journal mode (create it with a
raw connection, never through Store::open). Correct the comment at line 3.

### R43-8 (note): One migration list for three databases with different owners

master.db (accounts and the mirror), chat.db and node.db (the node's event
log) share harness_store::MIGRATIONS. A master-only change, say to `users`,
bumps node.db's version on every node. A node build rolled back afterwards is
then refused over a table the node never reads (docs/node-update.md §6.3), and
node.db and chat.db carry the account tables as dead weight in the baseline
(FIX_PLAN.md:182 wants the baseline free of dead tables). This is cheap to
split before the tag and a migration per role after it. Not this step's to
change, but the owner should decide before v0.1.0.

Proof: by reading only

Asked for: None required for this step; record the decision (keep one list, or
one per role) in PLAN.md §0 before the tag.

## 4. Claims with no test at the first review

- A real disk-full (ENOSPC from the file system) during COMMIT: I simulated
  full with max_page_count, which fails inside a step, not at the commit's
  fsync. A commit failure is reported as `reading or writing the schema
  version`, not as Failed with 'nothing was changed'.
- Two processes (not threads) racing a migration, and a file system without
  flock, where the data directory lock is skipped: measured with threads on
  ext4 only.
- A migration that needs Rust code: `Migration` is SQL text only, so the first
  non-SQL step means changing the type.
- A newer build's database left with a hot journal or an unchecked-pointed WAL
  after a crash: the older build's refused open would still run SQLite's
  recovery or checkpoint on it, so 'byte-identical' holds only for cleanly
  closed files. Not tested.
- Whether rusqlite_migration 2.7.0 meets the two-week rule: could not be
  checked offline (the builder said the same); moot as it was not adopted.
- That a rollback of a node auto-update across a schema bump ends in a node
  that will not start (docs/node-update.md §6.3): by reading only, auto-update
  is not built.
- The builder's 'failed on the placeholder' claims for the two memory tests:
  no log of that run is in target/tmp; plausible by reading the placeholder.

### D1 (medium): The read-only preflight refuses, on every start, a database of this build whose first creation was interrupted; Store::open on the same files recovers it

A fresh database is in rollback-journal mode until `journal_mode = WAL` runs
after migration 1. If the process dies while that first commit is being
written (kill -9, OOM kill, power cut, `docker kill`; the commit's fsync took
1.7 to 3.5 s on this disk in the first review), master.db has pages and
master.db-journal is hot. Before this fix the next start's Store::open rolled
the journal back and created the database. Now check_schemas
(cli/src/main.rs:1152) runs first, check_file opens SQLITE_OPEN_READ_ONLY,
SQLite cannot roll a hot journal back through a read-only connection
(SQLITE_READONLY_ROLLBACK, 776), and the start ends with `master.db: reading
or writing the schema version: attempt to write a readonly database`. It is
permanent: every later start fails the same way until someone deletes the
journal or the file by hand, and the message says neither what happened nor
what to do. Same for node.db, chat.db, and for a memory.db created for the
first time in a directory whose master.db already holds accounts and chats
(memory backend switched to builtin). T39's residual mentions only a NEWER
build's hot journal ('should fail closed', untested); this is the build's own
file and a regression against main.

Asked for: In check_file, treat extended code SQLITE_READONLY_ROLLBACK as
'cannot be judged read-only' and return Ok, so the real open rolls the journal
back and then applies the same version and schema checks (for a newer build's
file that rollback is the recovery the newer build would do itself; say so in
T39 instead of 'should fail closed'). Test first: the crash image (migration 1
in an open transaction with cache_size = 10, both files copied) must pass
check_file and then open at version 1.

### D2 (note): 'Nothing is written' and 'only `lock` beside it' do not hold for the kind of file the harness itself writes: the preflight leaves a -wal and a -shm beside every WAL database

A read-only connection to a WAL database creates <db>-shm and an empty
<db>-wal and cannot remove them on close. On a refused start they stay beside
the newer file. Harmless (the database's bytes are unchanged and the newer
build opens it), but migrate.rs:165 ('nothing is written') and T39 ('before
anything is created') overstate it, and the CLI test asserts the directory
listing only because its newer file is made with a raw connection in rollback
mode.

Asked for: Reword the comment and T39 to 'the database file is not changed
(SQLite may leave an empty -wal and a -shm beside a WAL database)', and give
the CLI test one case whose newer file went through Store::open (WAL) with the
expected list widened accordingly.

### D3 (note): The README tells the reader to wipe the data directory after a refusal that the program answers with 'run that build or a newer one'

The new paragraph names two refusals (a database a newer build wrote, and one
whose tables are not its version's) and then says 'such a refusal means: wipe
the data directory'. For the first case, a downgrade or a rolled-back update,
wiping is the wrong advice and destroys data the newer build can still open;
TooNew's own message (migrate.rs:42-44) says to run the newer build.

Asked for: Split the sentence: a newer build's database means run that build;
a schema mismatch before the first tag means wipe.

### D4 (note): A reference that dangled before the migration fails every later migration, and the error blames the migration

foreign_key_check runs over the whole database, not over what the migration
touched. One row orphaned earlier (a user deleted with the sqlite3 shell,
whose foreign keys are off by default, or a future bug) makes every upgrade
fail with 'migrating the schema from version N to M left rows of blobs
pointing at missing rows of users', although the migration never touched
either table. Fail-closed and the same choice rusqlite_migration makes, but
the wording sends the reader to the wrong place and there is no way forward
short of editing the database by hand.

Asked for: Run the check once before the first step too and, if it already
reports a row, fail with a message that says the reference was dangling before
the migration (name table and parent); or word the one message so it does not
claim the migration caused it.
