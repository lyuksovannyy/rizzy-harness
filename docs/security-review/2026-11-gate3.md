## 2. Findings, by severity

### S-1. Critical. A sub-agent's shell makes the node's own git run a command outside the sandbox

Severity: a prompt-injected model gets code execution as the node's OS user, outside
Landlock, with the data directory (node key, and on the embedded node the API token,
`secrets.toml` and `master.db`) in reach; in `auto` mode no person is involved.

- Adversary: a prompt-injected agent (1).
- Needs: the session's agent can delegate to a sub-agent with `bash` (the built-in Teamlead
  and Software Developer), and the folder is a git repository.
- Sequence:
  1. The parent delegates. `Session::isolate` (`crates/node/src/session.rs:1347-1408`) calls
     `check_worktree_safe` once (`:1370`, and again inside `worktree_add`,
     `crates/node/src/git.rs:1935`), then makes the worktree in `<repo>/.git/harness-worktrees/<id>`.
  2. The child's shell is granted read-write on all of `<repo>/.git`
     (`crates/tools/src/sandbox.rs:369-372`). It runs
     `git config filter.x.clean <command>` (this writes `<repo>/.git/config`) and
     `echo '* filter=x' > .gitattributes`.
  3. The child ends. `merge_back` (`session.rs:1413-1447`) snapshots the worktree with
     `Repo::project` (`:1415`). That is the user's repository with its own config and the
     worktree's attributes: `stage_without_nested` runs `git add -u` and
     `update-index --add` (`git.rs:834`, `:842-848`), then `write-tree`. Nothing looks at the
     config again. Git runs the clean filter. This git is a direct child of the node
     (`git.rs:154-191`), not started through `sandbox-exec`.
  4. `git::apply` (`git.rs:1968-1998`) then runs `diff` and `apply` in the main folder under
     the same config.
- A parent session can do the same without a child's help: its own shell may write
  `<repo>/.git/config` (R2 records that), and a process it left running (the recorded
  `setsid` survivor) can add the filter after the check and before the snapshot.
- Established: **proven by test.** `review_s1_a_sub_agent_makes_the_nodes_own_git_run_a_command`
  (`crates/node/tests/runtime.rs`): the filter's marker holds the command line of its parent
  process, `git -c core.fsmonitor=false -c core.hooksPath=/dev/null ... write-tree`, the node's
  own hardened call. `review_s1_a_sandboxed_sub_agent_writes_the_shared_git_config`
  (`crates/cli/tests/review_gate3.rs`): inside the real Landlock sandbox the child's
  `git config` succeeds and the main `.git/config` holds the filter. The two halves were
  proven separately, not in one run with Landlock on.
- Smallest fix: a config check before use cannot be made race-free. Take the sub-agent's base
  and result snapshots in a harness-owned git directory, as turn checkpoints do
  (`--git-dir <shadow> --work-tree <worktree>`, `GIT_ATTR_SOURCE` = empty tree,
  `core.attributesFile=/dev/null`), and build the patch from those, so no git call that
  stages or applies files reads the user's config. Also narrow the child's grant: read-write
  on `objects`, `refs`, `logs` and `worktrees/<id>` of the main `.git`, read-only on the rest
  (`config`, `hooks`, `info`).
- Threat table: T19 and T32. T19 says the config "is checked before anything runs there";
  T32's residual says the child "can still reach the parent's `.git`". Neither says the node
  then executes what was written. Worse than recorded.

### S-2. High. A sub-agent points its own folder at another folder; the file tools and the next shell follow

Severity: one shell command inside the sandbox gives the unsandboxed file tools, and then
the shell, any folder of the OS user except the data directory; `read` there needs no
approval in `ask` mode.

- Adversary: a prompt-injected agent (1), in a sub-agent with `bash` (or its parent, for it).
- Cause: a session's folder is trusted by name and resolved again on every call
  (`crates/tools/src/lib.rs:229-232`, `crates/tools/src/sandbox.rs:356-358`). The worktree's
  parent directory is inside the child's read-write grant (`sandbox.rs:369-372`). The per-turn
  re-check (`crates/node/src/policy.rs:281-286`) tests only the data directory, not
  `workspace_roots`.
- Sequence: `bash`: `cd / && mv <repo>/.git/harness-worktrees/<id> <same>.r && ln -s /home/u/.ssh <repo>/.git/harness-worktrees/<id>`.
  Then `read {"path":"id_ed25519"}` (no approval in `ask`), `write {"path":"authorized_keys"}`
  (the card shows a harmless relative path), and any later `bash`, which is now granted
  read-write on the link's target. With the link at `$HOME`, `write .bashrc` is code
  execution outside the sandbox at the user's next shell.
- Established: **proven by test**, `review_s2_a_sub_agent_points_its_folder_at_another_one`
  (`crates/cli/tests/review_gate3.rs`), real wrapper and real tools: the key is denied before
  the swap; after it `read` returns it, `write` creates `~/.ssh/authorized_keys`, and the next
  shell command reads the key and writes there.
- Smallest fix: keep the folder's canonical path and its device and inode at session
  creation; in `ToolCtx::resolve`, `Confinement::command`, `check_session` and
  `Stages::check` refuse when the path no longer resolves to itself or the inode differs.
  Do not grant a child write access to the directory that holds its own worktree (the
  narrowed grant of S-1 does this).
- Threat table: T4 and T32. The recorded residual is a race on an intermediate directory.
  This is no race and it is the workspace root. Worse than recorded.

### S-3. High. `core.worktree` in the session's own repository moves checkpoints and undo to any ancestor folder

Severity: one shell command in an ordinary session makes the node's unsandboxed git
snapshot, and on undo overwrite and delete, files outside the session folder and outside
`workspace_roots`.

- Adversary: a prompt-injected agent (1). No sub-agent needed.
- Cause: `repo_info` (`crates/node/src/git.rs:416-451`) takes the checkpoint root from
  `git rev-parse --show-toplevel` run in the user's repository. The only check (`:441`) is
  that the session folder is inside the root, which every ancestor satisfies. The comment at
  `:439-440` says a `core.worktree` cannot move the root; it can, upwards. `repo_for_with`
  (`:585`, `:636-640`) uses that root as `--work-tree`; nothing compares it with
  `workspace_roots` or `protected_dirs`.
- Sequence: `bash`: `git config core.worktree /home/u` (the session's `.git` is writable, R2).
  From the next turn on, every checkpoint stages `/home/u` into the checkpoint store. The
  `checkpoint{after}` event lists files that changed there during the turn (other projects,
  dotfiles), and those names go to the master. "Undo" of the turn, unforced, puts those files
  back and deletes new ones (`restore_paths`, `git.rs:1777-1838`). With the default data
  directory inside `$HOME` the root also contains the data directory; restore has no
  protected-folder check (shown by reading, not run). A large ancestor hits the 60 s snapshot
  limit every turn, so the session silently has no undo.
- Established: **proven by test**, `review_s3_core_worktree_moves_checkpoints_and_undo_out_of_the_session_folder`
  (`crates/node/src/git_review_gate3.rs`): the root becomes the parent, the change list names
  `other-project/notes.txt` and `.profile`, and the unforced restore reverts both and deletes
  a new file in the other project.
- Smallest fix: never take the root from git's configuration. Find the folder that holds the
  `.git` entry by walking up from the session folder, require `--show-toplevel` to equal it
  (else treat the session folder as a plain folder), and run the result through the same
  checks as a session cwd (`workspace_roots`, `check_protected`). Add the protected-folder
  check to `restore_paths`.
- Threat table: T19 ("trusted as data") and T33. None records it.

### P-1. High. The login cookie reaches every other port on the UI's host, so the agent's own server can answer approvals

Severity: one visit by the person to a page served by the agent's process (the dev server
they asked it to start) hands that process their login, and with it every approval.

- Adversary: a prompt-injected agent (1), or any other local web application.
- Cause: the session is one cookie, `HttpOnly; SameSite=Strict; Path=/`
  (`crates/master/src/auth.rs:652-659`), and it is the whole credential
  (`authenticate`, `auth.rs:740-764`). Cookies are not separated by port (RFC 6265 section
  8.5) and `SameSite` ignores the port. The second line of defence, `Origin`
  (`auth.rs:771-820`), is a header a non-browser client writes itself.
- Sequence: the agent runs a server on `127.0.0.1:8000` (TCP is allowed in the sandbox by
  default, T4). The person opens it in the browser that is logged in to
  `127.0.0.1:7777`. The browser sends the harness cookie. The agent's process reads the
  session's events for approval ids and posts
  `/api/sessions/{id}/approvals/{aid}` with the cookie and `Origin: http://127.0.0.1:7777`.
  From then on it approves its own calls. For an admin it can also mint join tokens and
  reset other users' passwords.
- Established: **shown by reading** for the server side (the lines above); the browser side
  rests on the RFC and was **not run** (no Playwright here). A run of a second listener on
  another port that prints the `Cookie` header would settle it.
- Smallest fix: bind the login to the origin, not only to the host. At login return a random
  value the page keeps in `sessionStorage` (per origin, port included), store its hash beside
  the session row, and require it as a header on every cookie-authenticated request and as
  the first WebSocket message. `network = "off"` as the default would close the agent's side
  of it and nothing else.
- Threat table: T2 and T4. Not recorded.

### L-1. Medium. A node names any chat as its session's parent and receives that chat's project context

Severity: a registered node obtains another project's instructions, board and recalled
facts from the master, but it must know a chat id in that project.

- Adversary: a hostile registered node (2) with one account that has a chat on it.
- Sequence: the node answers `session.create` with `session_created{parent_session: P}`.
  `Store::append` stores `parent_id` whatever it names (`crates/store/src/lib.rs:651-654`);
  only the owner adoption is limited to the same node (`:659`), and `claim_session` then sets
  the requesting user as owner. On the next prompt `projects::project_of`
  (`crates/master/src/projects.rs:279-304`) replaces the row with the parent's row with no
  check of node or owner, and `Master::prompt` (`crates/master/src/lib.rs:1295-1325`) sends
  that project's context to the node. `remember` proposals are filed into that project too.
- Established: store half **proven by test** (`review_l1_...`, `crates/store/tests/review_gate3.rs`);
  master half **shown by reading**.
- Smallest fix: in `project_of`, follow `parent_id` only when the parent has the same
  `node_id` and `owner_id`; in `append`, store `parent_id` only under the same-node rule.
- Threat table: T7, T20. Not recorded.

### L-2. Medium. A node moves a chat to another user with a second `session_created`

Severity: on a node's word alone the master shows one user's chat to another user and
hides it from its owner, against "never asserted by a node" (T10).

- Adversary: a hostile registered node (2), with or without a colluding account.
- Sequence: `session_created` is applied at any `seq` (`crates/store/src/lib.rs:636-672`).
  On Alice's chat the node appends `session_created{parent_session: <Bob's chat on this node>}`;
  `:659` sets `owner_id` to Bob. With an unknown parent the owner becomes NULL and only the
  API token can see or delete the chat. The same event rewrites `incognito` and `profile`.
- Established: **proven by test**, `review_l2_a_node_moves_a_chat_to_another_user`.
- Smallest fix: apply the row effects of `session_created` only at `seq == 1`, and never
  change `owner_id` once it is set.
- Threat table: T7, T10. The node already holds the chat's content; what is new is that the
  master serves it to another account.

### L-3. Medium. Node-supplied strings are stored without a limit and loaded by every listing

Severity: one registered node can make every user's session list allocate gigabytes, and it
survives a restart.

- Adversary: a hostile registered node (2).
- Sequence: `session_created` frames with titles of several MiB (`store/src/lib.rs:651-654`
  stores `title`, `cwd`, `model`, `agent_id` uncapped). `Store::sessions()` loads every row of
  every user before filtering (`crates/master/src/http.rs:1070`, also `projects.rs`,
  `workspaces.rs:533`).
- Established: **proven by test** for the store (`review_l3_...`); the callers **shown by
  reading**.
- Smallest fix: cap these fields at append (a few hundred characters), and cap an event's
  size where events are appended (already listed as open in `docs/security-node-link.md`).
- Threat table: T7, T8. The note records only that an oversized event breaks the link.

### L-4. Medium. A node revoked during its handshake stays linked

Severity: revocation is the control for a stolen key, and in a window of about a
millisecond it leaves the link up with nothing that looks again.

- Adversary: a hostile registered node (2) reconnecting in a loop while it is revoked.
- Sequence: `node_connection` reads the key (`crates/master/src/nodes.rs:180`), then
  registers the stop token and bridges (`:207-214`). `revoke_node` (`:57-66`) running in
  between finds no token to cancel. `add_link` and `send_command` never read `revoked_ms`.
  The node's events are refused (A.3), but prompts, context and images keep going to it and
  its acks count. The admin's node list shows it as revoked.
- Established: **shown by reading.** The race was not reproduced. A test that revokes and
  then calls `add_link` shows the missing check; a loop test would show the window.
- Smallest fix: after inserting the stop token, read `revoked_ms` again and cancel; refuse
  `send_command` to a revoked node.
- Threat table: T7.

### Note

- N-1. `outline` and the repository map run tree-sitter's C parsers on files of up to 8 MiB
  inside the node process that holds the keys (`crates/tools/src/outline.rs:53-66`). The PDF
  parser was moved out of process for this reason. No exploit shown.
- N-2. With `allow_outside_workspace = true`, `write` to `~/.bashrc` or `~/.gitconfig` is
  allowed; the sandbox and the protected folder do not help against that. The README should
  say so.
- N-3. The data directory is created with the umask and then chmod-ed, and the chmod error
  is ignored; ownership is never checked (T26 records the ownership part).
- N-4. `MasterCert::load_or_create` makes a new key pair on any read error
  (`crates/link/src/tls.rs:36-47`), which silently breaks every node's pin.
- N-5. A cancelled `send_command` leaves its `acks` entry; minting a join token is not
  audited; `approval_mode` and `model` at create are forwarded unchecked (the node clamps
  the mode).
- N-6. `read` vouches for URLs (`crates/agent-native/src/lib.rs:614`). Harmless while
  `web_fetch` and the file tools never share a runtime; ADOPTION_PLAN T.3 changes that.

## 3. What was checked and found sound

**A. Link and mirror**
- Node side, read in full by the reviewer (`crates/node/src/lib.rs`, `policy.rs`): every
  `MasterToNode` message. `Create`: profile must match the runtime, `check_cwd` canonicalises
  and tests the data directory and `workspace_roots`, the mode is clamped with `min`
  (`policy.rs:336-341`) and clamped again on load (`session.rs:155`). `Prompt`, `Restore`:
  the folder is re-checked (`session.rs:381`, `:895`). `ApprovalRespond`: looked up in the
  named session's own map and removed on first use (`session.rs:1482-1491`), so an id cannot
  be replayed or used across sessions. `Restore.turn_id` is only a map key, never a git
  argument. `ArtifactFetch`, `ArtifactStage`, `ArtifactRelease` go through the stage's own
  index. Lanes are bounded (64) and a full lane nacks.
- `Store::append` (read by the reviewer, `store/src/lib.rs:552-622`): revoked, tombstone,
  wrong owner, diverged, duplicate and gap are decided in one transaction, in that order;
  `seq` 0 and `u64::MAX` cannot store a row.
- By delegated reading: the handshake (signature checked before the join token is spent,
  one transaction, a revoked key cannot rejoin; a 256-bit nonce per connection bound to the
  certificate fingerprint; first frame must be `node.hello` for the authenticated id; chat
  profile refused for remote links); the client (`wss://` only, the leaf certificate pinned,
  no redirects, the token sent only after pinned TLS, a timeout on every step); acks bound to
  the node; artifact chunks routed by node and request id with offset, size and hash checks;
  frames capped at 8 MiB from the header; queue bounds; key files 0600 and checked at start;
  no lock held across an await in the link handling.

**B. Approval path**
- Read in full by the reviewer: `turn`, `run_tool`, `run_delegate`, `tool_specs`, `Logged`
  (`crates/agent-native/src/lib.rs`), `Session::approve`, `resolve`, `respond`, `emit`,
  `end_turn` (`crates/node/src/session.rs`), `call_key` (`crates/tools/src/approval.rs`).
  Every non-delegate call goes through `approve` with the input that is then run; a tool in
  `denied_tools` is denied before the mode is looked at; "for this turn" stores the SHA-256
  of this call only, the set is new for each turn and each sub-agent; an approval whose
  request or answer could not be logged denies; after one failed append nothing else runs
  and the token is cancelled; no call of a message cut by the output limit runs
  (`lib.rs:1225-1270`); a tool the agent's spec does not list is "unknown".
- By delegated reading: every master handler that takes a session id calls `visible_session`
  (owner equality, 404) before any side effect; the agentic gate is applied on prompt, allow,
  restore and save, and not on deny or cancel; `respond_approval` has one caller; routines
  never run in `auto`, re-check owner, grant and node at every fire, and only ever cancel
  approvals; webhook text reaches only the prompt; the WebSocket checks ownership on every
  subscribe and re-checks the login; no secret was found in a log line, event or URL in
  that slice.

**C. Sandbox and tools**
- Read by the reviewer: `ToolCtx::resolve`, `walk`, `resolve_for_write`
  (`crates/tools/src/lib.rs`), the grant construction in `Confinement::command` and
  `Sandbox::new` (`sandbox.rs:1-520`), the hardened git base and every shadow-repository
  call up to `snapshot_within` (`git.rs:29-1070`), `prune`, `apply`, `worktree_*`. For a
  folder that is not swapped (S-2) and a root that is not moved (S-3): symlinks out of the
  workspace and dangling links are refused, the data directory is refused in both modes,
  `.git` writes are refused by the real path. Shadow-repository calls do not read the user's
  config or attributes; hooks, fsmonitor, pager, editors, transports and signing are
  overridden on every call.
- By delegated reading or experiment: `bash` passes one `-c` argument with no
  interpolation, a cleared environment with an allow-list, null stdin, group TERM then KILL,
  a clamped timeout, bounded output; the Landlock rules require ABI 3 in full and ABI 4 for
  `network = "off"`; `replace_with` is atomic with an exclusive temp file, a mode mask and an
  inode re-check; `grep` and `glob` do not follow links and filter protected folders by real
  path; `tool_output` is keyed by session; `scrub_value` runs on every event payload
  (`session.rs:244-249`, read by the reviewer) and `StreamScrubber`'s hold-back is correct;
  `web_fetch` checks the address actually connected to on every hop, covers the listed
  IPv4 and IPv6 ranges, allows http(s) only, and matches provenance by exact token with the
  query kept; the PDF helper confines itself before reading input; `checkout-index -f` does
  not write through a symlinked directory (experiment, git 2.56); restore's blob copies take
  only harness-hashed ids; artifact staging re-checks the opened descriptor's real path,
  clamps fetch lengths, and resolves stage ids through its index per session; garbage
  collection and snapshots are serialised by `hold`.
