# T.8e review, 2026-11-12: the guard that watches every contained command

Reviewed: `feat/T.8e-kill-guard` at `9336473` (three commits on `origin/main`
`4a680d8`). Read in full, then attacked on the branch's own build. No product
change. Machine: Arch Linux, kernel 7.2.15, Landlock ABI 10, bubblewrap 0.13.1
(not setuid), `fusermount3` setuid, `pid_max` 4194304, 16 CPUs, the repository
on a rotational USB disk. Format and severity scale as in
`2026-11-T8a-containment.md`.

## 1. Verdict

**Fit after T8E-1, or with claim 1 reworded.** The guard does what it says on
every path I could reach from inside a command: 0 survivors in 260 kills of
the node spread over 0 to 6 ms, no order of deaths left a process behind when
the guard exited, the command cannot see, signal or hold anything of its
guard, and the sweep touched nothing that was not marked for its node. What
does not hold is the sentence "a node killed in any way, at any moment, leaves
no command running". The kill order is "the last copy of a descriptor
closes", and the node is not the only holder of that descriptor whenever one
of its own children is between `fork` and `exec`. `origin/main` did not have
this dependency.

## 2. Findings

### T8E-1. Medium. A child of the node that has not reached `exec` keeps every guard's channel open past the node's death

**The claim it breaks.** Claim 1 ("a node killed in any way, at any moment,
leaves no command running") and claim 3 ("a restarted node sweeps anything
left"). `PLAN.md:545`: "its stdin is one end of a Unix socket pair whose other
end only the node holds (close-on-exec, so no other child and not the command
holds it: tested)". `README.md:709-718`.

**The mechanism.** `contain::spawn` (`crates/tools/src/contain.rs:424`) keeps
`ours`, close-on-exec. Close-on-exec closes a copy at `exec`. Between `fork`
and `exec` a child has a copy of every descriptor of its parent. That is
microseconds, unless the child waits there. Two spawns of the node `chdir`
into a session's folder before `exec`:

- the node's git for checkpoints: `crates/node/src/git.rs:371` and `:377`,
  `c.current_dir(&repo.root)`;
- every tool that is not the shell: `crates/tools/src/sandbox.rs:797`,
  `current_dir(if contained { "/" } else { &ws })`.

When that folder is on a mount that has stopped answering (in scope: "a
session folder on a hung mount"), the child waits in `chdir` and holds the
node's end of the channel of **every** command running in **every** session.
If the node now dies (`kill -9`, the OOM killer, the operator who sees it
hang), no channel closes. No guard gets its order. The commands run on with
nobody enforcing their timeout. A restarted node's `sweep` finds nothing:
`orphans` (`contain.rs:517`) skips guards and everything under a marked
parent, and these guards are alive. It ends when the mount answers; with a
dead server and a hard mount, never.

A cancel is not affected (`shutdown` acts on the socket, not on one copy).
Only the death of the node is.

**Why it is this change's finding.** On `origin/main` the node's death reached
bubblewrap through `PR_SET_PDEATHSIG`, which does not care who holds which
descriptor. The same accident there killed every command (after the first
0.5 ms). T.8e replaced that with a descriptor's lifetime and removed the
spawner thread.

**An agent cannot trigger it** as far as I can see: a contained command cannot
mount (Landlock denies `mount`, `fusermount3` is setuid under `no_new_privs`),
and I found no path in a granted folder on which `chdir` or `exec` waits. It
is an accident, and the accident is on the task's own list.

**Reproduction 1, through the node's code**
(`crates/cli/tests/support/review_t8e/review_t8e_proofs.rs`,
`proof_t8e1_a_child_stuck_before_exec_keeps_the_channel_open`). A helper
process is the node: one contained `sleep` through `Confinement::spawn`, then
a tokio `Command` with `current_dir(<folder>)`, as `git.rs` starts git. The
folder is a FUSE folder the test stalls (`fuse_hang.py`). The helper is
SIGKILLed. Control first, without the second child.

```

the next start's sweep: []; the command is still running
```

**Reproduction 2, with a real node start** (`SWEEP=1 held_channel.py`: this
script as the node with the real guard and bwrap, then
`rizzy-harness --data-dir <the same> serve`):

```
control: node 636740 SIGKILLed; after 0.00 s: command gone; guard [636742] gone
stalled: node 636746 SIGKILLed; after 3.01 s: command STILL RUNNING [636750]; guard [636747] alive
  the node's unfinished child (same command line as the node, state ['S']): [636752]
  5 s later: command [636750]

    … INFO rizzy_harness: shell containment: contained (/usr/bin/bwrap: a PID namespace and /proc of its own per command; nothing a command starts outlives it)
    … INFO rizzy_harness: checkpoints: the node's git reads session folders in the sandbox (read-only on the folder, write on its checkpoint store only)
  after that start (its sweep): command [636750]
  the folder answers again (the child reaches exec or fails): command gone
```

The node says "nothing a command starts outlives it" while one does.

**How likely.** Two things must coincide: a spawn of the node waiting before
`exec`, and the node's death. The first needs the folder to stop answering
between the node's own check of it and the child's `chdir`, or a file system
that answers `stat` from its cache and not `chdir` (N-1 shows the bash tool
itself waits in the node first when the folder is already dead). Rare. When it
happens the result has no bound, which is why this is not Low.

**Smallest fix I would accept.** The guard must learn of the node's death from
something no third process can hold.

1. The node passes its pid (`--node <pid>`); the guard's `poll` in
   `Phase::Running` gets a timeout (1 s) and the loop treats
   `getppid() != <pid>` as the kill order. The kernel reparents the guard the
   instant the node is gone, whoever holds descriptors. One wakeup a second
   per running command. (A pidfd of the node in the `poll` set would cost no
   wakeup; `nix` 0.31 has no safe `pidfd_open`, so the timeout is the version
   without `unsafe`.) `PR_SET_PDEATHSIG` on the guard is not the fix: it names
   the tokio thread that spawned it.
2. Second line: `sweep` treats a guard with this node's mark whose parent is
   not a live node process as a leftover and sends it SIGTERM (its kill
   order).
3. `PLAN.md` T9: "only the node holds" becomes "the node, and for the moment
   before its `exec` every child the node forks".

**The test that should exist.** The proof inverted, in `cli/tests/guard.rs`:
a node with one contained command and one child stalled in `chdir` is
SIGKILLed; the command is gone within 2 s. It fails today.

### T8E-2. Low. A guard that dies in its first millisecond leaves the namespace, and the node that saw it die does nothing

**The claim it breaks.** Claim 3 ("a guard that is itself killed still ends
its namespace"). `PLAN.md` names the SIGKILL half as a residual of "half a
millisecond … until the node's next start". Two things are not said.

**(a) SIGTERM, SIGINT and SIGHUP have the same window, and it is not only
"by hand".** The guard clears its mask, starts bubblewrap, and only then
blocks the three signals (`guard.rs:153-182`; it must, the mask is inherited).
A SIGTERM that arrives before that line, the whole spawn included, ends the
guard by its default action, and when bubblewrap has just been started it has
no death signal yet. `systemctl stop` sends its signal to every process of
the unit at once.

**(b) The node knows and waits for a restart.** The tool sees its guard die
of a signal, reports `[exit code: signal]` and returns (`bash.rs:282-284`).
The namespace runs on with no timeout until the next start. The node holds
everything needed to end it now: the mark and the session.

**Reproduction** (`kill_windows.py guard 260`, `kill_windows.py term 260`; the
node alive throughout):

```
guard: 61 of 260 namespaces left running
  by delay (us: left/tries): 0: 20/20  250: 20/20  500: 19/20  750: 2/20  1000: 0/20  1250: 0/20  …  3000: 0/20
term: 5 of 260 namespaces left running
  by delay (us: left/tries): 0: 0/20  …  1250: 0/20  1500: 4/20  1750: 0/20  2000: 1/20  2250: 0/20  …  3000: 0/20
  145 x guard exit -15
  115 x guard exit 137
```

(The first delay is counted from bubblewrap's appearance, the second from the
guard's own spawn; 145 of 260 SIGTERMs found the signals not yet blocked.)

**Smallest fix I would accept.** (b) first: when a contained child ends by a
signal, or `stop` returns `Unconfirmed`, the tool runs the sweep for that one
mark and session before it returns, and reports what it found. That closes
the residual while the node lives, for SIGKILL too. For (a): catch the three
signals with handlers installed before the spawn instead of blocking them
after it (a handler is reset by `exec`, a mask is not; `signal-hook`'s
self-pipe is a safe API), so no moment exists in which their default action
applies. Otherwise say it in `PLAN.md` and the README, whose "killed by hand"
(`README.md:761`) is narrower than the truth.

**The test that should exist.** `kill_windows.py guard` as a test: the guard
SIGKILLed 0 to 1 ms after bubblewrap appears, the node alive, nothing left
2 s later. 61 of 260 today.

### T8E-3. Low. An unconfirmed stop is recorded as `[cancelled]`

**The claim it breaks.** Claim 2 ("a cancel or timeout returns only after the
guard confirmed … or reports 'still alive' instead of 'cancelled'").

**The mechanism.** `ContainedChild::stop` waits
`TERM_GRACE + CONFIRM_BOUND + 1 s` = 5 s for the guard's line
(`contain.rs:343`), then returns `Unconfirmed`; `bash.rs:328-331` then drains
for 100 ms. The agent loop abandons a cancelled tool after
`TOOL_CANCEL_GRACE` = 5 s and records `[cancelled]`
(`agent-native/src/lib.rs:1893-1897`, `:1927`). 5.1 s is after 5 s. The
`Unconfirmed("did not answer within 5 s")` branch cannot produce a transcript
line on a cancel. The unit test `the_stop_fits_the_loops_grace` asserts
`2 + 2 + 1 <= 5`, which is the inequality that fails by 100 ms.

The "still alive" report itself arrives at 4.11 s (measured by the branch's
own test), so it has 0.89 s to spare. Anything that delays the guard or the
node by that much (a starved CPU, the guard's pages read back from a slow
disk under memory pressure, which a command can cause) turns "NOT ended" into
`[cancelled]`.

**Reproduction** (`proof_t8e3_an_unconfirmed_stop_is_recorded_as_cancelled`:
the real bash tool; the guard is stopped with SIGSTOP as the stand-in for a
guard that cannot answer; the tool is given what `run_tool` gives it):

```
at the loop's grace (5.003271263s): the tool has not answered: the loop records "[cancelled]"; the command is ALIVE
the tool's own answer came after 5.102444875s: [stop ordered and killed; the end is not confirmed: its guard did not answer within 5 s]
```

I did not produce the delay with load alone (see section 4): the trigger here
is artificial, the arithmetic is not.

**Smallest fix I would accept.** `stop`'s bound becomes
`TERM_GRACE + CONFIRM_BOUND + 300 ms`, and the unit test asserts
`bound + drain + margin < TOOL_CANCEL_GRACE` against the real constant (move
it to a crate both can see, or assert it in `cli/tests/guard.rs`). Better: the
loop's abandonment of a contained bash call says "stop ordered, not
confirmed", not `[cancelled]`.

**The test that should exist.** The proof inverted: with a guard that does not
answer, the tool's result arrives inside `TOOL_CANCEL_GRACE` and does not
contain "cancelled".

### T8E-4. Low. The sweep says "ended" for a leftover that is still alive

**The claim it breaks.** Claim 3, and the change's own rule that an end is
proved, not assumed.

**The mechanism.** `sweep` calls a leftover gone when `/proc/<pid>` is missing
**or its command line changed** (`contain.rs:577`). It watches only the
process it found (bubblewrap), not the init it killed with it. bubblewrap dies
at once. The init, killed, waits in the kernel for a process of the namespace
that is in uninterruptible I/O; it has released its memory, so its command
line is empty and it no longer carries the mark. The log line is the plain
one, without "it is still alive 2 s after the kill", and at the following
start nothing is found.

**Reproduction** (`sweep_stuck.py`: a namespace without a guard whose command
is in a FUSE read the kernel cannot interrupt; then two real node starts on
that data directory):

```
left by a dead node and a dead guard: 650198[S] /usr/bin/bwrap --new-session …; 650199[S] /usr/bin/bwrap --new-session …
its command: 650200[S] cat …/mnt/stall
node start 1 logged: ['shell containment: ended a command a previous run of this node left running (pid 650198, session s1)']
  the reader after that start: 650200[D] cat …/mnt/stall; still marked: nothing
node start 2 logged: nothing about a leftover
  the reader after that start: 650200[D] cat …/mnt/stall; still marked: nothing
the read released: reader gone
```

The reader has SIGKILL pending and goes when its read returns. The harm is
the false line and the silence after it.

**Smallest fix I would accept.** `sweep` remembers the children it killed
too, and "gone" is: no `/proc` entry, or a zombie, or a non-empty command line
that differs (the reused pid). An init with an empty command line is not gone.

**The test that should exist.** `a_restarted_node_sweeps_what_a_dead_guard_left`
with the FUSE reader of the test above it: `ended` is false while the read is
held.

### T8E-5. Low. The guard is a second program outside the sandbox, and nothing checks who can replace it

**The claim it breaks.** Claim 4 in its plain sense (a command cannot reach
its guard), and the rule T.8a's review set as N-1: "bubblewrap is the one
program on the command path that runs outside the sandbox … so only one the
node's own user cannot replace is taken". Since T.8e there are two, and the
other one is `Sandbox::exe`, taken as it is.

**The mechanism.** Every command starts `<exe> sandbox-guard` in the host's
PID namespace, without Landlock. If a session's read-write folder holds that
file (a node run from its build tree with a session on that tree, which is
how this project is developed; the agent running `cargo build` there is
enough), a contained command renames it and writes its own. The next command
runs the agent's file as the guard. Before T.8e the same replacement gave an
unconfined `sandbox-exec`, which was already the end of the file policy, but
inside the PID namespace and under the node's kill. Now it is outside both,
it holds the control channel, and the sweep takes it for a guard and never
touches it.

**Reproduction**
(`proof_t8e5_a_replaced_binary_runs_as_the_guard_outside_everything`: the real
bash tool, the binary hard-linked into the session folder):

```
a contained command writing there itself: bash: line 1: …/written-outside-the-sandbox: Permission denied | direct-write=1 | [exit code: 0]
command 1: replaced | [exit code: 0]
command 2: (no output) | [exit code: 0]
outside every grant, written by command 2's "guard": ran as sandbox-guard: pid 659818, 447 processes in /proc, stdin socket:[13312823]
```

**Smallest fix I would accept.** At start: if the binary is inside a
workspace root or a `[sandbox] write` entry, `doctor` and the log say so as a
warning ("the agent can replace the program that guards it"), and
`contain = "required"` refuses. A session whose folder contains the binary is
refused at its creation. Not `contain::trusted` as it is (it demands root
ownership, which `~/.cargo/bin` fails).

**The test that should exist.** The proof inverted: the session is refused.

### Notes

- **N-1. A session folder that hangs stalls the node before any guard
  exists.** `PLAN.md` T9 now says "the guard starts in `/` (bubblewrap enters
  the folder), so a folder that hangs stalls the guard, not the node's spawn".
  True of the spawn, and it does not help: `Confinement::shell` resolves the
  workspace in the node first, in the async task, where no cancel reaches.
  `observe_a_bash_call_in_a_folder_that_hangs` (the bash tool, the folder
  stalled before the call):

  ```
  2 s into the call: guard None; children of the guard: None
  8 s after the cancel the call has NOT returned: it waits in the node, where no cancel reaches it
  after the folder answered: Ok("workspace …/mnt/d: Software caused connection abort (os error 103)")
  ```

  The code is the same on `main`; it is the new sentence that is wrong, and
  T9's "no tool can wedge a node" with it (by reading: `coalesce` polls the
  tool in the task that would abandon it, so the loop's 5 s cannot fire
  either; I ran the tool, not the loop). When the folder stops answering
  only after that check, the guard does its part (`hung_folder.py`:
  `alive 4008` at 4.01 s, bubblewrap's init in state D, everything gone once
  released). Fix: the blocking part of `shell` in `spawn_blocking` under the
  cancel and the timeout, or drop the sentence.
- **N-2. The node's stop under systemd (not run: no units on this machine).**
  The README unit has `KillSignal=SIGINT` and the default
  `KillMode=control-group`: systemd signals every process of the unit at once.
  Guards treat SIGINT as the kill order and SIGKILL their namespace with no
  grace, before the node has decided anything. On `main` bubblewrap died of
  the same signal and its init of the death signal: no better, no worse.
  Ctrl-C in a terminal reaches only the node: the guard and bubblewrap are
  each in a process group of their own (printed in T8E-1's output), as
  bubblewrap was on `main`. What matters is the drain of
  `docs/node-update.md` §7: with `control-group` there is nothing left to
  drain one millisecond after the signal, with or without the guard. That
  unit needs `KillMode=mixed`, and the note should say so. A guard ended
  through the window of T8E-2 leaves an init that ignores the signal; if its
  command ignores it too, systemd waits `TimeoutStopSec` for them (35 min in
  that design) before it kills.
- **N-3. A node that dumps core (not run: it would write to the owner's
  journal).** `core_pattern` here is `systemd-coredump`. The kernel dumps a
  process before it releases its descriptors, so after SIGQUIT, SIGABRT or
  SIGSEGV the kill order is late by the time the dump takes. Bounded; say it.
- **N-4. The tests against the claims.** I ran the tests-first commit
  (`98b94c0`) on `main`'s code: the kill window fails (22 of 40 left), the
  FUSE test fails (`[cancelled: process group killed]` with the reader in D),
  and **`cancel_returns_only_after_everything_ended` passes on `main`**: it
  does not test anything the guard added. Claim 2's confirmation rests on the
  FUSE test alone. No test covers `Unconfirmed` (T8E-3), a guard killed
  during a stop, the guard killed inside its window (the test kills it long
  after), a stuck leftover in the sweep (T8E-4), the sweep through
  `start_sandbox`, the shared-`/proc` form for claim 4, or exit codes through
  the guard. The kill-window test kills a node that has no other child, which
  is why it cannot see T8E-1.
- **N-5. What the removed spawner and its two tests protected.** The answer
  nobody reads: gone with the spawner, and a dropped `ContainedChild` is
  covered. The abandoned spawn: `Confinement::spawn` (`sandbox.rs:651`) no
  longer awaits anything, so the `select!` in `bash.rs:211-226` races a
  future that finishes inside its first poll. The comment says the spawn "is
  raced against the cancel and the timeout"; it is not, it is a blocking
  `fork` and `exec` on an async worker. With the guard in `/` the only stall
  left is the `exec` of the harness binary on storage that hangs, so the loss
  is small, but the comment and the two error strings are dead.
- **N-6. Error paths after the spawn.** `run` returns `Err` (exit 125) when
  `thread_block` or `SignalFd` fails after bubblewrap has started
  (`guard.rs:179-182`), without killing; `stop` reads an exit without a
  report as `Ended` (`contain.rs:368-371`: "a guard that exits on its own has
  reaped everything first"). I could not make either call fail (a descriptor
  limit low enough fails the spawn first). Create the `signalfd` before the
  spawn, or kill on that path, and count only exit codes below 125 as proof.
- **N-7. The documents.** (a) `PLAN.md` T9 says a node "restarted with another
  spelling of its data directory (a symbolic link)" misses its leftovers:
  `data_dir` canonicalizes (`cli/src/main.rs:193`), so that case is covered
  and the limit is overstated. (b) The same row says "the 2 s grace plus the
  2 s bound fit the agent loop's 5 s `TOOL_CANCEL_GRACE`" and, further on,
  "a tool has 2 s (`TOOL_CANCEL_GRACE`)" (old text; the constant is 5 s).
  (c) The README never says that the Landlock-only fallback and
  `contain = "off"` have no guard and confirm nothing; `PLAN.md` does. One
  clause in the `"auto"` bullet. (d) A confirmed contained stop and an
  unconfirmed process-group kill both print `[cancelled: process group
  killed]`; the contained one kills a namespace, and the transcript cannot
  tell which guarantee it got. (e) A kill order by signal to the guard is
  recorded as `[exit code: 137]`, as if the command had died by itself.
- **N-8. What the sweep does not say.** A guard of a dead node that is still
  killing a stuck process is skipped, correctly, and not mentioned: the node
  serves with a process of its previous run alive and nothing in the log.
  `reset_tmp` then removes that command's temp folder under it. One log line
  per live guard whose parent is not this node. Also by reading: "stopped, it
  cannot exit or exec" (`contain.rs:552`) is not true if another process
  continues or kills it, and a child of a process that ignores SIGCHLD is
  reaped while its parent is stopped; both need a pid to come round again
  within microseconds at `pid_max` 4194304, so not a finding.

## 3. What I tried that held

- **The node killed at any moment (without T8E-1's second child).**
  `kill_windows.py node 260`: SIGKILL 0 to 6 ms after the spawn returned,
  13 delays: `0 of 260 namespaces left running`. The branch's test: 0 of 200.
- **Every order of deaths** (`orders.py`, each line `HELD`): bubblewrap killed
  with its init left (the init without a death signal): the init became the
  guard's child, the guard killed it and exited 137 with nothing alive, and
  wrote `ended 0`; the init killed from outside; the graceful stop (the
  command's TERM trap ran, `ended 0`, exit 7); the channel closed without the
  byte (1 ms, no grace, as documented); SIGTERM, SIGINT, SIGHUP to the guard.
  `kill_windows.py bwrap 130`: bubblewrap SIGKILLed 0 to 3 ms after it
  appeared, 0 left, nothing alive at the guard's exit in any try.
- **ECHILD as proof.** Nothing I could do inside a command produced a process
  that was neither in the namespace nor a child of the guard: `CLONE_PARENT`
  from the namespace's init is refused by the kernel, a nested namespace dies
  with the outer one, and the reparenting of bubblewrap's child to the
  subreaper is what case A shows. The guard exits by `return` only at ECHILD.
- **A guard that waits for ever with nothing left.** Not found. 4000
  processes ignoring SIGTERM: `ended 2028` (the 2 s grace plus 28 ms to kill
  and reap all of them); 500: `ended 2003` (`many_processes.py`).
- **The channel.** The command's descriptors: `0 -> /dev/null`, its two
  pipes, no socket; `SigBlk` and `SigIgn` zero (`orders.py` F). The guard
  writes at most two short lines to a socket, so a node that never reads
  cannot block it. The node parses two words and a number and shows the
  number; the command cannot write there.
- **The sweep's safety.** The mark is compared as a whole argument (no
  prefix), the data directory is canonical, a live guard's namespace was left
  alone (the branch's test, and T8E-1's output shows the same from the other
  side), and a process that carries the mark of its own accord can only get
  itself and its own children killed.
- **Exit codes, output, timing.** `cargo test -p harness --test contain`
  (18 passed), `--test guard` (9 passed: 1.38 ms a command over bubblewrap
  directly, the guard's RSS 17.6 MB in the debug build of which the documents
  count the private 4 MB). `cargo fmt --all --check` and

### R-1. Low. A second start on the same data directory kills every running command of the node that is alive

**The claim it breaks.** Claim 3 ("never touching a process that is not its
own leftover"). New with the fix of T8E-1: before `1e73622` the same second
start touched nothing that was alive.

**The mechanism.** `sweep` sends SIGTERM to every guard with its mark whose
parent is not the starting process (`contain.rs`: `p.is_guard() && p.ppid !=
me`). A guard of a node that is alive has such a parent. Nothing stops two
processes from using one data directory, and the sweep runs before `serve`
binds its port (`cli/src/main.rs:297`, then `:350`), so the common mistake,
`rizzy-harness serve` typed again while it runs, ends with "address in use"
after every command of every session has been killed. `node run` beside a
`serve` with the same default directory does the same and stays up.

**Reproduction** (`recheck_r1_a_second_start_kills_the_live_nodes_commands`:
the test is the live node with one command through the bash tool; then the
real binary, `serve` on the same data directory):

```
the live node is pid 834096; its command's guard 835050 has parent 834096 and `--node 834096`
the second start logged: shell containment: told the guard of a previous run of this node to stop (pid 835050, session s1); its command has ended
the live node's command, 7.741660662s after its start: (no output) | [stopped: its guard was told to stop (a signal to the guard) and killed everything the command started; this is not the command's own exit]
```

**Smallest fix I would accept.** Signal only a guard that has lost its node:
its parent is not the pid in its own `--node` argument (`g.ppid != <--node>`).
A guard whose parent is still that pid has a live node and, since T8E-1,
would have noticed otherwise within 500 ms. Better and wider: a lock on the
data directory taken before the sweep and `reset_tmp` (which already empties
the live node's temp folders on a second start).

**The test that should exist.** The proof inverted: a command of a live node
survives a `serve` started on its data directory.

### R-2. Low. The node kills what `sandbox-leftovers` names, and a process of a command can write lines into it

**The claim it breaks.** Claim 3 again, and question 2 of the re-check ("can
a command … make the node's own sweep kill something else of the same user").

**The mechanism.** `sweep` reads `<data>/sandbox-leftovers` and SIGKILLs each
`pid start` for which a process with that pid and start time exists. Nothing
else is asked. Four faults, one fix:

- **(a) Not bound to a boot.** The start time is ticks since boot. The file
  survives a reboot (and a restore or copy of the data directory); a process
  that then has both numbers is killed. Within one boot the pair is unique.
  The leftover exists because something hung, which is when machines get
  rebooted.
- **(b) The session text is written as it came.** It is the
  `--mark-session` argument of the process the sweep killed. A process of a
  contained command can carry the mark of its own accord (documented, and the
  mark is in `/proc/1/cmdline` there) and then chooses that text. With a line
  break in it, it adds lines, and the next start kills what they name. The
  same text goes into the log unescaped and breaks the line there.
- **(c) No check of whose process it is.** Not the uid, not the node itself
  (an entry that matched the starting node would make it kill itself); an
  entry the node may not signal stays in the file and is reported "STILL
  ALIVE" at every start.
- **(d) The file is opened as any path**: a symbolic link is followed for
  reading and for the rewrite, the read has no size limit, a FIFO there
  stops the start. Only the node's user can put one there (the data
  directory is protected from sessions).

For (b) the process must be found by a start sweep and survive its SIGKILL
for 2 s: a leftover, or any process of a command in uninterruptible I/O when
the node is restarted (its namespace's init is exiting, has an empty command
line and no mark, so the process counts as an orphan). A long `fsync` on a
slow disk is that state without any mount. It must also know a pid and its
start time, which a command sees only in the shared-`/proc` form or without
containment. Hence Low.

**Reproduction (b)** (`leftovers_inject.py`: a marked reader in a FUSE read,
an unmarked `sleep` as the victim, two real `serve` starts):

```
victim: pid 840818 start 2303349 (an unmarked `sleep`)
the marked reader: pid 840819, its --mark-session is 's1\n840818 2303349 injected'
node start 1 logged: ['shell containment: killed a command a previous run of this node left running (pid 840819, session s1']
  …/data/sandbox-leftovers now holds: '840819 2303349 s1\n840818 2303349 injected\n'
  the victim: alive
node start 2 logged: [… 'shell containment: ended a command a previous run of this node left running (pid 840818, session injected)']
  the victim: KILLED, status -9
```

**Reproduction (a), (c), (d)** (`leftovers_file.py`: the file names an
ordinary `sleep` of the script, as a previous boot would have left the
numbers; once as a file, once through a link):

```
victim: pid 831212, started at tick 2272043, … parent this script; the file holds: '831212 2272043 some-session'
  the node logged: ['shell containment: ended a command a previous run of this node left running (pid 831212, session some-session)']
  the victim: KILLED, status -9
victim: pid 831478, … the file is a link to …/elsewhere/not-the-nodes-file: '831478 2272649 some-session'
  the victim: KILLED, status -9
```

**Smallest fix I would accept.** Write `boot_id pid start` only (the boot id
from `/proc/sys/kernel/random/boot_id`), nothing that came from a command
line; on reading, drop lines of another boot, lines that name this process,
and processes of another uid; open with `O_NOFOLLOW`, as a regular file, at
most a few kilobytes. The session for the log can be looked up again from the
process if it still has one, and is printed escaped (`{:?}`) everywhere.

**The test that should exist.** Both scripts as tests: an entry of another
boot kills nothing; a marked process whose session holds a line break adds
no line.

### What I attacked and what held

- **The parent check, node alive** (`parent_watch.py`, each `HELD`): a tracer
  that is not the parent attached to the guard (`TracerPid` set, `PPid`
  unchanged, the command alive 2 s later: `getppid` reads the real parent);
  the node's spawning thread ended; the node stopped for 2 s. A guard started
  by a helper instead of the pid in `--node` starts nothing (`125
  sandbox-guard: its node … is gone; nothing started`): the node must be the
  guard's direct parent, which it is on every path in the tree
  (`contain::spawn`, the probe). A node that re-executes itself keeps its pid
  and closes the channel: killed through the channel, as documented.
- **The parent check, node dead.** `getppid` cannot still be the node's pid:
  a process is reparented while its dying parent still holds its pid, and
  only to a process that is older than itself (another thread of the parent,
  a subreaper among its ancestors, or the namespace's init), by induction
  along every later reparenting. Each of those was alive beside the node when
  the guard was made, so none has the node's pid. `parent_watch.py` E: gone
  0.50 s after the kill with a second child holding the channel.
- **`sweep_session` while the node serves.** The builder's test keeps another
  command of the same session alive through 60 sweeps; I found no way to make
  a held namespace look orphaned: the only parents that ever `exec` or exit
  with marked children are an exiting bubblewrap or init, whose command is
  over. The session is compared whole, not as a prefix. No file is involved.
  The child of a guard between `fork` and `exec` has the guard's command line
  and is skipped as a guard; I looked for a namespace surviving through that
  moment and found none in 300 tries.
- **The held descriptor**: close-on-exec (`flags 02100000`), not 0 to 2 (the
  runtime fills closed standard descriptors), names the image after a rename
  and a replacement of the path; writing into the running image is refused
  ("Text file busy").
- **The bounds on a busy machine**: above. The in-call sweep reads every
  process of the machine, so its time grows with what a command starts; when
  that pushes the answer past 5 s the record is the abandoned note, which
  claims nothing.
- **Unchanged**: `kill_windows.py node 260`: 0 of 260; `orders.py`: all
  `HELD`, the reports now carry who gave the order (`ended 0 bwrap`, `ended 0
  signal`, `ended 0 node`).
- **The suites at `306b612`**: `--test guard` 19 passed, `--test contain` 18
  passed, `harness-tools` unit tests for `guard::`, `contain::`, `sandbox::`
  and all of `harness-agent-native` pass; `cargo fmt --all --check` and
  `cargo clippy -p harness-tools -p harness -p harness-agent-native
  --all-targets -- -D warnings` clean.
