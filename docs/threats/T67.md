# T67

## Threat

**Plan mode** (ADOPTION_PLAN X.7, README "Approval modes"): a chat set to plan changes something anyway: a named `write`, `edit`, `publish`, `remember` or MCP tool runs or shows a card someone allows; `bash` writes; a delegate that can write is started, or a sub-agent's changes are written back; the model, a tool result, a skill, an MCP server, a queued message, a routine's or webhook's data or a node message leaves plan mode; the master files a memory from a refused `remember`

## Mitigation

`plan` is the fifth and strictest approval mode (`plan < ask_all`), so the node's clamp, a sub-agent's ceiling (its parent's mode at every call) and a webhook run's `ask` cap keep it with no new rule; set and left only through `session.set_approval_mode` (T50: owner or API token, a raise passes the level check; entering is a lowering).
The node refuses, never asks: `ApprovalMode::refuses` names every mutating tool but `bash` and the read-only-risk `remember` (`PLAN_REFUSED`); three places, as research 02 §6 item 9 asks: the registry (the loop does not offer them, nor MCP tools, nor `bash` without a read-only shell; MCP servers are not started), the dispatcher (the loop refuses a call naming one, read per step, after its `tool_call_started` and before any card, with `policy::plan_refusal`; `Session::approve` denies them too as the node's floor), and the shell (`bash` in the read-only shell, T66, in both execution modes; none where the node has no containment, and the model is told why). `delegate` starts only an agent with no mutating tool other than `bash` and no MCP or "all" (`writes`); a child made in plan mode records `plan` and stays in it for life, needs no isolated folder (it cannot write), and a writer child's changes are not written into a folder whose chat is in plan mode when it ends (kept and shown).
A card waiting when plan mode begins is denied by the node at once (`set_mode` → `deny_waiting_for_plan`, for the chat and every sub-agent under it), recorded as resolved by its policy with the reason, and `approve` reads the floor again after any answer, so a late Allow runs nothing (review H1); the loop checks the mode again in `authorize` (a "for this turn" grant skips the card, never the mode) and in `execute` (a call authorised before the switch, waiting in a batch).
The master files a `remember` only from the node's successful `tool_call_finished` for it, never from `tool_call_started` (review M1: this also closes a call the node refused for any reason: plan mode, `denied_tools`, a person's denial, arguments it does not take, the repeated-call guard; the memory block shows such a call as refused, with the node's words), and still files nothing for a chat in plan mode or under one (`memory::in_plan_mode`, fails closed); a node whose `max_approval_mode` was lowered since a chat's mode was recorded records the mode in force (`approval_mode_changed`, `requested` = what the log said) before that chat's next turn, so the log, the master and the UI say it.
The model gets one harness line in the context block (`TurnExtra::mode_note`, recorded in `context_sent`, so requests rebuild byte for byte).
Residuals: a background command started before the switch keeps running as started (it can be stopped; plan mode allows `bash_stop`); reads and the network are as in any mode (plan mode is not secrecy: `web_fetch` and the shell can still send what they read where the network is on); leaving plan mid-turn makes `bash` writable from the next call while `write` stays unoffered until the next turn.
