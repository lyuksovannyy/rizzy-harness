# T7

## Threat

Rogue node / stolen node key; two processes with one key (a copied data directory, a node restored from an old disk)

## Mitigation

Node keys pinned after operator approval; revocation marks the key revoked and drops the link, and frames from a revoked node are refused in the append transaction, those already queued included.
A node only writes its own sessions; the master rejects events for sessions owned by another node.
A second writer under the same key is caught when its `seq` repeats one already stored with different content: the session is marked diverged and refused from then on, logged once at `error` without content, the node is sent `session.cancel`, and commands that would write to it are refused (§3).
What a registered node can do to the master and to other users through what it sends (Gate 3 review, R.3): it cannot rewrite a chat's row after creation or change its owner (a later `session_created` is refused, L-2), cannot name another node's or another owner's chat as its session's parent to receive that chat's project context (L-1), and its strings and events are bounded (L-3, below).
A node revoked while its handshake runs no longer stays linked (L-4): `node_connection` reads `revoked_ms` again once the link's stop token is registered, `add_link` refuses a revoked node (the store's record, and the in-memory set `revoke_node` writes under the same lock as the link table, so a link is either registered before a revoke, which takes it down, or refused after it), and `send_command` sends nothing to a revoked node (`a_node_revoked_while_it_reconnects_never_stays_linked`).
**Failed handshakes** (R.4, review L-7): node ids are the lowercased hostname, so a stranger can guess one.
A bad signature for a registered id writes an audit row only while that id and that peer address are each under 5 rows in 15 minutes (`nodes::AUTH_FAILURE_AUDITS`, the login path's `FailureMap`, one map for node ids and one for peer addresses: `AuthAuditLimits`, so addresses cannot push a node id's count out), so a flood writes a bounded number; an unknown id writes none.
Both are refused in the same words ("unknown or revoked node").
Minting a join token is audited (`node.join_token`, who and when; never the token) (review N-5).
**A node of another protocol version** is refused before `accepted` (A.19): the `auth` and `join` hellos carry the node's version (a required field: a hello without it is malformed and closed), compared only after its key is proved (and, for a join, its token found valid, before the token is spent), and answered `rejected` naming both versions and which side to upgrade; the node exits with it, status 77, instead of reconnecting (every `rejected` ends its loop: each needs a person; a master that is down is retried).
The node prints a refusal as printable ASCII on one line, spaces folded, at most 300 characters (`wire::printable`), and accepts only an id in the master's own shape (`wire::is_node_id`, at `node join` and at every `accepted`; otherwise it refuses that master, also 77): a master cannot write escape sequences, Unicode separators or overrides, or forged log lines on the node's terminal.
A peer without a registered key gets the same "unknown or revoked node" whatever it claims, so it learns nothing of the master's version; a registered node learns the master's protocol and crate version, which it runs against anyway (`master/tests/it/version_refusal.rs`, `cli/tests/stop_signal.rs`).
Test: `master/tests/it/remote_nodes.rs` `a_flood_of_bad_signatures_writes_a_bounded_audit`.
Residual: the time to refuse differs by one signature check (tens of microseconds) between an unknown id and a registered one, which tells a patient prober which hostnames are registered; the id is not secret (it is the hostname) and the key is.
Tests: `store/tests/event_log.rs`, `master/tests/it/link_hardening.rs`, `master/tests/it/hostile_node.rs`.
**Residual:** a copied key can freeze any session of that node's mirror by sending one differing frame (it could already do worse: write that node's new sessions); a second writer whose frames only extend the log (it starts at `head + 1` before the first writer does) is not detected until the first writer's frame collides, so up to that point the mirror shows the second writer's events; the node is not told why (it sees an ordinary cancel) and its own log keeps the session; the UI shows a chat that stops updating and refuses new messages with "diverged", with no banner yet (web follow-up).
The full fence (a generation per connection, an epoch per session) comes with workspace nodes (ADOPTION_PLAN C.1).
**Accepted (R.4)** from the R.3 residuals: a remote node may still declare the `chat` profile for a session it creates (the profile is checked against the known values, not against the link being remote); the row is that node's own chat on that node, so it gains nothing beyond a chat it could make anyway, and it would matter once the chat profile means a master-side runtime with wider rights.
The revocation race test runs 150 barrier-started add-and-revoke pairs and cannot force the narrowest interleaving; the second read in `node_connection` needs TLS and is covered by reading only.
**What a rogue or buggy node's payloads do in the browser** (A.25): nothing breaks the fold (checked where events enter it against the Rust schema, §2 "Fold"); no table or view map is read through a prototype; `ui:` card specs are checked by shape; a row that still throws costs that row (`RowBoundary`), a screen that throws that screen (`ScreenBoundary`).
A malformed optional part is shown without it, where the server's views count the event as unknown (deliberate, §2 "Fold").
