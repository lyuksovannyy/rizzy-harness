# T89

## Threat

**An agent that holds a repository's files and a shell's output also has the web** (ADOPTION_PLAN T.3's web half, README "Web tools in Agentic chats"; the 2026-11-19 trial: "agentic chats have no web tools at all", a docs lookup became `curl`): a prompt-injected agent (a hostile file, a command's output, an MCP result) uses `web_fetch` or `web_search` as a way out for what it has read, or as a way inward; and where the shell has no network (`network = "off"`, the read-only shell) these two tools are the agent's only way out, so whoever turns them on opens that door

## Mitigation

**The node decides.**
Both tools run in the node's own process (the master runs nothing; T22's code, unchanged).
The embedded node takes the server's `[web]` (the same tool objects and one HTTP client as the server's chats) and a `[web]` table in its node.toml can only take a tool away; a remote node takes `[web]` in its own `node.toml`, **off by default** (`search = "none"`, `fetch = false`), and nothing the master sends can switch either on; `denied_tools` refuses each by name and shows in `doctor` and the log (`crates/cli/src/main.rs` `NodeWeb`, `crates/node/src/policy.rs` `WebPolicy`).
**Every rule of T22 holds on the node path, each with a test** (`crates/node/tests/web_tools.rs`): public addresses only, also after a redirect and for a name that resolves to loopback; provenance, now over what an agentic chat holds (the person's words, a search's results, a fetched page's links: **not** a file `read` returned, not `bash` or `tool_output`, and not what the model composed, so a real host with a secret from a file pasted into its query is refused before any request); no tools for a turn nobody attended and for each of its sub-agents (the master's `deny_tools` on the spec, `crates/master/tests/it/seams_http.rs` `untrusted_agentic_turns_get_no_web_tools`, honoured on the node); the search key is in the node's scrubber (it reaches no event, log line, tool result or later model request, even where the backend echoes it); a page cannot pin a CPU or overflow a stack (`crates/web/src/tree.rs`, tests `deep_pages.rs`, `diff_pages.rs`, `parse_slots.rs`): there is **no second reading of the markup**.
A page of at most 1 MiB and 25,000 start tags (a byte pattern, `<` and a letter, that cannot count fewer than the tokenizer makes, which bounds the tree builder's worst case: its time is about 1.1 ns x depth x tags, 0.7 s at the cap, measured in release) is first run through a **counting pass** and then parsed by `dom_query`, the parser the readability pass uses (html5ever, scripting off; pinned to the exact version `dom_smoothie` resolves to, and a test fails if two versions appear), and the finished tree is measured iteratively (no recursion, no allocation): more than 512 levels (Chromium's own cap) is refused before readability or `html2text` run on it; `dom_smoothie` takes the parsed document (no second parse).
**The counting pass** (`crates/web/src/budget.rs`) exists because the tree builder can make far more nodes than the page has tags: text after closed blocks makes it re-open every active formatting element, and attributes that differ defeat its limit of three alike, so `<div>` x M, `<b a=i>` x N, `</div>x` x M makes N x M nodes from N + M tags (N = M = 2,000: 4 million nodes, 505 MB; at the caps, tens of GB), which no byte pattern can tell from a normal page.
The page is run through html5ever itself (0.40.1, the version `dom_query` drives, pinned exactly with a lock-file test; the same options, scripting off) into a counting sink of ours (a minimal arena of name, parent, depth and template contents), fed in 512-byte chunks.
The budget is on nodes **created** (a re-opened formatting element counts): past 150,000 the sink allocates nothing, hands out one dummy handle that is never the same node as anything, raises a flag, and the driver stops after that chunk, so memory is bounded by the budget and time by one chunk of cheap calls (worst measured, 500 formatting elements re-opened by each of 24,000 paragraphs: 15 ms and 20 MB in release; with 2,048-byte chunks it was 0.5 s).
**A page may therefore also be refused for making too many elements, counted while the tree is built.**
The sink also flags an element appended deeper than 512 levels (the tree builder's time is quadratic in depth: 1 MiB of nested `<div>` took 50 s, now 1 ms).
A page that creates more than 30,000 nodes is read as plain text (`html2text` holds about 1 MB per 1,000 nodes while it renders; 30,000 keeps a read near 40 MB); more than 150,000 is refused. `MAX_START_TAGS` stays: the sink's depth is the depth at the moment a node is appended and re-parenting is not followed, so the exact depth is still measured on the real tree, and the start-tag bound is what keeps that second parse (0.7 s worst) bounded.
The first design, a hand-written scan of the markup, was wrong six ways (noscript is markup with scripting off; SVG and MathML integration points; optional end tags in foreign content; raw-text elements in some insertion modes; `font` break-out; `</svg>` truncation) and is gone.
A page past the caps is read as plain text with no tree (`plain.rs`, linear), which shows less than the normal path, never more: it drops script, style, noscript, iframe, template and comment content, and shows what the normal path shows of the rest.
Two pages are parsed at once in the whole process; the slot belongs to the parse thread and is freed when that thread ends, a fetch that cannot get one in 5 s says the node is busy, and the 15 s wait for a parse is only a backstop (it does not stop the work, and does not free the slot).
The remaining cost is the real parser's: a page the tree builder is given is parsed in at most about 0.7 s in release; the search client follows no redirect and names the backend by host only; both tools are `read_only` by risk, so Ask runs them with no card, Ask-every-call asks for each, plan mode lets them run, and `denied_tools` answers before anyone is asked; the size limits (2 MiB read, 20,000 characters shown) apply unchanged.
Researcher is offered as a sub-agent again exactly where its tools exist (T27).
**Residual, stated plainly:** (0) **an API-token turn keeps both tools** (pinned by `seams_http` `r_api_token_turn_keeps_the_web_tools`, the chat runtime behaves the same): only chats a routine or webhook run marked untrusted get neither, in every later turn too; a URL in a token turn's text counts as the person's own words, so text piped through the token from elsewhere can vouch a URL. (1) **`web_search`'s query is free text** (400 characters at most, longer is refused, never cut; 20 searches a turn; the query is in the call's event, so it is visible in the chat afterwards): an agent that has read a file can put its contents in a query, which goes to the backend the node's owner configured (not an address the agent chooses) (a self-hosted SearXNG that forwards it to its engines, or Brave); no provenance rule applies to a query, and Ask, Accept-edits and Auto run it unasked.
This is the wide channel, wider than T22's `read` vouching.
It is bounded by what the owner enables: `web_search` is off in a default server (`search = "none"`) and on every remote node, an agent's own tool list must name it, `denied_tools` closes it, and Ask-every-call asks for each query.
Kept a read on purpose (the owner's decision: no card in Ask, no query screening, which would be guessing at secrets). (2) **A page that lists many links is a data channel.**
A URL a fetched page lists is vouched, so which of its links the agent fetches is a symbol the agent chooses and the page's author sees: about one byte per fetch with 256 links, whatever the page's author wants to learn from a steered agent.
It is bounded, not closed: `MAX_PAGE_VOUCHED_FETCHES` = 20 per turn (a named constant in `crates/web`, counted by the loop per turn: it survives a summary in the middle of the turn, a retry starts at zero, and a sub-agent's turn has its own) caps it at about 20 bytes a turn; fetches of the person's own URLs and of search results are not counted.
Nothing asks except in "Ask every call".
Where the shell has no network, `web_fetch` is therefore a slow way out for an agent a page has steered.
What a careful person does: Ask every call for chats that read untrusted pages beside secrets, or `denied_tools`.
Not mitigated: the person's own URL and a search's can be fetched without limit, and a sub-agent turn starts its own count.
(L4, known) `http`/`https` and `www.` are treated alike by the provenance match, and a dotted file name in the person's text can read as a host (it only ever matches the same string). (3) `web_fetch` is on by default in the server's own node (the server's `[web] fetch` default is on, and the node takes it): a default install's agentic chats can read public pages the person or a search named; turn it off with `fetch = false` or `denied_tools`. (4) A GET to a public URL can have an effect at that site; no credential, cookie or proxy is ever sent. (5) A search backend on a LAN address is reachable from the node because the owner typed it (as for chats).
Tests: `crates/node/tests/web_tools.rs` (11), `crates/cli/tests/web_agentic_e2e.rs` (4, the real binary), `agentic_nodes_register_the_web_tools_they_were_given` and `a_remote_nodes_web_tools_are_off_until_node_toml_turns_them_on` in `crates/cli`, `crates/master/tests/it/seams_http.rs`.
