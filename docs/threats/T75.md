# T75

## Threat

**The stream scrubber's hold-back as a side channel** (ADOPTION_PLAN X.30, `crates/core/src/secret.rs` `SEEN_PREFIX`): a streamed answer or command output is cut into frames the chat's owner watches, and the text in it is chosen by whoever prompts the model or prints from a command; the scrubber's secret set holds the master's API token, provider and web keys, `.env` secrets and MCP `env` values, shared by every chat of the process (and on a node by every chat there).
A hold-back that followed the whole secret (hold exactly the longest suffix that begins a secret) shows no secret, but where it cuts answers "does a secret start with this?": measured, an adaptive prober reads 39 of a 40-byte key's bytes in 1398 streams from nothing, or in 788 from its public prefix `sk-ant-api03-`, and the last byte by the replacement every scrubber shows (`the_obvious_fix_is_an_oracle`).
Control: the hold depends on the secrets only through the longest short and the longest long length (as the old constant hold did) and each long secret's first 4 bytes (`SEEN_PREFIX`); everything else it depends on is whether a whole secret was written.
**Bound:** whatever is written, in how many chats, through model output or command output, split however, ending the stream right after the guess or not, racing scrubbers (no state is shared between them), a watcher learns at most the first 4 bytes of each secret of 32 bytes or more and nothing of shorter ones; proved strategy-free by `what_a_watcher_sees_depends_only_on_a_long_secrets_first_bytes` (two secrets of one length agreeing on 4 bytes give every input the same frames; the exact hold fails the same check) and by the prober (`the_prober_learns_at_most_the_first_bytes`).
For a 40-byte key with a public `sk-ant-api03-` prefix that is nothing secret; for the 64-hex API token 16 of 256 bits; for a random 32-byte base64 key 24 of 192 bits.
No budget, counter or switch: nothing to burn and no process-wide state.
Residuals: (1) the frames still tell the longest short and the longest long secret's length (the old hold told the longest of all); (2) whether a whole secret was written is told by its replacement, as before; (3) text that agrees with a long secret's first 4 bytes (a public prefix such as `sk-a` in documentation) is held for up to `longest − 1` bytes after it, the old lag for that stretch; text that ends in a few of those bytes waits one piece.
A long secret that begins with common characters costs real lag: with a PEM key in the set (its `-----` is also a Markdown rule and table line) a 2.2 KB Markdown answer was on average 130 bytes behind (an ed25519 key) or 706 bytes behind (an RSA key), against 363 and 1,037 with the old constant hold; with only the API token, 0.1 bytes against 62 (review of PR 141, `review_markdown_lag`).
Six seen bytes instead of four would remove the PEM case at the cost of two more bytes told (24 of the API token's 256 bits); four is kept; (4) `push`'s time: the hold check is at most `held + piece` positions against each long secret's first 4 bytes and so depends on no more than the cut does; the full-secret comparison (`starts_with`, which stops at the first differing byte) was there before and runs on fewer bytes now; measured in process by the review: flat at about 110 ns a guess for 0 to 31 matching bytes, one step of 15 ns from 32 on (the comparison works in 32-byte blocks), so it says at most "the first 32 bytes are right"; a remote watcher sees it through a 75 ms flush tick and the link; (5) a secret longer than 4096 bytes that is split across pieces leaks, whole, as before (the review showed a 5,001-byte one come out raw); (6) not this change's and unchanged: `scrub` lets the tail of an occurrence show when it overlaps an earlier match; thinking is scrubbed whole and separately from the answer's text, so a secret split between the two is caught by neither; a command's output passes two scrubbers (the output ring's, then the loop's), and the second can redact a marker's neighbourhood again.
Found while proving this and fixed with it: the old scrubber re-scrubbed its own scrubbed tail, so a secret that begins a longer one was replaced as soon as it was whole and the longer one's rest came out as text (`a_longer_secret_completing_after_a_shorter_one_is_replaced_whole`); the held text is now raw.
Tests: `crates/core/src/secret.rs` (the property `the_stream_is_scrub_of_the_whole_text`, the lag `ordinary_text_is_not_held_back`), `crates/agent-native/src/lib.rs` `a_slow_answer_shows_piece_by_piece_and_a_split_key_never`, `crates/tools/src/background.rs` `output_is_readable_as_printed_and_a_split_key_never`.
