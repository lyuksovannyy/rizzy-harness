# T19

## Threat

A working copy arrives with a hostile git configuration (an unpacked archive, a shared folder): `.git/config` names `core.fsmonitor`, hooks, filter, diff or signing commands, and the harness runs git there before anything is approved (every turn starts with a checkpoint)

## Mitigation

**Turn checkpoints, their diffs and undo never use the user's repository:** they run in a harness-owned shadow repository (`<data>/checkpoints/<hash>.git`, `--git-dir`/`--work-tree`), which reads the user's objects through `objects/info/alternates` (data only; new objects go to the shadow) and copies `.git/info/exclude`; the work tree's `.gitattributes` are switched off (`GIT_ATTR_SOURCE` = empty tree, `core.attributesFile=/dev/null`) and name no defined filter in any case.
**Every git process** (`node/src/git.rs`): cleared environment (only `PATH`, `HOME`, `LANG`, `TMPDIR`; no inherited `GIT_*`), `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` (no exception since X.31: the user's global ignore file is not looked up, T76), no prompts or askpass, and `-c` overrides for `core.fsmonitor`, `core.hooksPath=/dev/null`, pager, editors, `core.askPass`, `credential.helper`, `commit.gpgSign`, `protocol.allow=never` (no ssh/proxy/`ext::`/lazy fetch), `submodule.recurse`, auto gc/maintenance; diffs pass `--no-ext-diff --no-textconv`; a 120 s timeout per call, and the process group is killed on timeout or cancel.
**No git process of the node runs with the user's git directory as its git directory or common directory** (R.1, review S-1, and the fix review's R1-1).
The first R.1 rule (no node git call that touches files reads config a session can write) left `rev-parse` and `worktree add` running in the user's repository, and the fix review proved that one line in the session's own `.git/commondir` then put a sub-agent's worktree, and its sandbox grant, inside another repository's `.git` (R1-1).
Every redirect git honours in a `.git` (`commondir`, a gitfile, `core.worktree`, `extensions.*`, alternates) steers whatever git runs there, so none runs there.
**What the node needs to know is read by our own code** (`node/src/git/user_repo.rs`): `<root>/.git` must be a real directory, not a link, without `commondir` or `gitdir` (a gitfile `.git`, a link, a `commondir`: the session folder is checkpointed as a plain folder and writing sub-agents are refused, with the reason); `HEAD` is read and one symbolic ref followed to a plain loose ref file or `packed-refs` (anything unusual: unknown); the object format is the length of that id; `info/exclude` and `index` are used only when they are regular files reached by no link.
**The only use of the user's repository by the node's git** is as an object store borrowed read-only through a shadow's `objects/info/alternates`, pointing at the canonical `<root>/.git/objects` our code computed, and only when that is a real directory, not a link, with no `objects/info/alternates` or `info/http-alternates` of its own (git follows those chains); otherwise nothing is borrowed (checkpoints store everything themselves) and writing sub-agents are refused.
What a session can still do through that door: the node's git reads objects only by ids it computed itself, from files it hashed in the session's folder or from trees it wrote, so a forged or chained object can change only what an undo writes back into that same folder, never reveal or write anything outside it; an alternates file created after the check is followed by git (residual, same bound); a crafted pack is parsed by git (git's own robustness, residual).
**Sub-agents** get a shadow of their own (`<data>/checkpoints/<hash>-sub.git`) for their base, result and the patch between them, and a node-owned folder (T32); the result is written into the parent's folder with the restore machinery; `git apply` and `worktree add` are gone.
**Every remaining git process of the node, by git directory:** the shadows (all snapshot, diff, restore, copy, gc calls); the child's folder is filled through its parent's sub-agent shadow (`read-tree`, `checkout-index` with the child's folder as work tree, and `read-tree` into the child's index file), all before the child starts.
Whether a published file's repository is dirty is asked of its checkpoint shadow (`diff-index --ignore-submodules=all` with a private copy of the user's index); its commit and branch are read from the files.
Tests: `node/tests/runtime.rs` `hostile_config_in_the_main_repository_never_runs_in_the_nodes_git`, `redirects_in_the_sessions_git_never_reach_another_repository` (`commondir`, a gitfile, `core.worktree`, `extensions.worktreeConfig` with `config.worktree`, a linked `objects`, alternates to another repository: a turn, a delegation and an undo; the other repository's canary is in no event and no file, its `.git` unchanged), `a_filter_a_sub_agent_defines_never_runs_in_the_nodes_git` (a filter, fsmonitor and three hooks in the child's own git directory), `node/src/git_child_tests.rs` (R1-1 inverted), `git_bounds_tests.rs` `a_git_entry_that_redirects_is_not_used_as_a_repository`.
**A nested repository or a gitlink runs nothing on the node (review of X.64, fixed with `git_submodule_tests.rs`).**
A nested repository's own `.git/config` and `.git/info/attributes` are the agent's to write, and `filter.<x>.clean` there names a program.
Git runs `git status` inside a gitlink (mode 160000) whenever a work-tree comparison meets one: `diff-index` (with `--quiet` too), `diff-files`, `status`, and `add -u` / `add -A`; that child reads the nested repository's config and attributes and runs the filter on a file whose stat changed.
No `-c` key stops it (`diff.ignoreSubmodules`, `submodule.recurse` and `status.submoduleSummary` were tried: the plumbing and `add` ignore them); only the flag `--ignore-submodules=all` does, and `git add` has none.
The one path that met a gitlink on main was `Repo::changed_since` (the published file's dirty flag): the copy of the user's index holds the user's own gitlinks, and the agent can also write a `160000` entry into a repository's index with `git update-index --cacheinfo`; it now passes `--ignore-submodules=all`, so a change inside a nested repository is not the folder's change and no process is started for it; git still opens the nested repository in its own process and parses its config (a broken one makes the comparison fail and the flag reads clean), which runs nothing.
Every checkpoint path is safe by construction: `stage_without_nested` takes every gitlink out of the shadow's index (`ls-files --stage`, `update-index --force-remove`, neither runs a child) before `add -u` compares anything, a nested repository is left out of the snapshot and never staged, so the shadow's index never holds a gitlink the folder made, and a gitlink an older snapshot left there is removed first; the diffs, restores, merges and the sub-agent paths run `diff`, `diff-tree`, `read-tree`, `write-tree`, `ls-tree`, `cat-file`, `merge-file`, `update-index`, `commit-tree` and `update-ref` on trees and indexes only (none compares a work tree).
The residual is `add -u`'s dependence on that invariant (a one-line change that stages before removing would break it); `a_gitlink_in_the_shadows_own_index_is_removed_before_the_next_snapshot_compares` is its test.
Tests: `describe_does_not_run_a_submodules_filter` (a gitlink in the user's index, with and without `.gitmodules`; failed on main: the filter's marker file was made), `a_checkpoint_does_not_run_a_nested_repositorys_filter` (snapshot, diff, restore and changed over a folder with a nested repository, with a gitlink in the user's index or none), `the_shadows_index_never_holds_a_gitlink_the_folder_made`, `a_gitlink_in_the_shadows_own_index_is_removed_before_the_next_snapshot_compares`.
**The header's git chip (X.64) runs no git process in the user's repository either.**
Its branch and commit are read by `user_repo::head_label` (the rules of `head_at`: a real `.git` directory, no gitfile, link or `commondir`, `HEAD` a small regular file); the count is asked of the checkpoint shadow with a private copy of the user's index (read through `read_bounded`, at most 64 MiB, written into the shadow's own directory): `update-index -q --refresh`, `diff-index --name-only -z --no-ext-diff --no-textconv --ignore-submodules=all` and `ls-files --others --exclude-standard --directory --no-empty-directory -z`, all through the hardened `command` (cleared environment, overrides, the sandbox of the shadow, the process group killed), each with a 5 s timeout and 12 s in all; the two listings are read as they stream and cut at 1,000 names (git is killed with its process group, so a folder of a million new files costs neither memory nor time); the count is absent, not zero, when any step fails.
The flag is the fix of the finding above for this call too: a gitlink in the user's index (or a 160000 entry the agent wrote with `update-index --cacheinfo`) otherwise runs the nested repository's clean filter on the node.
With the flag git still opens the nested repository in its own process and parses its `.git/config`: nothing is run, but a broken config makes `diff-index` exit 128, and the chip then shows the branch with no count (never an error).
`update-index --refresh` and `ls-files --others` were probed with a gitlink in the index by the reviewer of the fix (r-submodule-exec) and run nothing; they are kept.
What holds: no program named by the repository's config, hooks, attributes or by a nested repository's config or attributes runs; a nested repository's config is parsed, nothing more.
The branch name is the repository's text: replaced and cut at 200 bytes on the node, bounded again on the master, cut at 80 characters and drawn as text on the page; it is never an argument of a process, a path, a URL or markup.
A node that denies `read` answers nothing (the branch is text of the folder), and a sub-agent's own folder and a plain chat are not asked.
`GET /api/sessions/{id}/git` is owner only (T10), two places per account.
Tests: `node/src/git/state.rs` `a_gitlink_over_a_hostile_nested_repository_runs_nothing` (a gitlink in the user's index over a nested repository whose config names a clean filter: failed without the flag, the filter's marker file was made), `a_broken_nested_config_gives_the_branch_and_no_count`, `a_filter_the_worktree_and_the_user_config_name_runs_nothing` (the work tree's `.gitattributes` and the user's `.git/config` and `info/attributes` name filters, a textconv and an fsmonitor), `a_crafted_user_index_writes_nothing_and_runs_nothing` (a hand-written index with entries `../x` and `.git/config`: nothing written, config unchanged), `a_count_that_times_out_is_absent_and_leaves_nothing` (a stand-in git that sleeps: no count, the process dead, no `harness-index-*` or `.lock` left), `an_endless_listing_is_cut_at_the_cap_and_git_is_killed`; `node/src/git_state_busy_tests.rs` (a third concurrent request is `busy`); the earlier test `nothing_the_repository_configures_runs_and_its_settings_do_not_apply` guarded nothing (it wrote the user's `.git/config`, which the shadow's git never reads) and is gone; also `a_hostile_branch_name_is_cleaned_and_cut` (control and bidirectional characters, 4,000 characters, `<script>`, a leading `-`), `no_repository_a_gitfile_a_corrupt_git_and_a_bare_one_show_nothing`, `the_count_is_capped`, `a_large_untracked_folder_counts_once`; `node/tests/git_state.rs` (read denied, plain chat, no event appended); `master/tests/it/git_state_http.rs` (another member, a server admin, a workspace admin and a plain chat: 404 and the node never asked; a hostile node's answer bounded, bidirectional and hidden characters included; an aborted request keeps its place until the node answers; an answer from another node ignored; two places per account).
**Residual:** a sub-agent's folder holds the bytes of the folder, not what the repository's filters would check out (an LFS repository's real files, not pointers; no eol conversion), and its changes are applied as bytes; the published file's "dirty" flag compares bytes too, so a filtered file may count as changed; the session's own shell may still write its repository's `.git/config` (R2), which now affects only the person's own later git use there, never the node; the user's object store is trusted as data, so an attacker who controls `.git/objects` can make a checkpoint record (and undo write back) a forged blob for content git believes it already has, which only rewrites files inside that same working copy; config keys only consulted by commands the harness never runs (`alias.*`, `merge.<x>.driver`, `uploadpack`/`receivepack`, `core.alternateRefsCommand`, `sendemail.*`) are not overridden.
