# T51

## Threat

A person's answer does more than they meant, or someone else's does: a "for this chat" grant covers another call, another chat, a sub-agent, a background start, or outlives its removal; a note with a denial forges a harness line or a tool's output in what the model reads, or rides on an allow; another account adds or removes a grant; an older node is sent an answer it cannot parse; a card asks about a call that cannot happen (a `write` outside the folder on a node that keeps the file tools in it: allowed, then refused by the tool), which teaches people to click cards through

## Mitigation

**No card for a call its tool refuses anyway** (live test, 2026-11-15): after the arguments are checked against the schema (`tools::args`) and before the repeated-call guard and the card, the loop asks the tool itself (`Tool::refusal`, default "no opinion") whether the call is refused whatever anyone answers; `read`, `write`, `edit`, `outline`, `grep`, `glob` answer with the same `ToolCtx::resolve`/`resolve_for_write` their `run` uses (a path outside the folder where `allow_outside_workspace = false`, a dangling or outward link, `.git` for a write in every mode, the node's data directory, a moved folder), `bash` with its `workdir` check.
The context is built from the node's own configuration (`start_ctx`), never from the master or the model, and is never stricter than the run's (a call the Accept edits rule lets through runs confined, which refuses more).
Such a call ends with the tool's own refusal as its result, recorded as any refused call (`tool_call_started`, `tool_call_finished` with `ok: false`, no `approval_requested`).
The check only refuses earlier: it never allows, the tool checks again when it runs (the file system can change while a card waits), and a tool `denied_tools` names skips it, so the policy's refusal and its record stay as they were.
Tests: `crates/node/tests/approval_modes.rs` (`a_call_the_tool_refuses_anyway_shows_no_card`, `outside_the_folder_still_asks_where_the_node_allows_it`, `a_path_swapped_after_the_card_is_still_refused_when_it_runs`, `a_denied_tool_is_refused_by_policy_as_before`).
Residual: a `write` or `edit` of a file the agent has not read (or that changed since) is refused by the read-before-write guard (T45) only when it runs, so it can still show a card first.
**A note** goes only with a denial: the master drops it with an allow and refuses one over 2,000 characters (`policy::MAX_DENY_NOTE`), the node drops it with an allow and cuts it to the cap, records it in `approval_resolved.note`, and the loop gives it to the model after the fixed sentence with every line quoted (`| `, control and line-separator characters replaced, `event::denied_text`), so no line of it stands as the harness's or the tool's.
**A chat grant** (`allow_chat`) is recorded as `chat_allow_added` by the session actor after the answer, with the call's tool and input for display and its `key`: the `call_key` as computed at that moment, a SHA-256 digest (64 hex characters, not the text) of the tool, the session folder and the canonical input (for `write`/`edit` the real path then).
It covers exactly that key (tool, folder, canonical input: a `bash` command with every argument, `workdir` included; a file's real path and change) in that chat: rebuilt at load from the recorded `key` only, never worked out again from the logged input (which is scrubbed, and whose path a link may now lead elsewhere: review H1, H2; a grant without a valid key covers nothing), removed only by `session.revoke_allow` (`chat_allow_removed`), which only the chat's owner or the API token can send (`DELETE /api/sessions/{id}/allows/{grant}`; like a denial, no level check).
It is not offered or kept for a sub-agent's chat, a routine's chat, a background start or `ask_all` (which means every call), nor anywhere on a node with `chat_grants = false` (where logged grants are not honoured either; with it, `max_approval_mode = "ask"` makes every change and command ask); an `allow_chat` answer where it was not offered allows one call and is recorded as `allow`, applies only in `ask` and `accept_edits` (`auto` asks nothing), and `denied_tools` is checked first. `allow_chat`, a note and `session.revoke_allow` go only to a node announcing `answers`.
Also from the review of pull request 99: a mode change the master sends as a lowering (it skipped the level check) carries `lowering`, and the node refuses it, recording nothing, when it would in fact raise the mode (`MODE_NOT_A_LOWERING`; the master's copy was behind).
Tests: `crates/node/tests/approval_modes.rs` (`a_denials_note_is_quoted_and_an_allows_is_dropped`, `a_chat_grant_covers_the_exact_call_in_this_chat_until_removed`, `a_sub_agent_takes_no_chat_grant`, `a_lowering_that_would_raise_is_refused_by_the_node`), `crates/master/tests/it/approval_answers_http.rs`, `event::a_denial_note_is_quoted_after_the_fixed_sentence`, `web/src/components/approvalanswers.test.tsx`, `web/e2e/approval-answers.cjs`.
Residual: a grant is the exact call, not what the call does: it lasts for the chat, across restarts, and runs whatever the files it reads say then (`make test` runs the Makefile and tests of that moment, which in Accept edits the agent may rewrite without a card: the card says so beside the button); an MCP tool's grant depends on the server `node.toml` names under that name, which can change its behaviour or be replaced; a `publish` grant covers whatever the file holds when the call runs.
**Another harness's argument names are one call with the real ones** (trial 2026-11-19, item 8): `write`'s `file_text` and `edit`'s `old_str`/`new_str` are renamed to `content`/`old_string`/`new_string` once, by `Tool::normalize_args` in the loop's repair step, ahead of the schema check, the card, `call_key`, the node's `accept_edits` path rule and every deny rule; an alias beside the real name is refused naming both.
So a spelling is never a way past a check, and an approval given for a call covers the same call spelled either way.
