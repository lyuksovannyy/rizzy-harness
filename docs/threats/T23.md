# T23

## Threat

Any account (a chat-only guest included) uploads a hostile file the server parses: a PDF that loops, inflates without bound, overflows the stack, panics or exploits the parser, inside the process that holds every key; or floods uploads and paid dictation

## Mitigation

**The server never parses a PDF** (FIX_PLAN 3.4, AUDIT S7; `crates/master/src/pdf.rs`).
A file is a PDF only by `%PDF-` at offset 0, never by name (a `.pdf` text file is text).
The server starts its own binary as `rizzy-harness pdf-text` (dispatched before any runtime: one thread, no `.env`) with an empty environment, cwd `/`, stderr discarded, in its own process group.
Before reading a byte the helper confines itself with Landlock (ABI 3 file rights with **no** rule, so no file can be opened at all; ABI 4 TCP connect/bind denied; `no_new_privs`), then caps its address space (`RLIMIT_AS`) at 512 MiB above its start-up mappings, so a bomb's allocation fails and the helper aborts.
The server: 2 helpers at once, a request waits at most 10 s for a slot (then 503), 20 s per file, stdout capped at 400 KB (then killed), the group SIGKILLed and the child reaped on timeout, excess output or a dropped request; slots are RAII permits.
**Where Landlock or ABI 4 is missing (Linux before 6.7, non-Linux) PDFs are refused** (422 "cannot read PDFs safely"): an exploited parser that could read `<data>` could return `secrets.toml` as "extracted text" to the uploader, so timeout and memory limit alone are not enough.
Nothing about a file (name, bytes, text, parser message) is logged.
Unsent uploads: 20 and 8 MiB of text per account (counted and inserted under one lock; per owner, so one account never fills another's), swept after the incognito TTL; taking them for a message is one transaction, so the sweep never splits a send.
Dictation: one at a time per account (429, not queued) and `[voice] daily_requests` / `daily_mb` (200 / 100 MiB per UTC day) counted in memory before forwarding; a restart resets the day's counts (only an admin restarts).
Tests: `pdf.rs`, `attachments.rs`, `voice.rs`, `master/tests/it/pdf_http.rs`, `store/tests/attachments.rs`, `cli/tests/pdf_text.rs` (real helper: text, malformed file, a 768 MiB flate bomb aborts on its limit).
**Residual:** `ttf-parser` is unmaintained (`deny.toml` names this row); the helper can still spend 20 s of one CPU and 512 MiB per slot;
UDP is not covered by Landlock (the helper has nothing to send but the uploader's own file); a real parser-looping PDF is covered by the supervision test with a stand-in, not by a crafted file. **tree-sitter runs in the node process** (review N-1, accepted): `outline` and the repository map run tree-sitter's C parsers on files of up to 8 MiB inside the node process that holds the node key (and, on the embedded node, the server's), on files a session can write.
No exploit is known; the PDF parser was moved out of process for the same class of risk.
Moving it out would cost a helper process per file (as `pdf-text`: a confined `rizzy-harness` subcommand that reads one file and writes the outline), about a process start per `outline` call and a batch protocol for the repository map, and its result would have to be re-validated by the node.
Not done now; it would change with a tree-sitter memory-safety advisory, or once the map runs on large untrusted repositories by default.
