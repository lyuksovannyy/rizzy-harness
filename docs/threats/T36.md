# T36

## Threat

A steered agent keeps a process running or keeps acting after the person left: a listener, a miner, a chain of unattended turns, output that steers a later turn nobody watches (T.8d steps 1 to 3; step 3, callback turns, reviewed in `docs/security-review/2026-11-T8d-step3-callbacks.md`)

## Mitigation

**On by default since step 2** (`background_per_session = 8`; 0 turns it off), because **the person sees and stops them** (review T8D-4): while a command of the open chat runs, the chat's strip shows its id, its command's head as text and its time left (the node's deadline held to at most the command's timeout and at least zero, whatever the browser's clock), with Stop and Stop all, drawn from the log (a reload and a second tab show the same); `POST /api/sessions/{id}/background[/{bg_id}]/stop` is **owner only** (anyone else, admins and workspace admins included, gets the 404 of a chat that does not exist, T10), needs the login key and the page's Origin like every cookie write (Gate 3 P-1, AUDIT L6), and needs no settled password or agentic grant (stopping is always allowed, as cancel); the master runs nothing: an end the log already shows is answered from the log, anything else is relayed as `session.stop_background { by: user }` to the owning node, which alone decides and records `stopped_by_user` (its refusal is passed on as 409; a node that is away is said plainly as 503, its commands ending with it or at their timeout; a node without `CAP_BACKGROUND` is sent nothing, 409).
**Background commands where the shell is contained, and in a `host` chat** (the owner's decision of 2026-11-20, "Yes, allow", which replaces review N-c's refusal: a steered agent in a host chat can already leave a process from a foreground call with `setsid`, and refusing pushed agents to that invisible route, while a background command is listed with Stop and has a timeout; a `host` chat's runs under the guard without bubblewrap, T9; refused in a sub-agent's session and where the node holds no copy of its own program to start the guard from; a node with `[sandbox] mode = "off"` holds it and starts the guard directly, without the wrapper: the owner's decision of 2026-11-20, "dont, like if user selected host project workspace, why do we need to limit it? its his choice"), each the same command as a foreground one (in a `sandbox` chat: its own PID namespace, file view, network namespace with the network off; in a `host` chat: the node's PID namespace, a later command sees and can signal it).
**Each states its timeout** (`timeout_secs`, required for `background: true`, refused without before anything starts), at least 5 s, at most `bash_timeout_max_s`.
**Counts are node.toml's** (`[limits] background_per_session`, `background_per_node` 64); no argument, event or protocol field carries a bound; a start at a cap is refused naming the chat's own running ids (never another chat's), nothing evicted; a node slot is given back only for a confirmed end (one whose guard still kills it keeps its slot until the guard exits).
**Stopped** at its timeout, by `bash_stop` (read-only risk: it only ends this session's own), at the session's deletion (before the log goes), by the master's `session.stop_background` to **every** chat of an owner who lost access, on revocation and at the node's next hello, whatever the mirror shows (no count decides; the chat then refuses starts and stops a late hand-over until its owner prompts it), and at the node's stop (not waited for: stopped, recorded `node_stopping`; an end the log cannot take is retried on each pass and, once the commands are gone, named in the stop's result, which exits 1); the node's death ends them as any command, and the next start records `node_restarted` for each and starts no turn.
A turn's cancel does not stop them (the owner's decision).
**Output** is scrubbed where it enters (the streaming scrubber), kept in memory only: a running command's ring (head and tail, `background_output_kb`); an ended one's cut to 16 KiB of head and 16 KiB of tail, kept 30 minutes (pruned by time node-wide, every minute) and only for the newest `background_per_session` ended commands of a chat and `background_per_node` of the node: at most `background_per_node × (background_output_kb + 32 KiB)` in all (16.3 MiB at 64 and 256).
The end's tail (4 KiB) reaches the model quoted line by line, every line behind `| ` and control characters replaced, under one harness line that says how many lines follow, inside the step's last tool result or in front of the person's next message under a fixed separator (never a user-role message of its own), and is scrubbed again by the loop; it is kept out of the URL provenance (`ChatMsg::Note`);
**Callback turns (step 3).**
An end that exited or timed out while the chat was idle resumes the agent once: the master's watcher (told of every event the mirror takes; its position is the log itself, so a restarted master asks again and the node refuses a second ask) admits it as a routine fire less `routines` (the owner's account exists, is enabled and owes no password change; agentic grant, permission and node as for the owner's own prompt; not a routine's, an untrusted or a sub-agent's chat (a team chat whose owner left the workspace falls back to their Personal one and is admitted there exactly as the owner could go on in it); not a chat without an owner account; an end at most 60 minutes old, counted from the older of the node's clock and the moment the master first saw it); a node with `callback_turns = 0` announces no `CAP_CALLBACK`, so nothing is asked or shown and sends `session.callback { bg_ids }` with the chat's agent and no text, context or memory (`Master::prompt`'s third caller).
**The node decides:** it starts the turn only if every id names an end in its own log that may call back with no turn and no refusal after it, the chat is not `no_callbacks` (set for good at a routine chat's create), its table was not closed by a revocation, the node is not stopping, and fewer than `[limits] callback_turns` (3; 0: off) callback turns ran since the person's last `user_message`; otherwise it refuses (nothing to resume: quietly; on its rules: recorded as `callback_refused`, which the chat shows).
A callback turn's cap is `min(max_steps, callback_max_steps)` (20), it gets no sub-agents, and in a `host` chat it runs in the chat's own approval mode and budget exactly as in a `sandbox` one (nothing on the node or the master assumed "background means contained"; test `cli/tests/callbacks.rs` `a_host_chat_takes_a_callback_turn_in_its_approval_mode_and_budget`), and it may start background commands whose ends spend the same budget, which only a person's message refills:
**at most `callback_turns × callback_max_steps` steps (60) without the person after each message**.
It runs in the session's own mode (clamped by the node): in `ask` its calls park with no timeout.
Its opening is one user-role message written by the harness: a fixed first line saying the person has NOT written, then the ends' notes with every output line behind `| `, built from the log alone (no context, no images), the same bytes on every later request; it is `ChatMsg::Opening`, never URL provenance, never the person's words to memory (`file_proposal` files nothing from a turn whose `turn_started` has a cause), search, titles or the budget's refill; the demo provider never acts on program output (only `mock_obeys_output`, tests).
Attention: one row per chat with callback turns the owner has not seen, or why it was not resumed (kv `callback-attention:<sid>`, owner's own); the chat list counts the running commands (`background`).
A background start's approval card says the command keeps running and for how long, and with the network on that it can accept connections; it does not offer "for this turn", and such an answer allows that one start.
An undo is refused while the chat's own background commands run.
Tests: `cli/tests/callbacks.rs` and `callbacks_real.rs` (step 3: the node's checks over the protocol, the opening at the provider, the budget, the step cap, `callback_turns = 0`, `ask` on the real binary), `master/tests/it/callbacks_http.rs` (the watcher, admission, the 60-minute rule, a restart, attention), `master/tests/hooks_http.rs` (routine and untrusted chats), `agent-native/src/callback_tests.rs` (provenance, the cap), `cli/tests/background.rs` (the model's side read from the provider's requests; the person's stop over HTTP on the real binary), `master/tests/it/link_hardening.rs` (the sweep), `master/tests/it/background_stop_http.rs` (who may stop, the login key and Origin, an ended or unknown id, a node away or without the capability), `web/src/components/backgroundstrip.test.tsx`, `web/e2e/background.cjs`, `tools/src/background.rs`, `core/src/event.rs`, `agent-native/src/lib.rs`, `node/src/session.rs`.
**Residual:** with the network on a background server bound to `0.0.0.0` is reachable from the LAN for its lifetime (the login key, Gate 3 P-1, keeps the master's cookie harmless); there are no cgroups, so CPU and memory are bounded only by count × timeout; with the network off a server cannot be reached by a later command; one user's chats can hold every slot of the node, and a chat refused at the node's cap learns that other chats fill it; an end that waits for a running turn's step boundary is recorded as `node_restarted` if the node dies first (its exit code and output are lost); a delete whose log removal fails has stopped the commands already, and their starts get `node_restarted` at the next start; an undo does not check another chat's background commands in the same folder; the strip's "stopping…" is the tab's own (a second tab sees the end, not the click), and the time left is off by the node's and the browser's clock skew within those bounds.
Step 3: in `auto` a steered agent acts 60 steps without anyone after each message the person writes (the owner's Q2); quoted program output is still text the model reads and may obey; a node whose clock is more than 60 minutes behind gets no callback turns (the master cannot tell that from an end replayed late); an owner disabled in the instant between the master's admission and the node's `turn_started` gets that one callback turn (as their own prompt racing the disable would);  a callback turn is not resumed on the master's side for an ownerless (API-token) chat.
Details: `docs/background-commands.md`.

**Output on request (X.62):** the strip's Output button reads what a background command printed, so the route is as sensitive as the chat's events and carries the same guards.
`GET /api/sessions/{id}/background/{bg_id}/output` passes `visible_session` like the chat itself: another member, a workspace admin and a server admin get the 404 a chat that does not exist gets (T10), with the node never asked; the id must look like a node's (`bg-` and at most nine digits).
The master relays one `session.background_output` to the owning node only, behind the capability `bg-output` (an older node is told to update, 409), and hands the one answer from that node only to the waiting request (`crate::bg_output`); nothing is cached or stored and no command or text is logged; one account holds at most 4 of the master's 32 waiting places, and a refusal is a sentence (409 the node's words, 503 away or busy, 504 no answer), never a 500.
The node answers from the session's own table, so an id of another chat of the same node, or of the same owner, is not found there; it reads the ring the agent's `bash_output` reads (no second buffer, no new file), which holds no escape sequence at all (the pipe reader removes them before anything keeps the text, T3) and is scrubbed with the node's secrets where the output enters, the rule the events follow, and then scrubbed again after the view removed the escape sequences (removing one can join the halves of a key that a colour code split, which the ring's scrubber never saw whole; the marker is never itself a secret, `is_marker_part`, so a second pass changes nothing else); the view reads only the last 2 x 28,000 bytes of the ring, drops that window's first partial line when it does not begin at the start of the output (a key may begin before it), and cuts to 28,000 bytes after scrubbing; it applies the node's own policy (where `bash_output` or `bash` is denied the read is refused with a sentence) and writes no audit line: it is the owner reading their own chat's output, as reading the chat's events is not audited either, and a row polls every 3 s (an audit row each would be about 29,000 a day, with nothing pruning the table).
The node answers in two places of its own, not `@` completion's; past them the answer is a typed `busy`, which the master turns into a 503 that the page tries again (a refusal in words is final, 409).
The answer is the last 28,000 bytes at most (the master cuts anything more, from the front), on a character boundary, with terminal escape sequences removed (OSC, DCS, APC, PM and SOS strings and an open CSI end at a newline or after 4 KiB, so a command cannot blank the rest of what it prints) and a bare carriage return a line break; a flood of 50 MB or a line with no newline is one bounded answer.
The page shows it as text in a `<pre>` with every control and hidden character made visible, no HTML and no link made from it, and looks only while a row is open (every 3 s while the command runs, once when it ended; never hidden, never while the node is away).
Residual: the half of a key before an escape string that hides its second half is shown (the hidden half is not: it is removed with the string, as a terminal would not show it either); what a command prints is untrusted text the owner reads (the same as the chat's events); a node with only short secrets (under 32 bytes) holds back the last bytes of a running command's output from the scrubber's constant hold, so the strip lags the command by up to 30 bytes; a node that lies about the output misleads only its own owner.
