# T50

## Threat

A chat runs edits or commands without a click that its node or its owner did not allow (the defaults, by the owner's decision of 2026-11-14, in their words: "default accept mode is Auto for every chat type, no limits for apart chat types or agentic host access modes, so each can use auto, always accept, manual, etc...": every new chat, host chats included, and every routine that sets no mode start in `auto`; no mode is limited by the chat's kind or its execution mode): a steered model, a tool's output or a sub-agent switches the chat to a looser approval mode; another account, or the master, asks for one; an "accept edits" chat writes outside its folder through a path, a link or `.git`; a mode recorded before node.toml was tightened, or a sub-agent started before its chat was lowered, keeps running loose

## Mitigation

The mode is per chat (`plan` < `ask_all` < `ask` < `accept_edits` < `auto`; `plan` is T67), set at create and changed only by `session.set_approval_mode`, a command the master sends for the chat's owner or the server's API token (which can already prompt and approve any chat; the per-chat 404 for everyone else, admins included; the login key and Origin); a raise passes the owner's level check and the diverged-log check as a prompt does, and a raise to `auto` is written to the audit log; a lowering is never refused (review F6) and only to a node that announced `approval-max:*`.
The node clamps every request to its own `max_approval_mode` (default `auto`, `policy::DEFAULT_MAX_APPROVAL`) and to nothing else, refuses it for a sub-agent's, a routine's (`no_callbacks`) and a tool-less chat, and records `approval_mode_changed` (the clamped mode, and what was asked when it gave less) through the session actor before applying it; the fold takes the latest, and a load clamps it again against the node.toml of that start.
No tool, model text or tool result reaches that path: the command exists only on the master link.
A sub-agent starts at its chat's mode and reads its parent's mode (and so its ancestors') through the node's session table at every call, also after a restart and when loaded again later; a sub-agent whose parent the node does not hold asks; its own mode cannot be changed (review F2). `accept_edits` lets only `write` and `edit` through unasked, and only when the node, from the call's own input, resolves the path as the file tool does without `allow_outside_workspace` (links followed, a link out or a dangling one refused, `..` normalized, `.git` and the data directory refused, the folder checked against its pin) to a file inside the chat's folder; every command, publish and other mutating tool asks as under `ask`.
A card waiting when the mode changes is not answered by it.
A routine runs in the mode its owner picks when creating or editing it, `auto` by default (the owner's decision of 2026-11-14, in their words: "about routines default mode - auto, still when creating/editing an route - allows to select the mode"; it replaces ADOPTION_PLAN O6): a scheduled routine in `auto` runs commands with nobody present, bounded by the node's `max_approval_mode`, the routine's own mode, the sandbox for sandbox chats, and the `ask` cap for a run holding webhook data (`runner::run_mode`: whoever can send the webhook writes into the prompt).
What the decision gives up: in a `host` chat on `auto` nothing stands between a prompt-injected agent and the machine (every command runs as the node's user, unasked); in a `sandbox` chat on `auto` the sandbox is the boundary (T39, T.8a to T.8e).
The host warning and the picker's Auto line say so.
A node's owner keeps the last word with `max_approval_mode`.
A call the Accept edits rule allowed runs with `allow_outside_workspace` off, so the tool walks the path as the rule did and a link planted in between is refused (review F4).
Residual: An edit inside the folder can still plant what a later command runs (a `Makefile`, a test, `package.json` scripts): in a sandbox chat that command is contained, in a host chat it asks only in Ask or Accept edits and not for a call the person allowed for the chat (T51), and in Auto it runs unasked as the node's user; where it asks, the card shows the command, not the file it runs; `auto` in a sandbox chat rests wholly on the sandbox (T39, T.8a to T.8e).
Tests: `crates/node/tests/approval_modes.rs` (clamped by the node whatever the master sends, a node.toml ceiling of `ask` clamps sandbox and host chats, a host chat accepts auto, a new chat of each kind starts in auto, accept edits covers only edits inside the folder, a model- or tool-written switch changes nothing, the mode survives a restart and is re-clamped, a sub-agent never runs above its chat as it is now, a sub-agent's and a routine's chat refuse a change); `crates/master/tests/it/approval_mode_http.rs` (owner only, 404 for a member, a server admin and a workspace admin, the level check, an old node is not sent it); `core::policy` and `view` tests; `web/src/components/approvalmode.test.tsx`; `web/e2e/approval-mode.cjs`.
