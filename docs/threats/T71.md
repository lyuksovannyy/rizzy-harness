# T71

## Threat

**Images `read` returns** (ADOPTION_PLAN X.23, README "Images" under the file tools): the agent reads a PNG, JPEG, WebP or GIF of the chat's folder and the model is sent the image. (1) Hostile bytes: a decompression bomb, a malformed header, a huge file, a FIFO or device named `.png`, a link out of the folder. (2) Bytes as text, or an SVG (which can carry a script) treated as an image. (3) Megabytes in the log: the master mirrors every event and the UI folds them. (4) A request that is not the one the log rebuilds (the file changed or went, a restart), or one that grows without bound (N images of 5 MB each, every step), or a node that holds them all in memory. (5) A model without vision sent bytes, or a provider that refuses the request every time (an image it cannot read, one too large for it): the chat is wedged (review of PR 130: every later request, a Retry and the next message all failed). (6) Another account sees the image. (7) Text in the image as instructions; secrets in a screenshot.

## Mitigation

(1) The format is told by the first bytes only (`harness_core::image::raster`); nothing is decoded anywhere: the header is read for its size by the bounds-checked readers the master's sniffer shares (`image::dimensions`, a fuzz-style test of short and random headers); the file is opened under `read`'s own rules (`ToolCtx::resolve`, protected folders, links, `open_regular`: no FIFO or device), its size checked before a byte past the magic number is read, at most **3.5 MiB** (`image::MAX_FILE_BYTES`: the providers' limit is on the base64, Anthropic's 5 MiB per image, and 3.5 MiB is 4,893,356 bytes of base64; the first cut, 5 MiB raw, was 6.7 MB of base64 and refused every time), at most 8,000 px a side (`MAX_SIDE`, Anthropic's limit), a header that cannot be read refused.
The person's attached images have the same per-image cap now (the master's `prompt_images` answers 413, the node refuses too); before, one image of 3.75 to 5 MiB sent through the API wedged a chat the same way.
No resizing (the upload path resizes in the browser; no image crate is in the tree, and none was added). (2) A file whose first bytes are not one of the four is read as text, as before (an SVG stays text; a binary stays "looks like a binary file"); the result's text is one line of description, never bytes. (3) The event holds `{sha256, mime, width, height, bytes}` only; the node keeps the bytes in `session_images` (the table the person's images use), deleted with the chat under `secure_delete` (`node/tests/read_images.rs`: nothing the node publishes holds them). (4) The bytes read are the bytes kept, by hash, so a request rebuilds byte for byte from the log and the store after the file changed, went or the node restarted (`agent-native/tests/read_images.rs`, the property test `turn_compaction_review.rs` `rebuild_matches_live_with_image_reads`, with refusals); which images a request shows is decided from the conversation alone (`images::tool_window`: the newest 4, 5 MiB raw together, each under the per-image cap); at most 4 images (5 MiB) per step, 20 per turn, 100 MiB of images a chat (`CHAT_IMAGE_BYTES`, the person's included); a cleared or summarised result loses its image; a summary is told an image was read, never shown it.
The loop's conversation holds no image bytes: a request loads the bytes of the images it shows from the store into a cache that holds exactly those (`tool_wanted`), so a turn holds at most its window's (about 6.7 MB of base64) whatever its length, and loads each once while it stays there (`read_images_refusal.rs` `earlier_turn_images_are_loaded_once_and_held_bounded`, `images_read_this_turn_are_held_only_while_in_the_window`; before, one 3 MiB image from an earlier turn was held 41 times over 41 steps, 172 MB). (5) Only a model in `AgentSpec.vision` (the master's model list, `vision = true`; unlisted is no) gets an image, decided per request, so a fallback or a switch to a model without vision withholds them all; parallel answers get none.
A model that was not shown the image did not read the file: the read-first table records it only when it was shown.
**A refused image does not end the chat:** a request that carried images `read` returned and comes back 400, 413 or 422 (`ProviderError::may_be_the_images`: not a context overflow, not an unknown model; never 401, 403, 404, 429, 5xx or a broken connection) is sent once more, in the same step, with every image it carried withheld.
If that is answered, the loop records `images_withheld` (the calls, the status, the provider's words scrubbed and cut to 200 characters) before the answer; from there on those calls' images are the harness's line ("the provider refused a request that carried the image files …, so they are not shown; reading one of them again sends it alone"), in every rebuilt request too (a Retry's replay, the next turn, a restart, a callback turn); a withheld image keeps its place in the window and no older one is pulled in.
If the resend fails too, it was not the images: the original error stands as before and nothing is recorded.
Withheld by call, not by image: which of up to 4 images the provider refused is not known, so good ones go with a bad one, and a later `read` of a file is a new call, shown again, alone.
A blob the store lost is the harness's line that it could not be loaded, never an older image instead. (6) No route serves them: they are in the node's store only, read by the chat's own turns; the UI shows the path, format and size from the result's text, and the row of a withheld one says so (both folds, from `images_withheld`). (7) The harness's line after the result and the one in front of the image say it is a file from the chat's folder whose text is data, not the person's words.
**Costs:** a refusal costs one wasted request (the provider reports no usage for an error, so the usage and the cost estimate count only the answered resend, once), a rewrite of the prompt cache from the oldest withheld image on, and good images withheld with a bad one.
**Residuals:** the secret scrubber cannot read pixels: a screenshot of a key or a token goes to the provider as it is.
A header that is whole over a damaged body, or an animated GIF (OpenAI's chat API takes only still GIFs), is caught only by the provider's refusal and the resend (no structural checks of the file: they would save one request).
An overflow caused by images is not resolved by the resend (an overflow is excluded from it, and clearing and compaction do not remove images); with at most 4 images shown (about 6,400 tokens at most), accepted.
A crash between keeping the bytes and recording the result leaves an orphan blob that counts toward the chat's 100 MiB until the chat is deleted; there is no node-wide total; after a fallback to a model without vision the earlier results' "sent to you" lines are stale.
An image that is withheld or lost after its `read` still counts as read for the read-first rule (the file is noted when the result is processed, before the next request can be refused), so the model may write over an image file it was never shown.
The resend covers only images `read` returned: a person's attached image that a provider refuses for its content still fails the turn until that message is no longer among the newest that carry images.
A resend that streams some text and then breaks leaves the resend's error standing, not the original refusal (as any broken stream; re-check of PR 130).
A changed file is not noticed: the model sees the bytes it read, by design.
The meter counts 1,000 tokens an image (`IMAGE_CHARS`), providers bill by pixels.
