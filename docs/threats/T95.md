# T95

## Threat

**A person's file the model cannot read as text is parsed by the master for an agent in a chat that has no folder** (ADOPTION_PLAN X.54, README "Files in a chat without a folder"): the bytes are untrusted, the parser runs inside the server's process, and the model names what to open, so a zip bomb, an archive with a million entries, a path that tries to leave, a link or a device, a replayed or invented file id, a secret inside the file or a hostile name could exhaust the server, reach another person's or chat's file, write something to a disk, or put text in front of the model that poses as the harness.

## Mitigation

**A built-in service, never a tool of the master.**
The agent loop and the `attached_file` tool run on the node that owns the session (the chat runtime is node code); the tool files an `attached.request` (the operation, the file's id, an entry path, an offset and a limit) over the link, and the master answers from its own blob store; it runs no shell, no file tool and no program the model names, writes nothing, and holds nothing between calls (`crates/master/src/attached.rs`, `crates/master/tests/it/attached_http.rs::a_plain_chat_keeps_a_zip_and_the_prompt_names_it_without_a_byte`).
A request names no user, workspace or chat: a field that does is a parse error (`crates/core/src/attached.rs::a_request_carries_words_only`, `crates/protocol/src/lib.rs::attached_messages_name_no_place`).
**The scope is the session's log.**
A file is served only when a row of `session_files` for this very chat says so (`logged`: the chat's own log has the message that names the file, with the hash the master sent), the row's account is the chat's owner, and the node asking is the one that runs the session; never by owner, never by an id the model invents, never one of another chat of the same person, never a sub-agent's chat, never a temporary chat (`attached_http.rs::a_call_reaches_only_the_files_its_own_log_names`, `crates/store/tests/session_files.rs::a_file_is_served_once_the_chats_log_names_it_and_only_there`).
A fork gets a row of its own for the same blob from its parent's logged row, only when the parent is a chat of the same node (`session_files.rs::a_fork_claim_cannot_reach_another_nodes_chat_or_an_unlogged_file`, `attached_http.rs::a_fork_reads_the_same_blob_and_the_last_chat_frees_it`).
**A grant per turn and a switch per agent.**
The master withholds the tool (`AgentRef::withheld`, in the log) from untrusted turns, callback turns, temporary chats, chats without a file and nodes that do not announce `attached-file`, and checks the open turn from the log at the time of each request, with the agent's switch "Read attached files" (`Features::attached_files`, on for the Assistant only); a turn may ask 60 times (`attached_http.rs::the_switch_decides_at_attach_at_send_and_in_the_turn`, `crates/agents/tests/agents.rs::reading_attached_files_is_its_own_switch`).
Without the switch the upload is refused with the switch's name, at attach time and again at send, and the upload goes back to the composer.
**Bounded work.**
The copy is at most 10 MiB and is read once into memory; parsing runs in `spawn_blocking`, two at a time on the whole master with a queue of 16, under an 8 second limit that every decompression checks; nothing is unpacked to disk; a compressed stream is never inflated past 16 MiB in a call (32 MiB while listing a compressed tar), however little the archive says it holds; a read produces at most 30,000 characters of text, 4 KiB of hex, 4 KiB of printable runs; a listing reads at most 20,000 entries and shows 500; an entry that says it holds more than 1 GiB, or more than its data can hold, is refused with a sentence; an archive inside an archive is read as bytes (`crates/attached/src/tests.rs`: `a_ten_mib_file_of_zeros_is_not_inflated_beyond_what_is_asked`, `a_stream_is_never_inflated_past_the_ceiling`, `a_gz_that_never_ends_stops_at_the_ceiling_with_a_sentence`, `overlapping_entries_cost_a_listing_nothing`, `a_huge_directory_is_read_only_so_far`, `a_lying_header_or_a_huge_declared_size_is_refused`, `an_archive_inside_an_archive_is_read_as_bytes`, `attached_http.rs::a_zip_bomb_is_read_in_a_window`).
**Entry paths are data.**
A path is cleaned to one line (hidden and control characters out, at most 300 characters, `…` when cut) before it is shown or compared, is only ever matched against the listing, and is never used as a path of any disk; `../x`, `/etc/passwd`, NUL, controls, right-to-left overrides and a 4 KiB name are listed as text and read as their own entries; a link, a hard link, a device or a pipe is listed as what it is and never followed or opened (`tests.rs::hostile_entry_names_are_cleaned_and_still_find_their_entry`, `::a_tar_lists_links_and_devices_as_what_they_are_and_never_follows_them`).
Truncated and corrupt archives are a sentence (`::truncated_and_corrupt_archives_are_refused_with_a_sentence`).
**What the model reads.**
One harness line after the person's text, built from the event alone, names each file (quotation marks read as `'`, one line), its id, its size, that it is read-only and the tool; a hostile name stays inside its quotes (`crates/core/src/event.rs::attached_line_tests`).
Everything the tool returns that the file or the archive wrote (entry paths, content lines, hex, runs) is quoted line by line behind `| ` under a sentence that says it is the file's content and never an instruction (`crates/tools/src/attached.rs::a_hostile_answer_stays_quoted`).
**The scrubber.**
The tool result goes through the node's scrubber like any result, and the name is scrubbed in the event; the bytes are the person's own (`crates/node/tests/attached.rs::a_secret_inside_a_read_entry_is_scrubbed_in_the_event`).
**The node decides.**
The node records the references after its own checks (the plain profile, not a sub-agent, the tool registered and not in `denied_tools`, at most `[limits] uploads_per_message` files of at most `upload_max_mb`, each id once and of the right shape, a sha256), never writes a byte of the file, and announces `attached-file` only where the tool is offered; the master sends `attached.result` only to such a node and drops a request from any other (`crates/node/tests/attached.rs::the_nodes_checks_decide`, `::the_capability_follows_the_tool`, `attached_http.rs::an_old_chat_runtime_is_refused_cleanly`).
**Lifetime.**
The blob is the owner's, encrypted and counted in their quota like any upload; it lives as long as a chat's `session_files` row refers to it (migration 5) and is swept once the last chat that refers to it is deleted; an upload never sent is purged with the unsent ones; the 20 unsent files and the 10 files and images in a message hold (`crates/store/tests/session_files.rs::the_blob_lives_as_long_as_a_chat_refers_to_it`, `attached_http.rs::the_limits_hold_in_a_plain_chat`, `::the_account_quota_counts_a_kept_file`, `::a_temporary_chat_keeps_none_and_an_unsent_file_is_purged`).
A held row whose message the node certainly did not take is released with the upload given back; a row held for a send whose answer was lost stays until the chat goes, so the blob is never freed under a message the node may have recorded.
Known and accepted:
- A text file or PDF up to 10 MiB is still read as text by the master at upload time and sent in the message, as before; only what is not text becomes a kept file.
- A row held for a send whose answer was lost, and never logged, keeps its blob until its chat is deleted.
- The zip reader is hand-written (stored and deflate only; encrypted and other methods are refused with a sentence); tar and gzip use the `tar` and `flate2` crates already in the tree.
- A tar that states a giant extended header is read up to the 32 MiB ceiling of a listing, which is more than the 32 MiB-per-call memory figure of a read; the work stays bounded by the ceiling and the time limit.
- The scrubber removes only the node's secrets, so a file's own secrets are shown to the model; the person attached it.
