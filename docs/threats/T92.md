# T92

## Threat

**A person's fork of a chat copies its log into a new chat that can run commands in the same folder** (ADOPTION_PLAN C.2 and X.48, README "Fork a chat", docs/fork.md): a fork that a model, a tool, a routine or another account could cause would let an attacker clone a conversation (with its approvals, its secrets in tool output and its memory of instructions) into a chat of their choosing; a copy that carried the parent's grants, snapshots or side effects with it would give the new chat power or effects it was never given; and a master that took a copied event for a fresh one would act twice (a fact filed twice, a file published again, a chat resumed that nobody resumed); and, for a fork with a folder of its own (part 2), a node that ran git inside the parent's repository would run what an agent planted in that repository's `.git` (config, hooks, filters, `core.fsmonitor`, aliases, attributes), and the node is not sandboxed: a sandbox escape

## Mitigation

**Only the chat's owner causes one.**
`POST /api/sessions/{id}/fork` resolves the chat as every request that changes it does and then requires the account to be the chat's owner (the API token only for a chat nobody owns): anyone else, a server admin and a workspace admin included, gets the 404 of a chat that does not exist and nothing is sent to the node (`crates/master/tests/it/fork_http.rs`).
The model has no tool for it, no model, tool or routine text reaches the route, and the node starts one only from `session.fork`, which the master sends for that route.
A sub-agent's chat, a routine's run, a turn that has not ended, a turn a rewind took out and a chat on a node without the capability are refused (`harness_core::fork::check`, run by the master on its mirror and by the node on its own log).
**The node decides, and the new chat starts with nothing the old one was given.**
The folder is checked as at a create (`workspace_roots`, protected folders) and the execution mode must still be one the node offers; the owner's level and workspace are checked as for a prompt.
No grant is inherited (they are bound to the parent's folder: `Session::load` and the view fold take them from the fork's own events only; `a_chat_grant_is_not_inherited_by_the_fork` fails without the filter), no copied checkpoint can be restored in the fork (its refs are the parent's), and the file tools' seen table starts empty so an edit needs a fresh read (`crates/node/tests/fork.rs`, `crates/tools/src/seen.rs`).
The approval mode is the one the parent had at the cut, clamped by `node.toml` as at any create.
"Rewind files" in a fork to a message it copied is refused whole, because the folder would go back to before a copied turn whose snapshot is the parent's chat's; a rewind of the conversation alone works.
A fork of an incognito chat is incognito: it is not indexed, not in recall and not in earlier chats.
The fork's images are copied under its own id in the same transaction, so deleting the parent does not take them.
A cut inside a message that called several agents is said in the fork (`peers_skipped`, reason `forked`), so a node restart does not append a false "the node restarted".
**The parent is only read.**
The copy reads the parent's events `1..=T` from the node's store: the parent's later events, its running turn and its folder are not touched, and the fork's log is written, with the image bytes its events name, in one transaction (a crash leaves nothing or a whole chat).
Background commands running in the parent at the cut are not the fork's: each is closed by a `background_ended` with reason `forked`, which never calls back and says whose the command is.
**A copy is never a second effect.**
`Master::apply` runs one check first (`crates/master/src/forks.rs`): an event at or below the fork's `through_seq` (but never the first) is mirrored and shown and nothing else happens: no memory fact is filed again (its dedupe key holds the chat's id, so a copy would file it twice), no artifact version, no callback, no connector state.
The guard is the protection, not the divider: with it off, `a_copied_remember_is_filed_once`, `a_copied_background_end_applied_before_the_divider_calls_nothing_back` and `copied_turn_events_move_no_connector_grant_state` fail.
The routines watcher needs no guard, because it acts only on chats it launched and on sub-agent chats, which a fork is not.
The lineage is read before an event is taken, so a failed read stops the event (the node sends it again) and is never cached as "not a fork", and an event that arrives before the chat's first is not cached either (`a_failed_lineage_read_is_not_cached_and_the_copy_is_not_applied`).
The search index and the usage sums skip copies in the store (the parent holds them), and the callback watcher starts after the divider.
While the copy arrives the store moves only `head_seq` and the event row, so the fork never shows the parent's running, asking or unread state (`a_forks_row_stays_idle_after_every_copied_event`).
The "earlier chats" list and hand-off notes read a fork's own events only (`harness_core::fork::own`), so a fork with no turn of its own is not listed and is due no note.
Other readers of a chat's log by time were made to skip copies: another chat's undo (`others.rs`; without it the parent could not undo an old turn, refused as foreign work) and a deleted chat's write tombstone.
**What a lying node can do:** a node that wrote a false `forked` into its own chat's first event only hides that chat's own effects from the master (the claim must name another id and at least two events); the master's row, owner and workspace come from the master, never from the event.
**A late ack changes nothing about who owns the fork:** the create intent the master recorded before it sent the command carries the owner, the workspace, the parent's project and the follow-the-defaults mark, so a fork that arrives after the timeout is claimed and linked as one that did not.
**A fork's folder is the person's choice** (`session.fork` carries `checkout: "own" | "shared"`; the page offers both, "own" first where the node announced `fork_own`).
With `shared` each chat's changes are in the other's files (the page says so, and the T57 rules protect one chat's undo from reverting the other's work).
**An own copy never runs git in the parent's repository (part 2).**
The only command that touches the parent repository is `git clone --no-local --no-checkout --template= -- <parent root> <dest>`, run by the hardened runner of `crates/node/src/git.rs` (cleared environment, the node's command-line overrides, no system or global config) with its working directory outside both folders (the node's staging folder; the search for a repository above it is stopped by `GIT_CEILING_DIRECTORIES`).
There is no `git -C <parent>`, no `GIT_DIR` pointing at the parent's `.git` and no `git worktree add`; `git worktree add` runs inside the repository, reads its config, which is shared across worktrees, and runs its `post-checkout` hook, which a sandboxed agent can write.
Everything after the clone is the harness's: the copy's config is written by the harness (the clone's own, plus remote `upstream` when the parent had a usable `origin`), the branch `fork/<short id>` is made with `update-ref` at the commit the parent's log says HEAD was on at the cut (else the parent's HEAD now, and the chat says so), the working files are written from the cut's checkpoint by the checkpoint writers (attributes from the empty tree: no filter runs), the index is set to the branch's commit, and the parent's `.git/info/exclude` is copied as data (ignore patterns, so the same files stay ignored).
The parent's `origin` URL is read as data with `git config --file <parent>/.git/config --no-includes --get remote.origin.url`, which parses one file and runs nothing, and is kept only when it is plain text of a transport a person uses: https, ssh or scp-like, a file path or `file://`, with no control character or whitespace, not starting with `-`, and without `::` (`ext::`, other remote helpers); otherwise the copy has no `upstream`.
A parent whose `.git` is a file or a link, has a `commondir`, borrows objects (`objects/info/alternates`), whose `objects` or `refs` is a link, whose HEAD names no commit, or whose `packed-refs` git rejects, is refused before or by the clone, with the reason (`git/fork_copy.rs::check_source`).
Where the copy goes: the node's projects folder (`[projects] dir`, the place forge clones go), built in the staging folder (0700, protected, emptied at every start, so a copy half made when the node was killed is swept) and moved in with `renameat2(RENAME_NOREPLACE)`, which never replaces or follows what holds the name, then checked as a session folder (`policy.check_cwd`: inside `workspace_roots`, not protected).
No projects folder, a folder outside `workspace_roots`, no checkpoint store, a checkpoint that was pruned, a git older than the minimum below, no room on the disk (the repository's `.git` plus the tree, with a margin), a copy over `[limits] clone_max_mb`, `clone_timeout_s` exceeded, and more than `projects_per_hour` folders in an hour are each refused with a sentence that says which and that "the same folder" is possible, before the fork's chat is written.
A failure removes the build folder; a copy whose chat could not be written is removed while it is still the folder that was made; a kill between the move and the chat leaves a complete, valid clone in the projects folder that no chat uses (nothing half made).
The master waits for the ack as long as a node may take to copy (`MAX_CLONE_TIMEOUT_S`); the page shows "Making the copy…" and cannot close the choice meanwhile.
`session_created.forked.own_folder` says the folder is the fork's own; deleting the chat never deletes the folder, and the delete dialog says where it is.
**What is not copied:** files git ignores (build output, `.env`, `node_modules`), nested repositories and submodule contents, stashes, and the parent's hooks and local config.
Uncommitted and untracked files of the parent at the cut are in the copy, uncommitted.
**Minimum git:** 2.45.1, or 2.39.4, 2.40.2, 2.41.1, 2.42.2, 2.43.4, 2.44.1 on their lines; the node refuses an own copy below it and says which version it found.
Those releases (May 2024) fixed, in the release notes of v2.39.4 and v2.45.1 (https://raw.githubusercontent.com/git/git/master/Documentation/RelNotes/2.39.4.adoc and https://raw.githubusercontent.com/git/git/master/Documentation/RelNotes/2.45.1.adoc): CVE-2024-32004, "the ownership checks introduced in v2.30.3 are now extended to cover cloning local repositories", "Repositories can be configured to execute arbitrary code during local clones" (CVE-2024-32004); local clones that hard-link files into the target's object database (CVE-2024-32020, CVE-2024-32021); "Git can be tricked to run arbitrary code as part of the clone" (CVE-2024-32465); and the defence-in-depth items "clone: prevent hooks from running during a clone" and "core.hooksPath: add some protection while cloning".
`--no-local` does not use the local-clone path those fixes concern; the minimum is defence in depth.
This machine has 2.56.1.
**The documentation this rests on** (read on 2026-11-21; the pages were fetched through a summarising tool, and each sentence below was returned as a quotation of the page):
- https://git-scm.com/docs/git#_security: "Some configuration options and hook files may cause Git to run arbitrary shell commands. Because configuration and hooks are not copied using git clone, it is generally safe to clone remote repositories with untrusted content, inspect them with git log, and so on." and "However, it is not safe to run Git commands in a .git directory (or the working tree that surrounds it) when that .git directory itself comes from an untrusted source. The commands in its config and hooks are executed in the usual way." and "If you have an untrusted .git directory, you should first clone it with git clone --no-local to obtain a clean copy."
- https://git-scm.com/docs/git-upload-pack (SECURITY): "upload-pack tries to avoid any dangerous configuration options or hooks from the repository it's serving, making it safe to clone an untrusted directory and run commands on the resulting clone."
- https://git-scm.com/docs/git-config (`uploadpack.packObjectsHook`, the design note put this on the upload-pack page; it is on this one): "Note that this configuration variable is only respected when it is specified in protected configuration (see SCOPES). This is a safety measure against fetching from untrusted repositories." and (SCOPES) "Protected configuration refers to the system, global, and command scopes. For security reasons, certain options are only respected when they are specified in protected configuration, and ignored otherwise." The node's overrides are command-line (command scope); `--file`: "For reading options: read only from the specified file rather than from all available files."
- https://git-scm.com/docs/git-clone: `--local` "bypasses the normal "Git aware" transport mechanism and clones the repository by making a copy of HEAD and everything under objects and refs directories. The files under .git/objects/ directory are hardlinked to save space when possible."; "This option does not work with repositories owned by other users for security reasons, and --no-local must be specified for the clone to succeed."; "Specifying --no-local will override the default when /path/to/repo is given, using the regular Git transport instead."; `--shared`: "this is a possibly dangerous operation; do not use it unless you understand what it does" (the clone corrupts when the source prunes); `--no-checkout`: "Do not checkout HEAD after the clone is complete."; `--template`: "Specify the directory from which templates will be used".
- https://git-scm.com/docs/githooks (post-checkout): "It is also run after git-clone, unless the --no-checkout (-n) option is used." and "Likewise for git worktree add unless --no-checkout is used."
- https://git-scm.com/docs/git-init (TEMPLATE DIRECTORY): "Files and directories in the template directory whose name do not start with a dot will be copied to the $GIT_DIR after it is created." The page does not say what an empty `--template=` does; the hostile-repository test shows on 2.56.1 that the copy has no `hooks` folder at all.
The claim that a clone copies no configuration or hook is on the git(1) page (above), not on git-clone's; every claim of the design note held.
**The proof:** `git_fork_tests.rs` (beside `making_a_worktree_runs_no_hooks`) builds a parent whose own `.git` tries to run a program in more than seventy ways (every hook, `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, `core.editor`, `core.gitProxy`, `core.askPass`, `core.alternateRefsCommand`, `uploadpack.packObjectsHook`, aliases, clean, smudge and process filters with a committed `.gitattributes`, `diff.external`, textconv, merge drivers, `credential.helper`, `gpg.program` with `commit.gpgsign`, `include.path` and `includeIf`, `url.*.insteadOf`, `protocol.*.allow`, `receive.*` and `transfer.*`, `core.attributesFile`, `.git/info/attributes`, a template directory, a gitlink with a `file://` submodule URL and `submodule.*.update`, `remote.origin.uploadpack`) and odd shapes (`objects` or `refs` a link, `.git` a file, a link or with a `commondir`, alternates outside, a bare repository inside the tree, a HEAD that points nowhere, huge or malformed `packed-refs`, refs named `$(…)`, `;…`, `--upload-pack=…`, backticks); each plants a marker script.
It runs the whole own-copy operation and asserts no marker exists, the parent's folder and `.git` are byte for byte as they were, no object file of the copy is a hard link to the parent's, the copy's config holds none of it, and the result is a correct copy or a refusal that left nothing.
`the_test_notices_a_worktree_add` and `the_test_notices_a_plain_clone` prove it can fail: with the clone replaced by `git -C <parent> worktree add` the parent's hooks run (markers), with a plain `git clone` and a node template directory the template's `post-checkout` runs and the objects are hard links.
Other tests: `crates/node/src/fork_checkout.rs` (a full disk, a clone that dies midway, a taken name, a narrowed node.toml, the sweep, discard of a replaced folder), `crates/node/tests/fork_checkout.rs` (the cut's files on a real node, undo in both chats, two forks at once, refusals leave no chat and no folder, delete keeps the folder), `crates/master/tests/it/fork_http.rs`, `web/src/components/forkchoice.test.tsx`.
**Not done, stated plainly:** the clone runs under the node's hardening but not in the sandbox jail the checkpoint calls use (`Repo::jail`); it relies on `upload-pack`'s rules above, and on the node's `git` being the one on its `PATH`.
A fork made while the parent is working reads a consistent set of objects (upload-pack), and the tree is the cut's checkpoint, not the parent's current files.
**Not changed:** the parent's memory facts, published files and sub-agent chats stay the parent's, and the fork's model is told only that its copied background commands belong to the parent; a fork copies everything the owner saw in the conversation, secrets in tool output included, into a chat the same person owns.
