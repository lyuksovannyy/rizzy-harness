# T92

## Threat

**A person's fork of a chat copies its log into a new chat that can run commands in the same folder** (ADOPTION_PLAN C.2 and X.48, README "Fork a chat", docs/fork.md): a fork that a model, a tool, a routine or another account could cause would let an attacker clone a conversation (with its approvals, its secrets in tool output and its memory of instructions) into a chat of their choosing; a copy that carried the parent's grants, snapshots or side effects with it would give the new chat power or effects it was never given; and a master that took a copied event for a fresh one would act twice (a fact filed twice, a file published again, a chat resumed that nobody resumed); and, for a fork with a folder of its own (part 2), a node that ran git inside the parent's repository would run what an agent planted in that repository's `.git` (config, hooks, filters, `core.fsmonitor`, aliases, attributes), and the node is not sandboxed: a sandbox escape

## Mitigation

**Only the chat's owner causes one.**
`POST /api/sessions/{id}/fork` resolves the chat as every request that changes it does and then requires the account to be the chat's owner (the API token only for a chat nobody owns): anyone else, a server admin and a workspace admin included, gets the 404 of a chat that does not exist and nothing is sent to the node (`crates/master/tests/it/fork_http.rs`).
The model has no tool for it, no model, tool or routine text reaches the route, and the node starts one only from `session.fork`, which the master sends for that route.
A sub-agent's chat, a routine's run, a turn that has not ended, a turn a rewind took out and a chat on a node without the capability are refused (`harness_core::fork::check`, run by the master on its mirror and by the node on its own log).
**The node decides, and the new chat starts with nothing the old one was given.**
The folder is checked as at a create (`workspace_roots`, protected folders) and the execution mode must still be one the node offers; the owner's level and workspace are checked as for a prompt.
No grant is inherited (they are bound to the parent's folder: `Session::load` and the view fold take them from the fork's own events only; `a_chat_grant_is_not_inherited_by_the_fork` fails without the filter), no copied checkpoint can be restored in the fork (its refs are the parent's), and the file tools' seen table starts empty so an edit needs a fresh read (`crates/node/tests/fork.rs`, `crates/tools/src/seen.rs`).
The approval mode is the one the parent had at the cut, clamped by `node.toml` as at any create.
"Rewind files" in a fork to a message it copied is refused whole, because the folder would go back to before a copied turn whose snapshot is the parent's chat's; a rewind of the conversation alone works.
A fork of an incognito chat is incognito: it is not indexed, not in recall and not in earlier chats.
The fork's images are copied under its own id in the same transaction, so deleting the parent does not take them.
A cut inside a message that called several agents is said in the fork (`peers_skipped`, reason `forked`), so a node restart does not append a false "the node restarted".
**The parent is only read.**
The copy reads the parent's events `1..=T` from the node's store: the parent's later events, its running turn and its folder are not touched, and the fork's log is written, with the image bytes its events name, in one transaction (a crash leaves nothing or a whole chat).
Background commands running in the parent at the cut are not the fork's: each is closed by a `background_ended` with reason `forked`, which never calls back and says whose the command is.
**A copy is never a second effect.**
`Master::apply` runs one check first (`crates/master/src/forks.rs`): an event at or below the fork's `through_seq` (but never the first) is mirrored and shown and nothing else happens: no memory fact is filed again (its dedupe key holds the chat's id, so a copy would file it twice), no artifact version, no callback, no connector state.
The guard is the protection, not the divider: with it off, `a_copied_remember_is_filed_once`, `a_copied_background_end_applied_before_the_divider_calls_nothing_back` and `copied_turn_events_move_no_connector_grant_state` fail.
The routines watcher needs no guard, because it acts only on chats it launched and on sub-agent chats, which a fork is not.
The lineage is read before an event is taken, so a failed read stops the event (the node sends it again) and is never cached as "not a fork", and an event that arrives before the chat's first is not cached either (`a_failed_lineage_read_is_not_cached_and_the_copy_is_not_applied`).
The search index and the usage sums skip copies in the store (the parent holds them), and the callback watcher starts after the divider.
While the copy arrives the store moves only `head_seq` and the event row, so the fork never shows the parent's running, asking or unread state (`a_forks_row_stays_idle_after_every_copied_event`).
The "earlier chats" list and hand-off notes read a fork's own events only (`harness_core::fork::own`), so a fork with no turn of its own is not listed and is due no note.
Other readers of a chat's log by time were made to skip copies: another chat's undo (`others.rs`; without it the parent could not undo an old turn, refused as foreign work) and a deleted chat's write tombstone.
**What a lying node can do:** a node that wrote a false `forked` into its own chat's first event only hides that chat's own effects from the master (the claim must name another id and at least two events); the master's row, owner and workspace come from the master, never from the event.
**A late ack changes nothing about who owns the fork:** the create intent the master recorded before it sent the command carries the owner, the workspace, the parent's project and the follow-the-defaults mark, so a fork that arrives after the timeout is claimed and linked as one that did not.
**A fork's folder is the person's choice** (`session.fork` carries `checkout: "own" | "shared"`; the page offers both, "own" first where the node announced `fork_own`).
With `shared` each chat's changes are in the other's files (the page says so, and the T57 rules protect one chat's undo from reverting the other's work).
**An own copy never opens the parent's repository with git, and never follows a link inside it (part 2).**
The first design cloned the parent with `git clone --no-local` and relied on `upload-pack` being safe.
The review of it found that `upload-pack` runs in the parent's `.git`, as the node's user, and follows every link an agent planted there: `refs/heads/<x>`, `objects/pack/*.pack`, `objects/pack` itself, `objects/xx/<rest>` and `config` (the fork then held another repository's history, or its `origin` URL with credentials as `upstream`); it also reads the file `core.attributesFile` names in the parent's config and echoes a token of it in an error.
So the copy has two stages, both in the node's staging folder (0700, protected, emptied at every start).
Stage 1 is a sanitised copy made by the harness's own code, with no git process (`crates/node/src/git/fork_sanitise.rs`).
It walks the parent's `.git` with file descriptors only: `openat` with `O_NOFOLLOW | O_CLOEXEC` from the descriptor of the folder that holds each entry (`O_DIRECTORY` for folders), the kind from `fstat` on an `O_PATH` descriptor (so a FIFO, socket or device is never opened for reading and nothing waits), a second `fstat` on the readable descriptor that must be the same regular file, and no path-based `stat`, `open` or `read_link` on anything below `.git`.
It copies only `HEAD`, `refs/`, `packed-refs`, `shallow` and `objects/`, as new files made with `O_EXCL` (bytes copied, never hard-linked).
It copies no `config`, `hooks`, `info/`, `worktrees/`, `modules/`, `index`, `logs/` or `grafts`.
`HEAD`, the loose refs, `packed-refs` and `shallow` are not copied as bytes: each is parsed and written again from what parses, so a hostile file cannot reach git's own parsers.
A loose ref or `HEAD` is at most 512 bytes and holds a commit id (40 hex digits) and a newline, or `ref: <name>`; one that does not is refused by name, because skipping it would give a fork without that branch.
`packed-refs` (at most 16 MiB) is rewritten from its header (`# pack-refs with:` and the traits git knows), `<id> <refname>` lines and `^<id>` peel lines, and a file that says `sorted` must be; `shallow` is commit ids, one per line; any other line refuses the copy by its line number and never shows its content.
Every ref name (a file's name, a symbolic ref's target, a name in `packed-refs`) must be one `git check-ref-format` accepts, checked by the same rules in code, with no git process on the input.
Anything under what it copies that is not a regular file or a folder (a link, a FIFO, a socket, a device) ends the whole copy in a refusal that names the relative path, because skipping it would give a fork with a ref or a pack missing.
`objects/info/alternates` and `http-alternates` are never copied and refuse the copy when they hold anything; a `commondir` or `gitdir` file, a `.git` that is a file or a link, a missing `HEAD`, a HEAD that names no commit, the sha256 object format and the reftable ref storage are refused with a sentence.
The order is `HEAD`, loose refs, `packed-refs`, then objects, so every object a copied ref names existed when the ref was read and a parent that keeps working cannot make a ref point at an object the copy lacks; a parent repacked at that moment can still give a copy whose objects are missing, and stage 2 then fails cleanly and the person can try again.
The parent's `config` and `info/exclude` are read as data: a regular file, at most 1 MiB, its bytes copied into a file in the staging folder.
`git config --file <that staging file> --no-includes --list -z` parses the copy of the config (never a path in the parent), and the harness takes `remote.origin.url`, `extensions.objectformat`, `extensions.refstorage` and `core.repositoryformatversion` from it.
`upstream` is kept only when the URL is plain text of a transport a person uses (https, ssh or scp-like, a file path or `file://`; no control character or whitespace, not starting with `-`, no `::`); the user name and password of an https URL and the password of any other URL (`ssh://user:pw@host/x` becomes `ssh://user@host/x`) are dropped before it is stored, a scp-like form whose user part holds a `:` is refused, and a URL with a query or a fragment (a token may sit there) or an `http://` URL gives no `upstream` at all (the fork is not refused).
The harness writes the sanitised copy's own `config` (`repositoryformatversion = 0`, `bare = true`); nothing of the parent's config reaches the fork.
Bounds, all failing closed: bytes (`[limits] clone_max_mb`, counted as the walk copies), 1,000,000 files and folders, 32 levels of folders, 1 MiB for the config and for `info/exclude`, and `[limits] clone_timeout_s` for each stage; a cancelled copy stops the walk.
Stage 2 is `git clone --no-local --no-checkout --template= -- <sanitised copy> <dest>` by the hardened runner (cleared environment, the node's command-line overrides, no system or global config), from the sanitised copy and never from the parent.
It runs inside the same sandbox jail the checkpoint calls use whenever the node has one (`Repo::jail`), with only the sanitised copy's folder and the destination visible read-write and nothing of the parent mounted; `crates/cli/tests/fork_copy_sandbox.rs` runs it through the real wrapper.
On a node with `[sandbox] mode = "off"` there is no jail and the clone runs hardened but unjailed, which is acceptable here because git no longer touches anything an agent's links could redirect: its source is a folder the harness made, whose files are plain bytes and whose config is the harness's.
The sanitised copy is deleted after the clone, and by a `Drop` guard if the copy fails or is cancelled.
Git's own text is never shown or logged for stage 2 and the steps after it: it can quote bytes of the staged files (`bad shallow line: <line>`, `unexpected line in ./packed-refs: <line>`), so a failed step is a fixed sentence naming the step and the node's log keeps the step and the exit code only (`no_byte_of_a_staged_file_is_in_an_error_or_a_log_line`, `git_text_is_never_shown_for_stage_two_and_after`).
There is no `git -C <parent>`, no `GIT_DIR` pointing at the parent's `.git` and no `git worktree add` (it runs inside the repository, reads its shared config and runs its `post-checkout` hook).
`no_git_process_is_started_in_or_pointed_at_the_parent` logs every git the operation starts through a stand-in `git` and fails if any names the parent's folder; the mutation that reads the parent's config with `git config` pointed at it fails that test.
Everything after the clone is the harness's: remote `origin` is the parent's path, to fetch from, and its `pushurl` is `/nonexistent/no-push--bring-work-back-with-git-fetch-from-the-parent`, a path git prints back in its own error (a push into the parent would run `receive-pack` there, with the hooks and config an agent may have planted, as the person; work comes back with `git fetch <fork folder> fork/<short id>` run in the parent).
The branch `fork/<short id>` is made with `update-ref` at the commit the parent's log says HEAD was on at the cut (else the parent's HEAD now, and the chat says so), the working files are written from the cut's checkpoint by the checkpoint writers (attributes from the empty tree: no filter runs), the index is set to the branch's commit, the folder's size is measured again after the files are written, and the parent's `info/exclude` bytes become the fork's own (ignore patterns, so the same files stay ignored).
The size of the cut's files is counted from a streamed `ls-tree`; a listing that fails, is too long or times out refuses the copy, and what the copy's git calls keep in memory is capped (1 MiB of stdout, 64 KiB of stderr).
**Running any git command by hand inside a repository an agent could write to is the person's own risk.**
The git(1) SECURITY section says "it is not safe to run Git commands in a .git directory (or the working tree that surrounds it) when that .git directory itself comes from an untrusted source", and a chat's folder, the parent's and a fork's alike, is a place an agent can write; the fork's own config is the harness's, but the person's `git fetch` in the parent runs the parent's config and hooks as them, exactly as `git status` there would.
Where the copy goes: the node's projects folder (`[projects] dir`, the place forge clones go), built in the staging folder (0700, protected, emptied at every start, so a copy half made when the node was killed is swept) and moved in with `renameat2(RENAME_NOREPLACE)`, which never replaces or follows what holds the name, then checked as a session folder (`policy.check_cwd`: inside `workspace_roots`, not protected).
No projects folder, a folder outside `workspace_roots`, no checkpoint store, a checkpoint that was pruned, a git older than the minimum below, no room on the disk (the repository's `.git` plus the tree, with a margin), a copy over `[limits] clone_max_mb`, `clone_timeout_s` exceeded, and more than `projects_per_hour` folders in an hour are each refused with a sentence that says which and that "the same folder" is possible, before the fork's chat is written.
A failure or a cancelled copy removes the build folder and the sanitised copy (`Drop` guards; the walk's blocking task owns the sanitised copy's folder, so a cancel cannot remove it under the walk and it goes when the task ends); the marker and the move into the projects folder are one blocking task, so a cancelled request either never reaches it or leaves the marker beside the folder it made, and a `Copy` dropped before its chat is stored keeps its marker too (`a_cancel_during_the_walk_does_not_remove_its_folder_under_it`, `a_cancel_during_the_move_leaves_a_marker_for_the_folder_it_made`, `a_copy_dropped_before_its_chat_keeps_its_marker`); a copy whose chat could not be written is removed while it is still the folder that was made; a kill between the move and the chat leaves a marker (`pending-fork-<build>` in the staging folder, the folder's device and inode) that the next start decides about: a folder is removed only when it is a direct child of the projects folder with that identity, no session in the node's store works in it or under it, and nothing in it (looked at with descriptors, no link followed, within bounds) was modified later than the marker plus two seconds; otherwise it is kept, the marker goes and one log line names the folder for the person to decide (`the_sweep_keeps_the_folder_of_a_chat_that_exists`, `the_sweep_keeps_a_folder_with_a_file_newer_than_the_copy`, `the_sweep_keeps_an_unrelated_folder_that_reused_the_inode`, `the_sweep_removes_only_a_direct_child`).
The hourly limit is reserved before the copy starts and given back on failure, so copies at once cannot all pass it.
The master waits for the ack as long as a node may take to copy (`MAX_CLONE_TIMEOUT_S`); the page shows "Making the copy…" and cannot close the choice meanwhile.
`session_created.forked.own_folder` says the folder is the fork's own; deleting the chat never deletes the folder, and the delete dialog says where it is.
**What is not copied:** files git ignores (build output, `.env`, `node_modules`), nested repositories and submodule contents, stashes, and the parent's hooks and local config.
Uncommitted and untracked files of the parent at the cut are in the copy, uncommitted.
**Minimum git:** 2.45.1, or 2.39.4, 2.40.2, 2.41.1, 2.42.2, 2.43.4, 2.44.1 on their lines; the node refuses an own copy below it and says which version it found.
Those releases (May 2024) fixed, in the release notes of v2.39.4 and v2.45.1 (https://raw.githubusercontent.com/git/git/master/Documentation/RelNotes/2.39.4.adoc and https://raw.githubusercontent.com/git/git/master/Documentation/RelNotes/2.45.1.adoc): CVE-2024-32004, "the ownership checks introduced in v2.30.3 are now extended to cover cloning local repositories", "Repositories can be configured to execute arbitrary code during local clones" (CVE-2024-32004); local clones that hard-link files into the target's object database (CVE-2024-32020, CVE-2024-32021); "Git can be tricked to run arbitrary code as part of the clone" (CVE-2024-32465); and the defence-in-depth items "clone: prevent hooks from running during a clone" and "core.hooksPath: add some protection while cloning".
`--no-local` does not use the local-clone path those fixes concern; the minimum is defence in depth.
This machine has 2.56.1.

The claim that a clone copies no configuration or hook is on the git(1) page (above), not on git-clone's; every claim of the design note held.
**The proof of the sanitised copy:** `git_fork_tests.rs::leaks` plants, beside a "victim" repository holding a secret string, links in every place upload-pack followed (pack files with a loose ref naming the victim's commit, a ref link absolute and relative, `objects/pack` as a link, a folder of refs as a link, loose-object links, `packed-refs` and `config` as links) and asserts the string, the victim's objects and its URL are nowhere in the fork and the operation ends in a refusal naming the path; FIFOs and a socket at every copied path are refused in under four seconds; a 40 MB config is refused by the cap; `include.path` is not followed; userinfo is stripped; `core.attributesFile` and a `grafts` file appear in no message; sha256 and reftable parents are refused; the byte and entry bounds refuse; and a parent that commits, makes refs and repacks while it is copied gives a fork whose every ref has its objects or a refusal.
**The proof the parent is not run:** `git_fork_tests.rs`
 (beside `making_a_worktree_runs_no_hooks`) builds a parent whose own `.git` tries to run a program in more than seventy ways (every hook, `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, `core.editor`, `core.gitProxy`, `core.askPass`, `core.alternateRefsCommand`, `uploadpack.packObjectsHook`, aliases, clean, smudge and process filters with a committed `.gitattributes`, `diff.external`, textconv, merge drivers, `credential.helper`, `gpg.program` with `commit.gpgsign`, `include.path` and `includeIf`, `url.*.insteadOf`, `protocol.*.allow`, `receive.*` and `transfer.*`, `core.attributesFile`, `.git/info/attributes`, a template directory, a gitlink with a `file://` submodule URL and `submodule.*.update`, `remote.origin.uploadpack`) and odd shapes (`objects` or `refs` a link, `.git` a file, a link or with a `commondir`, alternates outside, a bare repository inside the tree, a HEAD that points nowhere, huge or malformed `packed-refs`, refs named `$(…)`, `;…`, `--upload-pack=…`, backticks); each plants a marker script.
It runs the whole own-copy operation and asserts no marker exists, the parent's folder and `.git` are byte for byte as they were, no object file of the copy is a hard link to the parent's, the copy's config holds none of it, and the result is a correct copy or a refusal that left nothing.
`the_test_notices_a_worktree_add` and `the_test_notices_a_plain_clone` prove it can fail: with the clone replaced by `git -C <parent> worktree add` the parent's hooks run (markers), with a plain `git clone` and a node template directory the template's `post-checkout` runs and the objects are hard links.
Other tests: `crates/node/src/fork_checkout.rs` (a full disk, a clone that dies midway, a taken name, a narrowed node.toml, the sweep, discard of a replaced folder), `crates/node/tests/fork_checkout.rs` (the cut's files on a real node, undo in both chats, two forks at once, refusals leave no chat and no folder, delete keeps the folder), `crates/master/tests/it/fork_http.rs`, `web/src/components/forkchoice.test.tsx`.
**Not done, stated plainly:** the clone relies on the node's `git` being the one on its `PATH`, and a node without the sandbox runs it unjailed (see above).
The walk is not atomic against a parent that is repacked while it runs; the copy then fails or is refused, never wrong, and the tree written is the cut's checkpoint, not the parent's current files.
The room estimate (`git_dir_bytes`) is a first pass of the same walk (`fork_sanitise::measure`): file descriptors and `O_NOFOLLOW`, the same bounds on bytes, entries, depth and time, cancelled when the future is dropped, nothing opened for reading; no path-based call on anything below the parent's folder is made anywhere on the copy path.
A kill between the chat's write and the marker's removal leaves a marker for a folder that has a chat: the next start sees the chat in the node's store and keeps the folder.
A folder kept because a file in it is newer than the copy, or because it could not be checked within the bounds, is left for the person (one log line names it).
**Not changed:** the parent's memory facts, published files and sub-agent chats stay the parent's, and the fork's model is told only that its copied background commands belong to the parent; a fork copies everything the owner saw in the conversation, secrets in tool output included, into a chat the same person owns.
