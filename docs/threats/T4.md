# T4

## Threat

Prompt injection from repo content makes the model run harmful commands

## Mitigation

Default approval mode `auto` since the owner's decision of 2026-11-14 (T50): a new chat runs every tool without a click unless its owner picks Accept edits or Ask, or the node's `max_approval_mode` is lower.
In Ask every mutating tool (bash, edit, write) needs a human click; read-only tools are confined to the session workspace. **bash and graphify run in a Landlock sandbox** (`rizzy-harness sandbox-exec`, `[sandbox]` in node.toml, FIX_PLAN 2.7): read-write only the session folder and a per-session `TMPDIR` (a sub-agent works in its own node-owned folder instead, with read-only access to the repository's object store only, T32), read-only `/usr /bin /sbin /lib* /etc /opt /proc` and node.toml's `[sandbox] read`, read-write `[sandbox] write`, five device files (not `/dev/tty`: TIOCSTI); `no_new_privs` (setuid programs such as `sudo` fail);
TCP connect/bind denied with `network = "off"` (default on, Q6); with the network off the contained shell (T9) also runs in a network namespace of its own (`bwrap --unshare-net`, ADOPTION_PLAN T.8b): only its own loopback, so no UDP or DNS leaves and the host's abstract Unix sockets are absent; the containment probe checks the namespace by identity (the command's `/proc/self/ns/net` is not the node's, in both forms of `/proc`; not by the interface list, which a tunnel module fills: review T8B-2).
Where the probe with `--unshare-net` fails and the one without passes, the start tries once more; if that fails too, `[execution] sandbox = "strict"` does not offer the sandbox mode (N.10a), naming what failed (bubblewrap's message, or the probe's own identity check), and `"auto"` still contains (PID namespace, guard, Landlock inside) without it, its containment line a warning "network off WITH A GAP" (TCP stopped by Landlock, UDP and DNS out, abstract sockets as Landlock's ABI allows).
An `"auto"` node in that gap keeps its bubblewrap and, when a shell command is started, probes the namespace again at most every 60 s (`STEP_UP_INTERVAL`), on a thread of its own, one at a time, each bounded by 2 s (`LATER_PROBE_BOUND`: then killed through the guard's channel and counted as failed); the command that noticed does not wait (re-check R-2).
From the first that passes, commands started from then on are in a namespace of their own, logged; the node only steps up, never down (`StepUp` in its `Sandbox`).
What remains of T8B-1: a node is below where it could be until its next shell command after the interval, and the command that triggers a probe, and every command already running, keep the mode they started in; a node whose probes all failed at start, or with no bubblewrap found, does not offer the sandbox mode and never probes again (N.10a removed re-check R-1's step up from Landlock alone: nothing would use it); `strict` does not offer the mode until restarted.
Only the node's own probes decide, held in its own `Sandbox`; nothing per call or from the protocol.
Below Landlock ABI 9 a resolver that answers over a named Unix socket is still reachable and can look names up for a command (review N-1, not tested; T.8c's file view closes it).
Tests: `crates/cli/tests/network_off.rs`.
With TCP on, the agent can start a server on another port of the person's machine.
When they open it in the browser that is logged in to the harness, the browser sends the harness cookie along (cookies are not separated by port).
Since Gate 3 P-1 the cookie alone authenticates nothing: approvals, events and admin actions need the login key that the page keeps in its own origin (T2). `network = "off"` would close the agent's side too, but it breaks dev servers and package installs, so it stays a per-node choice; abstract Unix socket and signal scoping (ABI 6) and pathname Unix socket connects (ABI 9) best-effort. `mode = "required"` (default) refuses agentic sessions (and `node run` refuses to start) unless a start-up self-test through the wrapper is denied a canary in the data directory and the kernel enforces Landlock ABI 3 in full (plus ABI 4 TCP rights with `network = "off"`); a `[sandbox]` entry or system folder that equals, contains or is inside the data directory stops the node.
Tests: `crates/cli/tests/sandbox.rs`, `tests/data_dir.rs`.
File tools walk every path with `lstat`: a symlink that dangles or leaves the workspace is refused, `write`/`edit` do not follow a link at the last component, and nothing is written under `.git` (its config and hooks run commands).
Stored shell output (`tool_output`) has random ids and belongs to the session that produced it.
**A session's folder is pinned by path, device and inode** (R.1, review S-2; `harness_core::folder::FolderPin`): taken when the session is made (and, after a restart, when it is loaded, from the canonical path the log recorded); `FolderPin::check` (the path still canonicalises to itself and is the same directory) runs before every use: `ToolCtx::resolve`/`resolve_for_write`/`workspace_dir` (every file tool, `grep` and `glob` without a path), `Confinement::command` before any grant is built (bash, graphify; the command then starts in the checked path), `Session::checked_folder` before every turn, restore, delegation, checkpoint and the write of an undo, and every publish.
A replaced folder is refused with "this session's folder was replaced", and nothing is read, written or granted there.
The per-call part of this held through the real agent loop only from 2026-11-13 (fix/turn-host-folder-pin): from 1220e1a (pin) and f83a87a (owned folder) until then the loop's `Logged` wrapper did not forward `TurnHost::folder_pin`/`owned_folder`, so every tool call in production ran with neither (no per-call pin check; a writing sub-agent's `write` and shell refused in its own folder); `agent-native/tests/host_forwarding.rs` now fails if a wrapper drops them.
The same per-turn check also tests `workspace_roots` and the protected folders again (before, only the data directory).
The review found that a sub-agent could rename its own worktree away and put a link to `~/.ssh` in its place, after which `read` (no approval), `write` and the next shell followed it; a sub-agent's folder is now node-owned and out of every other session's reach (T32).
Tests: `node/tests/runtime.rs` `a_session_whose_folder_was_replaced_refuses_to_work`, `cli/tests/sub_agent_sandbox.rs` (`a_sandboxed_sub_agent_cannot_point_its_folder_at_another_one`, `the_file_tools_and_the_shell_refuse_a_replaced_folder`), `core/src/folder.rs`.
Residual: the path is resolved again by whatever uses it after the check (an `open`, a `chdir`), so a swap inside that window (microseconds to a millisecond) is followed once; only a process that may write the folder's parent can swap it, and no sandboxed shell may (a session's folder is the top of its own grant; a sub-agent's folder lies in the node's protected sessions folder, `cli/tests/sub_agent_sandbox.rs`).
**The node's own git reads a session's folder in the sandbox** (R.1, fix review 3 R1b-2): every git process of a checkpoint or sub-agent shadow (snapshots, the sub-agent's base and result, the fill of its folder, restore's reads, copies, gc, a published file's state) is started through `sandbox-exec` with read-only on the folder and on the borrowed object store, read-write on its own shadow (where every private index lives) and, while it fills a new sub-agent folder, on that folder; nothing else of the data directory or the home folder (`git::command_std`, `Sandbox::helper`; node.toml's `[sandbox] read`/`write` are not added).
Before, a process the session left running could swap a folder in it for a link while a snapshot walked it, and the node's unsandboxed git read the outside file into the checkpoint, and into a sub-agent's folder with no click: built as a test, 4 of 300 snapshots and 2 of 100 sub-agent folders held a canary from outside the folder or from a fake data directory; confined, 0 and 0 (`cli/tests/snapshot_sandbox.rs`).
A second line: a new file whose folder really lies outside the folder or in a protected one is left out of the snapshot (`git::inside_only`).
A link inside the folder is stored as a link, never followed, confined or not.
The cost: one more process per git call; a checkpoint of a 100,000-file folder took 1.66 s confined against 1.57 s (the next one 0.36 s against 0.34 s).
The start-up log and `doctor` ("checkpoint git") say whether it is confined; with `mode = "off"` it is not, and the read window is open there (residual).
Where the node itself writes into a folder a session can still change (an undo, a sub-agent's result written into the parent's folder), it writes relative to directories it opened without following links (T33), so there is no window there; the review's proof that a left-running process won the old window on 7 to 17 of 120 delegations (R1-2) now lands 0 of 120 (`git::child_tests::no_swap_during_the_child_folder_fill_writes_into_another_folder`).
After a restart a folder replaced while the node was down by another real directory at the same path is not noticed (the inode is taken at load; storing it in the log would refuse a folder restored from a backup forever).
An intermediate directory swapped for a link between check and open is followed (by the file tools; the sandbox still bounds bash); sandbox residuals in R2.
"Allow for this turn" (`allow_session`) allows **this exact call** again in the turn, never the tool as a whole (final review A1, ADOPTION_PLAN A.2): the key is the tool and its canonical argument (`harness_tools::call_key`, a SHA-256; the argument is not kept): `bash`'s command string byte for byte with its other arguments, `write`/`edit`'s real target path and the rest of their input, any other tool's input as sorted-key JSON.
Approving `ls` never lets `rm -rf x` run unasked.
It is offered and honoured from the first request for a call, because it covers only the call shown on that card.
The answer is bound by its approval id to that one request, and the loop records that call's own key.
It lasts until the turn ends; a sub-agent starts without it; a single allow covers one call; a `node.toml` denial is resolved by the node and can never be covered.
Tests: `tools/src/approval.rs`, `agent-native` (`turn_allowance_*`), `node/tests/runtime.rs` (`allow_for_this_turn_*`, `a_single_allow_does_not_cover_the_next_identical_call`, `a_sub_agent_does_not_inherit_allow_for_this_turn`, `a_policy_denied_call_cannot_be_allowed_for_the_turn`).
**Residual:** a symlink on a `write`/`edit` path swapped between the key check and the tool's own resolve sends an allowed write elsewhere inside the workspace (the same window as the file tools' own residual above).
**The approval card** (Gate 3 fix review 2, W-1; `web/src/components/CallInput.tsx`, `web/src/lib/callText.ts`) shows the call as it will run, for every tool: every key and value of the input (named fields for `bash`, `write`, `edit`, `delegate`, `publish`; any other tool, or a key the layout does not name, as a complete key-by-key list), rendered from the input object the event carried, strings as themselves (never escaped JSON, never markup).
Nothing is cut silently: a text over 1,500 characters or 40 lines states its size, shows its first and its last part (an attacker picks the middle), says how many characters of the middle are not shown, and opens in place; while any part is collapsed, Allow stays usable and a line beside the buttons (their `aria-describedby`) says "You are approving N characters you have not expanded".
Text wraps and no box has a fixed height.
Runs of blanks are counted markers (`⟨500 spaces⟩`, `⟨60 line breaks⟩`; 8 spaces, 4 tabs or 3 breaks in a command or short value, 40/8/6 in file content and prose).
Hidden, control and unusual blank characters are `<U+…>` codes (`showHidden`, W-5: a rule by Unicode category, not a list, in `web/src/md/hiddenChars.ts`: every control (Cc) except tab and line feed, format (Cf), private-use (Co), unassigned (Cn), lone-surrogate (Cs), space (Zs) except the plain one, line and paragraph separator (Zl, Zp) and default-ignorable character, plus a short named list of blanks that are letters or symbols by category (braille blank, Hangul and Khmer fillers, grapheme joiner, object replacement); a variation selector right after a pictograph is the one exception, and chat titles and names also keep the zero-width joiner of emoji sequences. Each marker is its own element, so text that merely looks like one is not one; a test checks that the strip's set is inside the marked set).
In a command, a path or a short value, a word mixing scripts is named with its odd letters (`сurl`: Cyrillic с U+0441); a whole word in another script, and Japanese/Korean/Latin-with-CJK mixes, are not flagged, and there is no confusables table. `write`/`edit`/`publish` paths have their own wrapping line, with "absolute path", "outside this chat's folder" (lexical, against the chat's `cwd`) or "leaves this chat's folder through .." when the input shows it; links and the node's policy are not visible to the card.
The buttons read "Allow once", "Allow this exact call for this turn" (only when the request carries `turn_allow`) and "Deny".
**What the card cannot do:** make anyone read it (a person can approve without expanding, and is told so, not stopped), judge intent (a fully shown `curl … | sh` is still approvable), or show what the node resolves (a symlink's target, a path the policy will refuse).
Tests: `web/src/components/approvalcard.test.tsx`, `review-gate3.test.tsx`.
**A sandbox grant is checked by identity when it is opened** (R.1, fix review 4 R1c-1): every grant passed to `sandbox-exec` names what it expects there (`Grant`, `Expect`): the device and inode the node took when it pinned or made the folder (the session's folder from its pin, a sub-agent's folder and its `.git`, the borrowed object store when `user_repo` accepted it, a shadow, the temp and output folders), or the explicit marker that no session can write the path (the system folders, the device files, node.toml's `[sandbox] read`/`write`); the command line forces one of the two for every grant.
The wrapper opens each path once (`O_PATH`, `O_NOFOLLOW` for an identity grant), compares the opened descriptor's device and inode, and builds the Landlock rule from that same descriptor; a mismatch refuses the whole command before anything runs, naming the grant ("the folder granted as the session's folder was replaced").
So no grant follows a link swapped in between a check and the sandbox's open, and the sandbox side of S-2's check-then-use window is gone.
The fix review proved that a process the parent left running could replace `<repo>/.git/objects` by a link to `~/.ssh` and the child's shell then read the key (R1c-1); now the node leaves out a store that is no longer the one it accepted (the child loses history, gains nothing) and the wrapper refuses it if it changes after that check.
Tests: `cli/tests/sub_agent_sandbox.rs` `a_replaced_object_store_is_never_granted_to_a_child` (`objects` and `.git` replaced, links to `~/.ssh` and to the data directory), `the_wrapper_refuses_a_grant_that_was_replaced_and_names_it` (the session's folder swapped after its pin check), `cli/tests/snapshot_sandbox.rs` `the_nodes_git_never_follows_a_replaced_object_store`.
Residual: a path marked not session-writable is opened following links, so a future grant marked so wrongly would reopen the hole; `exposes` still judges the agent's grants by real path first, a cheap first line behind which the identity check stands. **node.toml's `[sandbox] read`/`write` entries are no longer marked so** (R.4, fix review 5 R1d-1): an entry may lie where a session can write (inside a workspace root, which by default is the whole home folder, or inside another `write` entry), so a process the session left running could replace it by a link and the next command was granted the link's target.
At start the node records where each entry's path really leads (canonicalized), and nothing more; at each command it canonicalizes the entry again, grants it only if it still leads to that same place, and passes the identity it finds there now, which the wrapper checks on the descriptor it opens (`Extra::grant`).
The identity is therefore taken per command, not at start.
A link put in its place, or in place of a folder above it, gets nothing; a file rewritten by renaming a new one over it (as git does with `~/.gitconfig`) keeps its grant.
Refused at start, naming the key and the path (`check_extras_against_roots`, `exposes`): an entry that equals or contains a workspace root; one that equals, contains or is inside a protected folder; one inside another `write` entry (whose folder every command may change; the outer entry already grants it), naming both (fix review 6 R4-1); and one below a workspace root whose path holds a symbolic link below the root, each component checked with `lstat` and the link named, with the advice to list the real path (R4-1: a chat may have put that link in place of a real folder while the node was down, and the next start would otherwise grant its target; a real toolchain folder such as `~/.cargo` passes).
Not refused: an entry inside a workspace root.
Refusing it, as the review proposed, would refuse every toolchain entry the README lists under the default root (`$HOME`), and the identity binding closes the swap without that.
Tests: `tools/src/sandbox.rs` `an_extra_replaced_by_a_link_is_not_granted`, `an_extra_that_holds_a_workspace_root_is_refused`; `tools/tests/review_gate3_extras.rs` (the reviewer's R4-1 proof, inverted: `review_r4_1_an_extra_swapped_before_a_restart_is_refused_at_the_restart`, and `an_extra_inside_a_write_extra_is_refused_at_start`).
Residual: an entry listed through a link that lies outside every workspace root and leads into one is checked only where it leads, so a swap there before a restart is not caught; listing the real path avoids it.
Residual: graphify's install folders (its venv and Python) are still granted following links; they are found from the binary's path at each call, never taken from a session.
Fix review 5's notes, accepted: the identity is device and inode, and an inode number can be reused after a delete (ext4); a session cannot delete the node-owned grants, and for its own folder a reused inode would hold its own content, so nothing is gained. `exposes` canonicalizes an extra at start, following a link present then: that is the operator's choice, judged once.
**Accepted (R.4)** from the Gate 3 reads. *Writes outside the folder* (review N-2): with `allow_outside_workspace = true` the file tools may write anywhere the OS user may, `~/.bashrc` and `~/.gitconfig` included, which is code execution outside the sandbox at the user's next shell; the sandbox bounds only bash and graphify, and the protected folders are only the data directory and `protected_dirs`.
Accepted because the key exists for exactly that, is off by default and is a node.toml choice; the README says so where the key is documented.
It would change with a refused list of start-up files that holds even with the key on. *The card* (fix review 3): a person can approve a long input without expanding its middle; the card says how much is unread and does not stop them, a deliberate choice, since a forced expand is one more reflex click and pushes people towards `auto` (W-4).
A word wholly in another script (`сору`) is not named, only mixed ones (N-1); text shaped like the card's own markers (`⟨500 spaces⟩`), which fix review 3 found told apart only by colour (N-2), is no longer mistaken for one since W-5 made each marker its own element; the card renders the tool call's input, not the approval event's copy, which the node sends from the same value (N-3; a fold-time comparison would guard the day that stops holding).
Not checked without a real browser (R.6): that a wrapped command lays out with nothing off-screen, screen-reader output, the warning colour in the light theme.
Any of these would be reopened by a card change or a browser run that shows otherwise.
