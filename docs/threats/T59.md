# T59

## Threat

**Shortening what the model is sent inside a turn** (ADOPTION_PLAN X.15, `docs/turn-compaction.md`): old tool results are replaced by a stub and a turn's earlier steps by a model-written summary, mid-turn.
A hostile tool result (a page, a file, command output) could survive into the stub as the harness's own line, or steer, trigger or prevent clearing; a summary could carry injected text as the person's words or as fact; the model could lose the person's instructions, a message they sent during the turn or its task list; it could think it still has a file it no longer sees and edit from memory; it could use clearing to escape the repeated-call guard (T40); a restart or a retry could send other bytes than the log implies, or a cut on every step could make every request re-read the whole conversation

## Mitigation

**A stub holds no result text:** it is built from the call (the tool's name when it is a plain name, one argument as a JSON string on one line through `quoted_line`, cut to 120 characters) and the result's line and character counts, and it is sent as the call's note after an empty result, so the result's own `[harness]` lines go with the result (test `a_hostile_result_plants_nothing_in_its_stub`).
**Only size triggers it:** the request's estimate against the window's line; nothing a model or a tool writes is read as a switch (a step alone over the line has its older results cleared, all but its newest).
**The model is told:** where a window is known, the system prompt says once that old results may be cleared, to write down what it will need and to read a cleared result again before relying on it (the live test saw a model answer from cleared results without re-reading).
**The summary is model text everywhere:** quoted line by line behind `| ` under the harness's line, in a message of its own after the turn's opening (never inside the person's message; review P1), never the person's (the transcript the summariser reads is T38's), and shown in the chat as text (`<p>{text}</p>`, test in `conversation.test.tsx`).
**Kept verbatim:** the opening (the person's words, attachments' framing, the context block with its standing sections), the person's messages sent during summarised steps, the task list (in the event, re-sent under the summary), the newest steps (test `an_in_turn_summary_keeps_the_opening_sections_queued_and_tasks`); the `todo` tool's results and every load of a skill's instructions are never cleared.
**What the opening reads stays in the log (review H1):** a summary of earlier turns made inside a turn stops before the turn in which a queued message the running turn reads at its start was sent, and before a background end logged after the last turn (a callback turn's opening), so the log still rebuilds that opening (`queued_before_the_turn_survives_an_in_turn_summary`, `a_callback_turns_ends_survive_an_in_turn_summary`, and the property test `rebuild_matches_live_at_every_step`: about 1,750 requests compared byte for byte over random steps).
**Measured size:** the provider's correction is capped at twice our estimate, so a router that over-reports cannot make every step look full (`an_over_reporting_router`).
With a known window the count-based mask does not act; clearing replaces it (review M1).
**Files:** the read-before-write table (T45) is outside the history and unchanged; a cleared `read` stub says the file still counts as read and to read it again for its text; an `edit` after it still needs its old text to match, and a changed file is still refused by its hash.
**The guard:** a call whose result left the request may repeat once without counting (`RepeatGuard::forgive`), once per call per turn, so a stuck model is refused after at most four more runs (`clearing_does_not_defeat_the_repeat_guard`, `a_reread_after_clearing_is_not_a_loop`).
**Recorded:** each cut is a `context_shortened` event through the session's one writer, before the request; `rebuild` applies it, so the next turn starts with the same bytes (`the_log_rebuilds_the_same_request`).
**Bounded:** clearing is linear in the history; a cut frees down to half the line, a check waits until the request grew by a quarter of it, so never on consecutive steps (300 steps of 6,000-character results with the default token-saving settings: 7 rewrites on a 128k window, 52 on 32k, `shortening_is_rare_and_never_on_consecutive_steps`, `mask_and_clearing_at_128k`); a summary of steps is asked for only when dropping those steps would make room (`a_window_the_fixed_part_fills_ends_through_the_last_resort`); at most 12 summaries of a turn's steps, each in one request that fits the window;
A.7's shrink check and breaker apply (`a_summary_that_does_not_shrink_is_dropped_and_the_breaker_holds`); the wrap-up on a provider's refusal stays the last resort.
Sub-agents run the same loop (`a_sub_agent_is_shortened_the_same_way`).
**Residual:** a cleared result is gone from the model's view until it calls the tool again, and a weak model may answer from it anyway (live: `mistral-small` made up a constant from a cleared read; `mistral-medium` re-read and was right); for a tool that changes things (`bash`, `write`, MCP) the stub asks it not to re-run only to see the output, which a model may ignore (the approval path still applies to the re-run); a summary can lose a detail the model needed, as any compaction does; for a model with an unknown window the count-based mask (`keep_tool_outputs`) still rewrites the newest outputs every `keep` steps.
