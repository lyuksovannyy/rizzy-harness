# T94

## Threat

**A person's file the model cannot read is written into a chat's folder by the node** (ADOPTION_PLAN X.53, README "Any other file"): the bytes come from a browser through the master to a node and land in a folder the agent can also write to, so a name, a planted link, a replayed id or a full disk could write outside the folder, overwrite the person's or the agent's files, leave a file without a message, or let one account send another's file.

## Mitigation

**The node writes, the master only forwards.**
The master stores the upload as the owner's encrypted blob and pushes it in 256 KiB `session.upload` chunks, one in flight, each acked, in the chat's lane ahead of the prompt; it runs no file tool and writes nothing into any folder (`crates/master/tests/it/uploads_http.rs::a_zip_is_stored_pushed_in_chunks_and_named_in_the_prompt`).
**The node decides.**
`[limits] upload_max_mb` (10) and `uploads_per_message` (10) are the node's; the master follows what the node announces and checks again, the node refuses a larger first chunk, a larger prompt and more files on its own, and a prompt that claims a bigger size than the node allows saves nothing (`crates/node/tests/uploads.rs::the_nodes_limits_decide`).
**One safe name.**
The name is the last path segment, hidden characters and controls out, look-alikes of `/` and `\` and Windows-reserved characters `_`, no leading dot, dash or space, at most 120 bytes with the extension kept, `file` when nothing is left; `../../x`, `/etc/passwd`, `a/b`, `...`, `-rf`, NUL, a 300-byte name and a Windows path each give one component inside `attachments/` (`crates/node/src/uploads_tests.rs::a_name_becomes_one_safe_component`).
**Nothing followed, nothing replaced.**
The folder and `attachments` are opened with `O_DIRECTORY | O_NOFOLLOW` (the folder is checked against the session's pin first), a link or a file where `attachments` should be is refused with a sentence and nothing is written, the bytes go to a create-exclusive temporary name and get their name with `renameat2(RENAME_NOREPLACE)` (`linkat` where the filesystem lacks it), so a name taken by a file, a folder or a link, dangling or not, becomes `x (2).ext` and the target of a planted link is untouched (`uploads_tests.rs::attachments_planted_as_a_link_is_not_followed`, `::a_planted_link_in_the_name_is_never_written_through_or_replaced`, `::the_same_name_twice_does_not_overwrite`).
**Checked before it gets its name.**
The staged file lives in the node's protected data directory (no agent can write there), its size and sha256 are checked at the last chunk and again as it is copied into the folder, and a wrong hash, a short or long file, a gap, a chunk over 256 KiB or a second start leaves nothing behind; staging is bounded (16 files, an hour) and emptied at start (`uploads_tests.rs::a_wrong_hash_or_size_saves_nothing`, `::bad_chunks_are_refused_and_delete_what_was_staged`).
**A full disk or a dropped link saves nothing.**
A failed copy removes its temporary file and says so; a link that drops mid-push fails the send before any prompt, the master gives the upload back, and the node's partial copy is replaced by the next start or swept (`uploads_tests.rs::a_full_disk_saves_nothing_and_says_so`, `uploads_http.rs::a_chunk_the_node_refuses_stops_the_send`).
**Only the owner's upload, once.**
An upload id belongs to the account that made it (the API token may use any, as for text attachments); another account's id, an unknown id and one already used are `400` and consume nothing; the row is held while a send uses it, given back when the node certainly did not take the message, and not given back when only the answer was lost (the node may have the file), then purged with the unsent text after the TTL (`uploads_http.rs::another_persons_upload_is_not_theirs_to_send`, `::a_lost_answer_does_not_give_the_upload_back`, `::an_abandoned_upload_is_purged`, `crates/store/tests/chat_uploads.rs`).
**No file without a message.**
The files are saved last in building the message and taken back (only the very file saved: same device and inode) if the message is not recorded; a refused prompt records nothing and writes nothing (`crates/node/tests/uploads.rs::a_planted_attachments_link_refuses_the_prompt`, `uploads_tests.rs::a_rollback_removes_only_the_saved_file`).
**A chat without tools, a sub-agent, an old node.**
A plain chat refuses the file at attach time and at send, a sub-agent's chat takes none, a node that does not announce `uploads` refuses the send with "update the node" and the composer keeps the file (`uploads_http.rs::a_plain_chat_refuses_the_file_with_the_reason`, `::an_old_node_refuses_the_send_and_nothing_is_lost`, `crates/node/tests/uploads.rs::a_chat_without_tools_and_a_node_without_staging_refuse`).
**Undo keeps it.**
The file is written before the turn's `before` checkpoint, so undoing the turn leaves what the person attached; a message sent while a turn runs may not carry files, since its file would land inside that turn's changes (`crates/node/tests/uploads.rs::undoing_the_turn_leaves_the_attached_file`, `::a_message_with_files_waits_for_the_running_turn`).
**What the model reads.**
One harness line after the person's text lists each path (made one line, quotation marks read as `'`) and size, built from the event alone so every request rebuilds the same bytes; it ends the person's own words like every harness line (`crates/core/src/event.rs::upload_line_tests`, `crates/agent-native/src/history_tests.rs::the_persons_words_end_before_the_line_about_saved_files`).
The file's content is never put in front of the model by the harness: the agent opens it with its own tools under their rules, and a zip's content is the agent's to treat as untrusted like any file of the folder.
**The scrubber.**
The name and path are text and are scrubbed in the event like any text, and the name is scrubbed before the file is named so the recorded path is the real one; the bytes are the person's own and are not scrubbed, so a secret inside an attached file is saved as it is (`crates/node/tests/uploads.rs::the_name_is_scrubbed_in_the_event_but_the_bytes_are_not`).
Not undone, stated plainly: an attached file stays in the folder after a rewind, a fork shares it, and the agent in that folder (or any process of the same user) can read, change or delete it; a zip is not unpacked or inspected by the harness.
**By construction, not tested.**
The files are saved last in building the message, and taken back if `begin()` then fails to record it; no test reaches that arm (it needs the node's log to refuse a write at that moment), so the order and `rollback` (tested alone) are the evidence.
**A send cut off.**
The take, the send and the done or give-back run in a task of their own and the prompt route has no wall-time limit (each chunk has its ack wait, files are at most 10 MiB, at most 10 a message), so a request that is dropped cannot strand an upload (`uploads_http.rs::a_dropped_send_does_not_strand_the_upload`, `::a_dropped_send_the_node_took_is_finished`); the prompt's ack wait grows by 0.5 s per MiB of files it names (`uploads.rs::the_ack_wait_grows_with_the_bytes_a_prompt_carries`).
**Limits of every kind.**
Every attachment is at most 10 MiB, and a message carries at most 10 files and images together (counted on the master at send and in the composer); images keep their lower limits, 4 a message and 3.5 MiB each (`uploads_http.rs::a_message_carries_at_most_ten_files_and_images_together`).
Known and accepted:
- Up to 10 MiB of a body is held before the upload slot is taken (as the old route did).
- `agentic=1` is granted to an account without coding chats, bounded by the account quota and the 20 unsent files.
- The upload route resolves the chat with `acting_session`, which marks a chat another caller acts in (the API token) as foreign although nothing is sent.
- The name travels in the query string, which a reverse proxy in front of the server may log (the old route did the same); the server logs only the path.
- After a refusal because a turn is running, the retry pushes the files again.
- The folder is re-opened by path after the pin check (T4's window), never to overwrite.
