# T9

## Threat

Runaway processes

## Mitigation

**A command's processes outlive its `bash` call only as a background command the node holds (T.8d, T36), and never outlive its timeout, its session, its owner's access or the node, where Landlock ABI 9 (Linux 7.1) closes Unix sockets** (a background command is the same command, held in its session's table instead of the call: in a `sandbox` chat the contained one, in a `host` chat the same command under the guard without bubblewrap, by the owner's decision of 2026-11-20 ("Yes, allow"; proof and leftovers below); its timeout, `bash_stop`, the session's deletion, the master's `session.stop_background` for a revoked owner and the node's stop each stop it through its guard, and the node's death ends it as any command; tests `cli/tests/background.rs`) (ADOPTION_PLAN T.8a, T.8e; experiments B.1, B.11; condition from review T8A-1, `docs/security-review/2026-11-T8a-containment.md`): each `bash` call runs as `sandbox-guard --mark <temp root> --mark-session <id> -- bwrap --die-with-parent --new-session --unshare-pid --proc /proc --dev /dev <the file view> --remount-ro / -- /.rizzy-harness/rizzy-harness sandbox-exec … -- bash -c` (`tools/src/contain.rs`, `tools/src/guard.rs`), so it is a PID namespace whose init is bwrap's; when the init dies the kernel kills every process in it, `setsid`, `nohup`, double-forked and SIGTERM-ignoring children included.
**The guard** (T.8e) is one short-lived process of our own binary per command, bubblewrap's parent, started from a descriptor of `/proc/self/exe` the node opens once at start and keeps (`/proc/self/fd/<n>`: the node's own running image, whatever is at the binary's path now: review T8E-5, tested with the binary replaced by a command; `/proc/self/exe` resolved at each spawn would name a test binary's own image in the tests).
Its stdin is one end of a Unix socket pair whose other end the node holds, close-on-exec: the command never holds it (tested), but for the moment between `fork` and `exec` every child the node forks has a copy, and a child that waits there (its `chdir` into a folder that does not answer, as the node's git does into a session's folder) holds every guard's channel open past the node's death (review T8E-1).
So the channel is the fast path, not the only one: the guard is given the node's pid (`--node`), checks `getppid()` against it before it starts bubblewrap and at least every 500 ms after, and takes a different parent (the kernel reparents it when the node process dies, whoever holds descriptors; a node thread that ends is not that, tested) as the kill order (`a_node_killed_while_a_child_waits_before_exec_leaves_nothing`: gone within 2 s, where before the command ran on until the folder answered).
The channel closing is the kill order the kernel delivers whenever the node dies and nothing else holds it, `kill -9` included; the node half-closes it to cancel (a byte first asks for the graceful stop: SIGTERM to the command's session, the namespace init's, found as bwrap's only child in `/proc/<bwrap>/task/<bwrap>/children`, then 2 s), and dropping a `ContainedChild` anywhere closes it.
The guard is a child subreaper, kills with `contain::kill_namespace` (stop bwrap's group, SIGKILL the init it names, then the group) and SIGKILLs its own children, and repeats until `waitpid` gives ECHILD; a namespace's init is reaped only after every process in it is released, so that is the proof nothing is left.
It then reports "ended" to the node; if something is still not reaped 2 s after the kill (a process in uninterruptible I/O), it reports "still alive" once and keeps killing, and the tool result says so instead of "cancelled".
A cancel or timeout returns only after that report, or after the node's own bound for a guard that does not answer (2 s grace, 2 s, 300 ms), when the result says the end is not confirmed; with the sweep below (300 ms) and the output drain (100 ms) that fits inside the agent loop's 5 s `TOOL_CANCEL_GRACE` (asserted against the constants; review T8E-3: the bound was 5 s and could never be recorded).
A tool the loop does abandon at its grace is recorded as "stop ordered … abandoned: whether what it started has ended is not known", for every tool, not "[cancelled]".
A confirmed contained stop says so ("its guard confirmed the end (N ms)"), distinct from the uncontained "process group killed"; a `host` background command's says only what its guard proves: "the command and every process descended from it were killed, and that end is confirmed; what it asked another service to start (a container runtime, a systemd unit, an already running tmux or similar server) is not covered"; a stop signal sent to the guard itself is reported as that, not as the command's exit code.
**While the node lives** (review T8E-2): when a contained command's guard dies of a signal (in its first millisecond, before bubblewrap or its init set the death signal, the namespace would run on) or does not answer a stop, the tool runs the sweep for that one session before it returns (`contain::sweep_session`: orphans only; a namespace under a live guard, another command of the same session, is never touched, tested) and the result says what it found (`a_guard_killed_in_its_first_millisecond_leaves_nothing_once_the_tool_returned`: 0 left, where 61 of 260 ran on before). bubblewrap's `--die-with-parent` names the guard's only thread, so a guard killed by itself takes the namespace with it, and the spawner thread of T.8a is gone (a command spawned from a thread that ends at once runs to its end: tested).
The guard starts in `/` (bubblewrap enters the folder), so the spawn itself does not enter the session's folder; but the bash tool resolves that folder in the node first, in its async task, and a folder that already hangs holds the call there before any guard exists, where neither the cancel nor the loop's grace reaches it (review N-1, observed; the same on `main`).
A folder that stops answering after that check stalls bubblewrap under its guard, which kills and reports it still alive.
It costs one more `exec` of the harness binary per command: about 1.4 ms (median of 40, debug build; unchanged by the 500 ms look at its parent) over bubblewrap started directly, and about 4 MB of private memory (debug) while its command runs; it does not exist otherwise.
**Second line:** at start, before it serves, the node ends namespaces a dead node left (`contain::sweep`): processes of its own user whose command line carries `--mark <its temp root>`, that are not a guard and whose parent does not carry the mark (bwrap whose guard died, or an init whose bwrap died), each stopped, checked again (same start time), its child killed, then it; and it sends SIGTERM (the guard's kill order) to every guard with its mark whose node is dead.
Each is named in the log, with whether it ended.
"Ended" means the process and the children it was killed with have no `/proc` entry or are zombies (a killed init waiting for a process in uninterruptible I/O has an empty command line and is not ended: review T8E-4); what has not ended within 2 s is logged STILL ALIVE (killed; it ends when the kernel releases it) and never "ended"; nothing is kept for a later start, which kills nothing that carries no mark (re-check R-2: a file of pids to kill was a way to make the node kill other processes; `the_sweep_does_not_call_a_stuck_leftover_ended`, `a_planted_leftovers_file_kills_nothing`).
A session text in the log comes from a process's own arguments and is printed escaped (`a_session_with_a_line_break_injects_nothing`).
A guard is told to stop only when its parent is no longer the pid of its own `--node` (its node is dead), never by comparing with the process that is starting: a second start on a live node's data directory leaves that node's commands alone (re-check R-1, `a_second_start_leaves_the_live_nodes_commands_alone`); a guard without a readable `--node` is left alone and named.
A process without the mark, with another data directory's, or under a live guard is never touched (tested with the user's own other bubblewraps running); the start's sweep is tested through `serve` (`the_node_start_sweeps_what_a_dead_node_left`).
**The binary's path** (review T8E-5, **closed for contained commands by T.8f**, T.8c's bind of the image replaced): the guard opens its own running image (`/proc/self/exe`, the node's: it was started from it) `O_PATH`, not close-on-exec, and gives bubblewrap `/proc/self/fd/<n>` as the program to run; bubblewrap names no such descriptor, so it stays open in the command's process (bubblewrap 0.9.0 and 0.13.1 close extra descriptors only in their monitor and their pid-1 init, never in the process that `execvp`s the program, by their source; tested on 0.13.1) and `execve` runs that inode.
No path of the harness binary is bound, resolved or executed for a contained command (where the node holds a descriptor of its image, below), so nothing at that path, a session's file, a rebuild or an upgrade, ever runs as `sandbox-exec` (`cli/tests/own_image.rs`: 200 races by path, 0; before, 2 of 200 ran the session's file before Landlock, review T8F-3b), and a binary replaced or deleted under the running node changes nothing for contained commands, whatever file systems the binary and the data directory are on (`a_binary_replaced_after_the_start_still_runs_from_the_old_image`, both forms, both binds, the network on and off; before, every command after it was refused, T8C-N3). `sandbox-exec` closes every descriptor above 2 before it reads its arguments (`close_inherited`), so the command holds nothing of the image, the view or the guard (review T8F-2: by path the command held the image's descriptor and could `chmod 000` the binary; `nothing_of_the_image_reaches_the_command`).
A hard link of the image into the data directory was built first and dropped: it could not be made across file systems or for a root-owned binary, and by path it was itself bound by a path after the guard's check (review T8F-1 to T8F-4).

**The file view** (T.8c, `contain.rs`): the command's root is bubblewrap's fresh tmpfs, made read-only once built, holding only the system read set (`SYSTEM_READ`; the top-level links such as `/bin -> usr/bin` as links), node.toml's `[sandbox] read` (read-only) and `write` (read-write) entries as they resolve now, the session's grants (its folder and temp folder read-write; a sub-agent's folder, git directory and borrowed object store as granted), a private `/dev` (`--dev`), `/proc` (its own, or the outer one bound in the shared form) and an empty `/tmp` (the image is not in it, T.8f).
A path that is not granted does not exist for the command: a sibling session's folder, `~/.ssh`, the data directory's files and the target of a link out of the session folder are absent, with Landlock and with the wrapper taken out (`outside_the_grants_is_absent`, `…_without_landlock`, `…_in_every_form_and_bind`).
Landlock inside keeps the same rules (the sandbox tests run both ways).
**What is bound is what the node checked** (S-2): with bubblewrap 0.10.0 or newer (the release that added `--bind-fd`; v0.9.0's source has none) each grant with an identity is bound with `--bind-fd`/`--ro-bind-fd` from a descriptor the guard opens `O_PATH` without following a link and checks against the node's device and inode; a folder swapped since refuses the command (`a_folder_swapped_for_a_link_after_the_check_is_not_mounted`, with only the view too), and bubblewrap, which mounts a descriptor through the path it names now (`realpath` of `/proc/self/fd/<n>`: a descriptor of another user namespace cannot be mounted directly), compares the mount with the descriptor and refuses on a difference, so a swap after the guard's open gets the command refused, never another folder mounted; it closes the descriptor before the command starts (no descriptor of a host folder reaches the command, tested).

**On a node with `[sandbox] mode = "off"`** (no wrapper) the guard is started the same way, directly from the node's own image: `start()` holds it (`hold_own_image`, the descriptor of `/proc/self/exe`, never `current_exe` resolved at a spawn: review T8E-5) before its early return and carries it in `Confinement::Unconfined { image }`, and `Confinement::shell` builds `<image> sandbox-guard --node <pid> --host -- bash -c …` with no `sandbox-exec` and no `@rizzy-image`, and the guard starts `bash` under its own name (`arg0` is the node's only for the image token); this was refused (`NO_GUARD`) until the owner's decision of 2026-11-20 ("dont, like if user selected host project workspace, why do we need to limit it? its his choice"); the foreground call of that node is built exactly as before, the read-only shell, MCP servers and the `sandbox` mode are unchanged, and a node that could not hold its image still refuses (`NO_GUARD`).
**Proof without a namespace:** every descendant of the command stays inside the guard's subtree whatever session or process group it joined (`setsid`, a double fork), because an orphan is reparented to the nearest ancestor that is a child subreaper, which is the guard (`PR_SET_CHILD_SUBREAPER`); so "the guard has no child left" (`waitpid` says ECHILD) still means "no descendant is left", provided the loop kills the command's process group while its leader is unreaped, SIGKILLs each of its own children (every reparented orphan is one; the `children` file lists unreaped ones only, so each number is its own) and repeats every 20 ms until ECHILD (without a namespace a chain of nested processes is ended one level per pass, about 0.8 µs times depth squared, 2 s near depth 1600, so "still alive" there need not mean a stuck process; the guard goes on to "ended"); `ended <ms>` is written only then, `alive <ms>` after 2 s if something forks faster than it is killed or sits in I/O the kernel cannot interrupt.
The graceful stop is SIGTERM to the command's process group and to orphans already reparented; a leader that dies of it ends the rest at once, as a contained init's death does.
The same stop paths hold as for a contained one (timeout, `bash_stop`, the chat's Stop and Stop all, the session's deletion, `session.stop_background` for a revoked owner, the node's stop, the node's death through the closing channel or the parent look; tests `cli/tests/background.rs` `*host*`, `cli/tests/guard.rs` `*host*`).
**Leftovers of the host form:** (1) a service the command only asked to start (a container runtime, a systemd unit, an already running tmux server) is not its descendant and is not covered; (2) a guard killed with SIGKILL (not by its node's death) leaves the command and what it started reparented to the user's manager and nothing ends them: there is no `--die-with-parent` without bubblewrap, and the node's start sweep (`contain::sweep`) finds processes by the `--mark` argument, which neither this guard nor the Landlock wrapper line carries, so it finds nothing of it (a documented leftover, no new mechanism; the owner's own `kill -9` of a guard, or the OOM killer, is the case); (3) there is no PID namespace: a later command sees and can signal the command, and where the network is on reaches a server it starts (the start note's network sentence is for the sandbox's namespace only), and a steered agent can still leave a process from a foreground call.
Bash runs in its own process group; cancel/timeout sends SIGTERM then SIGKILL to the group.
Cancel propagates master → node as `session.cancel`.
Time and steps are the node's: a call's timeout is the `timeout_secs` it states, at least 5 s, clamped to `[limits] bash_timeout_max_s` (default and maximum 3600 s, which wins over the floor), 60 s for a foreground call that states none (T.8d; it was 600 s; held while the node's out queue was full until A.21, below), and a background call that states none is refused, and a turn ends after `[limits] max_steps` model calls (a sub-agent's cap is at most its parent chat's limit, of its own; the caps are not one shared budget) (default 1,000, 1 to 10,000; a chat's owner may set the chat lower, X.14) with a message naming the key.
A tool call in a message cut by the model's output limit never runs, even if its arguments parse; three such messages in a row end the turn (Status, 2026-11-11).
Both come only from `node.toml` (out of range stops the node at start); no agent definition, prompt or protocol message carries a step or timeout value.
Output is capped: the model's copy at 30 000 characters; the live stream (`ToolOutputDelta` events, stored and replicated) at `[limits] tool_stream_bytes` per call (default 1 MiB, 4 KiB–1 GiB), after which one marker is sent and the rest is read and dropped so the child never blocks.
The stream's channels are bounded (8 pipe chunks, 32 sink chunks); a full channel back-pressures the pipe reader, and cancel and timeout are awaited alongside every send.
**No tool can wedge a node** (AUDIT S10): file tools open regular files only, checked before opening (a device is never opened) and again with `fstat` on the handle, opened `O_NONBLOCK`/`O_NOCTTY` so a FIFO swapped in meanwhile never blocks; `read` streams through a fixed buffer, keeps only its line window and stops at 32 MiB with a `file truncated at N bytes` note; `grep` skips non-regular files (links are not followed) and files over 8 MiB, saying how many; `edit`/`outline` refuse files over 8 MiB.
Every tool gets the turn's live cancel token (`read`, `grep`, `glob` check it per chunk or entry); after a cancel a tool has 5 s (`TOOL_CANCEL_GRACE`) to return before the loop abandons it (recorded as abandoned, its end not known), so a tool stuck in a syscall cannot hold the turn (its blocking thread may linger).
**A full uplink holds back neither a Stop nor a timeout** (ADOPTION_PLAN A.21; it closes the residual of experiment B.7, reviews B7-R1, B7-R2, B7-D1, B7-D2).
While the agent loop appends a batch of output, which waits for room when the node's out queue is full (the node produces faster than its uplink carries), it keeps polling the tool and the cancel (`coalesce_led`) and reads no more output meanwhile, so the tool waits for room in its own stream, where `bash` watches its cancel and its timeout: a Stop, a call's timeout and the node's stop end a command that streams output whatever the link holds, and the 5 s grace is not spent unseen (`node/tests/control_under_load.rs`, with the uplink taking nothing: a streaming command, and a silent one stopped right after an approval answer, showed no write in the first look after the Stop, where before A.21 they were still writing 6.0 s and 6.1 s after it; a 15 s timeout held, where before the command was still writing at 21 s; with the uplink taking one message every 200 ms and twelve other sessions streaming, another session's Stop ended its command at once and was acked after 0.4 s, before 2.6 s and 54 s).
A batch whose append has begun is finished, never dropped.
The out queue (`node/src/outbox.rs`) has two lanes.
In order: events, snapshots, `deleted`, artifact chunks and every lane command's ack, at most 256 messages and 1 MiB (a larger message goes alone); a session's events stay in `seq` order and a create's ack after its `session_created` (`Master::create_session` relies on it; tested).
Past that the sender waits, the back-pressure that keeps an agent from running further ahead of what the person sees than the queue holds (a design that never waited, the store as the overflow, was rejected for that reason: an agent in `auto` could run minutes ahead of the person's Stop).
Ahead of it: the acks of the three commands the command loop answers inline (cancel, approval answer, `stop_background`), which never wait; at most 64 are kept and past that one is dropped (its command was acted on; the master's request times out), and while output waits at most 8 go in a row, so a master flooding inline commands neither stops the node reading its commands nor starves the output (tested: 2,000 approval answers read with the uplink taking nothing, 64 acks kept; then one in nine messages output).
Ahead of an inline ack there is then at most the message handed to the link and the frame it is writing (an event, or a snapshot batch, now cut at 512 KiB, `SNAPSHOT_BYTES`), and the kernel's unsent bytes, capped on the node's socket at 128 KiB (`TCP_NOTSENT_LOWAT`, `link::UNSENT_LIMIT`; without it the send buffer autotunes up to `tcp_wmem`'s maximum, 4 MiB here, 16 s at 256 KiB/s: with the lane alone the ack below took 8.9 s): over the real link at 256 KiB/s with twelve sessions streaming, a Stop and an approval answer were acked after 1.0 s (`node/tests/control_over_link.rs`; B.7 measured 26.2 s and 28.2 s, past the master's 15 s `ACK_TIMEOUT`).
The command loop never waits for the store either (review A21-1): it acts, queues the ack, then hands the audit line to one audit writer (`node/src/audit.rs`), which writes what is queued in one transaction; a line that finds its queue (1,024) full, or whose write the store refused, is counted, and the count is written as one `audit.not_recorded` line (`{"count": N}`) once the store takes writes again, so every inline command is recorded or counted (tested with the store's write lock held: 3,000 answers read in 15 ms, 1,024 lines written, 1,976 counted).
An inline command for a session the node has neither as a session nor as a lane is refused at once ("unknown session"), and at most 256 sessions have a lane at a time, a command for another being refused at once (review A21-2: 20,000 cancels for unknown sessions left 20,000 tasks; now none); these refusals, and those past a lane's depth of 64, go in the lane ahead of the queued output like the inline acks, so they reach the master on a full uplink too, up to the 64 that lane keeps unread (re-check D-1: in the ordered queue they were dropped and the master timed out).
So a flood of inline commands costs one bounded queue and one task, and one of lane commands at most 256 tasks, whatever the store's speed.
**Residual (A.21):** the cancelled turn's end is an event of its session and waits behind the output queued before it (up to 1 MiB and the kernel's 128 KiB, about 4.5 s at 256 KiB/s), so the UI shows the turn running for that long after Stop answered; one event handed to the link holds an ack back by its wire time (an event may be 4 MiB, 16 s at 256 KiB/s; `bash` output is about 8 KiB an event); bytes in flight (the congestion window, a router's queue) are not capped; on systems other than Linux and Android the kernel's buffer is not capped; the master's own reading is unchanged (`FROM_NODE_QUEUE`, its mirror's appends, its socket's receive buffer), so a master slower than the uplink holds acks behind what it has not read; the ordered lane is first come, not fair per session (one session's output delays another's events, not its Stop); the acks that stay in order (create, prompt, delete, restore) wait behind up to 1 MiB and the socket's 128 KiB, past the master's 15 s `ACK_TIMEOUT` on an uplink below about 75 KiB/s, so a person may get a 504 for a prompt that runs and send it again (review A21-5); and with the socket's unsent bytes capped, the node's write of one frame now waits on the network itself, so a frame larger than the uplink carries in the link's 60 s idle limit (a 4 MiB event below about 68 KiB/s) drops the link, as the master's read timeout already could (review A21-6).
The node's command loop answers `Cancel`, `ApprovalRespond` and `StopBackground` inline, without waiting on the link (their acks go ahead of the output, above), and hands every other command to its session's lane (a bounded queue of 64 and one task per session, ended after 30 s idle): one session's commands run in order, sessions never wait for each other, a full lane nacks at once; an inline cancel also leaves a marker in the lane so a prompt queued before it is stopped too.
Events are still appended only through the session's `append` (one writer, contiguous `seq`).
Residual: the type check before `open` and the open itself race, so a device swapped in at that instant is opened (and refused on `fstat`); a node restart loses queued commands, which were never acked.
