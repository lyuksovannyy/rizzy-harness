# T88

## Threat

**The agent's commits carry the person's identity** (the 2026-11-19 readiness trial, item 3; README "What an agent's commits are signed with"): every `git commit` an agent makes carries the chat owner's name and an e-mail they set in their profile, in the sandbox and the host shell, with no set-up. (1) A hostile value: an e-mail or name with a newline, angle brackets, quotes, a backslash, two `@`, 300 characters, control, zero-width or direction-override characters, a section header of git's configuration file (`"\n[core]\n\tsshCommand = ...`), non-ASCII look-alikes, breaking out of a commit header or of the configuration file the node writes. (2) A master (or a request that reached it) sending such a value to a node. (3) Someone else's identity on a commit: two people on one node, a sub-agent, an API-token turn in a person's chat, a routine's run, a callback turn, a chat nobody owns. (4) The address leaking: into an event, an audit line, a log line, the model, other people, the node's own git. (5) The harness's identity overriding one the person configured. (6) A file the agent can write that the node's own git reads with more rights. (7) In a host chat Landlock denies reading `~/.gitconfig`, so every git command warned and then refused to run (found by the trial: this is the deliberate rule of that mode, not a bug)

## Mitigation

(1) **Checked twice, by the master and again by the node:** `harness_core::identity::check_email` (ASCII only, 254 bytes at most, exactly one `@`, a local part of letters, digits and `. _ % + -`, a domain of at least two dot-separated labels of letters, digits and `-`: no space, control, quote, backslash, angle bracket or `;`/`#`) and `clean_name` (non-ASCII letters allowed; none of control, `< > " \`, U+2028/2029, zero-width U+200B..200F/FEFF, direction overrides U+202A..202E/2066..2069; 128 characters at most).
The master refuses a bad e-mail at save (400, the message never repeats the value).
The node does not trust it: `CommitIdentity::resolve` replaces a bad e-mail by `<login>@users.noreply.rizzy.invalid` (`.invalid` is reserved, never a mailbox), a bad name by the login, and a login keeps only `A-Za-z0-9._-` (64 bytes) or becomes `user`; nothing is repaired, so nothing a value holds can reach git.
The configuration file takes the two values in quotes, and no character that needs escaping is possible in either. (2) As (1): the node decides what is signed. (3) **The chat's owner, from the row, at the one place every turn command passes** (`send_command_noted`, beside `owner`, X.36): a prompt, a retry and a callback carry the owner's login, display name and e-mail read at that turn, whoever built the command (the person, a routine, a callback, the API token); the node keeps it per session in memory, and a sub-agent's session reads the session at the top of its parents (`Session::commit_identity`, at most 8 levels), never its own turn's sender; a chat nobody owns, or whose owner has no account, signs as `Harness agent <agent@users.noreply.rizzy.invalid>`. Tests: `cli/tests/git_identity.rs` (`two_users_on_one_node_each_get_their_own_identity`, `a_sub_agents_commit_carries_the_root_chats_owner`, `without_an_email_commits_carry_the_no_reply_address`), `master/tests/it/profile_http.rs` `a_turn_carries_the_chat_owners_commit_identity`, `master/src/lib.rs` `every_turn_command_carries_the_commit_identity`. (4) **Not in any event, audit line or log line:** the identity is in the turn command only (`Debug` prints `<hidden>` for the address), in the node's memory and in one file in the chat's own temp folder; it is never in the model's settings line.
It goes only to the node that runs the person's chat.
**The agent's own shell sees it** (`git log`, `git config user.email`, the file), as every commit shows it: said in the README.
The node's own git (checkpoints, snapshots, clones; `node/src/git.rs`, `forge_clone.rs`) keeps its hardened environment (`env_clear`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`) and gets none of this: its commits are the harness's own.
Tests: `the_email_is_in_no_event_audit_line_or_log_line` (a canary address across the chat's events, the node's audit lines, TRACE logs and the data directory's logs), `the_nodes_own_checkpoint_commits_are_unchanged`. (5) **A default, never an override:** the identity is a git configuration file named by `GIT_CONFIG_SYSTEM`, the lowest level git reads, so an identity in the person's `~/.gitconfig` (where `[sandbox] read` makes it readable), in the repository's config or in `git -c` wins; the variables `GIT_AUTHOR_*`, which override every level, are deliberately not used.
Tests: `an_identity_the_person_configured_is_not_overridden`, `a_repository_or_command_line_identity_wins_over_the_default`. (6) The file lives in the session's temp folder (`.harness-git-identity`), written by the node as a new file renamed into place (an agent's link at the name is replaced, never followed); only the agent's own commands read it (the node's git is hardened as in (4)); what the agent writes there changes only its own commands' defaults, which it could set with `-c` anyway. (7) **The guard stays:** a host chat's shell still cannot read the home folder; where the shell cannot open `~/.gitconfig` (or the XDG file), `GIT_CONFIG_GLOBAL=/dev/null` (empty, never writable, always granted) makes git run silently (`a_host_chats_git_runs_without_the_warning_and_commits_as_the_owner`); where a `[sandbox] read` entry covers it (also through a link), git reads it.
**Nothing the agent controls is read by the node (review of PR 167):** the identity file is made new (`create_new`, `O_NOFOLLOW`) under a random name in the chat's temp folder and its path remembered in memory; the node never opens, reads, lists or stats an entry there (a FIFO or a link to `/dev/zero` or a 400 MB file planted at the old fixed name once hung the node or took its memory).
Whether the node user's git configuration is readable is decided from node.toml and the node's own `HOME`.
The values are written by git's quoting rules (`\\`, `"`, newline, tab escaped) although the validators exclude them; a display name git would strip to nothing (`;`, `'`, `,`, `:`) falls back to the login, since git refuses every commit with it.
**Whose configuration:** where node.toml makes the node user's `~/.gitconfig` readable, every chat on the node reads that configuration whoever owns it (its identity wins; its credential helpers, `insteadOf` rules and `core.sshCommand` apply to everyone's commands); the node logs one warning at start (`a_shared_global_config_wins_for_every_chat_on_the_node`).
The settings save keeps a stored e-mail unless the request carries the field, and `Prefs` hides it in `Debug`.
**Residual:** the identity is in memory only, so a restored session commits with the fallback until its next message; a sub-agent finds its root chat within 8 levels of parents; a git older than 2.32 ignores the identity file; an agent can remove or replace the file it was given (it loses its own default, nothing else); with `[sandbox] mode = "off"` the node adds nothing; a git older than 2.32 ignores `GIT_CONFIG_SYSTEM` and asks for an identity as before; an agent can commit under any name with `-c`, as before (this is the default, not a restriction: the trial's agents had invented identities, which is now unnecessary); a person who pushes commits publishes the e-mail they chose (the README suggests a forge no-reply address).
