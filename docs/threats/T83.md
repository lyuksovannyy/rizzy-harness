# T83

## Threat

**Sealed storage and a person's forge connections** (ADOPTION_PLAN X.27 step 1 and C.5's sealing; README "Connections"; `crates/master/src/sealed.rs`, `forge.rs` (its outbound rules now in `remote.rs`, shared with T84), `http/connections.rs`, `crates/store/src/connections.rs`): a pasted forge token leaks (a copied `master.db`, a log line, an answer, a socket frame, an audit line, an outbound URL), is read or used by someone other than its person, or the paste route becomes a token-guessing or SSRF tool

## Mitigation

**Sealing:** AES-256-GCM (aws-lc-rs) under `<data>/keys/secrets.key` (32 random bytes; made on the first seal only while no sealed value exists, created exclusively (`O_EXCL`, `O_NOFOLLOW`, mode 0600 from the start) under its final name so an existing file is never replaced, and removed again if writing or syncing it fails; the folder made 0700, narrowed when wider, refused when a link or another user's).
A sealed value is `0x01 | 12-byte random nonce | ciphertext | 16-byte tag`; the associated data is `"rizzy-harness sealed\0" | version | len32(table) table | len32(owner) owner | len32(field) field…` (for a connection: `user_connections`, the user id, the host, the account id).
A copied `master.db` without the key, a value moved to another user, host, account or table, a flipped bit, a cut blob and an unknown version all fail to open with an error that names no secret.
The key file must be a regular file of the server's user, no group or other bits, exactly 32 bytes (opened with `O_NOFOLLOW`, judged by `fstat`); otherwise sealing and opening are refused (503 to the person, the reason and the fix in the log) and the file is never regenerated.
**A key that is not the one** (a valid key from another server's backup) is found by trying it on up to 5 stored values at start and at every first use (a trial open of real rows rather than a separate key-check value: nothing extra to keep in step, and it checks the very values that must open) and refused the same way, so nothing new is sealed under a key that does not open the old ones.
The key is obtained (made or proven) **before** a pasted token is sent to the forge, and the list's `available` says whether it can be, so a paste that could not be stored never leaves the machine; `serve` already refuses a `keys/*.key` readable by others at start.
**The token** is trimmed and must be 1-512 visible ASCII bytes; it travels only in the request header the forge's API documents (GitHub `Authorization: Bearer`, GitLab `PRIVATE-TOKEN`, Gitea/Forgejo `Authorization: token`), marked sensitive; it is never in a URL, an event, an answer, a frame, an audit line or a log line (no `SecretSet` entry either, since nothing sends it on).
Bodies are parsed by the route, so a malformed one gets a fixed message quoting nothing.
**Who:** every query names the caller; another member, a server admin and an id not theirs get 404 or an empty list; the API token has no account and every route refuses it (403); rows cascade with the user.
**Outbound:** the host is the exact listed name (built-in `github.com` with its API on `api.github.com`, and `gitlab.com`; others only from `config.toml` `[[forge.hosts]]`, checked at load: lower-case name or IPv4, no port, `api_base` on that host or on the entry's own `api_host` when it names one, https or plain http only where `url_allowed` permits; the built-in list passes the same checks, under test); the request goes to the entry's `api_base`, never to anything typed; every name is looked up by the forge client's own resolver, which keeps public addresses only (checked on every connection, so rebinding is refused) unless the entry says `private_address = true`, and IP literals are checked as such; same-origin redirects, judged against the API host; `no_proxy` (tested with `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` set); 10 s and 64 KiB; the forge's error body is never read and statuses come back as `HTTP <n>`. **Answers:** the id must be a JSON number, the login `[A-Za-z0-9._-]{1,100}`, the display name loses control, bidi and invisible characters and is cut to 128, the e-mail must be visible ASCII with one `@`, scopes are filtered and capped at 32 names and 2,048 bytes (the rest counted and shown as "and N more"), so what is stored always fits its column; the UI renders all of it as text.
**Floods:** 10 checks per person per 10 minutes; 60 **failed** checks per host per 10 minutes, everyone together (it keeps this server from hammering a forge with bad tokens; working checks do not use it, but failures alone can still exhaust it for everyone); bounded maps, failing closed past 10 000 keys; 20 connections per person, counted in the insert's transaction.
Tests: `sealed.rs` (9), `forge.rs` (6), `store/tests/connections.rs`, `master/tests/forge_connections_http.rs` (the token canary over answers, frames, logs at TRACE, audit, every file of the data directory and the forge's URLs; others and the API token; hosts and spellings with no request made; redirects, 50 MB, a drip, HTML login, a TLS handshake that fails; private address, for a literal and for a name that resolves inward; the built-in list as shipped, up to its API hosts' lookup; redirects judged on the API host; environment proxies; floods; the cap; many scopes; deletion; a moved value and a copied database; a lost key and a key from another backup, with no request reaching the forge), `web/e2e/forge-connections.cjs`.
**Listing repositories (X.27 step 2, `forge_repos.rs`, `http/connection_repos.rs`):** `GET /api/connections/{id}/repositories?q&page` for the connection's owner only, in this order: the caller (API token 403); the query (`q` and `page` only, each once, else 400 quoting nothing; `q` trimmed, at most 100 characters, no control, bidi, invisible or replacement character; `page` 1 to 10, digits with no leading zero); the row by (caller, id) (anyone else 404); its host still listed (else 409, no call); the cache; the limits; then the token through `Master::connection_token`, which proves the key (a missing or foreign `secrets.key` is 503 with zero requests).
Every URL is built from the entry's `api_base`, a fixed path and fixed parameters, the word one `application/x-www-form-urlencoded` value (asserted on the exact URL the fake saw for `& = # ? % / .. ; space`); a `Link` header is read only for `rel="next"` (or GitLab's `x-next-page`) and never followed; nothing the forge returns is requested.
Per forge, from its own documentation: GitHub `/user/repos` (all affiliations, `sort=updated`; no search parameter, so a word filters one forge page of 100 here and never reaches GitHub);
GitLab `/projects?membership=true&order_by=last_activity_at&search=…&search_namespaces=true` (so a group's name matches);
Gitea/Forgejo `/repos/search?uid=<stored numeric account id>&private=true&sort=updated&q=` (`{ok, data}`). The shared client and rules of step 1 (public-only resolver unless `private_address`, same-origin redirects on the API host, no proxy, 5 s connect, 10 s for the whole request including the body), **1 MiB** of answer (100 GitHub entries are about half), error bodies unread, **read in one pass without building the JSON** (review of PR 158, HIGH 1: a tree of `[{"a":0},…]` cut to 1 MiB was about 60 MB, and 80 at once took the process past 1 GB): at most the page size asked for of entries, each into the few fields used (strings kept are slices of the answer already held, so they are bounded by it; the checks after refuse long ones), the rest of the answer skipped by a visitor that keeps nothing and stays under the parser's nesting limit of 128 (serde's `IgnoredAny` would skip any depth), later entries only counted; measured in the suite's debug build, one hostile listing's peak growth went from 62 MB to about 2 MB; and **at most 2 listings in flight on the server and 1 per person**, from before the token is opened until the answer is built (the person's slot is taken first, so a person's second request never holds a server slot: re-review, MEDIUM 2, one person had held both for a minute; one more is 429 at once, never queued, saying whether the server is busy or the person's earlier listing still runs; both slots are guards dropped on every path, a request the client gives up included); 20 hostile listings at once: 2 run, 18 refused, about 8 MB peak growth.
A description is cut to 800 characters before it is cleaned (the shared cleaning splits all it is given: 1 MiB of `"a a a …"` cost about 11 to 13 MB before).
A 401/403 says to replace the token and keeps the row.
**Answers:** at most the page size of entries read (the rest counted); each needs a positive JSON-number id (strings, negatives, floats out), a name of the forge's shape (GitHub `[A-Za-z0-9-]{1,39}/[A-Za-z0-9._-]{1,100}`, Gitea/Forgejo `[A-Za-z0-9._-]{1,40}/[A-Za-z0-9._-]{1,100}`, GitLab 2-21 parts of `[A-Za-z0-9._-]{1,255}` not ending `.git`/`.atom`; never `.`, `..` or a leading `-`; 512 bytes in all) and a visibility (GitLab `internal` counts as private), each id once; otherwise left out and counted (`left_out`), because step 3 will build a clone URL from the name.
The default branch must pass a `check-ref-format`-like rule with no leading `-` (else null), the time a strict RFC 3339 string (else null), "may push" a boolean the forge sent (GitHub, Gitea: `permissions.push`; GitLab: access level 30 or more) or null; the description cleaned and cut to 200; no URL passed on.
**Floods:** 20 forge calls per person per minute; a listing is refused while the host's shared budget of 60 failures in 10 minutes is used up, and a failed listing counts against it **only when it says the host itself is failing** (a connection or TLS failure, a timeout, a body cut off or over the cap, a 5xx, a 3xx not followed, a malformed answer to a 2xx); while the budget is used up a listing gets its own message (listing is paused), not step 1's "token checks".
**No 4xx counts:** it is the forge's answer to this request (review of PR 158, HIGH 2: one person's revoked token, listed 60 times, had refused everyone's listings and connects to that host; re-review, MEDIUM 1: the same with a search word GitLab answered 422 for, since the word is the person's).
A 401, 403 or 429 is about the token or the account and is **remembered for 60 s** per (person, connection, `api_base`, hash of the sealed token), for every word; another 4xx (400, 404, 409, 422 …) is remembered for 60 s for that key with its word and page only, and its message says which ("answered HTTP 422 for this search"); at most 1,024 remembered, so a retry gets the same answer with no call and no token opened, and a replaced token is asked at once.
**Accepted trade-off:** a 403 from a host that blocks this *server* (an IP block, an abuse limit) is not counted across people; each person is bounded by the memory (one call per connection, word and page per minute) and by the 20 per minute; a misconfigured `api_base` answering 404 likewise costs each person one call per word per minute; a cache of answers per (person, connection, the host's `api_base`, a SHA-256 of the sealed token as stored (a fresh nonce per seal, so a replaced token is always a new key, even against an answer still in flight), word, page), 60 s, 256 entries, 32 and 512 KiB per person (an entry's size counted as the capacities of its strings and lists plus the key's and the entry's own sizes and a map slot), 4 MiB, emptied for a connection when it is disconnected; errors are not cached.
No audit line (a read).
Tests: `master/tests/forge_repositories_http.rs` (the canary across success, 401, 403, 500, timeout, TLS failure, redirects, 50 MB, a non-JSON and a wrong-shaped answer; others, a workspace admin, a server admin, the API token, a disabled account; hostile names, branches, ids, shapes, 10,000 entries, a drip; the word and page; floods and cache; a replaced token; a removed host; a missing and a foreign key), unit tests in `forge_repos.rs`.
**Residual:** no key rotation; losing `secrets.key` loses every token (backups must carry it); the key (inside the crypto library's key object, for the life of the process) and every opened token and its working buffers are in the server's memory and are not wiped; root on the master reads everything; `private_address = true` lets any person who can sign in make the server send GETs with what they paste to that host's `/user`, and a person whose token passed that check there send GETs to its `/user/repos`, `/projects` or `/repos/search` (fixed parameters, `page` 1-10 and their encoded search word varying); a listing in flight when its connection is deleted stores one cache entry nobody can reach (the id is gone), which expires within 60 s; an admin's edit or removal of a host does not stop a listing already in flight (up to 10 s, that call goes to the old `api_base` with the token); a self-hosted forge's admin sees the tokens sent to it (that is the forge); the rate limits are per process and reset on restart; a forge learns the search words people type for its repositories (GitLab, Gitea, Forgejo; GitHub does not, at the cost of searching one page at a time); a GitHub search finds a repository only within the page of 100 it is on; a cached listing can be up to 60 s old (a repository removed or a permission withdrawn in that time still shows); a listing's parsed answer (up to 1 MiB of JSON) is held in memory while it is read; over a plain-http network bind the token travels in clear text like the password (the start-up warning says so).
