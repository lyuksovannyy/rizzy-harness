# T77

## Threat

**A node makes folders on request** (ADOPTION_PLAN X.26, README "Projects", `docs/projects.md`): the start screen's "New project" asks a node for a new folder, a git repository, for a project.
Before it no message could make anything on a node's disk but a session's own files.
A hostile or compromised master, a member who may create projects, or a sandboxed agent that can write in the projects folder could use it to make folders where the node's user did not want them, to steer the node's git into another repository, to plant something at the new name, or to fill the disk

## Mitigation

**The node decides where, by name only.** `project.create` carries a display name and nothing else (an unknown field such as a path is dropped by the parse, `harness-protocol` test).
The folder is made only in the one folder node.toml names (`[projects] dir`, default `~/rizzy-projects`, `dir = ""` turns it off), checked at start: inside a `workspace_roots` entry (so `check_cwd` then accepts what is made), not being, holding or inside a protected folder (the data directory, the sub-agents' folders, the operator's instruction file), not a link, its parent existing (nothing is made through a missing component: review of PR 143), on the data directory's file system; a named one that breaks a rule stops the node, the default that breaks one only turns the feature off with the reason in the log.
The node announces `projects` and never the path.
**The name is the node's:** `<slug>-<4 characters>`, the slug ASCII letters and digits, every other run one `-`, at most 48 characters, `project` when empty; the four characters from `a-z0-9` by the OS's randomness. **git never runs where anything but the node can write** (review of PR 143: a `.git` file planted in the new folder between its making and `git init` sent the node's init and first commit into another repository, 20 of 20): the repository is built in `<data>/projects-staging/<random>` (0700, protected, emptied at start, so a half-made project of a killed node goes), by the node's hardened git (no system or global config, no hooks, no template, no transport, the node's identity), checked there (only a real `.git` folder, no `commondir`, exactly one commit by the node's identity), then moved in with `renameat2(RENAME_NOREPLACE)`, which never replaces or follows whatever holds the name (a link, a folder with its own `.git`, a git file: the next 4 characters are tried, 8 tries), and the entry is checked again from the open projects folder (the same folder, a real `.git` folder, `check_cwd` on its path; otherwise it is removed again).
The projects folder's parent is opened without following a link at its name and compared (device and inode) with what was recorded at start, the folder's own identity too when it existed at start; it is made (last component only) and opened relative to the parent.
**Bounded:** one at a time per node, `[limits] projects_per_hour` (default 20, 0 off; only folders made count, in memory: a restart starts the count again), a name of at most 256 bytes.
**The master:** asks only for someone who may change the workspace's projects (`settings` permission), may run agent chats there (level at least `sandbox`) and may use that node (`node_refusal`); the project row is written only after the node answered with a folder, so a refusal leaves nothing (a clone, T86, has a **pending row** meanwhile: a row of `project_clones`, never of `projects`, so no route that takes a project id, for a chat, a link, a folder request, the board, memory, `.mcp.json`, a routine or a board template, can find it; it has no folder and becomes the project, same id, in one transaction with the delete of the pending row, only once the node answered with the folder);
"Create its folder" claims the project before any node is asked, so two requests at once make one folder; the node request and the row write run in a task of their own, so a client that goes away does not stop them in between; the path is stored as the project's `cwd` and checked by the node again for every chat

## Column 4

The path a node answers with is shown to every member of the workspace (it is the node's own, as a chat's folder is) and to nobody else, never in a URL; error texts carry the projects folder's path to the person who asked and to the node's own log, which stays on the node.
A folder no project keeps can still be made: a node that answers after the master's 30-second wait (the answer names the node and the name's first part, the master's log the path), a store failure after the folder exists or a folder set by hand meanwhile (the answer names node and path), and, for a clone (T86), a starter who lost the right to make the project while it ran, or a node whose link closed meanwhile (the reason says so); nobody removes it but the person. `renameat2(RENAME_NOREPLACE)` is refused by some file systems (older NFS): probed at start: where it fails for the default folder the node makes no project folders and its log says why; for a folder node.toml names the node does not start.
The device and inode recorded at start are a hint, not the guard (re-check of PR 143): a projects folder deleted and made again can get its inode back (seen on ext4) and is then accepted, and a folder that did not exist at start has no recorded identity; what holds is that the last component is opened without following a link, relative to the pinned parent, and that `check_cwd` checks the finished path again.
Staging lies under the data directory, which sandboxed and host sessions alike cannot reach (host mode keeps the Landlock rules, T62); what remains is host mode's own documented gaps, and a host-mode command runs as the node's user anyway.
Two workspaces on one node share its projects folder; names cannot collide (no-replace move, random part), and a chat of workspace B can open workspace A's project folder through "Existing folder" exactly as any folder inside `workspace_roots` today: the node's roots are its rule, not the workspace (N.1 changes that).
A sandboxed agent whose chat folder is or holds the projects folder can change other projects' folders and can deny creation (`chmod 555`, a rename of the projects folder): no more than such a chat can do to any folder in its view.
A process of the node's own user that renames ancestors above the recorded parent is not caught (that user can do anything the node can)
