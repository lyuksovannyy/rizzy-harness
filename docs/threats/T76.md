# T76

## Threat

**Checkpoints no longer follow the user's global git ignore file** (owner, 2026-11-17, ADOPTION_PLAN X.31): a file only `core.excludesFile` or `~/.config/git/ignore` names (`.env`, `.idea/`, a `node_modules/` the repository does not ignore) is now in turn checkpoints, the "changed between turns" copy, the copy a forced undo keeps, sub-agents' bases, folders and results, and their merge-back;
Undo puts an agent's edit to it back.
**Size:** nothing bounds a checkpoint's bytes or file count; time is bounded (`SNAPSHOT_TIMEOUT` 60 s a snapshot, `GIT_TIMEOUT` 120 s a git call), and a snapshot past it leaves the turn without a checkpoint with a notice in the chat ("This turn has no checkpoint, so it cannot be undone: … (snapshot took too long (folder too large?))"), so Undo stays truthful.
Measured (`git_ignore_bench.rs`, warm page cache, the rotational USB disk; docs/undo-and-stash.md §2.7): a 20,000-file 286 MiB tree only the global file named: first checkpoint 8 ms → 1.6 s, later ones 6 → 66 ms, store 0 → 159 MiB, a sub-agent's base/fill/result 1.7 s / 0.5 s (312 MiB copied) / 0.6 s and 160 MiB more in its own shadow; 1.9 GiB in four files: 12.6 s, 783 MiB, sub-agent 9.6 s / 7.7 s (1.9 GiB copied) / 2.9 s.
Residual, accepted by the owner's decision: disk (each shadow stores the compressed bytes until pruned and collected; each running writing sub-agent holds a full copy); a folder past the time bound loses Undo for every turn.
Not built (proposal): a per-file size cap at snapshot, as OpenCode (2 MiB untracked), Hermes (10 MB) and Warp (25 MiB) have (research/harnesses-round-2-appendix.md §4.6); it needs the skipped paths carried into the restore plan, or a file skipped before a turn and kept after it reads as created and an undo deletes it.
**Secrets:** a `.env` the repository does not ignore now has its bytes in `<data>/checkpoints/<hash>.git` and `<hash>-sub.git` (the node's data directory: `protected_dirs`, no file tool or contained command reaches it), in a running sub-agent's `<data>/sessions/<id>/files` (removed when it ends), and in the copy a forced undo keeps (pruned with the checkpoints; the 30-day stash of `docs/undo-and-stash.md` §3 is not built yet).
Nothing new is sent unasked, with one exception that is an event: a sub-agent's changes that could not be applied reach its parent as a tool result with their hunks (`git/merge.rs` `unapplied_text`), and a tool result is an event, mirrored on the master and in the owner's export and search; such a hunk can now hold lines of a `.env` (3 lines of context the model may not have read).
It is the owner's own chat, and the scrubber removes only the secrets the node knows.
Checkpoint events themselves carry paths and sizes only; a turn's diff (X.12, T53) is fetched by the chat's owner on demand, scrubbed of the secrets the node knows only, and kept by no master, and it can now show a changed `.env` hunk with up to 3 unchanged context lines the model may not have read; a sub-agent's unapplied changes reach its parent model the same way (the child wrote them).
The model could already `read` the file; the chat's owner already reaches it through the agent.
Not removed with the chat: checkpoint refs of a deleted chat stay until later turns in that folder prune them (`checkpoints_keep`) and gc runs (an existing gap, now also covering files only the global ignore named: a deleted chat's `.env` snapshot stays on the node's disk until ten later turns in that folder prune it and gc runs, or for as long as no later turn runs there).
The data directory never enters a checkpoint (`Bounds::exposes`, unchanged).
Tests: `crates/cli/tests/stop_signal.rs` `a_served_node_does_not_follow_the_users_global_git_ignore` (served binary with `GIT_CONFIG_GLOBAL` naming an ignore file: checkpointed, undone, seen by a sub-agent and merged back; `.gitignore` and `.git/info/exclude` still apply), `git.rs` `repository_checkpoints_live_outside_and_restore_exact_bytes` (the shadow's `info/exclude` is the repository's, nothing added).
