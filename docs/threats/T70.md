# T70

## Threat

**One rule for "this agent can change things", and a shell for read-only agents** (ADOPTION_PLAN T.7): before, three places judged differently (the master's small-model list by names, the node's sub-agent folders by `write`/`edit`/`bash`, the loop's plan mode and parallel batch by declared risk), so an agent could be "read-only" to one and a writer to another; a read-only agent given `bash` would have had a writable shell in its parent's folder; and a reader's uncarded commands would run a hostile repository's code with the network on

## Mitigation

**One allow-list in `harness-core`** (`agent::READ_ONLY_TOOLS`, `tool_changes`), two questions from the same inputs (the tools the agent may call that the node offers: its denials, the node's `denied_tools`).
**"Changes things"** (`AgentSpec::changes_things`): `all`, an MCP tool, or any tool not on the list (a tool added later is a writer until someone lists it); it decides plan mode (`ApprovalMode::refuses`, delegates and follow-ups), the approval risk of `bash`, the small model, the parallel batch, the repeated-call guard and **which shell**: `bash` does not count, because an agent that changes nothing else gets `bash` only in the read-only shell (T66), picked by the loop per call from the same answer (`read_only_turn`) in every approval and execution mode, so no spec field, switch or call can ask for a writable one; where the node has none, the shell tools are not offered and a call is refused with the reason.
**"Needs its own folder"** (`AgentSpec::needs_own_folder`, the node's `can_change_files`, also on a follow-up to a child, T68): an agent that changes things and may call `write`, `edit`, a writable `bash`, `all` or an unlisted tool; `publish`- and MCP-only agents share the parent's folder as before (review of PR 131: a chat in a plain folder delegating to a notes or calendar agent keeps working).
Proved over every subset of a tool set: an agent sharing the folder never has the writable shell, `write`, `edit` or an unlisted tool.
A child whose agent now needs another folder than it had is not continued. `remember` is on the list (a sub-agent's call always waits for a person's Keep) and plan mode still refuses it (`PLAN_REFUSED`).
A reader's `bash` is asked about as read-only (no card in `ask`/`accept_edits`, a card in `ask_all`), as Claude Code runs sandboxed commands unasked; therefore the read-only shell has **no network** by default (`[sandbox] read_only_network`, T66).
Tests: `core/src/agent.rs` (truth table; `an_agent_sharing_the_folder_never_writes_files_directly`), `agents/tests/agents.rs`, `master/src/resolver.rs`, `master/tests/it/orchestration.rs`, `node/tests/runtime.rs` (`publish_and_mcp_sub_agents_share_the_folder_outside_a_repository`, writers refused outside a repository), `node/tests/continue_child.rs` (`a_reader_with_a_shell_is_continued_as_a_reader`, `a_child_whose_agent_now_needs_another_folder_is_not_continued`), `agent-native/src/plan_tests.rs`, `cli/tests/read_only_agents.rs` (Scout end to end with bubblewrap; `a_continued_scout_is_still_read_only`).
**Residuals:** as T66; a filesystem-style MCP server of a sub-agent that shares the folder can write it (kept from before; MCP calls keep their own approval); a node with no read-only shell gives read-only agents no `bash` at all; an agent whose only changing tool was `bash` (a hand-written file agent) now has a read-only shell (list `write` or `edit` too for a writable one).
