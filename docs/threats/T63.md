# T63

## Threat

**`@` file mentions** (README "Mentioning a file"): the person types `@path` and the node puts that file's content into the message. (0) A pasted `@token` (`@types/node`) becomes a mention the person did not mean, or a node secret in a mentioned file reaches the model (review of PR 120 H2: the first request was built from the unscrubbed message while the log held the scrubbed one). (1) A mention shows the model a file its `read` would be refused (a way out of the folder, the data directory, a link out), or bypasses `denied_tools = ["read"]`. (2) The file's text poses as the harness or the person (a forged `[harness]` line, a fake `User:` turn) or its name breaks the harness's line. (3) The master (or a forged request) puts content or a read-first record into the message. (4) A huge file, a FIFO, a binary or many mentions flood the event, stall the turn or the node. (5) Another member or an admin lists or mentions files of someone's chat. (6) The completion becomes an index or a crawl on the master. (7) The read-first guard counts a file the model never saw.

## Mitigation

(0) Only a token that names an existing path of the chat's folder is a mention: the composer asks the node for each token's own path (its folder's entries starting with that name, the exact name first, never a walk; answers kept 10 s), shows them as chips before sending, each removable, checks the text again on send (waiting at most 2 s), and sends only paths that exist and were not taken off; the node drops a path that names nothing (no note to the model).
The node scrubs each file's text and path with its secrets, and the whole message is scrubbed as the log stores it before the turn's first request is built from it, so the model gets exactly what the log holds, the person's text and attachments included, and a sub-agent's task, which the parent model writes, the same way (`r6_a_sub_agents_task_is_scrubbed_like_a_message`, `r2_a_mentioned_file_is_scrubbed_like_read`, `r2b_typed_text_and_attachments_reach_the_model_as_the_log_holds_them`, composer `only paths the folder holds are attached`). (1) The node resolves each path with `ToolCtx::resolve` in a context built like a `read` call's of the session (its folder and pin, a sub-agent's own folder, the protected folders, node.toml's `allow_outside_workspace`), then reads a regular file only, without waiting on a FIFO; a node that denies `read` shows none; no approval card is asked for (it is the person's own act, as attaching a file is) (`a_mention_never_shows_what_read_refuses`, `refused_mentions_are_named_and_show_nothing`, `a_node_that_denies_read_shows_no_mention`). (2) One harness line per file with the path made one line and every quotation mark read as `'` (`shown_name`), the text quoted line by line behind `\| ` as attachments are (T43/R76), after the person's text so `own_words` never includes it (`a_files_forged_lines_arrive_quoted`, `a_mentioned_file_is_the_harness_line_then_quoted_lines`, `a_mentioned_file_is_quoted_and_counts_as_read`). (3) The protocol carries paths only (`session.prompt.files`); `user_message.files` is written by the node from its own read. (4) At most 20 files read per message (the rest named), 64 KiB of text shared by all, a file over 256 KiB or with a NUL byte named not shown, a folder at most 200 entries, a path at most 1,024 bytes and no control character, the whole read bounded by 5 s (the prompt is refused past it) (`large_binary_and_special_files_are_named`, `mentions_share_one_cap_and_a_count`). (5) `GET /api/sessions/{id}/files` and the prompt go through `visible_session` (owner only, 404 for anyone else, admins included) and the agentic grant; a chat without a folder offers none. (6) Each completion is one bounded walk on the node (`.gitignore` honoured, links not followed, `.git` and protected folders skipped, at most 20,000 entries, 1.5 s, 50 results, two at once per node); the master keeps nothing (the folder of a `dir/` query is canonicalized before the inside check, so a link out is not listed through, also in outside mode: `completion_lists_the_folders_paths_only`, `r3_completion_lists_through_a_link_out_and_ignored_names`, `completion_lists_the_chats_folder`). (7) `seen` only when the node read all of the file and showed its text (whole, or its first lines as a paged `read` does), with the hash a `read` records; rebuilt from the log at each turn (`SeenStore::sync`) and noted at once for the turn's own message; a queued one's only where the table knows nothing of the file, so an older hash never replaces a newer `read`/`write` (`a_queued_mention_never_replaces_a_newer_record`).
Recorded in `user_message`, so the request rebuilds byte for byte and an in-turn summary keeps it (`a_mentioned_file_survives_an_in_turn_summary`).
Residuals: the content is what the file held when the message was sent; the master can still drop or reorder the paths (it relays them); one person can hold both of a node's listing slots; `.gitignore` is not honoured by the listing outside a git repository; the API token can send mentions for any chat it can see (that token's design).
