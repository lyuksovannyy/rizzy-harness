# T90

## Threat

**A person's rewind of the conversation changes what the model is sent, and what a chat's log means, by one event** (ADOPTION_PLAN X.46, README "Rewind", docs/rewind.md): a rewind that a model, a tool, a routine, another account or a replayed request could cause would let an attacker take the agent's memory of a refusal, an approval or an instruction out of its context, or hide what happened in the chat; and a rewind that touched more than the conversation (files, other chats, an approval already given) would be a second way to write to the person's folder

## Mitigation

**Only the chat's owner causes one.**
`POST /api/sessions/{id}/rewind` and `.../rewind/{seq}/undo` resolve the chat as every request that changes it does and then require the account to be the chat's owner (the API token only for a chat nobody owns): anyone else, a server admin and a workspace admin included, gets the 404 of a chat that does not exist and nothing is sent to the node (`crates/master/tests/it/rewind_http.rs`).
The model has no tool for it, no model, tool or routine text reaches the route, and the node starts one only from `session.rewind`, which the master sends for those two routes (`crates/protocol/tests/rewind_wire.rs`: every field named by every sender, a missing `files` or `force` is an error and never false).
**The node decides.**
It checks `harness_core::rewind::check` against its own log under the turn slot (so no turn, `/compact` or second rewind is racing it), refuses while the chat has background commands or sub-agents running or an end not recorded, in a sub-agent's chat, and on a stopping node (`crates/node/tests/rewind.rs`, `crates/cli/tests/background.rs`, `background_agents.rs`); the master's check of its mirror is an early answer, never the authority; a node without the capability is told nothing and the person is told to update it.
**A forged or corrupt rewind event hides nothing it does not name.**
One counts only when its range is not empty and its `message_seq` is a (not queued) message of the person's of its own `turn_id`; otherwise it counts for nothing, not even for its turn's `turn_started`, and `visible` is idempotent on such logs (`crates/core/tests/rewind_fuzz.rs`).
**Nothing is deleted and nothing is forged.**
The rewind is one event the session's one writer appends with the next seq; the log, the mirror and the browser keep every event, so what a rewound turn did stays visible (muted) and the raw log is the record; an undo is allowed only before a message, a turn or a summary comes after the rewind.
**The model is never sent a rewound range** (`crates/agent-native/tests/rewind.rs`): not its messages, calls, results, context blocks, queued messages or thinking, and not the end of a command it started; turns before the cut are sent byte for byte as before, so a signed thinking block's prefix still matches; and what the agent read in a rewound turn is not read any more, so an edit needs a fresh read (`crates/node/tests/rewind.rs`).
The one line the harness adds after a rewind that kept the files names the files the removed turns changed, each quoted behind `| ` as data and cut to 20 (`harness_core::rewind::kept_line`), so a file name cannot forge a harness line.
**No other chat's model is sent rewound text either**: the chat's `chat_fts` rows are rebuilt from its visible log in the transaction that appends a rewind or an undo (so `recall` and search do not find it), and `earlier_chats` skips rewound notes, summaries and replies (`crates/core/tests/rewind_fuzz.rs`, `crates/store/tests/search.rs`, `crates/store/tests/projects.rs`).
**The files part is the existing restore, nothing wider**: the same checks (changes made after the turn, another chat's work in the folder, the folder still allowed, nested repositories left alone), written as its own `before_restore` checkpoint; if it is refused the whole request is refused and no rewind is written; an undo of a rewind never writes a file.
**Not undone, stated plainly:** a rewind does not reduce usage, and does not undo memory facts saved, board changes, published artifacts, commands run, network calls or sub-agent chats and their merges; an account's forge or connector action done in a rewound turn stays done; the browser of the chat's owner still receives every event; `others.rs` (T57) still reads rewound turns to say who changed a file.
A person who wants a thing gone from the model's sight should know it is gone from the model's context only, and that an attacker who could already write into the chat as the owner could do this and more.
