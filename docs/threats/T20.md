# T20

## Threat

A project member plants instructions in every other member's agent through shared project memory (cross-user prompt injection, audit S12)

## Mitigation

Project facts reach every member's turns, so only active ones do and only a manager activates them: `PATCH {status: "active"}` needs `settings` unless a manager turned on the project's `members_activate_facts` (default off), and then a member confirms only their own proposal.
Adding, rewording or deleting an active fact is always a manager's.
A proposal is visible only to its source chat's owner.
The agent path (`remember` scope `project`) only files proposals, for a manager's chat too: activation is a human request; agentic nodes offer it too, and the master files a call only from a node whose hello lists `CAP_REMEMBER` (registered there, not in its `denied_tools`), so a node's `node.toml` can stop proposals from its chats.
Project context (instructions, board, every active fact up to 4,000 characters plus recalled older ones) goes only to chats in the project and to sub-agent sessions whose parent is such a chat on the same node with the same owner: a node that names another chat as its session's parent gets nothing (§3, Gate 3 review L-1; `a_node_cannot_borrow_another_users_chat_as_parent`).
Residual: with the switch on, a member (guests included) can publish text to the project; a node that hosts a project chat already receives that project's context for its turns, and can start sub-agent sessions under it (that is delegation). [docs/projects.md](docs/projects.md).
**Project settings reach every member's agentic turns** (review P-5, accepted): the project's instructions, board, default folder and default node go into every member's turn, and editing them needs the workspace `settings` role, not the agentic grant, so a member with `settings` but without `agentic` steers what other members' agents run.
The same cross-user prompt-injection path as shared memory above, through text a person wrote rather than a fact an agent proposed; the agentic member's own approval mode and node policy still bound what runs.
It would change if instructions and default node became agentic-only to edit, or were shown to each member as the project's, with the editor named, before a turn.
**Earlier chats are not a cross-user path**: the first turn of a project chat also gets its owner's own earlier chats in the project (summary or last reply, quoted, ≤ 4,000 characters), filtered by the chat's owner in SQL (`Store::earlier_chats`), never another member's, an incognito or a sub-agent's chat (`another_members_chats_in_a_team_project_never_appear`).
