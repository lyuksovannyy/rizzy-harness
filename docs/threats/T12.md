# T12

## Threat

Password guessing / account takeover

## Mitigation

Login throttle (5 failures per username per 15 min → 429 with `Retry-After`; while locked even the right password is refused).
Order of checks at `/api/login` (`Auth::login`): body over 16 KiB → 413 before parsing (also `/api/setup`); a username that fails the account format (1–32 of `a-z 0-9 _ . -`, checked on length before any copy) or a password over 1024 bytes → the same 401 body as a wrong password, with no map entry and no hash; a locked name → 429 without waiting; then one of **4 Argon2 permits** (wait at most 2 s, else 429 `Retry-After: 1`); then a failure slot is **reserved under one lock** before hashing (so 50 parallel guesses record 5 failures and the rest get 429), kept on failure, cleared on success, given back on a store error or a cancelled request.
Well-formed unknown names take the same path (permit, slot, dummy hash) as known ones.
Every Argon2 run in the process (login, setup, account creation, password change and reset) shares the 4 permits, so hashing uses at most 4 × 19 MiB; a permit moves into the blocking task, so a disconnect frees it when the hash ends and a panic frees it while unwinding.
The failure map (`keyed_limit::FailureMap`, the master's one keyed limiter) holds at most 65,536 names (about 10 MiB); when full, expired names go first, then the name whose latest failure is oldest.
The key is the lowercased username only: there is no per-address login throttle (residual 2).
Tests: `auth/limits` and `keyed_limit` unit tests (`reservations_count_until_given_back`, `a_dropped_reservation_leaves_no_key`, `the_map_is_bounded_and_drops_expired_then_oldest`, `a_flood_below_the_bound_neither_frees_a_locked_key_nor_locks_another`, `a_flood_past_the_bound_pushes_out_the_oldest_key_and_nothing_else`), `auth::tests::ten_thousand_one_mib_usernames_leave_no_trace`, `login_limits_http.rs`.
Residuals, accepted: (1) an attacker can lock out a known username for 15 minutes; (2) anyone who can reach the port can keep all 4 permits busy, so other logins, setups and password changes get 429 while the flood lasts (no per-IP limit yet; it ends when the flood does); (3) eviction: flushing a locked name needs 65,536 newer failed names, each a full hash through the 4 permits: at ~50 ms per hash (estimate for a current x86 core, not measured) that is ~80/s, about 14 min per flush, ~7 min on hardware twice as fast, during which (2) holds for everyone.
That buys at most 5 extra guesses per flush, so a single name sees at most ~2–3× the 20 guesses/hour the throttle allows.
Refusing new names when full was rejected: the same cost would lock every not-yet-listed username out for 15 minutes after the flood stops. `/api/setup` gets the format check first, the body limit and the permits, but no failure throttle: the claim code has ~100 bits, a wrong code costs no hash, and a global throttle would let anyone block the owner's claim.
No self-signup; admin-created accounts start with a temporary password that must be changed.
The server makes it (audit L14, `http/users.rs`, `auth::temporary_password`): 20 symbols of lower-case Crockford base32 from the OS generator (100 bits, no bias: 32 divides 256), shown as 4 groups of 5; only its Argon2id hash is stored; it is returned once, in the body of the create or `POST /api/users/{id}/password` answer, and never logged, put in an event or a URL (`master/tests/logs/temp_passwords_http.rs` captures every log line and searches the data directory).
A request that names a password is refused (400), so no admin picks a weak one or types it where it can be read; the claim (`/api/setup`) is the only place a password is chosen without an account.
The UI shows it in a dialog with a copy button and forgets it on close.
Login rules (throttle, lockout) apply to it like any password.
An admin cannot reset their own (409: they use `/api/me/password`); disabling, deleting or resetting a password signs the user out everywhere, open WebSockets included (T2).
The last active admin cannot be removed or demoted, and admins cannot change their own access.
Workspace managers add members by username, so the answer tells them whether a username exists: failed adds are throttled per caller (user id; 10 per 15 min → 429), accepted as a residual leak.
The throttle is the same `FailureMap` as the login one (before FIX_PLAN 4.2 a hand copy with no bound on callers and no removal of empty ones): at most 65,536 callers, a slot taken before the lookup, kept when the name does not exist, given back by reservation id when it does, when the store cannot tell or when the request is cut before it answers; it is checked after the caller layer and the member-management permission, so an unauthenticated flood never reaches it.
Tests: `auth::tests::the_lookup_map_keeps_a_bounded_number_of_callers`, `a_caller_with_nothing_left_in_the_window_leaves_no_entry`, `throttle_window`, `keyed_limit::tests::a_release_takes_back_its_own_slot_whatever_the_timestamps`, and the member-add cases of `workspaces_http.rs` and `accounts_http.rs`.
