# T3

## Threat

Secrets leak via logs, URLs, event log

## Mitigation

Provider keys are referenced by env-var name in config, held in `Secret<String>` (redacted `Debug`), never put in events.
A person's forge tokens (X.27) are not in `secrets.toml` or the environment: they are sealed in `master.db` under `<data>/keys/secrets.key`, held in `Secret<String>` when open, and never returned, logged or sent (T83).
Tool output is scrubbed of known secret values before it is stored.
No token in any URL (no `?token=`). `tracing` never logs headers.
Tool child processes (bash, graphify) get an allow-listed environment: `env_clear()`, then `PATH HOME USER LOGNAME SHELL LANG LANGUAGE LC_* TERM COLORTERM TZ TMPDIR` and the names node.toml's `env_pass` matches; provider key variables, `.env` names and `HARNESS_*` are removed even when `env_pass` matches them.
The embedded node and `node run` build it through the same code.
Open: `git` children (`node/src/git.rs`) still inherit the node's environment.
Redaction guards against accidents only: it replaces exact known values, so an agent (or a hostile prompt) that encodes, reverses, splits or otherwise transforms a secret gets past it; the control is keeping secrets out of the shell's reach.
Within that limit it is exact on streams: streamed output (tool output and model text) goes through a `StreamScrubber` whose output, put together, is the scrub of the whole stream, so a secret that straddles a flush is still replaced: it holds back, unscrubbed, only text that could begin a secret (the last `longest short secret − 1` bytes for secrets under 32 bytes; for longer ones, from a place agreeing with a secret's first 4 bytes, for `longest − 1` bytes; at most 4096), judged so that where it cuts tells nothing past those 4 bytes (T75); matching is leftmost-longest, and event payloads are scrubbed field by field (never as serialized JSON, where a secret containing a quote or backslash is escaped and would be missed).
**What the event scrubber touches (A.23):** a secret can be any configured value, node.toml's MCP `env` values included, so it can equal a word the harness writes itself; scrubbing such a word in a field name, a type tag or an enum value made an event undecodable, and a node whose `session_created` does not decode does not start (independent review of the project-MCP change).
So `SecretSet::scrub_event` scrubs only free text: what a model, a tool, a provider or a person wrote (message and thinking text, tool input including the keys of its JSON, tool and MCP output, errors, attachments, sub-agent reports, streamed deltas, titles, paths, call ids, tool names).
The event's types decide, by probing once per kind and path for the life of the process: field names, tags, enum values and typed ids are never touched; below a `serde_json::Value` everything is free, keys included; a map's keys are free.
Text is scrubbed except at an explicit allowlist of positions by kind and path (`KEPT` in `core/src/secret/schema.rs`, each with the code that reads it back): the session's folder, model and agent, the turn, message, approval, grant, background and artifact ids, checkpoint refs, file and image hashes, the model a thinking block or a usage belongs to (`usage.model` and the keys of `usage.by_model` alike, so two models never merge), the digests of context sections, and a section's key when it is one of the harness's own (a subfolder file's key keeps its `instructions:` prefix and has its path scrubbed, the same in every turn).
The list fails closed: a position not on it, a field added later included, is scrubbed.
A kept position is never changed, whole value or part: a configured value that is not a secret is often a prefix of one (an env `HOME=/home/someone` is a prefix of every chat's folder), and a folder rewritten to `[REDACTED]/proj` breaks the session at its next load as a broken key does.
Accepted cost: a secret a person puts into a folder's name, a model's name or an agent's id is stored in that one position (it is still removed from all free text).
Not taken: keeping only whole-value matches there, for that prefix reason.
Keys of free JSON that would scrub to the same text are numbered (` (2)`), never merged; keys keep their order.
A configured value that is part of the marker `[REDACTED]` is never redacted (it cannot be a secret, and it would make a second pass change scrubbed text); a node names such an `env` value once at start.
The person's message is scrubbed once, before the model is sent it, and stored as sent.
A kind this build does not know has its string values scrubbed and no key touched.
Cost: after a kind's paths are known, a scrub is one pass over the event, the lookups, one copy and one decode-and-encode of the result to check it; measured on a 2.2 MB event, about 65 ms against 15 ms for the old rewrite-everything pass, and on 428 KB about 8 ms against 2 ms (`crates/core/tests/scrub_cost.rs`).
The first event of a kind that meets a new path probes it: a few decodes of a copy with long strings cut short, once per path per process (about 12 ms for a 40 KB event with every path new).
Both run with the session's log lock held, on its task.
Should a path ever have two classes (none does: a test checks every kind), the result fails the check, the changes are retried one path at a time, each checked, and the paths that do not decode keep their text, with a logged line naming the kind only.
Nothing is scrubbed when nothing matches: such an event is stored byte for byte as before.
Tests: `crates/core/tests/scrub_event.rs`, `crates/node/tests/scrubber_schema.rs`, `crates/agent-native/tests/section_keys.rs`.
Residual: a secret cut off by the output cap leaves its prefix before the cap marker, and a secret longer than 4096 bytes may leak if split.
