# T3

## Threat

Secrets leak via logs, URLs, event log

## Mitigation

Provider keys are referenced by env-var name in config, held in `Secret<String>` (redacted `Debug`), never put in events.
A person's forge tokens (X.27) are not in `secrets.toml` or the environment: they are sealed in `master.db` under `<data>/keys/secrets.key`, held in `Secret<String>` when open, and never returned, logged or sent (T83).
Tool output is scrubbed of known secret values before it is stored.
No token in any URL (no `?token=`). `tracing` never logs headers.
Tool child processes (bash, graphify) get an allow-listed environment: `env_clear()`, then `PATH HOME USER LOGNAME SHELL LANG LANGUAGE LC_* TERM COLORTERM TZ TMPDIR` and the names node.toml's `env_pass` matches; provider key variables, `.env` names and `HARNESS_*` are removed even when `env_pass` matches them.
The embedded node and `node run` build it through the same code.
Open: `git` children (`node/src/git.rs`) still inherit the node's environment.
Redaction guards against accidents only: it replaces exact known values, so an agent (or a hostile prompt) that encodes, reverses, splits or otherwise transforms a secret gets past it; the control is keeping secrets out of the shell's reach.
Output of commands the agent runs with the `bash` tool (foreground and background) has terminal escape sequences removed where the node reads the pipe (`AnsiStripper`, `crates/tools/src/filter.rs`), before the result, the kept full output (`tool_output`), the live pieces, a background ring or an end's tail are made, so a secret a command colours (`grep --color=always`, `rg --color`, `git diff --color-words` put an escape inside the match) is whole for the scrubber, which matches exact bytes.
The stripper must not become a way to hide text, so it removes only what is certainly a sequence: CSI, other escapes with their intermediate bytes, `U+009B` with parameters and a final byte, and OSC, DCS, APC, PM and SOS strings that are closed (BEL for OSC, or `ESC \`).
A string that is never closed (it runs into a line break or past 4096 characters) is not removed: only its introducer goes and the payload is shown as text; for that the stripper holds at most 4096 characters per stream while a string is open and releases them at the stream's end.
Per line (the count restarts at each newline) at most 256 characters go without a trace from closed strings; past that each removal, the one that crosses the bound included, leaves `[N characters of an escape sequence not shown]`.
The other C1 code points (`U+0080` to `U+009F`) are dropped one at a time and open nothing, as a UTF-8 terminal does not act on them.
The state is kept across reads (an escape cut in two by a read is still one; one stripper per stream, so stdout and stderr never run into each other's), a CSI or an open escape hides at most 4096 characters, and `\r` and `\n` end any open sequence and stay.
A property test puts random sequences inside a key and at read seams and checks that nothing visible is lost, and every path is tested (`crates/tools/tests/scrub_escapes.rs`, `a_key_split_by_an_escape_is_in_no_background_result_event_or_tail`).
The node's own git runs with `color.ui=never` and the other colour keys forced off, so a repository's config cannot colour what it prints (`a_repository_that_asks_for_colour_gets_none`).
Known, not covered: other ways a command can split a secret without an escape sequence (a backspace `a\bb`, a `\r` overwrite, `cut`, `sed`, an encoding) get past the exact match, as the line above says.
Known, not covered: the marker counts closed strings only, so a chain of short escapes can still take text away without a trace, a character or a few per sequence (`ESC` and one character, or a CSI whose parameters and final byte are the text), exactly as a terminal would not draw them; what the model and the person read is then what a terminal shows, not the file's bytes.
Known, not covered: a secret that itself contains an escape byte is not found after the strip, and a key split by a string that is closed and larger than the per-line bound leaves its marker inside it, not its text.
Known, not covered: raw bytes `0x80` to `0x9f` that are not UTF-8 are not C1 controls, they become `U+FFFD` like any invalid byte.
Known, not covered: text that is not output of the `bash` tool is not read by this stripper: graphify's output (`crates/tools/src/graphify.rs`), a project MCP server's stderr tail quoted in error text (`crates/tools/src/mcp.rs`), git run by the node (only its colour is forced off), web and MCP results.
Within that limit it is exact on streams: streamed output (tool output and model text) goes through a `StreamScrubber` whose output, put together, is the scrub of the whole stream, so a secret that straddles a flush is still replaced: it holds back, unscrubbed, only text that could begin a secret (the last `longest short secret − 1` bytes for secrets under 32 bytes; for longer ones, from a place agreeing with a secret's first 4 bytes, for `longest − 1` bytes; at most 4096), judged so that where it cuts tells nothing past those 4 bytes (T75); matching is leftmost-longest, and event payloads are scrubbed field by field (never as serialized JSON, where a secret containing a quote or backslash is escaped and would be missed).
**What the event scrubber touches (A.23):** a secret can be any configured value, node.toml's MCP `env` values included, so it can equal a word the harness writes itself; scrubbing such a word in a field name, a type tag or an enum value made an event undecodable, and a node whose `session_created` does not decode does not start (independent review of the project-MCP change).
So `SecretSet::scrub_event` scrubs only free text: what a model, a tool, a provider or a person wrote (message and thinking text, tool input including the keys of its JSON, tool and MCP output, errors, attachments, sub-agent reports, streamed deltas, titles, paths, call ids, tool names).
The event's types decide, by probing once per kind, path and shape of the node for the life of the process: field names, tags, enum values and typed ids are never touched; below a `serde_json::Value` everything is free, keys included; a map's keys are free.
Text is scrubbed except at an explicit allowlist of positions by kind and path (`KEPT` in `core/src/secret/schema.rs`, each with the code that reads it back): the session's folder, model and agent, the turn, message, approval, grant, background and artifact ids, checkpoint refs, file and image hashes, the model a thinking block or a usage belongs to (`usage.model` and the keys of `usage.by_model` alike, so two models never merge), the digests of context sections, and a section's key when it is one of the harness's own (a subfolder file's key keeps its `instructions:` prefix and has its path scrubbed, the same in every turn).
The list fails closed: a position not on it, a field added later included, is scrubbed.
A kept position is never changed, whole value or part: a configured value that is not a secret is often a prefix of one (an env `HOME=/home/someone` is a prefix of every chat's folder), and a folder rewritten to `[REDACTED]/proj` breaks the session at its next load as a broken key does.
Accepted cost: a secret a person puts into a folder's name, a model's name or an agent's id is stored in that one position (it is still removed from all free text).
Not taken: keeping only whole-value matches there, for that prefix reason.
Keys of free JSON that would scrub to the same text are numbered (` (2)`), never merged; keys keep their order.
A configured value that is part of the marker `[REDACTED]` is never redacted (it cannot be a secret, and it would make a second pass change scrubbed text); a node names such an `env` value once at start.
The person's message is scrubbed once, before the model is sent it, and stored as sent.
A kind this build does not know has its string values scrubbed and no key touched.
Cost: after a kind's paths are known, a scrub is one pass over the event, the lookups, one copy and one decode-and-encode of the result to check it; measured on a 2.2 MB event, about 65 ms against 15 ms for the old rewrite-everything pass, and on 428 KB about 8 ms against 2 ms (`crates/core/tests/scrub_cost.rs`).
The first event of a kind that meets a new path probes it: a few decodes of a copy with long strings cut short, once per path per process (about 12 ms for a 40 KB event with every path new).
Both run with the session's log lock held, on its task.
Should a path of one shape ever have two classes (none is known in the event schema: `a_path_has_one_class_in_every_instance` checks the instances the tests build of every kind, and a review's wider run over 815 type-valid variants found none), the result fails the check, the changes are retried one path at a time, each checked, and the paths that do not decode keep their text, with a logged line naming the kind only.
A position's class does not depend on which payload of its kind the process met first: a class is learned only from a node that can tell (a string, or an object or array with something in it), never from a `null`, an empty object or array, a number or a bool, and it is kept per path and per shape of the node.
A class that does not fit the node is not taken as "nothing here": the node is scrubbed as free text (when in doubt, scrub).
A limit of the design, should such a type ever be added: a path that is a fixed word in one variant of an enum and free text in another, both strings, has one class, and when the fixed word is met first the other variant's text stays unscrubbed with no fallback, because the result still decodes; the event schema has no such path.
The defect this closes was real from the commit that introduced the per-process class cache (`e365b3f8`, 2026-11-18) until its fix: when the first event of a kind that had something to scrub held a `null` or an empty object at a position, that position was classed as a sequence or a struct for the life of the process, and a later string there, or a later map's keys, stayed unscrubbed.
It needed a node with configured secrets, and it reached three positions: `artifact_staged.packed` (the harness writes `tar.gz` or nothing), the keys of `artifact_staged.meta.skipped` (the harness writes the reasons), and the keys of `user_message.reply.values`, the field names of a form's answer, which a model's form spec names and a person fills in; the values under them were scrubbed all along.
Nothing is scrubbed when nothing matches: such an event is stored byte for byte as before.
Tests: `crates/core/tests/scrub_event.rs`, `crates/core/tests/scrub_class_null_first.rs` and `crates/core/tests/scrub_order.rs` (each instance in turn is the first of its kind, in a process of its own, and so is every order: all store the same, and what is left of the secret is at a kept position; one kind, `artifact_staged`, is met by eight threads at once, 200 times), `crates/core/src/secret/schema.rs` (unit tests), `crates/node/tests/scrubber_schema.rs`, `crates/agent-native/tests/section_keys.rs`.
Residual: a secret cut off by the output cap leaves its prefix before the cap marker, and a secret longer than 4096 bytes may leak if split.
A configured value shorter than 8 bytes is never redacted (too many false hits).
A secret written as a JSON number in free JSON (a tool input `{"pin": 12345678901}`, a form's number field) is redacted: the number becomes its scrubbed text, as `serde_json` writes the number (`"[REDACTED]"`, `"99[REDACTED]55"`).
A number that stands directly at a typed position is asked about on its own, with a string probed in its place: free JSON takes it and the number is replaced, a typed number does not and stays; the answer is never kept for the path, because one path can name a typed number in one element and free JSON in the next (past 256 such numbers in one event the rest are taken as free, and the check of the result decides).
Numbers are looked at only when a configured value is made of digits and the signs a number is written with.
The match is against the number as it is written back, so it misses a value configured in another spelling of the same number: leading zeros, a leading `+`, a trailing zero after the point (`12345678901.50` against `12345678901.5`).
Not redacted: a number the event's types fix (an exit code, a count), which cannot hold the marker; a number of a kind this build does not know; a number too large for 64 bits, which was read as a float before any scrubber saw it and is stored as `1.2345678901234568e+20`: the first 16 or 17 digits of such a value are stored in the clear.
Tests: `crates/core/tests/scrub_numbers.rs`.
