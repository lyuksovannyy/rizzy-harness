# T21

## Threat

Slow or numerous clients hold the HTTP server's connections and handlers (slowloris, a silent socket, a TLS handshake that never completes, a handler that never returns)

## Mitigation

**The serve loop is ours** (`master/src/serve.rs`, replacing `axum::serve` and the old accept-loop in `cli/src/net.rs`): hyper's HTTP/1 server with a header-read timeout of 10 s over the whole request head (half a request line, silence and a header a byte at a time all end at the same deadline; it is also the idle time of a keep-alive connection), and a 10 s timeout on the TLS handshake.
**Connection cap** 512: the permit is taken before `accept`, so at the cap the server stops accepting and clients wait in the kernel backlog; the permit lives in the connection task and is released however the connection ends.
An upgraded connection (WebSocket) releases its permit at the upgrade: sockets neither count against the HTTP cap nor hold shutdown; their number is bounded per user in `ws.rs`.
**Request timeout** (`master/src/limits.rs`, a route layer keyed by the route template): 30 s on every route by default, 120 s on the routes that call a provider, none on the WebSocket, uploads, blob downloads and artifact saves; a timed-out request answers 504 `{"error":"request timed out"}` and its handler future is dropped.
A new route is limited by default.
**Shutdown**: Ctrl-C stops accepting, lets in-flight requests finish for up to 30 s, then closes.
HTTP/2 is not enabled.
Tests in `master/tests/it/server_limits.rs`.
**Residual:** the request timeout bounds the handler's future, not the work it spawned (`spawn_blocking`, detached tasks); there is no write timeout, so a client that reads a response slowly holds its connection (and permit) until it finishes or disconnects; nothing limits connections per source address.
