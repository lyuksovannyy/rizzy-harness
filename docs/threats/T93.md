# T93

## Threat

**A person's bookmark on a message is one more event the owner's click writes into a chat's log** (ADOPTION_PLAN X.51, README "Pinned messages"): if anything but the owner could write it, a pin could be a way to mark another person's chat, to change what a model is sent, or to grow a log without bound.

## Mitigation

**Only the chat's owner pins.**
`POST /api/sessions/{id}/pins` answers anyone else, admins, workspace admins and the API token on an owned chat included, with the 404 of a chat that does not exist, the same bytes (`crates/master/tests/it/pins_http.rs`).
**A pin is not sent to the model.**
The rebuild, the `history` tool, the hand-off note, search and recall ignore `message_pinned`, and no model, tool or routine can send `session.pin` (`crates/node/tests/pins.rs::the_model_is_sent_nothing_about_a_pin`).
**A chat holds at most 50 pins.**
`harness_core::pins::check` refuses the 51st, a message that is not in the chat, one a rewind hides, a repeat and an unpin of nothing, on the master from its mirror and again on the node from its own log under one gate, so two clicks cannot pass the limit.
The node writes through the session's one writer, so `seq` stays contiguous also while a turn runs.
Not undone, stated plainly: a pin shows the first 120 characters of a message in a list on the page of the person who could already read the whole message.
