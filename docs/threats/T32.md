# T32

## Threat

A sub-agent that can change files runs in the parent's folder because its worktree could not be made (not a repository, `worktree add` failing, a hostile repository config): parallel sub-agents and the parent overwrite each other's files, and a child whose log failed has already changed the folder, so T28's "not applied" rule cannot hold (final review A8)

## Mitigation

**Isolation or no start** (§5, checkpoints): `Session::isolate` decides from the child's effective tools on this node (`write`, `edit` or `bash`, after the agent's own denials and the node's `denied_tools`); without a worktree the delegation is refused before the child session is created, with the reason and what would work as the parent's tool result, and a half-made worktree and base ref are removed.
The fallback to the shared folder and its note are gone; no setting restores them.
Read-only sub-agents still work in the parent's folder.
Tests in `node/tests/runtime.rs`: `a_writing_sub_agent_is_refused_outside_a_repository` (`write`, `edit` and `bash`; no child session, folder unchanged), `a_writing_sub_agent_is_refused_when_its_folder_cannot_be_made` (`<data>/sessions` is a file; no ref left), `a_read_only_sub_agent_runs_outside_a_repository`, `a_writing_sub_agent_changes_are_applied_from_its_worktree` (from its own folder since R.1), `parallel_writing_sub_agents_do_not_see_each_other`.
**A sub-agent's folder is node-owned** (R.1 follow-up, the fix review's R1-1 to R1-3; `git::SubRepo::make_folder`, `session.rs` `isolate`): `<data>/sessions/<child id>/files`, beside the checkpoint store, in the folder of per-session folders the signed-off node layout uses (docs/nodes-credentials-environments.md §4.11).
The sessions folder is protected like the data directory (`NodePolicy::protect` at start; no session folder may be it, hold it or be inside it, no file tool reaches it, no sandbox grant exposes it) except for the one child each folder belongs to: the node passes that child its folder (`harness_core::folder::OwnedFolder`, through `TurnHost::owned_folder`), the file tools let exactly that folder through, and its sandbox gets read-write on it (and on its `.git` when it works in a sub-folder) and read-only on the user's `<root>/.git/objects`.
Nothing is judged from a path or from a file the child can write.
The node fills the folder from the sub-agent shadow (the base snapshot) and writes it a git directory of its own (`files/.git`: `HEAD` at the user's `HEAD` commit, a minimal `config`, the user's object store as its alternates, the index from `HEAD`'s tree made by the shadow) before the child starts; **the node never runs git with that directory**, so the child may write its config and hooks freely.
No other session can reach the folder while it is filled or while the child works, so the paths the node's git uses are not swapped under it (R1-2).
The child's grant on the user's repository is read-only `objects` only: no `worktree add`, no `worktrees/<id>`, no write on the objects.
A writing sub-agent of a sub-agent is refused; a read-only one (where `[limits] max_delegation_depth`, T5, allows a second level at all) works in its parent's node-owned folder (`node/tests/runtime.rs` `a_nested_delegation_reads_in_the_childs_folder_and_never_writes`).
The folders of sub-agents running when the node stopped are removed at the next start.
Tests: `cli/tests/sub_agent_sandbox.rs` (`git status`, `add`, `commit`, `diff` and `log` with the user's history work in the child's folder; the child cannot write the user's `.git` config, hooks, `info/attributes`, `packed-refs` or objects, nor read its config; the child's own alternates pointed at another repository read nothing there; a sibling's folder is unreadable and unwritable to it; the child cannot rename its folder; the parent can neither list nor write the child's folder nor rename its own; the file tools agree), `node/src/git_child_tests.rs` (R1-1 and R1-2 inverted, 120 racing tries, 0 landed), `node/tests/runtime.rs` (`a_writing_sub_agent_is_refused_when_its_folder_cannot_be_made`, the delegation flows below).
The child's own `git status`/`git diff` show the parent's uncommitted work as changes against `HEAD`.
Since R.1 a writing sub-agent also needs the node's checkpoint store (`checkpoints_dir`, always set by `node run` and `serve`).
**Merge-back, per file, three ways** (fix of 2026-11-15 after the first live test with real models, where the second of two writing children that touched one file was refused whole and its work was out of everyone's reach; `git/merge.rs`): for each path the child changed, base `B`, the folder's snapshot now `N`, the child's `C`: only the child changed it, taken; both made the same change, nothing to write; both changed text, `git merge-file --object-id` on the three blobs in the sub-agent shadow (object ids as arguments, never a path; the shadow's confined git: no user or system config, attributes from the empty tree, so no merge driver, filter, `textconv` or hook of the repository runs; bounded by `GIT_TIMEOUT`), a clean merge taken, overlapping hunks a conflict; deleted on one side and changed on the other, added on both, a link or gitlink on any side, binary content (a NUL in the first 8,000 bytes), a side over 1 MiB, a file where the folder now has a folder (or the reverse): a conflict, never a silent pick of one side; renames are a deletion and an addition (no rename detection).
Any conflict: nothing of that child is written.
Otherwise one target commit (the folder's snapshot with the child's and the merged blobs put in, at `refs/harness/<child>/merged`) is written by the restore machinery as before (paths checked inside the folder, writes relative to directories opened without following links, `WriteLimits::SUB_AGENT`), after a second snapshot of the folder: a file changed between the merge and that snapshot is a conflict too (not overwritten).
The residual window between that snapshot and the write is T33's.
The result and the ref stay in the sub-agent shadow as before; the parent's `delegate` result says how many files were applied and which were merged, or, when not applied, which files conflict and why and the child's diff against its base (from the same bounded diff as a turn's, T53, the node's secrets scrubbed; at most 16,000 characters, files in path order, cut at a file's boundary with the rest named and the cut said in the harness's note), every line behind `| ` like the child's report, with one sentence that nothing was written and that the agent can redo the changes with its own tools.
Tests: `node/src/git_child_tests.rs` (different parts land; overlapping writes nothing of the child; binary, deleted, link, added-on-both and oversized cases; what only the child changed is taken whatever it is; a hostile repository's merge driver, filter, diff driver and `merge.default` never run, files named `--theirs`, `-p`, `:(glob)*` and one with a line break merge, a conflict on the last is listed without its line break; a file edited during the merge is not overwritten), `node/tests/child_merge.rs` (two children changing different functions of one file both land and one Undo of the turn restores the folder; overlapping children leave the folder alone and the parent gets the file named and the diff quoted), `core/src/subagent.rs` (`an_unapplied_diff_is_quoted_line_by_line_after_the_note`).
**Review of PR 118 (fixed in it):** a write that fails partway is put back, and only what it left of the child (re-check of PR 118, RC1): the folder is snapshotted again after the failure (`refs/harness/<child>/failed`); a path that still holds the child's version is put back as the snapshot taken right before the write (`refs/harness/<child>/check`) holds it, through the restore's own check; a path already as it was needs nothing; a path that holds neither was changed by someone else after the failure and is left alone and named in the outcome ("left as they are"); folders the write made above a file it created are removed when empty.
So "nothing was written" holds, a file restores its mode, and the turn's Undo stays exact.
If putting back fails too, the result is `NotApplied::Partial`, naming the files that hold the child's version and that snapshot.
A path the plan adds that is on disk all the same (or below a parent that is on disk as a file) is a file no snapshot holds, one git ignores: a conflict ("a file of yours that git ignores is in the way"), so a child that un-ignores the person's `.env` and writes one never overwrites it (this hole is older than the merge).
A folder on disk where the plan writes a file (a child that replaced a tracked folder by a file, RC2) is in the way only through what it holds that the plan does not delete, and those files are named; otherwise the child lands.
What the child made that the repository ignores is listed (`SubRepo::ignored`, `ls-files --others --ignored --directory` in the shadow, an empty index) and named in the note, as are changes to nested repositories (never applied).
Work under the node-wide merge lock is bounded: more than 500 files changed on both sides make the child a conflict, and the line-by-line merging stops after 60 s (nothing written; the parent gets the diff); per file three git processes (sizes, one `cat-file --batch`, `merge-file`).
A child whose changes are not in the folder makes the `delegate` result not ok (the card is not green; its own status line is kept) and the result ends with `subagent::NOT_APPLIED_LAST`, telling the parent to apply the changes itself or delegate them again before it answers.
The unapplied diff names every changed file first (up to 200) and counts its 16,000 characters as quoted.
Tests in `node/src/git_child_tests.rs` (`a_failure_partway_is_put_back`, `a_failed_put_back_says_what_was_written`, `a_child_unignoring_a_path_does_not_overwrite_the_persons_ignored_file`, `a_childs_ignored_new_file_is_named`, `too_many_two_sided_files_are_a_conflict`, `a_put_back_leaves_what_changed_after_the_failed_write`, `a_put_back_removes_only_what_the_failed_write_made_and_undo_is_exact`, `a_child_replacing_a_folder_by_a_file_lands`, `a_child_replacing_a_folder_with_an_ignored_file_in_it_is_a_conflict`, `a_dangling_ignored_link_in_the_way_is_a_conflict`, and the reviewer's three-children, concurrency, content-case and old-git tests), `node/tests/child_merge.rs` (`a_refused_childs_delegate_result_is_not_ok_and_ends_with_what_to_do`, `a_childs_ignored_files_are_named_in_the_note`).
**Residual:** a file changed in the moment between the snapshot after a failed write and the put-back's write of that file is still overwritten by the put-back (the same narrow window as T33's, now per file instead of from the failure on).
**Residual:** a merge that is textually clean can still be semantically wrong (two children each adding a function of the same name in different places): as with `git merge`, the parent is told which files were merged and is expected to check them; `merge-file --object-id` needs git 2.43 or newer, older git makes every two-sided change a conflict.
**Residual:** delegating file changes in a folder that is not a plain git repository within the workspace roots no longer works (the parent makes the change itself, or the user runs `git init`); the child can read all of the repository's objects (its whole history, as the parent can); a child writing objects into its own `.git` can fill the disk (no quota).
Since fix review 4 (R1c-1) every grant of the child carries the identity the node took: its folder and `.git` when made, the user's object store when accepted; a store replaced since is not granted (no history for the child), and the wrapper re-checks each identity on the descriptor it opens (T4).
**Accepted (R.4)** from the R.1 residuals and fix review 3: `worktree add --orphan` (a repository with no commit) needs git 2.42 or newer; on older git a writing sub-agent there is refused.
A child session's `cwd` is a path inside the data directory and goes into `session_created` and the system prompt, so the model and the chat learn where the data directory is (fix review 3 N-4); the data directory is closed to sessions by the sandbox and the file tools, so knowing its path gives nothing. `NodeRuntime::start` empties `<checkpoints>/../sessions` unconditionally (fix review 3 N-5); in the shipped binary that is `<data>/sessions`, but an embedding that pointed the checkpoint store elsewhere would empty another folder: tying it to the data directory explicitly, with a marker the node wrote, is the fix, not done here.


## Since 2026-11-21: a writing sub-agent works in the chat's folder unless a copy is asked for

By the owner's decision of 2026-11-21 a writing sub-agent works in the chat's folder unless the delegating agent asks for a copy.
"Isolation or no start" now applies to `folder: "own"` in the `delegate` call and to nodes that set `[limits] sub_agent_folder = "own"` in node.toml.
The node decides: `"own"` there gives every writing sub-agent a copy whatever the call asks, with a refusal that names the setting when `shared` was asked for by name and the folder is not a repository; nothing over the protocol or HTTP changes it.
The default is `"shared"`: no snapshot, no copy, no merge, no base ref, and a writing sub-agent runs in a folder that is not a git repository (`own` there is refused, and the sentence says that leaving `folder` out works).
No per-agent switch: anything a shared sub-agent writes, the chat's own tools or an `own` sub-agent's merge could write too.
A shared sub-agent's session has the parent's `cwd`, folder pin and sandbox view (read-write on the folder, the same protected paths), nothing more: it cannot reach the node's data directory, another sub-agent's folder or the sessions folder (`cli/tests/sub_agent_sandbox.rs`, `a_shared_sub_agent_writes_the_chats_folder_and_reaches_nothing_else`).
A writing sub-agent of a sub-agent stays refused, shared or not.
In plan mode nothing writes, whatever `folder` says; the child asks under the parent's mode cap and chat grants are the parent's (`node/tests/approval_modes.rs` runs on the shared default).
`session_created` of a sub-agent that can change files records `sub_folder` (additive), which the delegate card and the child chat's banner show.
What this weakens:
Parallel writers in one folder can step on each other's files: the staleness guard of `edit` and `write` (T45) stops a blind overwrite of a file changed since that agent read it, nothing stops a command (`bash` is not covered), and the delegating agent is told to ask for a copy for parallel work.
There is no merge step in between for a shared sub-agent, so "nothing of that child is written on a conflict" does not apply to it.
The turn's Undo is the way back: the lead's turn checkpoint is a snapshot of the whole folder, so it holds what a sub-agent the lead waited for wrote in that turn (`checkpoint.files`, "Show changes" and Undo cover it), and T57 does not count that sub-agent as another chat.
A shared sub-agent takes turn checkpoints of its own in the same folder, as a reader always did: its own chat can undo its turn, which T57 holds against the lead's calls in that span like against any other chat.
A sub-agent started in the background was not waited for: its work counts as another chat's for the lead's undo (it asks first, naming the files, and "Undo anyway" still passes), and what it writes after the lead's turn ended is in no turn of the lead and is undone in its own chat; its own entry in its parent's log is not another chat's command when it undoes itself.
The `delegate` result of a shared sub-agent ends with one harness line: where it worked and the files that changed in the folder while it worked (from its turn's checkpoints, at most 20 then "and N more", names made harmless), so the lead knows its earlier reads are out of date; with overlapping writers it lists the other writer's files too.
The A8 case, shared: a sub-agent whose log fails after it changed files leaves them (nothing un-writes them), and the result says its record is incomplete, that its changes are in the folder and that the turn's Undo restores them.
Tests: `node/tests/shared_folder.rs` (default, outside a repository, `own`, the node's setting, a reader, two writers' staleness, the failed record, depth, plan mode, follow-ups), `node/tests/shared_folder_undo.rs` (the lead's Undo exact with one and two shared children, another chat's file still refusing it, a background child's writes in and after the turn), `cli/tests/sub_agent_sandbox.rs`, `agent-native/src/delegate_availability_tests.rs`, `core/src/subagent.rs`.
**Residual:** a foreground shared sub-agent's own Undo is refused by T57 against the lead's `delegate` call in that span when the lead's turn changed the same files ("Undo anyway" passes); the lead's turn Undo is the way back.
**Residual:** a file a command of one writer changed that the other's guard never saw is overwritten without a word if the other uses `write` after a `read` that came after the change (the guard compares content, it cannot know who wrote it).
