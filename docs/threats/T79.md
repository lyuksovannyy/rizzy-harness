# T79

## Threat

**A workspace's own agents** (ADOPTION_PLAN X.33, README "Workspace agents", docs/agent-pages.md "Workspace agents"): whoever holds a workspace's `settings` permission makes agents only that workspace has and adds its summary and additional instructions to the server's agents.
Abuse cases: (a) an agent of workspace A is listed in, resolved in or run from workspace B (by `agent_id` on a new chat or a prompt, an `@mention`, the agent switch, a workspace default or chain, a routine, a sub-agent's delegates, its page by id, the API token without a workspace); (b) a removed or unknown workspace agent id resolves to a stronger agent (a server agent of that id, a default); (c) a member without `settings`, a workspace admin at the server's scope or in another workspace, or a server admin who is not a member writes or reads a workspace's agents; (d) a workspace editor gives an agent power the editor or the person using it does not have, or makes one that poses as a server agent; (e) a workspace fills the master with agents; (f) a workspace's edit of a built-in leaks into another workspace, or the listing, the picker and the turn disagree; (g) a turn changes agent mid-way when the agent is edited or deleted.
What stops each: (a) one path: `Master::agents_in` composes base → server edits → that workspace's edits (`AgentSet::with_layers`) and every resolver (`resolver_for`, `resolver_in`, `Access::resolver`) is built from the chat's own workspace's set, so an id from elsewhere is `UnknownAgent` (400), a mention of it is text, `GET /api/agents/{id}?workspace=B` is 404; delegates come only from the agent's own layer or a wider one, so a built-in, file or server agent never gets a workspace's agent, even one named in its `delegates`; (b) a deleted workspace agent degrades as a removed server agent does (T27): the chat's next prompt is `AgentGone` (409), a default naming it `BadDefault` (409), a routine naming it is blocked, and its chain there is removed; a workspace agent cannot take a server agent's id or alias (409); the server's agents win, by one rule, as a later file does: a server agent made with an id a workspace's agent has is accepted (the server's admin is told nothing about workspaces), that workspace's agent is skipped there with a log line and listed to the workspace's editors as hidden (`hidden` on `GET /api/agents`), and **in that workspace the id then means the server's agent**, its stored chats included; ids beat aliases, and in a workspace's set the server's agents claim aliases first, so a server alias equal to a workspace agent's id loses in that workspace and holds everywhere else; deleting a server agent deletes every workspace's overlay on it, so an overlay never lands on a later agent with its id; (c) a write names its scope (`?scope=server` server admins only, `?workspace=` needs `Access::require(Perm::Settings)`, neither is 400); a non-member gets 404 (`workspaces::access`), server admins included; reads need membership; (d) every switch is a request, not a grant: the tools run only within the chat owner's level in the workspace (N.10a), the node's `node.toml` (T4, T5), approvals, and the workspace's model chains; no field sets a model, an effort, a `ui` level, caps beyond the defaults (4 sub-agents, 200k tokens per turn), a node or a level; looks stay server-wide.
**This does not stop a workspace's admin from steering members' chats** (accepted, below).
A workspace's agent may not be called what a server agent is called, nor its id or an alias, compared with only letters and digits, case-folded (409; a name it already had stays when a server agent takes it later, and both show, the workspace's marked "workspace"), so no workspace shows a second "Assistant"; (e) at most 30 own agents per workspace (an account has one Personal workspace and may make team workspaces, each with its own 30; ids are per workspace, so this squats nothing on the server) (checked in the store's transaction), at most 64 KiB per stored agent (master and a CHECK on the column), refused past either; overlays exist only for the server's agents; the cache keeps at most 32 workspaces; (f) the workspace's overlay applies only in its set, under its own heading after the server's, and changes the prompt hash; listing, picker and turn read one composed set, cached per workspace and dropped by every write to it or to the server's scope; (g) the spec is fixed when a turn is dispatched and travels to the node with it: an edit or deletion mid-turn reaches the next turn only.
Tests: `crates/master/tests/it/workspace_agents_http.rs` (every case above, written first and failing on the old code; the review's cases: `a_server_agent_wins_over_a_workspace_agents_id`, `a_workspace_agent_cannot_take_a_server_agents_name`, `a_deleted_server_agent_takes_workspace_overlays_with_it`, `a_workspace_agents_id_beats_a_server_alias_in_its_workspace`), `agent_edits::tests::a_workspace_set_is_cached_until_a_write_changes_it`, `a_load_that_began_before_a_write_is_not_kept`, `crates/agents/tests/agents.rs` (`a_workspace_layer_goes_on_the_servers`), `crates/store/tests/workspaces.rs` (`workspace_agents_are_bounded_and_go_with_the_workspace`).
**Accepted leftover, against "chats are private to their owner, for admins too"** (the owner, 2026-11-18: "Allow it", to "In team workspaces, refuse agents that combine chat search with commands, MCP or file edits?"): a workspace's admin writes the system prompt of the agents its members use, may make one both defaults (a member's ordinary new chat runs it), may add switches later to an agent a member already chose, and may give it "Earlier chats and memory search" together with commands, MCP, the web or file edits; such an agent can search the member's own earlier chats in that workspace and their memory (when they share it there) and has a way to send text out, bounded only by the member's approval mode, level and the node's network rule (T55).
Pinned by `a_workspace_admin_may_give_members_agents_chat_search_with_commands_as_decided`.
What a member has: the agent's origin on the Agents pages ("workspace", and "Made by this workspace's admins" with its switches on its page, read-only); the composer's agent picker, its @mention list and the routine editor's agent list say "workspace agent" for it, from the server's `scope`, never from the agent's own text (`lib/agents.ts` `marked`; `composer.test.tsx`, `routines.test.tsx`); the picker's closed button shows the name only.
**Residual:** writing a summary (`POST /api/agent-summary`) is open to every `settings` holder, Personal included, on the server's default model: one request, at most 40,000 characters in, 60 s, no rate limit of its own, the same cost as a chat message to the default model, which every account can already send.
Names are compared letters-and-digits only: a look-alike from another script (Cyrillic "а") is not caught.
A store that cannot be read gives the server's set for that request, uncached: its own agents are then unknown (refused, never stood in for), but **its overlays are missing too, so additional instructions written as restrictions do not apply to that request** (making every resolver fallible is a larger change; left).
