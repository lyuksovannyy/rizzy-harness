# T56

## Threat

A chat runs far longer than its owner meant (ADOPTION_PLAN X.14): the default step limit is 1,000 (the owner's decision, 2026-11-15: "Raise max to 1000 by default + add ability for session owners to override max steps (min: 1 - {max setted})"), so with Auto, the default approval mode, one message can run a thousand model requests and tool calls with nobody clicking: provider spend, load on the node, and a prompt-injected agent's time to act.

## Mitigation

Bounded by the chat's own limit (set by its owner only, through `session.set_step_limit`, clamped by the node to `1..=` its `[limits] max_steps` whatever the master sends, recorded as `step_limit_changed` by the session actor), the node's `max_steps` (node.toml decides), the repeated-call guard (T40), the model stream timeouts, Stop, and the provider's limits.
No model output, tool, skill or MCP server can change the limit; a node that does not announce `steps-max:*` is never sent the command.
A sub-agent's cap is at most its parent chat's limit (1 when the parent chat is gone); a callback turn takes the lower of `callback_max_steps` (default 20) and the chat's limit; a scheduled routine in Auto gets up to the node's limit of unattended steps per run.
A step may carry several tool calls, and sub-agents multiply the cost (by default 4 in parallel, each up to the chat's limit), so one message can cost about (1 + sub-agents) × the limit; the sub-agent token budget refuses only new sub-agents, not a running one (follow-up).
A change the master sends as a lowering (skipping the owner's level check) that would raise the limit in force is refused by the node (`STEPS_NOT_A_LOWERING`).
Residual: a long Auto turn is, by the owner's choice, a thousand unattended steps.
