# T81

## Threat

**Skills stored on the master** (ADOPTION_PLAN X.34 step B, README "Skills stored on the server"; the owner, 2026-11-17: "we must have sort of skills storage … skills must be used as well only when required", which is the yes for master-sent skill text and changes T46's "from the node only"): the server's admins (Built-in) and a workspace's editors write skills as text (`stored_skills`), the master lists their names and descriptions with each turn, and a node asks for one body when its agent loads it (`skill.request`).
Abuse cases: (a) a body or a list entry reaches another workspace's chat, an agent the skill is Assigned away from (directly, as a sub-agent, through `/name`), a chat outside any workspace, or a node asking for a session it does not run; (b) a master uses the list to shadow a node's own skill or to make the node read or run something on its disk; (c) a node with `[skills] from_master = false` still lists or asks; (d) hidden or control characters, an over-long field, a name of the wrong shape, a 10 MB upload or front matter that does not end is stored, or stored cut; (e) a body forges a harness line or closes its wrapper; (f) a member writes, a workspace admin writes the server's scope or another workspace's, caps pass under concurrent creates, a workspace's skills outlive it, a server skill takes a workspace skill's name; (g) a flood of loads in one turn, a load after the turn ended, the master away, a repeated `req_id`; (h) an edit or a delete mid-chat; (i) text reaches the browser as markup

## Mitigation

**Text only, names first, body on request.**
A stored skill is a name (the Agent Skills rule: 1 to 64 of `a-z0-9-`, no leading, trailing or double `-`; `valid_stored_skill_name`), a one-line description (1 to 1,024 characters) and a body (1 byte to 24 KiB); `harness_tools::skills::check_stored` refuses control characters (but a body's `\n` and tab), U+2028 and U+2029, and the hidden set (`text::is_hidden`) anywhere (review of PR 148 L1), the check running off the async workers (a YAML alias bomb parses for about a second, L3), with the reason, for a write, an edit and an upload alike; an upload is read by discovery's own reader (`read_skill_md`: same `split_front`, YAML then the line reader, which the answer says), its other keys listed back as not used and `allowed-tools`/`hooks`/`model`/… said to have no effect; a file over 40 KiB (`MAX_SKILL_MD`, the browser refusing the same number first) is refused before it is read (the HTTP body limit stops a 10 MB one first); the table's CHECKs say the same again.
**Scopes** (the agents rule of PR 146): `workspace_id` NULL is the server's, else the workspace's (cascade on delete); one name per scope (a unique index), a workspace skill under a server skill's name is refused in the same transaction, and one made earlier is left out of that workspace's turns and shown to its editors as hidden (`stored_skills::layered`); writes need the server admin (server scope) or the workspace's `settings` (404 to a non-member); 75 skills and 1 MiB per scope, counted in the write's transaction (`store::stored_skill_create`; 8 concurrent creates at a cap of 3 make 3).
**The list** (`AgentSpec::stored_skills`, names, scope and a description cut to one line of 200 characters, the store keeping the whole) travels once per command, on the top spec only, holding every stored skill that the turn's agent or any of its delegates may use after the Plugins deny list (`Offered::offer` in `Resolver::agent_spec_with`, so every path that sends a spec gets it), only for a chat in a workspace; each spec, the top one included, carries its own `deny_skills`, and the node gives a child (started, continued or in the background, all through the `delegate` tool in `agent_native`) its parent's list, which the child's own denials then narrow.
Copied onto each delegate as first built, 150 descriptions of 1,024 four-byte characters made a teamlead prompt 3.1 MB and an agent switch with 18 delegates 10.6 MB, over the link's frame (review of PR 148, H1; now about 130 KiB at most, `the_list_travels_once_and_fits_the_link`).
Whether a spec without file access keeps `skill` (it has something of the list to load) is decided per spec on the master.
A node without the `stored-skills` capability gets none (`stored_skills::strip`).
**Every command** is measured in `send_command` before it goes on the link: one over `MAX_PROMPT_JSON` (7 MiB) is refused with `TooLarge` and never sent, so no command can close a node's link for its other chats (a prompt, a retry, the agent switch and a new chat answer 413; a callback is recorded as refused).
**The node decides:** it takes the list only where node.toml `[skills] from_master` is on (default on: the same kind of text as the instructions and memory the master sends; off, it neither lists nor asks and does not announce the capability), merges it after discovery and its own deny list (`merge_stored`; names in order: the node's own `[skills] roots`, a folder of them discovery refused included, then the stored ones, server before workspace, then the repository's, a repository skill hidden by a stored one being left out with discovery's note, review of PR 148 M3 and L2; a denied name, a bad name or a list over 150 entries is not taken), and offers skill folders only to an agent that works on files or runs commands (`AgentSpec::works_on_files`); a stored entry has no folder (`dir` empty), is never a shell grant, and the tool refuses `file` for it without asking anyone.
Nothing in the new fields names a path or a program.
**The body:** `skill.request` carries a request id, the session id and the name, nothing else (an extra field is ignored); the master answers from the session alone (`stored_skills::answer`): the node must run it (`recall::sessions`), the chat (a sub-agent's: its parent) must have a workspace, the session must have an open turn whose `skill` was not withheld, that turn's agent (a sub-agent's session: the sub-agent's own id) must have `skill` and pass the workspace's Plugins rule computed again here, and the name must be one that workspace sees now; 16 loads per chat turn, its sub-agents' included (counted on the top chat's open turn as `recall` counts; a background sub-agent whose parent turn has ended counts on its own; a repeated `req_id` counts; review of PR 148 M2), 4 in progress per node; the counts live in the master's memory and start over past 4,096 tracked chats and at a restart, as `recall`'s do (review L6); **unlike `recall` and the board, a callback, untrusted (webhook) or temporary turn is answered too** (the coordinator's decision on review M1): a stored skill is instruction text an admin wrote for agents, not the person's private data, and such a turn should work with the same skills as a typed prompt (`callback_and_temporary_turns_load_stored_skills`); the node waits 20 s, takes only the first answer to a waiting id, and refuses a body over 48 KiB.
**Framing:** the body is a tool result under the same header as a folder skill's (whose text it is, that it changes nothing) and cut at the same 24 KiB; every tool result's lines that start like a harness line are escaped on the way to the provider (`escape_leads`, R-2), and nothing follows the body, so there is no end marker to forge; descriptions are one line in the quoted list.
**Mid-chat:** an edit or delete holds from the next load (the history keeps what was loaded, as for any tool result) and the next turn's list.
The screen renders every name, description and body as text (`<pre>`).
Tests: `store/tests/workspaces.rs` (`stored_skills_are_scoped_capped_and_cascade`), `protocol/src/lib.rs` (`skill_messages_name_no_place`), `tools/tests/skills.rs` (`stored_skills_merge_under_the_nodes_own`, `a_stored_skill_loads_from_the_master_as_text_only`, `the_stored_skill_check_refuses_with_a_reason`, `a_skill_md_is_read_by_the_nodes_reader`), `node/src/stored_skills.rs`, `node/tests/skills.rs` (`stored_skills_list_under_the_nodes_own_and_load_from_the_master`, `from_master_off_ignores_the_list_and_never_asks`, `an_agent_without_file_access_gets_stored_skills_only`), `node/tests/stored_skills_children.rs` (a child's list from its parent, both ways of a denial, a continued and a background child), `tools/tests/skills.rs` after the review (`node_roots_then_stored_then_the_repository`, `the_check_refuses_every_line_break_but_a_plain_one`), `master/src/stored_skills.rs`, `master/tests/it/stored_skills_http.rs` (editors and scopes, the check, the name rule, the list per agent and sub-agent and workspace, an old node, the body's checks, the cap, edit and delete), `cli/tests/stored_skills_e2e.rs` (the Assistant on the master's chat runtime loads one), `web/src/components/plugins.test.tsx`, `web/e2e/plugins.cjs`.
**Residual:** a stored body is written to be followed, so a workspace admin's skill steers that workspace's agents as its agent instructions can, inside the approval mode and the sandbox; a server admin's reaches every workspace; a loaded body stays in the chat's history after an edit, a delete or an assignment change; the line reader accepts front matter YAML would refuse (as on a node); the list does not change the prompt hash; the turn's agent is the one the node recorded in `turn_started` (as for `recall` and the board), so a hostile node can read any stored skill of a workspace whose chats it runs, which is where those skills are meant to run; the node's 20 s wait is not tested end to end (the code is `recall`'s);
Plugins rows are by name, so when a server skill takes the name of a workspace skill that had Assigned rows, those rows govern the server's skill in that workspace and the agents they name get the server's body (review L4).
