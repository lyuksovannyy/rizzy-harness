# T62

## Threat

**The node operator's instruction file** (ADOPTION_PLAN X.2; node.toml `[instructions] user_file`, default `AGENTS.md` in the node's data directory): text the node sends with every agentic chat on the node. (1) An agent rewrites it and so steers every later chat on the node (persistence across chats and users; review of PR 120 H1: with `user_file` in a writable place, chat A's `write` became chat B's operator section). (2) Something over the protocol sets or widens the path, or the read follows a link to a key beside it in the data directory. (3) A FIFO, device or huge file at the path hangs or floods the turn, or a stalled one costs the repository's files their read. (4) On a shared node one person's rules reach another's chats. (5) Another account owns or can write the file. (6) A repository file poses as the operator's section inside the same quoted block.

## Mitigation

(1) At start the path is resolved once (`resolve_file`: the deepest existing ancestor of its folder canonical, the rest appended; `.`/`..` refused at load) and that resolved path is what the refusal below checks, what is protected and what is read; the located file joins `protected_dirs` wherever it lies (`NodePolicy::locate_instructions`); at every read it is resolved again and, on the opened descriptor, checked against `/proc/self/fd`: a folder on the way that became a link or appeared as one since start makes it "not read" with the reason (re-check of PR 120, x1-x3 and x6: `the_operators_file_is_resolved_before_it_is_checked`, `the_operators_file_is_read_only_where_it_led_at_start`, `x1_absent_file_behind_a_linked_parent_is_protected`, `x2_absent_folder_behind_a_link_into_a_root_is_refused`, `x3_dotdot_in_the_operators_file_is_refused`, `x6_a_folder_that_appears_later_as_a_link_is_not_followed`), so `read`, `write`, `edit`, mentions and the listing refuse it in every mode and no sandbox grant may expose it; a `user_file` inside a `workspace_roots` entry, a `[sandbox]` read or write folder, or a folder the sandbox grants every command (`/etc`, `/usr`, `/opt`...) refuses the start with the reason (`r1a_one_chat_plants_the_operators_file_outside_the_folder`, `r1b_an_operators_file_inside_a_workspace_root_is_refused`, `an_operators_file_agents_can_reach_is_refused`).
In the sandbox mode the shell does not see it (bubblewrap's view holds only grants); in the host mode (`Sandbox::uncontained()`: no bubblewrap, the same Landlock rules) it rests on Landlock alone, so it holds where Landlock is enforced and has that mode's documented gaps (README "Execution modes": below Landlock ABI 9 a command can ask another service of the user over a socket) (`the_operators_file_in_the_data_directory_is_out_of_every_tools_reach`, both modes, `allow_outside_workspace` on). (2) Only node.toml sets it; `TurnExtra::user_instructions` is set only by the node; the file at that very path is opened with `O_NOFOLLOW`, a link there is refused (`the_operators_file_follows_no_link_and_opens_nothing_else`). (3) `O_NONBLOCK`, a regular file only (checked before and after the open), at most 16 KiB + 1 read and 16 KiB sent, indentation counted (half the repository cap on a small window; `short_lines_stay_within_the_cap_as_sent`), a note where cut, a 5 s bound of its own beside the repository files' (`a_large_operators_file_is_cut_at_its_cap`, `a_stalled_operators_file_costs_the_repository_files_nothing`). (4) Labelled to the model as the operator's for every chat, never the person's words;
README says plainly it reaches every user's chats. (5) A file not owned by the node's user or root, or one its group or other users can write (root's included; the group is not checked for being the node user's own), is named, not read (fstat on the opened descriptor); a folder another user can write and a file with more than one name (hard link) are warned about in the node's log and `doctor` (`a_foreign_owner_is_refused`). (6) Every line of the operator's and the repository's files is indented by two spaces, the blocks' own lines never are (`a_file_cannot_forge_another_sections_label`).
A standing section of its own (`user_instructions`, T52): replaced when changed, withdrawn when gone, rebuilt byte for byte (`the_operators_file_is_its_own_standing_section`).
Residuals: no ownership check beyond the owner and the write bits above; links in the folders above the file are followed, but only to where they led at start; a hard-linked file is read (warned); no per-user file; the operator can write anything there, as in `[skills] roots`; the master's standing sections (memory, project) are not indented, so text in them could still imitate another label.
