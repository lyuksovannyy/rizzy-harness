# T33

## Threat

An undo or rewind overwrites work no checkpoint holds: the user's own edits since the turn, or anything else changed in the folder, discarded by "Undo anyway" (`force`) with nothing to bring it back; or the restore changes files and its events then fail to append, so the log does not show it (final review A14, missed 9)

## Mitigation

**The checkpoint root is found on the file system, never from git's configuration** (R.1, review S-3): the nearest folder at or above the session folder that holds a `.git` entry (`git::find_repo`, one `lstat` per level), never above the innermost workspace root the session is in; git is never asked (T19), so `core.worktree`, `commondir`, a gitfile and the like have no effect on it; a `.git` that is not a plain repository directory makes the session folder a plain one.
The review proved that one `git config core.worktree /home/u` from the agent's shell had moved every later checkpoint to the home folder: file names from other projects in `checkpoint` events, an undo writing and deleting there.
A repository whose folder holds the node's data directory (one at `$HOME`), or a repository above the workspace root, is not used: the session folder alone is checkpointed as a plain folder, so undo keeps working for what the session may touch and nothing outside it is read; a sub-agent that changes files is then refused ("not a git repository").
**A restore never writes or deletes outside its folder** (`git::check_inside`, in `restore_plan` and again right before `restore_paths` writes): every path relative with plain components, the folder still at its real path, and the deepest existing folder on the way to each path really inside it and outside every protected folder; one failing path refuses the whole restore ("nothing was changed: the checkpoint names …").
Before, a forced undo deleted through a link the agent had put in place of a folder.
Since the R.1 follow-up the writes and deletes themselves are made by our code relative to the folder's top, opened once, and to directories opened from it with `O_NOFOLLOW` (`node/src/git/at.rs`; contents from `cat-file --batch` in the shadow; `checkout-index` and deletes by path are gone), so a link swapped in for a folder at any moment is never written or deleted through: a link met where a directory is expected is replaced by a directory for a write and means "already gone" for a delete; the folder's top cannot be swapped by any sandboxed shell (its parent is in no grant, `cli/tests/sub_agent_sandbox.rs`).
Test: `git_bounds_tests.rs` `a_folder_swapped_for_a_link_during_an_undo_is_never_written_through` (120 tries against a thread swapping the folder for a link to another one: nothing there is ever written or deleted).
Tests: `node/src/git_bounds_tests.rs` (`core.worktree` has no effect; a gitfile, a linked `.git` and `commondir` are not used; a repository above the workspace root and one holding the data directory are not the root; names stay inside the folder; a restore through a link is refused).
**What the unforced check compares** (`git::changed_in_the_way`, 2026-11-19, found by the third review of pull request 154): every path that differs between `expected` and the folder's snapshot is read once (`diff --name-only -z --no-renames`, no pathspec) and matched in Rust as bytes against the plan: a path it writes or deletes, anything below one, and a folder above one.
Before, the names went to git as pathspecs, which broke three ways: (1) only at and below a path, so a file or link the person put where a folder the undo puts back goes (the turn deleted `a/x`, the person made a file `a`) was written over without a word; (2) as patterns, so `a*` also matched `ab` (a false refusal) and a name that reads as pathspec magic (`:(attr:zz)k`, `:!q1`) matched nothing or everything else, so a later change to it was written over; (3) as lossy UTF-8, so a later change to `n<FF>m` was missed and written over.
The folder check of a directory the undo replaces by a file (`unsaved_in_replaced_dirs`) now asks `ls-tree` with the name's bytes and `GIT_LITERAL_PATHSPECS`: a lossy name refused over saved files, and a name like `:!q1` made the forced undo fail.
Rename detection is off because with every change read it would report a file renamed after the turn only under its new name.
Tests (each failed on `main`): `node/src/git_check_tests.rs` `an_unforced_undo_refuses_over_a_file_where_a_folder_it_writes_goes`, `a_name_with_glob_characters_matches_only_itself`, `a_name_that_reads_as_pathspec_magic_changed_after_the_turn_is_refused`, `a_name_that_is_not_utf8_changed_after_the_turn_is_refused`, `a_folder_with_a_name_that_is_not_utf8_replaced_by_a_file_is_undone`; through a node, `node/tests/undo_check.rs`; `a_rename_after_the_turn_is_refused` guards the rename setting.
**A folder replaced by a link that loops** (`a -> a`) made every later snapshot fail (`git add -u` keeps `a/x` when `lstat` says ELOOP, then adding `a` conflicted), so turns had no checkpoint: new paths are staged with `update-index --replace`, and `check_inside` treats ELOOP like a missing folder (the write replaces the link and follows none); test `a_folder_replaced_by_a_looping_link_is_checkpointed_and_undone`.
**Files in no checkpoint in the undo's way** (review of pull request 160, on `main` too): the pre-restore snapshot leaves out what git ignores, and the check compares snapshots only, so an unforced undo wrote over an ignored file the person made after the turn and nothing held it (the turn untracks and ignores `.env`, the person writes a new `.env`, the undo put the old one back; or an ignored file `cache` where the folder `cache/` comes back).
Now `unsaved_in_the_way` looks at the disk as the writer walks it (`git::at`, `Top::in_the_way`: `openat` with `O_NOFOLLOW`, no link followed) at every path the undo writes or deletes and, for a write, at the folders on the way: a file or link there that the pre-restore snapshot does not hold joins the files `unsaved_in_replaced_dirs` finds, in one list with one wording.
An unforced undo is refused, naming them, before anything is written;
"Undo anyway" deletes or replaces them and its note names them again.
The node cannot tell the turn's ignored file from the person's, so one the turn wrote in the undo's way counts the same (it needs a turn that makes a path ignored and writes a new file where the tree before it had a folder or nothing; a file a snapshot held stays in the checkpoint index when it becomes ignored, so it is held and not in the way).
Tests: `git_check_tests.rs` `an_ignored_file_at_a_path_the_undo_writes_is_named_and_refused`, `an_ignored_file_where_a_folder_the_undo_writes_goes_is_named_and_refused`, `an_ignored_file_the_turn_wrote_in_the_undos_way_is_named_and_refused` (each failed before), the guards `ignored_files_beside_the_paths_the_undo_writes_do_not_count` and `an_ignored_file_the_checkpoints_still_hold_is_not_in_the_way`; through a node `undo_check.rs` `undo_refuses_over_an_ignored_file_in_its_way_and_names_it`.
A name in a listed refusal never writes the backticks that mark names (`a_name_with_backticks_reads_as_one_name_in_a_refusal`).
Which of the entries found `now` holds is read with one `ls-tree -r` of `now` (by name, as literal pathspecs, for up to 256 paths and 64 KiB of names: 256 names of 3,750 bytes failed with `E2BIG` under `ulimit -s 2048`; both ways give the same answer, `by_name_and_the_listing_agree`, and more than 256 ignored files in the way are named exactly, `an_undo_with_hundreds_of_ignored_files_in_its_way_names_exactly_those`): a pathspec per path cost 0.5 s for an Undo of 50,000 files, the listing 0.15 s (tmpfs and this machine's slow disk alike, page cache warm; `bench_unsaved_in_the_way`); a path `now` holds as a folder counts as not held (`a_file_where_now_holds_a_folder_counts_as_not_held`).
The unforced refusal ends "\"Undo anyway\" deletes or replaces them".
**A named pipe, a socket or a device where a tracked file was** (review 2 of pull request 160, on `main` too) made `add -u` fail ("can only add regular files"), so every snapshot failed while it was there: no checkpoint, no Undo.
Now, only when `add -u` fails, the modified paths are looked at (`lstat`, never opened): those that are no file, link or folder leave the checkpoint index and that snapshot holds the file as deleted (`git::add_tracked`, `Snapshot::special`; looked at through folders opened without following links, `Top::is_special`, so a link above never leads outside; only those paths leave the index and `add -u` runs again, so a file the same turn changed is held with its new content); a sub-agent's base snapshot leaves such a file out without a note of its own (the child starts without it; the parent's checkpoint before the turn has already named it, or, for a pipe made during the turn, its checkpoint after the turn names it when the turn ends); the chat says so once ("Left out of this turn's checkpoint: …"), since the next snapshot no longer has the path.
An untracked pipe is not listed by git's walk and never staged.
An Undo across that state treats the pipe like any file in no checkpoint: refused naming it, forced deletes or replaces it and names it.

**Random invariants** (`node/src/git_undo_random_tests.rs`, 200 seeds, `UNDO_SEEDS`/`UNDO_SEED`/`UNDO_SEED_FROM`): links (also to `a/b`, `x`, `.`), executable bits, empty folders, hard links, ignored files and ignore rules edited by the turn or the person, reverts to the content before the turn, the person ignoring a path the turn deleted or replaced and writing a new file there (without `unsaved_in_the_way` the default 200 seeds fail, 4 of 200; with the person aiming there, the default 200 seeds no longer catch the above-folder match, `--replace` or an exactly-at match, which their named tests catch; lowering the aim to 30% did not bring them back, and costs the new catch, 2 of 200), odd names and near names (`ab`, `a.b`, `a/b.c`), `git add`/`rm --cached`, the person's changes at, above and below the turn's; an unforced undo loses nothing and writes over nothing changed after the turn, a forced one keeps everything in its pre-restore snapshot but the files it names, what it names is as said, and undoing it returns the folder, exempting exactly what no checkpoint records (6,000 seeds clean; on `main`'s code 88 of 3,000 failed with the first generator, and the extended one found the ignored-file loss 3 times in 3,000 on the code before this fix).
A size cap for untracked files was built and dropped on 2026-11-19 after three reviews (pull request 154): a record of what a snapshot left out cannot be compared safely with what the person changed later, because size alone misses an edit of the same size.
Do not rebuild it that way (docs/undo-and-stash.md §2.7).
**A restore first saves the folder** (`session.rs`, `restore`): a snapshot of the folder as it is, at `refs/harness/<session>/restore-<id>/before`, recorded as `checkpoint{phase: before_restore, turn_id: restore-<id>, files: the paths it writes}` **before any file changes**.
If the snapshot fails (an unreadable file, the 60 s limit) or its event cannot be appended, nothing is restored, the ref is deleted and the caller gets the reason.
The unforced check (files changed since `expected`) uses the same snapshot, so only a forced restore costs one more scan of the folder.
Then the files are written, the result is snapshotted at `.../restore-<id>/after` and recorded as `checkpoint{after}` for `restore-<id>`, then `restored` for each undone turn.
A failure after the `before_restore` event names that checkpoint and ref in the error.
**All or nothing (A.16):** a checkpoint in a git repository borrows the user's objects (`objects/info/alternates`), and the user's own history rewrite plus pruning (`gc --prune=now`, `repack -ad` after the reflog expired, about a month of git's defaults, a re-clone without unpushed work) can remove a blob or tree it needs;
B.2 showed a restore then deleted the file (`checkout-index -f` unlinks first) and left the folder half-restored.
Now the restore reads its diff before anything else (`git::restore_diff`; a failure because a tree is gone, found by `rev-list --objects --missing=print --filter=blob:none`, gets the plain reason), then takes the pre-restore snapshot (a ref only) and makes its plan, and **before the `before_restore` event** makes exactly the blobs the plan writes safe (`git::secure_blobs`; not those of paths it skips, such as inside a nested repository, which only the snapshot reveals): `cat-file --batch-check` on those blobs (machine-readable `<id> missing`), and when the shadow borrows, one `pack-objects` that writes them as a pack into the shadow's own `objects/pack` (read through the alternates; nothing written or touched in the user's repository; `hash-object -w` would only "freshen" the user's copy; a failed copy removes its own `tmp_*` files and index-less pack, nothing else).
A missing one refuses the restore with "nothing was changed: this checkpoint depends on content that the git repository in this folder no longer has (…history rewritten … cleaned up by `git gc`)", naming the files; the folder is not touched, no event is written and the snapshot's ref is deleted.
The write deletes the paths the turn added first (a path that is missing, under a parent that is no longer a directory, or now a directory, counts as already gone; any other failure is an error), then builds a private index from the blob ids only (`update-index -z --index-info`, then `checkout-index -f -z --stdin`), so it reads no tree and needs no other object; this order handles a file and a directory swapped under one name, at any depth.
**A directory the restore replaces by a file** is walked first: files in it that the pre-restore snapshot does not hold (ignored ones, say) refuse an unforced restore, naming the directory; a forced one deletes them and the chat note after it names them as deleted and not saved; one holding a `.git` is refused either way.
**An interrupted restore is restorable:** a `before_restore` checkpoint whose `after` never came (the restore failed while writing) is restored through the same call: its paths (the event's `files`) go back to their saved content over the folder as it is, after the folder is saved again; such a restore never refuses for edits made since the failure (it compares the folder with itself), so it overwrites them, and the chat note after it names the checkpoint that saved them.
A turn without `after` stays "incomplete".
**Self-repair (A.16):** a shadow index that still names a blob the user's repository pruned (an unchanged file after `git reset` plus gc) made `write-tree` fail on every later snapshot, so turns ran without checkpoints; now a failed `write-tree` (the step, never git's message) rebuilds the index from the folder once with the same staging (nested-repository rules kept) and retries; a second failure is reported.
No checkpoint or ref is deleted.
A turn that runs without a checkpoint for any reason gets an `error` note in the chat ("This turn has no checkpoint, so it cannot be undone…"), not only a log line.
**Copies of what an undo needs (A.17):** after a turn's `after` checkpoint is logged, `git::pin_changed` takes one `diff-tree -r -t` of before and after (no folder scan), checks the objects with `cat-file --batch-check`, and copies the old blob of every changed or deleted path plus both snapshots' root trees and the trees on the way to each change into the shadow's own store with the same `pack-objects` as `secure_blobs` (nothing written or touched in the user's repository), without flushing the pack to disk (`core.fsync=none`: git's flush of a one-blob pack cost 0.2 to 1.4 s on a slow rotational disk, against 1 ms without; the copies are then as durable as the checkpoint's own loose objects and refs, which git does not flush either; a restore's copy keeps git's default).
Established by test (`git/upkeep.rs`): the shadow's own `gc` (`repack -d -l`) drops a local copy of an object the alternate has packed, packed or loose (a loose user copy keeps it, by `--local`'s rules), so the copy is a pack with a `.keep` file, which `gc`, `gc --prune=now`, `repack -a -d -l` and `repack -A -d` all leave alone; the file's lines name the turn's checkpoint group (`harness-pin refs/harness/<session>/<turn>`), `git::prune` removes the lines of every group it no longer keeps and the file with the last one, and the next collection drops the copy.
A `.keep` file with a line that is not ours is never touched.
Only a repository folder gets copies (a plain folder's shadow owns everything and gc keeps what a ref reaches).
A restore's own checkpoint is copied the same way (the versions it overwrote), so undoing a restore does not depend on the user's repository either.
When an old version is already gone at the end of the turn, the chat gets an `error` note ("This turn's undo is incomplete: the earlier versions of `a.txt`, … were already gone …"), the turn ends normally and its undo is refused as above.
**Garbage collection (A.18):** `git::prune` deletes the dropped groups' refs and releases their copies on every turn, and counts the dropped groups in `harness-gc` in the shadow (`last <seconds>`, `dropped <n>`; survives a restart); `git gc --prune=<its start − 1 s> --quiet` runs from a task spawned after `turn_ended` is written (and after a restore) when 16 groups were dropped since the last one, or `count-objects -v` shows 6,700 loose objects or 50 packs (git's own auto-gc thresholds), and not within 5 minutes of the last start.
**It is serialised with everything that writes there (review F2):** one async read-write lock per shadow (`git::hold`); a snapshot, a copy and a whole restore take it shared, a collection takes it alone for its whole run, so a collection waits for them and a snapshot that starts while one runs (the next turn's "before", at most once in sixteen turns) waits for it to finish; shared holds are taken around a step by the session, never nested and never across anything that waits on a person.
Without that, an old unreachable object a snapshot only "freshens" after gc counted it as expired could be pruned under the new checkpoint.
It also prunes nothing younger than its start, runs with `gc.writeCommitGraph=false` and `repack.writeBitmaps=false` (the shadow needs neither; a commit-graph lock left by a killed gc made every later one fail, F1), and checks the rule again under the lock.
A failed collection (a kept checkpoint reaches an object the user's repository lost, a damaged pack) is logged once with git's first line and retried after an interval that doubles per failure in a row, up to a day; a success resets it (`failures` in `harness-gc`, F3).
At start-up every pack one of our `.keep` files protects is checked with `git verify-pack`, and the `.keep` of one git rejects (a copy damaged by a power loss) is released with a warning.
**Changes between turns (review F5):** the person's own edits and commits between two turns are not the "before" of any turn's change; at the start of a turn, the diff between the session's last recorded state (the previous turn's `after` or a restore's result, kept in memory and read from the log at load) and the new "before" is copied the same way into the new turn's group, so a rewind across them survives a prune.
A turn that changed nothing copies nothing; when the agent's prune took a snapshot's tree, the note says the content was already gone; a restore copies its saved checkpoint's content right after the `before_restore` event, so the way back from a restore that fails while writing is covered too.
**Lock files (A.18):** a private index and its `.lock` are removed by a guard on every path, also when the call is dropped at the 60 s snapshot limit with git killed holding the lock; at start-up and before each collection, `*.lock` files at the shadow's top and under `refs/`, and `harness-index-*` files, older than 5 minutes (two `GIT_TIMEOUT`s plus a minute: no command of ours lives longer) are removed; younger ones may belong to a running command and stay.
An undo checks that a ref still names the checkpoint (`git::exists`), since a dropped one's objects stay until the next collection.

**Nested repositories (A.15):** a git repository inside the folder (a directory holding a `.git` directory, file or symlink, with or without a commit, registered submodule or not) is left out of every snapshot, never as a gitlink and never as files, so one `git init` no longer disables undo for the whole folder (`add -A` failed on a repository without a commit) and another repository's work tree is never captured without its history and restored over the user's uncommitted work.

computing exactly which files only the new rules ignore needs the old rules evaluated against the folder, not done); with `[sandbox] mode = "off"` (and `best-effort` on a kernel without Landlock) the node's git reads the folder unconfined, so the snapshot read window closed in T4 is open there; work inside a nested repository (its uncommitted changes, a repository the agent deleted) is in no checkpoint and undo cannot bring it back, it only says so (and only when one appeared or went away), and the chat shows the note but not the per-checkpoint `excluded` list; a repository made over tracked files keeps being captured as files while the index tracks paths there (git enters it), so later undos write into its work tree as into any folder; new files inside a repository that appeared where nothing was tracked are not recorded; files git ignores are in no checkpoint: an undo does not remove an ignored file the turn made and does not bring back one the turn changed or deleted, and an undo of an undo cannot see a file whose state an ignore rule kept out of the snapshot it restores over (an undo that removed an ignore rule leaves the file, which the undo of the undo then deletes, holding it in its own pre-restore snapshot; a file an undo wrote under the person's new ignore rule stays after the undo of the undo); a person's revert to the content before the turn counts as a change (refused; "Undo anyway" goes ahead); a file whose name is not UTF-8 is written, deleted and checked by its bytes (since 2026-11-19 the unforced check too), but the event's `files` and the names in a refusal are lossy text, so two such names can read alike (`n<FF>m`, `n<01>m` both show as `n�m`); the check and the write are not atomic: a file the person makes between the pre-restore snapshot and the write can be written over and is in no checkpoint (measured for a sub-agent's merge-back, which uses the same check: 3 of 48 timed tries lost the person's new file on `main`; not fixed, it needs a per-file check at write time); two chats' turns in one folder are not serialised (a design question for later); sessions on other nodes, and programs outside the harness, are not seen by the registry.
**A restore keeps the permission bits of the file it replaces** (trial 2026-11-19, task 5: a restored file was created `0666`/`0777` less the umask, so a `.env` at 0600 came back 0644): `git::at::restored_perm` reads the old file's mode with `fstatat` on the directory descriptor (no link followed, never a path string); a regular file there keeps its bits, with the executable bits taken from the snapshot's mode (git records nothing else) set for those who can read the old file plus those who could already execute it (cleared when the snapshot is not executable), and `fchmod` sets them on the temporary file before the rename (an `fchmod` the filesystem refuses with not-supported, not-implemented or not-permitted is let go: the file keeps the mode the open gave, never wider; any other error fails the write); **the mode kept is the file's mode at the moment of the Undo, not before the turn** (git records only the executable bit), so a turn that widened a file leaves it wide; nothing there, a link or a folder gives the old default (nothing to keep); if the mode cannot be read the new file gets the owner's bits of the default only, never wider.
Not kept: set-user-id, set-group-id, sticky, ownership, ACLs and extended attributes (the new file is the node user's).
**The branch is never moved back, and the chat says so (X.42):** a turn's "files changed" holds what a `git checkout` or a commit in the turn changed, and an undo writes files only (it never moves `HEAD`, as above).
When `HEAD`'s branch or commit differs between a turn's start and end, the Undo block and the changes panel say so in one sentence (the branch switched, or commits made or moved on the same branch; detached variants), and name what the undo does (puts the files back on whatever is checked out now; the commits stay). `HEAD` is read by the node from files (`user_repo::head_at`: bounded reads, no link followed, no `commondir`, a branch only under `refs/heads/` with plain path components), never by asking git, so a hostile `.git/config` runs nothing for it; the names are bounded and cleaned in the event.
The note changes nothing about when an undo is refused.
