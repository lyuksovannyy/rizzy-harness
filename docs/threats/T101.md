# T101

## Threat

**An agent pushes to a forge with the chat owner's connection** (ADOPTION_PLAN X.27 step 4; README "Pushing to the repository"; `docs/forge-push.md`; `crates/node/src/forge_push.rs`, `session_push.rs`, `crates/master/src/forge_push.rs`, `crates/tools/src/push.rs`): the token leaks (to another host, the agent's shell, an event, a log or audit line, a file, argv or the environment), is handed out without the owner's click or for another person's chat, the push reads or runs what the folder's agent-written `.git` names, sends another repository's objects, goes to another repository or ref, forces, deletes or tags, or happens where nobody can answer

## Mitigation

**Where to:** only the project's recorded `source` (host and name, written once at the clone, T86); the tool's one argument is a branch name of `[A-Za-z0-9._+@-]` parts (`harness_core::forge::valid_branch`, stricter than `check-ref-format`); the node builds `https://<host>/<name>.git` and `<40|64 hex>:refs/heads/<branch>` itself, so no URL, remote, `+`, `--force`, `--delete`, tag, `--mirror`, `--all` or push option can be asked for; node.toml decides (`[forge] push`, default on, and `[forge] hosts`).
**Which turns:** the master names a target (`MasterContext::push`, no secret) only in a project chat's own turn its owner sent signed in (not the API token, a routine run, a webhook or a callback turn; not a sub-agent's, temporary, forked or marked chat; not parallel answers or several called agents), for an agent that names `push` (never through `tools: all`), with the owner's connection for the source host (the newest), the host still allowed, on a node that announced `forge-push`; the node keeps it only for an agentic chat of its own that is not a sub-agent's or a routine's, in a turn that is not a callback, on a node that pushes to that host, and otherwise withholds the tool.
**The card:** `ToolRisk::External`, a card in every mode, Auto included, refused in plan mode and by `denied_tools`; no "for this turn" or "for this chat" and no grant covers it; it shows the master's host, name and login, the branch, and the pinned commit's id and subject (agent text, one cleaned line, inert); not the node's `reason` line; a collapsed preview must be shown once before Allow appears (T102).
**Order:** the commit is read from the refs as files (`user_repo::branch_commit`); after the Allow it is read again and a moved branch refuses; the objects are listed and linked after the Allow.
**No git in the folder's repository (T19):** the chat's folder is opened once (`O_DIRECTORY | O_NOFOLLOW`, checked to be the pinned inode) and held for the whole push; `.git`, `objects`, each object folder and each ref component are opened by `openat` with `O_DIRECTORY | O_NOFOLLOW` relative to the one before and listed through their descriptors, so a folder swapped for a link mid-walk refuses the push (review F1: the first, path-based walk followed such a swap and pushed another repository's commit); only loose objects and `pack-*.pack`/`.idx` are taken, each checked by `fstatat(AT_SYMLINK_NOFOLLOW)` to be a regular file, hard-linked with `linkat` (no follow) into a node-made bare repository in its staging folder and checked again through the node's side to be that device and inode (copied by `openat(O_NOFOLLOW)` within `clone_max_mb` where a link is refused); no `info/alternates`, `http-alternates`, commit-graph, multi-pack-index, promisor or keep file is taken; 200,000 listed entries (junk names included) and 120 s at most, the clock read at every entry; git runs there with `--git-dir`, the hardened base, one protocol, redirects off, no proxy, its own empty home, `--no-verify`, no submodule recursion, memory limits for compressed blobs, a core-file limit of 0, in the node's helper jail where there is one (`Sandbox::helper_net`: its own folder read-write, the network open).
**What the walk does not stop:** the agent putting another repository's objects into the folder (a copy, or a hard link where it may make one: a host chat any file of the node's user on that file system, a sandbox chat only within its writable grants, `a_sandboxed_shell_cannot_hard_link_outside_files_into_its_folder`); so whatever repository content the agent can read can be pushed, to the project's own source only.
**The card is bound:** the destination line is the master's (`GET /api/sessions/{id}/push-target`, owner only), the branch and commit are re-read after the Allow and must be unchanged, the subject is shown only when the commit's bytes hash to the pinned id (review F6); a card whose approval names another tool than its call is drawn as invalid, Deny only.
**The token:** the master hands it only to the session's own node, only against an Allow of that very push card that the master itself relayed from the chat's owner signed in (recorded by the approval route before relaying, only when the approval id is on exactly one `approval_requested` and its call id on exactly one `tool_call_started`, both name `push`, and the card is not yet answered, checked again at the request: review F2 and N1, a reused approval id or a retitled call refused; an approval id or call id outside `[A-Za-z0-9_-]{1,128}` names no card and the approval route answers 404 for it, and the page encodes every id in an `/api/` path: review N4; the page draws such cards invalid, Deny only), one token per approval id ever (F3), within 10 minutes; a token the master could not send to the node is given back, uncounted (F7); with the owner's account, level and membership, the open turn (not a callback, its agent's switch), the chat (no one else acted in it), the project's source and the connection checked again, one request per chat at a time and 20 per chat per hour; one audit line without the token; on the wire a redacted secret; on the node a close-on-exec pipe at the one git's standard input read by the clone's host-and-path helper (T86), never argv, environment, file or config; git's text stripped of terminal escapes, the token in every form, hints, then the secret scrubber.
**One at a time:** one push per node; one credential request per chat.
Tests: `crates/node/src/forge_push_tests.rs` (`.git`, `objects`, `pack`, a loose folder, a file and a ref folder swapped for links at deterministic race points, and the threaded stress probe, ignored; the post-link check proven by turning it off; a rewritten commit object shows no subject; no core dump; hostile config, include, hooks and helpers run and reach nothing; an alternates chain and a linked object reach no other repository; only objects and packs taken; redirects; a rejection; a rewritten object fails the push; the copy fallback and its cap; the file cap; a stalled push with no token in `/proc` and its time limit; pins; the text scrub; no file holds the token), `forge_push_runtime_tests.rs` (Auto shows the card and Allow pushes; Deny sends nothing and asks for no credential; a moved branch; a second push refused; no offer without a target, in a routine's chat, on a node that does not push or for an unlisted host; no token in events, TRACE logs, audit or files), `crates/master/tests/logs/forge_push_http.rs` (a bash card labelled push; a used or answered card; a chat marked after the turn started; a forked chat; a sub-agent's session; a second request meanwhile; a token that could not be sent given back; the page's destination owner only; the relayed Allow once; no click, a denial, another tool's card, another node; the API token's Allow; turns that name no target; an owner disabled or lowered; the hourly cap; a callback turn), `crates/cli/tests/push_token_reach.rs` (a sandboxed shell, Landlock alone and contained, cannot read the token from git's `/proc`; the unconfined calibration can; the jail reaches the network and not the data directory), `plan_tests.rs`, `agents.rs`, core and protocol units, `approvalpreview.test.tsx`.
**Residual:** **any** host chat on the node, of any person, runs as the node's user: while any push runs there (another person's from a sandbox chat included) it can read the token from the pipe at `/proc/<git>/fd/0` until the helper has read it, and from the memory of `git` and `git-remote-https` after that (same-user ptrace rules), and it can read the node's own key, which makes it a compromised node; on a node that offers host mode to more than one person, pushes are only as private as they trust each other (`[forge] push = false` or no host mode on a shared node); a host chat's agent can also push with the machine's own credentials; a sandboxed shell cannot read the token (tested); a node that runs the session and is compromised gets, for one real click on a push card, a bearer token as wide as the connection's scope on the forge (every repository and API it reaches), not only a push to the source, and can make the card's folder part (branch, commit, subject) say what it likes; the forge's `index-pack` and connectivity check are what keep a rewritten object from becoming content under the pinned id; git parses the folder's loose objects and packs (git's robustness); the card does not mark the default branch or how far ahead the branch is; the limits are per process and reset on restart; the jailed push is tested by its wrapper's network and file rules, not end to end against a forge (the production push is https only, the tests' forge is plain http on loopback).
