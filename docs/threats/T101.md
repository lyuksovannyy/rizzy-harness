# T101

## Threat

**An agent pushes to a forge with the chat owner's connection** (ADOPTION_PLAN X.27 step 4; README "Pushing to the repository"; `docs/forge-push.md`; `crates/node/src/forge_push.rs`, `session_push.rs`, `crates/master/src/forge_push.rs`, `crates/tools/src/push.rs`): the token leaks (to another host, the agent's shell, an event, a log or audit line, a file, argv or the environment), is handed out without the owner's click or for another person's chat, the push reads or runs what the folder's agent-written `.git` names, sends another repository's objects, goes to another repository or ref, forces, deletes or tags, or happens where nobody can answer

## Mitigation

**Where to:** only the project's recorded `source` (host and name, written once at the clone, T86); the tool's one argument is a branch name of `[A-Za-z0-9._+@-]` parts (`harness_core::forge::valid_branch`, stricter than `check-ref-format`); the node builds `https://<host>/<name>.git` and `<40|64 hex>:refs/heads/<branch>` itself, so no URL, remote, `+`, `--force`, `--delete`, tag, `--mirror`, `--all` or push option can be asked for; node.toml decides (`[forge] push`, default on, and `[forge] hosts`).
**Which turns:** the master names a target (`MasterContext::push`, no secret) only in a project chat's own turn its owner sent signed in (not the API token, a routine run, a webhook or a callback turn; not a sub-agent's, temporary, forked or marked chat; not parallel answers or several called agents), for an agent that names `push` (never through `tools: all`), with the owner's connection for the source host (the newest), the host still allowed, on a node that announced `forge-push`; the node keeps it only for an agentic chat of its own that is not a sub-agent's or a routine's, in a turn that is not a callback, on a node that pushes to that host, and otherwise withholds the tool.
**The card:** `ToolRisk::External`, a card in every mode, Auto included, refused in plan mode and by `denied_tools`; no "for this turn" or "for this chat" and no grant covers it; it shows the master's host, name and login, the branch, and the pinned commit's id and subject (agent text, one cleaned line, inert).
**Order:** the commit is read from the refs as files (`user_repo::branch_commit`); after the Allow it is read again and a moved branch refuses; the objects are listed and linked after the Allow.
**No git in the folder's repository (T19):** the folder's loose objects and `pack-*.pack`/`.idx` are hard-linked (copied within `clone_max_mb` where a link is refused) by the node's own walk into a node-made bare repository in its staging folder; regular files only, no link followed, a link swapped in afterwards refused; no `info/alternates`, `http-alternates`, commit-graph, multi-pack-index, promisor or keep file is taken; 200,000 files and 120 s at most; git runs there with `--git-dir`, the hardened base, one protocol, redirects off, no proxy, its own empty home, `--no-verify`, no submodule recursion, memory limits for compressed blobs, in the node's helper jail where there is one (`Sandbox::helper_net`: its own folder read-write, the network open).
**The token:** the master hands it only to the session's own node, only against an Allow of that very push card that the master itself relayed from the chat's owner signed in (recorded by the approval route before relaying, checked against the mirror's `approval_requested`), once, within 10 minutes, with the owner's account, level and membership, the open turn (not a callback, its agent's switch), the chat (no one else acted in it), the project's source and the connection checked again, one request per chat at a time and 20 per chat per hour; one audit line without the token; on the wire a redacted secret; on the node a close-on-exec pipe at the one git's standard input read by the clone's host-and-path helper (T86), never argv, environment, file or config; git's text stripped of terminal escapes, the token in every form, hints, then the secret scrubber.
**One at a time:** one push per node; one credential request per chat.
Tests: `crates/node/src/forge_push_tests.rs` (hostile config, include, hooks and helpers run and reach nothing; an alternates chain and a linked object reach no other repository; only objects and packs taken; redirects; a rejection; a rewritten object fails the push; the copy fallback and its cap; the file cap; a stalled push with no token in `/proc` and its time limit; pins; the text scrub; no file holds the token), `forge_push_runtime_tests.rs` (Auto shows the card and Allow pushes; Deny sends nothing and asks for no credential; a moved branch; a second push refused; no offer without a target, in a routine's chat, on a node that does not push or for an unlisted host; no token in events, TRACE logs, audit or files), `crates/master/tests/logs/forge_push_http.rs` (the relayed Allow once; no click, a denial, another tool's card, another node; the API token's Allow; turns that name no target; an owner disabled or lowered; the hourly cap; a callback turn), `crates/cli/tests/push_token_reach.rs` (a sandboxed shell, Landlock alone and contained, cannot read the token from git's `/proc`; the unconfined calibration can; the jail reaches the network and not the data directory), `plan_tests.rs`, `agents.rs`, core and protocol units, `approvalpreview.test.tsx`.
**Residual:** in a host chat the agent's shell is the node's user: it can push with the machine's own credentials, and a background command can read the connection's token from `/proc/<git>/fd/0` while the push runs (same-user ptrace access; a sandboxed shell cannot); a node that runs the session and is compromised can show a misleading card text and spend one real click on a push of its choosing to the same repository and branch rules, and holds the token it is given; the forge's `index-pack` and connectivity check are what keep a rewritten object from becoming content under the pinned id; git parses the folder's loose objects and packs (git's robustness); the card does not mark the default branch or how far ahead the branch is; the limits are per process and reset on restart; the jailed push is tested by its wrapper's network and file rules, not end to end against a forge (the production push is https only, the tests' forge is plain http on loopback).
