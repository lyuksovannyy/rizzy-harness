# T84

## Threat

**A workspace's custom connectors and each person's account** (ADOPTION_PLAN X.35 step 1; README "Custom connectors"; `crates/master/src/connectors/` (`mod.rs`, `client.rs`, `pool.rs`), `remote.rs`, `http/custom_connectors.rs`, `crates/store/src/custom_connectors.rs`; the owner, 2026-11-18: "for connectors make each user can connect own account (if connector supports auth)"; fixes of the review of PR 155): an admin-typed address turns the master's MCP client into an SSRF or token-exfiltration tool; a person's token leaks (answer, frame, log, audit, file, URL, a proxy's log) or is used by someone else or sent to an address its owner did not see; a hostile remote server or admin exhausts the master (memory, threads, time) or puts its words into the log, an error or the UI as anything but text

## Mitigation

**Definitions:** by the workspace's `settings` permission (and the API token, which acts as an owner); name by the node's MCP server rule, unique per workspace, refused when a node the caller may see on the Plugins screen announces a server of that name (the local node's only to those who may use it; a later announcement is shown as a clash; this tells an admin nothing the Plugins list does not already show every member); the URL `https://` as written on a lower-case public DNS name with a dot, no IP literal, no `.localhost`, no `xn--` label, no port (`:443` too), no userinfo, query or fragment, at most 512 bytes; sign-in `none` or `token` (OAuth refused with "not built yet").
**The token's header is an allow rule** (the header decides who on the way reads it: proxies and access logs redact `Authorization` and log or forward others): exactly `Authorization` (sent as `Bearer <token>`), or a name ending in `-Key`, `-Token` or `-Auth`, or one starting `X-` that is not `X-Forwarded-*`, `X-Real-IP`, `X-Original-*`, `X-Request-*`, `X-Correlation-*`, `X-Envoy-*`, `X-Amzn-*`, `X-Cloud-Trace-*` (one list, `X_REFUSED`); never `Sec-*`, `Proxy-*`, `Mcp-*`; letters, digits and `-`, 1-64.
The name never changes.
**A new URL, sign-in or header** removes every account of the connector in the same transaction as the edit, before anything can be sent there (the UI asks first); the store also refuses an account whose connector's URL is no longer the one its token was checked with.
**What the person saw:** connect, replace and check carry the connector's stamp (a hash of URL, sign-in and header) and are refused with 409 "this connector changed" on a mismatch, before any lookup or request; the page reloads on the `connectors_changed` event and an open token form on a changed connector closes.
**Accounts:** a row (person, workspace, connector) with the token sealed (`sealed.rs`; associated data `connector_accounts`, the user id, the workspace id, the connector id, the connector's URL as stored), so a row copied to another person, workspace or connector, or kept under a changed URL, does not open; foreign keys cascade it with the connector, the membership, the person and the workspace; at most 100 per person.
The key is obtained before the token is sent anywhere; the token is 1-2,048 visible ASCII bytes, sent only in its header (marked sensitive) and only to the connector's URL (any other URL the transport asks for is refused before sending); every route names the caller and the workspace: another member, a workspace admin, a server admin (not a member: 404) and the API token (no account: 403 on connect, check and disconnect) cannot read, use, replace or delete it.
**Audit:** add, edit and delete name the editor, the connector and its host; connect, replace and disconnect name the person's user id and the connector's id, so a server admin reading the audit sees who connected what (as for forge connections), never a token.
**The client** (`connectors/client.rs`): rmcp 3.8.0's streamable HTTP transport (feature `transport-streamable-http-client`; new crate `sse-stream` 0.2.6, MIT OR Apache-2.0, its `tracing` feature off, checked by a test) with our own `StreamableHttpClient` on the shared rules of `remote.rs` (also forge's): the public-only resolver on every connection; **no redirect followed**, not even to the same origin (a 3xx is a fixed error telling an admin to enter the final address; the `Location` is not shown); `no_proxy`; connect 5 s, each request and the whole check 10 s; no idle connection; **nothing compressed** (no `Accept-Encoding` sent, reqwest's gzip decoder off, an answer with a `Content-Encoding` refused unread), so the budget counts wire bytes: one **512 KiB budget per check** over every request's raw body before any parsing (so the event-stream parser's unbounded line buffer is bounded by it), a declared length over what is left refused unread; **no message with more than 8,192 JSON values** (objects, arrays and elements, counted by a scan outside strings) reaches the parser, as a body or as an event (a value costs about 1 KB once parsed into rmcp's types); a non-success answer is never read (status only, tested by what the fake could send); a success that is neither JSON nor `text/event-stream` refused; only our headers (`Accept`, `Content-Type`, `Mcp-Session-Id`, a checked `MCP-Protocol-Version`, the token's header, `User-Agent`; reqwest adds `Accept: */*` on the DELETE), the requested version pinned to 2025-11-25 so rmcp's `Mcp-Method`/`Mcp-Name` are not needed; `get_stream` answers that there is no standalone stream, so **server-initiated messages are not received in this version, by design** (the master advertises no capability at all, asserted against the fake); `DELETE` of the session at the end, unread, its failure ignored.
**Where checks run** (`pool.rs`): two check slots on the one connector thread (since X.35 step 2, shared with agents' calls, T85), with the no-op log subscriber installed once and a one-thread runtime with at most two blocking threads, one of them for checks' name lookups; a check goes to an idle worker or is refused at once (429, never queued); a person has one check at a time (429); a stuck check ends at its time limit inside the worker; a stuck name lookup holds that worker's one blocking thread until the system resolver gives up and later lookups there wait (and fail at their limit), so threads stay at 2 + 2 whatever happens (`tests/connector_stall.rs`: six checks against a lookup that never answers, each ended at its limit, threads up by at most the two blocking threads); the runtime is kept across checks (a new one would bring a new blocking thread while a stuck lookup holds the old), and tasks left after a check (none, asserted) would run to their end on it.
Measured with step 1's two worker threads (`tests/connector_memory.rs`; for the one connector thread since step 2 see T85), against about 1 MB of minimal tools, 400 KB of them in one array and a list just under the caps, 30 checks in a row and 3 rounds of 20 at once): at most 2 at once, threads unchanged, peak growth about 14 MB and the same kept (the two workers' allocator arenas, reused, not growing), bounds 48 MB and 24 MB; before the fix one check grew the process by 37 MB and 20 at once by 488 MB with 306 MB kept.
**Errors and logs:** failures are a fixed enum (`Failure`) recorded by our client, never remote text; `rmcp::service`'s lines (peer info, results, session ids) are kept out by the workers' no-op subscriber; the server's log also drops the target `rmcp::transport::streamable_http_client` whatever `HARNESS_LOG` says, a backstop for that one target only (the node's stdio MCP client keeps its lines).
**What it offers:** server name and version (128), instructions (1,024), tools by name (128) and description (512), 64 tools, 8 pages, 32 Ki characters of descriptions, the rest "and more"; hidden characters removed; shown as text only; each tool's future agent name `mcp__<connector>__…` (`public_name`), so a tool named like a built-in or like `mcp__other__x` stays this connector's, and two tools whose agent names collide keep the first (the other counted as left out); kept only in memory per person for 10 minutes, at most 256 offers and 4 MiB by their own count (one offer at every cap is about 0.2 MiB, asserted), forgotten on edit, delete and disconnect; nothing reaches a node.
**Floods:** 20 checks per person and 60 failed checks per connector per 10 minutes (bounded tables, failing closed); 50 connectors per workspace.
Tests: `connectors/mod.rs` (6), `store/tests/custom_connectors.rs` (4), `master/tests/logs/connector_client.rs` (19), `master/tests/connector_memory.rs`, `master/tests/connector_stall.rs`, `master/tests/logs/custom_connectors_http.rs` (8), `tools/tests/mcp.rs` (`two_tools_with_one_public_name_keep_the_first`), the CLI's log filter test, `web/src/components/customConnectors.test.tsx`.
**Residual:** no OAuth; a check can still make the server connect to any public https host an admin names (that is the feature; static rules, the resolver and the limits bound it); the remote server's operator sees each person's token (that is the service); a server whose tool list is a page of more than 8,192 values cannot be checked until it pages smaller; the two workers' allocator arenas keep up to about the peak of two checks (some MB) after the checks end, reused by the next; tokens and offers are in memory unwiped while in use; limits reset on restart; a member keeps seeing the definition's address;
Shared / Assigned rows are keyed by name, so a connector deleted and added again under the same name with another URL inherits them (it matters in step 2); no browser script (the real binary has no hook to trust a fake server's certificate).
Step 2 (agents calling tools through the master) is T85; it sets its own budget per call, and a connector deleted and added again under the same name inherits its Plugins rows there too.
