# T45

## Threat

The agent overwrites changes it never saw: it rewrites a file whole, or edits it, from a picture of the file that is out of date (the person edited it in their editor, a formatter or a `bash` command changed it, another chat or a parallel sub-agent wrote it), or edits a file it never read, so the person's work is silently lost or the edit lands on text the model guessed (ADOPTION_PLAN T.2)

## Mitigation

**A per-session record of what the agent saw, checked under a per-path lock** (`crates/tools/src/seen.rs`, `edit.rs`, `fs.rs`): `read` records the file's SHA-256; `edit`, and `write` over an existing file, refuse a file not read in this chat; the agent's own writes re-record.
For a file changed since (hash differs), `edit` goes ahead only where every replaced span lies outside the changed lines, found against the text the agent was shown (kept in node memory, 512 KiB a file, 8 MiB per node; at most 4,096 files per node, which bounds the record's worst case near 30.5 MB (4,096 entries of a 4,096-byte path and 1,300 bytes of entry, map bucket, four version records and remembered tags, `seen::ENTRY_OVERHEAD`, measured from `size_of` by a test, plus the 8 MiB: about 19 MB under the 50 MB idle rule; an earlier version of this note said 26 MB, and the audit of pull request 188 measured what the remembered tags really cost, 4.6 KB an entry, because a `Vec` pushed before it removed and a tag kept the capacity of a whole hash); dropped when the session is deleted), and otherwise refuses with those lines as they are now; with no such text (a restart, a large file, evicted) any change refuses with "read it again".
The check, the match and the atomic replace (T30) run under one node-wide lock per real path, so two chats or sub-agents cannot interleave.
**The log is the authority:** the record rides on `tool_call_finished.seen` (real path and hash; written only by the node's loop from what the tool did, never from the model's arguments, and not at all when the secret scrubber would change the path) and is rebuilt from the log at the start of every turn, so a restart or a failed append cannot leave a record the log does not hold; a sub-agent's session has its own.
Tests: `tools/src/edit_tests.rs` (never read, partial read for `edit` and `write`, a file read in pieces and one with a long line can be written, stale elsewhere applied with the changed lines shown, stale in the span refused, own edits, sessions apart), `tools/src/seen.rs` (rebuild without snapshots, bounds over all sessions, `forget`, the lock), `agent-native/src/edit_guard_tests.rs` (a new backend rebuilds from the log; a changed file after a restart is refused; a summary keeps what was read; a deleted session is forgotten).
**Asked before the card** (live test 2026-11-15, T51's `Tool::refusal`): an `edit` of, or a `write` over, an existing regular file this session's table has no entry for is refused before any approval card, with the words the run would use (an `edit` of a UTF-8 file of at most 512 KiB also shows the lines around its match and counts those lines as shown, not the file as read, as at run time; larger or non-UTF-8 files are left to the run); it reads the session's own table through the same context the run gets (`NativeBackend::refusal_ctx`), only ever refuses earlier, and leaves a file read before and changed since to the run (it may be read again before the call runs); calls of one step are checked one at a time, right before each runs and only once the repeated-call guard admits the call, so a `read` earlier in the same step counts and a call the guard refuses counts nothing as read.
The early `edit` answer shows the file's lines (and counts them as shown) only where a `read` of the same path would run right then with no card and no refusal (`TurnHost::runs_unasked`: the chat's mode and the node's `denied_tools`; the agent having `read`; the path one `read` accepts); otherwise it gives the plain refusal and reads nothing (review of PR 118, H1: in Ask every call, or with `read` denied by the node, the lines were shown with no card).
The run-time answer after an approved `edit` no longer shows lines where the node denies `read` or `read` would refuse the path (older than this change).
The `bash`, `read`, `edit` and `write` descriptions and both refusals say that a file is read with `read` and that `cat`, `head` or `sed` in `bash` do not count (the guard itself is unchanged: shell output is still no read).
Test: `node/tests/approval_modes.rs` `an_unread_existing_file_is_refused_before_any_card`; the wording in `agent-native/src/delegate_availability_tests.rs`.
**Residual:** a change between the guard's read and the rename is caught only by T30's inode check, not by content (a same-inode in-place write in that window is overwritten); `bash` and other processes are not under the lock; viewing a file with `cat` in `bash` does not count as a read (one extra `read`); old tool output hidden by `keep_tool_outputs`, or summarised, still counts as seen (the hash, not the model's memory, is what is checked: a `write` after a summary may replace text the model only knows from the summary); the guard is about integrity of the person's work, not a security boundary: a model that reads a file first can still overwrite it, within the approval mode.
**Line form of `edit`: tags, kept versions, shown rows** (owner, 2026-11-20: "make editing by hash then like in oh my pi"; `crates/tools/src/edit_lines.rs`, `seen.rs`, `fs.rs`). `read` starts its result, and `edit` and `write` end theirs, with `[path#TAG]`: the first six hex characters, upper case, of the SHA-256 the table already holds, **longer when six collide**.
**The tag is a lookup key, checked against the kept text; it is not a security boundary** (24 bits collide, 1 in 16,777,216 per pair of versions of a path; it was 4 characters, 1 in 65,536, until the audit of pull request 188; the guard still compares the full hash).
**A tag, once issued for a path in a session, never names another version of it** (found by the random test, seed 941788: the agent's own edit made a file whose tag characters (then four) were those it was read with, the older version was dropped, and the old tag, with the row numbers of the old version, was applied by number to the new one, silently, the model seeing the same tag in both results).
A version recorded for a path whose base tag equals a tag issued for it before takes the shortest longer prefix of its hash (7, 8, … characters) that equals no issued tag of that path; the older version keeps its tag and stays kept; every kept version stores its own tag, and every header, comparison and refusal text uses the stored one, never one recomputed from the hash.
A tag the model sends is compared as a whole string (after case, a leading `#` or the whole header pasted is normalised), never by prefix in either direction.
The same content seen again (the hash equals a kept or remembered version's) has the tag it had.
A version that leaves the table (the cap of 4, the memory bounds, a new turn's rebuild) leaves its tag and hash in a per-path list of at most 16 remembered tags, oldest forgotten first: it is refused as unknown, with the rows, and no new version takes it.
The bound is safe enough because forgetting needs 17 evicted versions of one path in one session, then a new version whose hash starts with that very tag (1 in 16,777,216), then a model that still holds a tag from that long ago; a remembered tag is 33 bytes (the hash and the tag's length: the tag is a prefix of the hash, so no string), the list is kept at exactly 16 (528 bytes per entry at most, 2.2 MB over 4,096 entries) and is not counted in the snapshot bytes but in the entry bound above (`ENTRY_OVERHEAD`). `sync` carries the list over where the entry survives in memory (a file the log does not name keeps its tags, not its texts) and replays the hashes the log names for each path, in log order, so that a version rebuilt from the log has the tag it was issued with.
**Not covered, two cases, and the odds:** (1) a tag printed by a search, a refusal, or a line edit that landed on a file changed since the guard's version, for a version the log does not hold, after a node restart: the replay does not know of that version, so a later version may take its tag; (2) an entry dropped whole by the file bounds (1,024 files a session, 4,096 on the node, 256 sessions) forgets its tags with it, and a later version of that path may take one.
In both a model that still holds the old tag reaches the new version by chance, 1 in 16,777,216 per later version (six hex characters; the audit reproduced it with a one-character tag, 6 wrong landings in 4,000 sequences with whole-entry drops and 25 in 100,000 with restarts), and the rows it names must still have been shown there and the guard still compares the full hash.
The table keeps per session and path the newest 4 versions the agent was shown or wrote (text and the row ranges shown, in memory only; no event or schema change), inside the same 8 MiB node-wide bound (every kept version's text and 8 bytes per range are counted; least recently used file loses its oldest version first), so the 30.5 MB worst case above does not grow.
A row counts as shown when `read` or `grep` printed it whole (a row cut with `…` never does), when an `edit` result or a refusal printed it, or when the agent wrote the file, and only if it is in the text the model receives (next paragraph).
The call `{path, tag, lines: [{from, to, text} | {after, text}]}` (never together with `old_string`/`edits`) is checked under the path's lock: (1) a version with that tag is kept, else the rows named plus 3 rows of context are printed from the file as it is (at most 40 rows) and count as shown, with the file's current tag; (2) every row named was shown whole, else those rows are printed from the tagged version; a row longer than `read` shows is refused (use the old form); (3) if the file is not the tagged version (the agent's own edit above, another writer), the rows replaced and both neighbours of each insertion point must be unchanged and still adjacent, and each replaced range must still be one run of rows of the same length in the file as it is (a row inserted into it since the tag refuses: replacing the range would delete it; random-case test `tools/src/edit_fuzz_tests.rs`), mapped with `edit.rs`'s changed-lines logic (one contiguous changed part; two separate changes since the tag refuse) and accepted only where a diff from the other end of the file reads them the same way, so a block pasted next to a copy of itself (many `}` rows) is refused, never guessed; otherwise the changed rows as they are now are printed; (4) a call that changes nothing writes nothing.
Rows printed by a refusal, the line form's and (since the review of PR 187, which showed about 7 rows making the whole file count as read) the `old_string` form's too, are recorded without moving the guard's hash of a file that changed since it was read, and without making one for a file never read (it still counts as unread for `write`); an edit applied to such a file does not move it either, so the old form still says "read it again".
The `old_string` form edits a file that is not guarded only when the call is one edit without `replace_all`, the file is not binary, the bytes on disk hash to a kept version (the full hash, not the tag) and the one match lies wholly in rows shown of that version; anything else, `write` included, gets the unread refusal (the limits of the review's F4, F7 and F9 hold: binary files, `replace_all` or several edits, an agent without `read`, get the plain refusal and print nothing). **`grep` records versions** (`crates/tools/src/search.rs`): each file with matches is headed `[path#TAG]` as `read` heads it and the matched rows it printed in full, within the result's budget, are recorded as shown for that version, through the same call as a refusal's rows (no read, no hash for the guard; a row cut at 200 or 300 characters is marked `…` and not shown).
Bounds per search: at most 16 files and 1 MiB of file text get a version (the rest are listed without a tag, so the model sees it must `read` them), none over 512 KiB, not UTF-8 or binary; versions of files nobody read are the first evicted when the 8 MiB node bound is reached, so a wide search cannot push out snapshots of files really read.
No tag is recorded or printed for a path `resolve` or `resolve_for_write` refuses (protected folders, `.git`) or that the walk reached through a link; the search itself skips those.
The tag holds within the turn: the table is rebuilt from the log at the next turn, which names no hash for a search, so a later line edit gets the unknown-tag refusal with the rows and the resend works (test `agent-native/src/edit_guard_tests.rs`).
Tests: `tools/src/search_tag_tests.rs`, the `fuzz_search_tags` mode of `tools/src/edit_fuzz_tests.rs`.
Before the card (`Tool::refusal`): arguments, an unknown tag and rows not shown, printing rows only where a `read` would run unasked.
Tests: `tools/src/edit_lines_tests.rs`, `tools/src/seen.rs`, `agent-native/src/edit_guard_tests.rs`.
**The approval card shows what a line edit replaces:** `Tool::preview` (`edit` only, line form; made by the same plan `run` uses, writes and records nothing, `None` where the plan is refused) is asked by the loop (`authorize`) for a call that may go to a card, handed to the host with the request (`TurnHost::approve_from`), and put in `approval_requested.preview`; the node scrubs it with the rest of the event (`append`: every free-text position is scrubbed, a new one unless someone lists it) and the card draws it as plain text in a monospace block under a fixed label (never HTML, Markdown or a link: a row is file content and may be hostile; every row sits behind its number so none reads as the harness's line or the card's button, control characters and bidirectional overrides are shown as `?`, hidden characters are marked as in any card field).
It is not sent to the model and not part of the grant key.
Tests: `tools/src/edit_preview_tests.rs`, `agent-native/src/edit_guard_tests.rs`, `node/tests/approval_modes.rs` (a line edit's card, the secret, the bound, the grant), `core/tests/scrub_event.rs`, `web/src/components/approvalpreview.test.tsx`.
The `[path#TAG]` header shows the path as the model addresses it (relative to the session folder when inside it).
The result of an applied line edit repeats the replaced rows (at most 20) for the chat.
**Shown means received** (review of PR 188: `grep` printed 200 rows of 300 characters, a refusal 40 rows of 2,000, an edit's result 60 rows of 2,000, and the result cap, which keeps the first and last 15,000 characters of anything over 30,000 (`crates/tools/src/lib.rs` `cap`), cut the middle after the rows had been recorded, so a row the model never saw could be edited, and a `read` of a path of 2,900 characters did the same through its header).
Every producer of rows (`read`, `grep`, the line form's refusal and result, the `old_string` form's refusal and result) prints through a `Budget` of 29,000 characters (`crates/tools/src/shown.rs`; the fixed text is paid first), stops at the first row that does not fit, says how many rows it left out and how to get them, and records only the rows it printed; recording (`SessionSeen::add_shown`) takes a `Sealed` that only `shown::seal(final text)` makes, and `seal` refuses text the cap would cut and panics in a debug build, so a producer that forgets its budget fails the first test that prints enough rows (`tools/src/shown_tests.rs`; the search mode of `edit_fuzz_tests.rs` has files whose results exceed the budget). `write`'s result is a path and a header, under the cap whatever the path; the rows of the content count as shown because the model wrote them.
**Between a tool's text and the model** the loop keeps every row of a result it sends: the scrubber replaces a secret inside a row (accepted: the row stays); `escape_leads` puts a `\` before a line that starts `[harness]`; `bash`'s filter and `tool_output` act on `bash` only.
Whole results are dropped later and the rows stay recorded: masking old outputs, clearing and folding (`shorten`), compaction and the summary of a turn, as for a `read` (a model that no longer has the rows can still name them; the tag and the hash checks still apply, as the rows it names must be unchanged).
**The old_string form at the edge of a shown row:** a match that ends with a row's newline and a replacement that does not end with one join the next row to the line the replacement ends, so that next row must have been shown too (else the unread refusal, which prints it); a match that ends the file's last row needs none.
**Widening on purpose (PR 188):** an agent that has `grep` and `edit` but not `read` could before edit only files it wrote itself; it can now make one `old_string` edit, or line edits, at rows a search printed in full (never `write`, never `replace_all`, never several `edits`), on the very version the search printed (the full hash is compared).
A file changed on disk since rows of it were shown is refused as unread with the words "changed on disk since rows of it were shown" and the changed rows as they are now.
**Eviction order** is one rule everywhere: entries and versions nobody read go before any text the guard holds, then the least recently used (the per-session 1,024 files, the node's 4,096 entries, the 8 MiB of snapshots, the 4 versions a path keeps: a read file's own snapshot is the last of its versions to go).
**Residual:** the preview is made before the card and the file may change while it waits (the run checks again; the card shows the rows as they were); the rows the agent was shown live in node memory only.
