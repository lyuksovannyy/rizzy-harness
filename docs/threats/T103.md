# T103

## Threat

**A backup of the data directory is taken or restored** (FIX_PLAN 4.4; README "Back up and restore"; `docs/backup-restore.md`; `crates/cli/src/backup.rs`, `crates/store/src/backup.rs`): the backup is written where others can read it or through a planted link, holds a half-copied or inconsistent state that restores into a broken or frozen server, leaks a secret in its output, or a hostile or damaged backup writes outside the data directory, plants files the server then trusts, or starts a server on half a restore.

## Mitigation

**Who runs it:** the operator's own CLI, as a second process; the server gets no route for it and runs nothing on its behalf.
**The destination:** absent or an empty folder of this user's, never a symbolic link, never inside the data directory or holding it; made 0700; every file created 0600 with `O_EXCL|O_NOFOLLOW` under a temporary name, synced, renamed, the folders synced, and `MANIFEST.json` written last, so a backup without it is unfinished and restore refuses it; a failed or interrupted (SIGINT, SIGTERM) backup removes what it wrote.
**Consistency beside a running server:** `master.db` first by `VACUUM INTO` through a read-only connection; every stored file it names hard-linked into `<data>/backup-staging` (0700, one backup at a time by `backup.lock`, removed on every exit but SIGKILL and by the next backup; outside `blobs/`, so no server sweep reads it; the links are only ever read); a file gone between the copy and its link makes the copy be taken again, at most 5 times, then the backup fails with nothing kept; then `memory.db`, `chat.db`, `node.db`, so a node log is never behind the mirror (a mirror ahead freezes the chat); chats begun after the `master.db` copy are removed from the node-log copies (they would come back without their owner); then the plain files and `keys/`; the stored files copied for real (never linked into the backup) and each decrypted and checked against its row's SHA-256; every database copy passes `integrity_check`, `foreign_key_check` and the schema check, and one of a newer build is refused.
**With the server stopped:** the same steps holding the data directory's lock, so a server started meanwhile is refused.
**Restore:** under the target's lock (a running server's directory is refused); only into an empty directory (nothing but the lock file); the manifest is the only source of names, each in a fixed shape (known top-level names, `keys/<name>`, `agents/<name>`, `blobs/<xx>/<32 hex>.rzb`; no `..`, no absolute path) and listed once; no link at the file or on the way to it; format and schema versions this build knows; every file's size and SHA-256 checked while it streams in; files not in the manifest ignored and counted; `RESTORING` written first and removed last, and `serve` and `node` refuse a directory holding it; a failure empties the directory again; logins (`ui_sessions`) dropped; `--pause-routines` for a trial copy.
**Output:** counts, sizes, the paths the operator gave and the manifest's SHA-256; never a token, key or file content; errors name files, never what they hold.
**The server's own reads:** `Store::checkpoint` no longer waits for an outside reader (it held the store's only connection for the 5 s busy timeout and then skipped the truncate silently): it reports a missed truncate, logs it once, and the next checkpoint or the hourly sweep makes it.
Tests: `crates/cli/tests/backup_restore.rs` (the row's test with the server running and stopped, an account's chat and stored file read back after signing in again, an old login refused; a file deleted between the copy and its link; events and a chat added between `master.db` and the node logs; refused destinations, a newer schema; SIGTERM and SIGKILL in the middle; a flipped byte, a truncated database, no manifest, paths with `..`, absolute and outside the shape, a link at a file and on the way, a newer schema and format, a planted file; a non-empty target, `lost+found`, a running server's directory, `RESTORING`; `--pause-routines`; an older schema migrated at the first start; undo without checkpoints), `crates/cli/src/backup.rs` (the path shapes, a 2 GB file through the fixed buffer, a stop), `crates/store/src/backup.rs` (the private copy, implicit rowids kept, logins and routines), `crates/store/tests/checkpoint.rs`.
**Residual:** the backup is not encrypted: whoever reads it has the server (every password hash, chat, stored file and its key, provider key, the sealing key and the API token); the manifest's hashes catch damage, not an attacker who can rewrite the manifest too; a restored copy is the same identity, and run beside the original it shares its nodes, tokens and routines; a remote node restored from an older backup freezes its chats that moved on; a file uploaded between the `master.db` copy and the node logs may be named by a kept chat event and missing from the backup; a chat begun in that window is left out; under a delete rate that beats five link passes the online backup fails (stopping the server always works); undo after a restore says the checkpoint is "no longer kept (only the latest 100 changes are)", a sentence written for the pruning case.
