# T103

## Threat

**A backup of the data directory is taken or restored** (FIX_PLAN 4.4; README "Back up and restore"; `docs/backup-restore.md`; `crates/cli/src/backup.rs`, `crates/store/src/backup.rs`): the backup is written where others can read it or through a planted link, holds a half-copied or inconsistent state that restores into a broken or frozen server, leaks a secret in its output, or a hostile or damaged backup writes outside the data directory, plants files the server then trusts, or starts a server on half a restore.

## Mitigation

**Who runs it:** the operator's own CLI, as a second process; the server gets no route for it and runs nothing on its behalf.
**The destination:** absent or an empty folder of this user's, never a symbolic link, never inside the data directory or holding it; made 0700; every file created 0600 with `O_EXCL|O_NOFOLLOW` under a temporary name, synced, renamed, the folders synced, and `MANIFEST.json` written last, so a backup without it is unfinished and restore refuses it; a failed or interrupted (SIGINT, SIGTERM) backup removes what it wrote.
**Refused before anything is opened:** a data directory or target holding `RESTORING` (every command that uses a data directory refuses it and says what to do; `doctor` reports it and checks nothing else, so it writes nothing there); a database, its `-wal`, `-shm` or `-journal`, a plain file or a file of `keys/` or `agents/` that is a FIFO, device or socket, or a symbolic link among these fixed items whose target is missing, not a regular file or over 16 MiB (a link to a regular file is followed and its content kept as a plain file; the manifest records the item's name, never the target), a database or `blobs/` behind a link (a FIFO would block the open: each file is judged by `lstat` first, then opened `O_NONBLOCK|O_NOFOLLOW|O_NOCTTY` and checked to be the file judged); a destination that is the data directory or inside or around it by name or by device and inode.
**Consistency beside a running server:** `master.db` first by `VACUUM INTO` through a read-only connection (offline: from a byte copy of the stopped server's files in the staging folder, so the source is not changed by a byte, its `-shm` included); every stored file it names hard-linked into `<data>/backup-staging` (0700, one backup at a time by `backup.lock`, removed on every exit but SIGKILL and by the next backup; outside `blobs/`, so no server sweep reads it; the links are only ever read); a file gone between the copy and its link makes the copy be taken again, at most 5 times, then the backup fails with nothing kept; then `memory.db`, `chat.db`, `node.db`, so a node log is never behind the mirror (a mirror ahead freezes the chat); the copies are settled as of the `master.db` copy: a chat caught between its create and its owner's stamp is stamped from the create intent only when the intent has not expired at the snapshot's moment (the master's own rule, shared; an expired one leaves the chat ownerless as on the live server), the master now dropping the intent only after the stamp, chats begun after the copy are removed from the node-log copies (they would come back without their owner), chats deleted meanwhile are removed from the `master.db` copy by the master's own forget path; what a backup skips is listed in its manifest and said by every command; then the plain files and `keys/`; the stored files copied for real (never linked into the backup) and each decrypted and checked against its row's SHA-256; every database copy passes `integrity_check`, `foreign_key_check` and the schema check, and one of a newer build is refused.
**With the server stopped:** the same steps holding the data directory's lock, so a server started meanwhile is refused; the staging folder needs file locks, and a file system without them is refused.
**Restore:** under the target's lock (a running server's directory is refused); only into an empty directory (nothing but the lock file); the manifest is the only source of names, each in a fixed shape (known top-level names, `keys/<name>`, `agents/<name>`, `blobs/<xx>/<32 hex>.rzb`; no `..`, no absolute path) and listed once; no link at the file or on the way to it; format and schema versions this build knows; each file judged before it is opened (regular, no link on the way or at it), opened non-blocking, read at most to its declared size and one byte (a file that grows is refused), its SHA-256 checked; files not in the manifest ignored and counted; `RESTORING` written first and removed last, and `serve` and `node` refuse a directory holding it; a failure empties the directory again; logins (`ui_sessions`) dropped; `--pause-routines` for a trial copy.
**Before a migration (PR B):** a start that will migrate copies every database into `pre-migration/` (0700/0600, a manifest, the complete set swapped in by rename) after the schema preflight and before any database is opened; a copy that cannot be written stops the start before anything is migrated, unless the operator passes `--migrate-without-copy`, which is logged; `restore --pre-migration` runs under the lock, refuses an incomplete or changed set, keeps the upgraded files aside (0600) and never deletes them; `backup` leaves the set out and restore's path shape refuses it.
**Output:** counts, sizes, the paths the operator gave and the manifest's SHA-256; never a token, key or file content; errors name files, never what they hold.
**The server's own reads:** `Store::checkpoint` no longer waits for an outside reader (it held the store's only connection for the 5 s busy timeout and then skipped the truncate silently): it reports a missed truncate, logs it once, leaves `<db>-truncate-pending` for `doctor`, and the next checkpoint or the retry (master.db hourly, `chat.db` and `node.db` every minute) makes it.
Tests: `crates/cli/tests/backup_restore.rs` (a FIFO in place of each kind of file in a backup and in a data directory, refused within seconds naming it, nothing left (device nodes: skipped where `mknod` is refused, as here); every command refusing a half-restored directory and the advice followed in a test; an offline backup of a killed server byte-identical and holding the WAL's rows; a newer schema refused with the source byte-identical; a chat deleted during the backup not restored; every command with a deadline; the row's test with the server running and stopped, an account's chat and stored file read back after signing in again, an old login refused; a file deleted between the copy and its link; events and a chat added between `master.db` and the node logs; refused destinations, a newer schema; SIGTERM and SIGKILL in the middle; a flipped byte, a truncated database, no manifest, paths with `..`, absolute and outside the shape, a link at a file and on the way, a newer schema and format, a planted file; a non-empty target, `lost+found`, a running server's directory, `RESTORING`; `--pause-routines`; an older schema migrated at the first start; undo without checkpoints), `crates/cli/src/backup.rs` (the path shapes, a 2 GB file through the fixed buffer, a stop), `crates/store/src/backup.rs` (the private copy, implicit rowids kept, logins and routines, a crashed WAL read from a private copy, the create intent, the settling), `crates/cli/src/backup.rs` (a file that grows is refused), `crates/store/tests/checkpoint.rs`, `crates/cli/tests/pre_migration.rs` (a migrating start copies all databases first, an up-to-date one leaves the set, a failed second migration names the rollback and the rollback restores version 1 everywhere with the failed files aside, no room stops the start and the escape migrates without a set, a rollback refuses no set, a missing or changed file and a running server, a backup leaves the set out).
**Residual:** the backup is not encrypted: whoever reads it has the server (every password hash, chat, stored file and its key, provider key, the sealing key and the API token); the manifest's hashes catch damage, not an attacker who can rewrite the manifest too; a restored copy is the same identity, and run beside the original it shares its nodes, tokens and routines; a remote node restored from an older backup freezes its chats that moved on; a file uploaded between the `master.db` copy and the node logs may be named by a kept chat event and missing from the backup; a chat begun in that window is left out; under a delete rate that beats five link passes the online backup fails (stopping the server always works); undo after a restore says the checkpoint is "no longer kept (only the latest 100 changes are)", a sentence written for the pruning case.
