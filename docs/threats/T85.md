# T85

## Threat

**Agents call a custom connector's tools through the master** (ADOPTION_PLAN X.35 step 2; README "Custom connectors"; `crates/master/src/connectors/` (`call.rs`, `grant.rs`, `tools.rs`, `pool.rs`), `http.rs` (`acting_session`), `crates/store/src/custom_connectors.rs` (`foreign_chats`), `crates/node/src/connectors.rs`, `crates/tools/src/connector.rs`, `crates/core/src/connectors.rs`; the owner, 2026-11-18: "for connectors make each user can connect own account (if connector supports auth)"; three reviews of PR 157; the coordinator's rule of the third): a person's online-account token used on a model's request.
Abuse cases: (a) someone other than the chat's owner (the API token, another person's routine, a webhook, a node) gets the owner's account used, directly or by text or a decision the model reads (a message, an approval answer or note, a Retry of their turn, a background end of their command, their turn in the chat's history); (b) a node asks for a session it does not run, another workspace's, a tool the master never listed, a connector edited or deleted since; (c) the agent rule is bypassed (the Connectors switch, Assigned, a sub-agent's own denial, plan mode, `denied_tools`, `master_connectors = false`); (d) the token leaks; (e) a hostile connector; (f) stalls and floods; (g) a call is made without the person's approval in an Ask mode; (h) one approval covers another origin's tool

## Mitigation

**The rule: connectors are used only in a chat in which nobody but its owner has ever acted.**
A persisted mark (`foreign_chats`, one row per chat, set once, never cleared; a deleted chat first hands what its sub-agents' chats inherited through it, its own mark or one above it, to them, and external event data above it the same way, as their walk up ends at the deleted chat) is written BEFORE the action is forwarded, for the chat AND every chat above it to its root (delegation can be several levels deep; an honest node delegates 4 levels at most; a chat 16 or more levels below its root counts as marked, and a mark written there goes to every chat the walk reached and then refuses the action, so nothing is forwarded into a chain whose root the mark may have missed), with a full sync for that one write (the master's store runs at `NORMAL`), and a mark that cannot be written refuses the action.
Reading walks the same way: a chat is off when it or any chat above it is marked or holds external event data (`routines::chat_untrusted` walks every ancestor too since this round; it looked one hop up before).
It is written at one place per path: every HTTP route that puts text or a decision into a chat or its turns resolves its caller in `http::acting_session`, which marks the chat and every chat above it when the caller is not its owner (a person sees only their own chats, so that is the API token): prompt (also a queued message and a form reply), cancel, agent switch, variant choice, approval answer and note, restore, retry, approval mode, step limit, background stop (all or one), revoke a chat allow, compact, chat project, title, save an artifact, a composer image upload; reads (the chat, its events, files, artifacts list, diff, seen, the card check) do not mark. `Master::prompt`, which every prompt, retry and routine run passes, marks a chat when the send is neither the signed-in owner's nor a run of the owner's own routine (`board::routine_turn`), and not a callback (the node's own).
A chat holding external event data (`routines::chat_untrusted`) counts as marked.
A marked chat also writes nothing other chats read without a person's click: every `remember` of its turns, the owner's own included, is a proposal the person keeps or dismisses (`TurnMemory::by_owner` off, as for an API-token turn; departure from review 4's "no remember at all": proposals keep the API's own memory workflow and still put the person between foreign text and shared memory), and its turns get no `board_edit`; both are read from the store at each call (`projects::turn_memory` for every `remember` filed, `board::answer` for every board write; the ancestor rule; a read error counts as marked), not taken from what the turn was given at its start, so a mark that lands while the owner's clean turn runs (the API token's approval note, its queued message) stops that turn's and its sub-agents' writes from that moment (review 5); an agent's staged file from such a chat is recorded as failed when its lineage is shared with the workspace (`IngestCaps::not_into_shared`, read at ingest; a new name is published, private; a person's own save from the chat is their click); a memory proposal from such a chat says so on its card (`from_marked_chat` in `GET /api/sessions/{id}/memory/{call}`); a chat nobody owns (made with the API token) is never marked, as it has no account to use; and the project's "Earlier chats" (`Store::earlier_chats`) leaves out every marked or untrusted chat, for every chat.
The session's API says why connectors are off (`connectors_off`: `this_chat`, `parent_chat`, `event_data`; `no_owner` for a chat nobody owns; `unknown` when the store cannot be read, connectors then off); the model is told once, also in a sub-agent's chat of a marked chat.
Every node request the master answers, checked at the call: `connector.request` reads the mark (refused); a `board` write reads it (refused), a board read does not need to; a `remember` filed reads it (a proposal); `artifact_staged` reads it (refused into a shared lineage); `recall` and `skill.request` only read (recall's earlier chats leave out marked chats; stored skills are written by people with rights); the replies to the master's own requests (files, diff, artifact bytes, project folder, project MCP list) write nothing other chats read. `offer_connectors` and `answer` both read the mark from the store, failing closed: a marked chat gets no list, no call, and its first turn that would have had connectors is told once: "Custom connectors are off in this chat because someone other than its owner acted in it (the API token, an automation or a webhook).
A new chat has them." (a).
**The grant** (`grant.rs`), the second layer, keeps a NODE from inventing one: every prompt and retry the master hands a node for a chat whose workspace has a connector the owner can use is recorded at the moment it goes on the link (`send_command_noted`), by a SHA-256 of its whole input (text, attachment names and types, image ids and digests, file mentions; a form reply by its message id), and taken out on every failure after (the queue full, the node offline, a refusal, a timeout); chats without such a send have no entry.
A turn is granted when its first `user_message` is not queued and matches the oldest matching send, the owner's; a Retry when its send was the owner's and the retried turn was itself granted; a callback never; a turn the master sent nothing for never; a sub-agent's turn is bound when it starts to its chat's open granted turn, unless the master sent that sub-agent's chat a message of its own meanwhile (a person typed into it; the log has no other mark of it).
A message the node records with another text than was sent (its scrubber blanked a secret) matches nothing: that turn has no connectors (fail closed).
Removed in the third round: the rule that a later or queued (`queued_delivered`) message of another sender takes a granted turn's grant (every such sender marks the chat first; what it still caught was a message the node made up, and such a node can call within any grant it has).
Chats tracked: 1,024, least recently used forgotten first; 16 sends, 8 turns per chat; 2,048 sub-agent turns; about 5 MB at worst.
**Counts:** 30 calls per granted turn (`grant::PER_TURN`), its sub-agents' included, under the master's own key, so 30 per owner send; 200 per chat in any hour (`grant::PER_HOUR`); a call not made for a reason of the server's own (no room, a token that does not open) gives its count back; there is no per-person cap (a person's chats × 200 per hour), acceptable because every grant needs a real send of the owner's; 8 in progress per node.
**The end:** the chat's own calls only while its granted turn is open; a sub-agent's only while the log shows its turn open and no longer than 60 minutes (`grant::AFTER_END`) after the chat's turn ended; a background sub-agent's grant also ends early once its chat has had 8 newer turns (the turn table) (b, f).
**The list** (`AgentSpec::connector_tools`, top spec only): only when the turn may, only connectors the owner can use (sign-in `none`, or `token` with their account and a key file that opens it), only tools some spec may use, at most 40 tools and 64,000 bytes; from a per-person cache keyed with the connector's stamp and bound to the digest of the sealed token it was read with (a set read with a token replaced since is not used on the call path, and a background read never overwrites a set put since it began); filled by Connect, Check or a background read on the connector thread under its own key (`fill:<person>`), its own failure budget (10 per connector per 10 minutes) and a 5-minute back-off per person and connector after a failure (the turn is told which connectors could not be read); never on a turn's path; refreshed after 10 minutes, unused after an hour; 256 sets, 8 MiB.
Untrusted text cleaned to one line under `(MCP server \`<connector>\`)`, schemas cleaned and capped (e). **The node** offers the list only where node.toml `[mcp] master_connectors` is on, only to a turn that gets its chat's MCP tools (never a person's message in a sub-agent's chat), never to a turn that only reads queued messages, for an agent with MCP that changes things, never in plan mode, after its own servers under one set of per-chat caps; entries are checked; `denied_tools` applies (c). A connector tool is `ToolRisk::Mutating`: asked in Ask, Ask for everything and Accept edits, run unasked in Auto, refused in plan mode; its card is its own; every approval key carries the tool's origin (`connector:<name>` or `server:<name>:<node.toml|repository>`) in the turn's and the chat's grants, so a grant for one never covers the other's tool of the same public name (the loop's turn key cannot meet that case inside one turn, where one public name is one tool; the chat's key is tested) (g, h). **A call** (`connector.request`, at most 64 KiB of arguments; a reused request id is refused, the first keeps its cancel) is answered from the session alone: the node runs it, the chat is not marked, the grant holds, not a callback turn, the agent has MCP and the tool, the owner active and a member, the connector the workspace's by name, the tool one the owner's cached set of the current stamp lists; then the owner's sealed token, ONE `initialize` + `tools/call_once` by step 1's client rules on the ONE connector thread that checks use too (`pool::Thread`: one allocator arena; 4 call slots, 2 per person and per connector, refused when busy, never queued; name lookups under gates of their own (calls, checks, background reads: one permit each, two blocking threads in all), so a name that never resolves for calls or a background read never starves a person's Check), 256 KiB and 8,192 values per message, 120 s. Text only; nothing logged, no audit line per call (b, d). Tests: `master/tests/logs/connector_calls_http.rs` (41, among them a mark during a running turn and a queued message stopping its writes, a chain too deep to mark, the history case, the Retry of an API-token turn, API-token approval answers and notes, a background end, the same text from two senders, the mark across a restart, in a sub-agent and for a webhook chat, the owner's own chat through everything the owner does, every chat-changing route), `master/src/connectors/{grant,tools,pool}.rs`, `master/src/remote.rs`, `master/tests/connector_call_memory.rs`, `master/tests/it/artifacts_http.rs` (a marked chat and a shared file), `store/tests/custom_connectors.rs` (the walk, its depth, a deleted middle chat), `node/tests/connectors.rs`. **Memory** (measured 2026-11-19, a release test process, the fake server in another process; accepted by the owner the same day, to "Accept up to about 55 MB after heavy connector use, with the reason written into PLAN.md?": "Accept, write reason"; the reason is in §Principles): idle 7.8 MB; one plain check +5.1 MB; heavy checks +6.9 MB; 200 heavy calls +8.2 to +10.4 MB, unchanged 60 s later (the six worker threads before: +18.8 MB); a release `serve` without connector use idles between 34.6 and 45.7 MB from run to run (`origin/main` 35.1 to 40.3 MB the same way). **Not covered, by design (say it plainly):** the mark covers what others do in a chat, not text that people with rights write for every chat to read: the server's and the workspace's admins (agent instructions, stored skills, workspace memory), a project's managers (brief, facts, board cards and columns), the API token wherever it holds those rights, and files in a shared project folder that a node reads as instructions (`AGENTS.md`, `CLAUDE.md`); `recall` results can carry a marked chat's text and the board tool shows cards and notes, as tool results. The owner decided (2026-11-19), to "Should a connector call always ask the first time per tool per chat, even in Auto mode?": "No, keep Auto". So in Auto mode nothing asks before a connector call, and a call steered by such text (agent instructions, skills, workspace memory, a project's brief and facts, board cards, instruction files in a shared folder) is not stopped by the harness; in the Ask modes the approval card is the check; a person who wants every connector call asked sets the chat to an Ask mode. **Residual:** a compromised node that runs the owner's chat can, during a turn the master granted, call the owner's connectors with any arguments: up to 30 calls per owner send and 200 per chat per hour; it cannot grant itself a turn, keep a grant past its turn, or lift a chat's mark; an owner whose message the node rewrites (a scrubbed secret) or queues gets no connectors for that turn; the remote server's operator sees the token and arguments; a dropped call may still have been done remotely; a connector's tool list can change between the read and the call; a connector deleted and added again under the same name inherits its Plugins rows; grants and counts live in memory (a restart ends every grant; 1,024 chats).
