# T39

## Threat

Commands of a chat run with more power than the chat, or its owner, was given: the master (or a member, through it) asks a node for an execution mode it should not get, a member runs a mode above their level (an account ceiling, a level per workspace), a level raised by someone not allowed to grant it, or a lowered level that leaves work running, a session moves from the `sandbox` mode to the unconfined `host` mode (or the reverse) without its owner choosing it, or by a switch that someone else asks for, that leaves something built under the old mode running (an MCP server, a call allowed for the chat) or that is made while the chat runs, or a node quietly runs commands uncontained where it could not contain them (N.10a parts 1 and 2, O13; `docs/execution-modes.md`)

## Mitigation

**The node decides the ceiling** (`[execution]` in node.toml): `sandbox` offered only where its bubblewrap probe passed at start (`auto`; `strict` only without a gap; `off` never), `host` only with `host = true` and not where the Landlock sandbox is required and does not work; computed once at start from the node's own self-test, never from anything received (`ExecOffers::from_start`).
A node offering neither runs no agentic session and says so at start (`node run` refuses to start), in `doctor` and in the refusal.
The old `contain = "auto"` fallback (Landlock alone, a warning) is gone: the sandbox mode's `Sandbox` refuses a shell command without a containment (`require_contain`), and the step up from Landlock alone is removed.
**The mode is chosen at create, and moved only by the chat's owner, only while nothing of the chat runs (N.10b, the owner's decision of 2026-11-21):** `session.create` carries it as a request; the node refuses one it does not offer, and without one takes `sandbox` or refuses (never `host` by default: review L-a; `ExecOffers::choose`); recorded in `session_created`; checked against what the node offers before every turn, callback, restore and delegation (`checked_folder`), and a session whose mode is gone runs nothing; a sub-agent gets its parent's, as it is when the sub-agent starts or is continued; chat sessions have none.
**The switch** is one additive event, `exec_mode_changed { mode, from }`, appended by the session actor on `session.set_exec_mode` (capability `exec-switch`); the chat's mode is the latest such event, else `session_created.exec_mode` (`harness_core::exec_mode`: the node's load, the Rust view, the master's mirror and the browser's fold all read that one rule), and a mode the log names that this build cannot read is unreadable and runs nothing (the master's check fails closed on the same text).
`POST /api/sessions/{id}/exec-mode` is the chat's owner only (the 404 of a chat that does not exist for an admin, a workspace admin and the API token on a person's chat), refused for a chat without tools, a sub-agent's chat, a routine's chat and a chat nobody owns, and makes the checks of a create for the target mode in the same order: the owner's effective level in the chat's workspace allows it (`workspaces::switch_refusal`, not the work rule, which asks the mode the chat has now, so a host chat of a lowered owner can still leave it), the node rule, a connected node announced the mode and the switch (an older node: update it), the log is not diverged.
Every request for `host` is audited whatever refuses it (`session.exec_mode.host`), a granted switch to `sandbox` too; no chat content.
The node decides again under the turn slot: it offers the mode (the `[execution]` and `[sandbox] mode = "required"` rules), and no turn runs or is being stopped, no `/compact`, no background command or sub-agent runs or has an end not recorded, no approval waits.
Before the ack it stops the chat's MCP servers and waits until they are gone (one that does not die in ten seconds refuses the switch with nothing recorded), removes every chat grant by its own `chat_allow_removed` (a call allowed in one shell is asked again in the other, and when the chat returns), and only then records the event: the crash order is the safe one.
The approval mode stays the person's (in `auto` the next turn runs host commands unasked: the web warning says so), and the next turn's environment line tells the model the mode and the change.
The mode is state, not conversation: a rewind does not move it back; a fork's copied events carry the changes up to its cut.
The backend picks the confinement by the recorded mode (`NativeConfig::confinement`): `host` gets the uncontained twin (`Sandbox::uncontained`, which can never gain a containment), and the confinement of a mode the node does not offer refuses every command (`ExecOffers::confinement_for`, review L-f).
A `host` session has a background table like a `sandbox` one since the owner's decision of 2026-11-20 (its command runs under the guard without bubblewrap, T9; before it had none and its model was not offered the tools: N-c) and background sub-agents like a `sandbox` one (the owner, 2026-11-20: "dont, like if user selected host project workspace, why do we need to limit it? its his choice"; T72); its approval card says it runs in the host shell (N-e).
Review N-e's clamp of host chats to `ask` was removed by the owner's decision of 2026-11-14, in their words: "default accept mode is Auto for every chat type, no limits for apart chat types or agentic host access modes, so each can use auto, always accept, manual, etc..."; a host chat may run in `auto` and new chats start there, so in a host chat on Auto nothing stands between a prompt-injected agent and the machine (T50).
The start probes bubblewrap up to 3 times, 1 s apart, each failure logged; after that the start is the only moment that counts (L-b). `strict` does not offer the sandbox mode with any gap its line names: below ABI 9, the network-off gap, the shared-`/proc` form, an image not held, the binary in reach, a `[sandbox] write` entry holding `/tmp` or `/run/user/<uid>` (sockets elsewhere in a write entry are not looked for) or a folder on the node's `PATH` (L-c).
The hello announces each gap (`gap:sandbox:netns`, `:sockets`, `:proc`; `gap:host:netns` where Landlock stops TCP, `gap:host:net-open` where nothing does: L-d, L-e) as a snapshot of the start, and the master shows modes and gaps only to accounts whose ceiling runs agent chats (L-i).
**The master (part 2): levels per member** (`master/src/levels.rs`; `docs/execution-modes.md`).
An account has a ceiling (`users.exec_ceiling`, `none` for every new account, also one a server admin creates; a server admin's counts as `host` while they are one, a disabled account's as `none`), set by server admins only and never their own; a member has a level in each team workspace (`workspace_members.exec_level`, `none` for every new member; an owner's counts as `host`), set by its admins: never their own, never above their own effective level, `host` only by an owner, an owner's never; a Personal workspace has none of its own, so there the ceiling applies (which closes review H1: neither owning one's Personal workspace nor a team one made raises anyone past the ceiling).
The effective level is the lower; `Perm::Agentic`, `can_agentic` and part 1's "`host` for server admins only" are gone.
A chat's mode must be at most it: at create (`levels::create_mode` in the handler, and again in `Master::create_session` for every caller), and on every later command that makes a node work on the session, in `Master::send_command` for every command `writes_to` names (prompt, callback, allowing approval, restore, `set_agent` and `select_variant`, which had no gate, artifact staging), decided by the chat's owner, never the caller (the API token, `host` and an owner of every workspace, gets the owner's answer on their chat), failing closed on a row without a readable mode, an owner that cannot be loaded and a session the mirror does not know; denying, cancelling, stopping and deleting are never refused, and reading never is.
A lowering (ceiling, workspace level, demotion of a server admin to their stored ceiling) runs the revocation sweep, still keyed by owner, workspace, node and recorded mode (RN-1), so only chats above the new level lose their running turn and background commands; a removal also stops what ran in the member's chats from that workspace, which return to their Personal one at the ceiling.
Each change is conditional on what its guards read, the setter's own standing included (two admins at once, or a setter lowered meanwhile: 409; review L2-9), nobody changes a member whose level is above their own (L2-10), every acked work command is checked again (L2-1), deleting a workspace stops what removal stops (L2-3), and the member list shows others' levels only to those who manage members (L2-7) and writes one `level.account` or `level.workspace` audit line in the same transaction (by, user, workspace, from, to); role changes that make or unmake an owner or a server admin, disabling, an account created above `none` and a removal write one too.
Every create that asks for `host` is still audited (`session.create.host`, RN-4); a routine's chat always asks for `sandbox` and fires at its owner's level on the day it fires.
The UI sets the levels (Settings → Users, Workspace admin → Members) offering only grantable ones, shows the host warning before granting `host` (cancelling saves nothing), and offers a chat's `host` mode only at the `host` level.

T82 (i)); it is a property of that configuration, the node's start and `doctor` warn (`doctor_warns_where_a_host_chat_can_reach_the_data_directory`), and the default `required` keeps the directory out of reach (`cli/tests/exec_modes.rs` `a_host_chats_shell_cannot_read_or_change_the_data_directory`); a data directory from before `sessions.exec_mode`, or from before the levels, does not open (refused at start as a schema mismatch; no migration before the first tag; RN-6); **a workspace's levels are not yet tied to its nodes**: a node is not attached to a workspace (C.12, N.1), so a member whose ceiling is `sandbox` can run a `sandbox` chat on a team's node from their Personal workspace whatever their level in that team, and a removed member's chats go on in Personal at their ceiling: until N.1 the account's ceiling is the boundary between people; leaving or being removed unblocks what a team's level blocked (the chats return to Personal; review L2-6); the start retries a failing probe, so a slow failure is three times as slow and a hanging bubblewrap still hangs the start (RN-7); a stolen master can ask for any mode up to the ceiling (the modes protect against members, not against the master; T5); `host` is as strong as the node's OS user, and below Landlock ABI 9 the session bus gets a `host` command everything that user has (R2); a `sandbox` chat can write what a `host` chat in the same folder later runs (scripts, `.git/hooks`, `.git/config`), which the modes cannot close (said in the warning and the README; C.8's read-only `.git` binds narrow it), and a switch makes it one chat: the folder and the chat's session temp folder are shared by both modes, so what the chat's sandbox commands wrote the host commands may run after a switch; a switch to `host` with the approval mode on `auto` runs the next turn's commands unasked (said in the warning; the approval mode is not changed by it); the provider's prompt cache of the tool descriptions is lost at a switch (the bash description differs by mode); a node serving several workspaces does not refuse `host` yet, because it cannot know (workspaces are the master's; it belongs with the node's attached list, C.12 / N.1); `graph_query` in a `sandbox` chat starts graphify under Landlock alone, outside bubblewrap (review N-a, not changed here), so not every command of a sandbox chat is contained; the hello is a snapshot (a gap closed later by the step up shows until the next hello).
