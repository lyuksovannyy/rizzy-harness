# T96

## Threat

**A person's Word, Excel, PowerPoint or OpenDocument file is parsed so that the model can read its text** (ADOPTION_PLAN X.55, README "Office documents"): the bytes come from a browser and are a zip of XML parts, so a zip bomb, a part that says it holds a gigabyte, elements nested a million deep, a billion-laughs or external-entity DTD (`file:///etc/passwd`, a URL), a million shared strings or rows, an index that points nowhere, a zip that only claims to be a document, or text that poses as the harness could exhaust the server, read a file or the network of the machine it runs on, crash the process that holds every provider key, or put instructions in front of the model.

## Mitigation

**Never in the server's process.**
The server starts its own binary as `rizzy-harness doc-text` (dispatched before any runtime, like `pdf-text`), writes the file to its stdin and reads the type and text from its stdout; the helper is the PDF helper's twin and shares its code: `confined_helper` (Landlock with no file and no TCP access, failing closed where the kernel cannot; an address-space cap above what it maps at start; one thread; an empty environment) and `PdfReader::run` on the server (two helpers at once and a third waits ten seconds for a 503, twenty seconds of wall time, stdout capped, stderr discarded, its own process group killed on timeout, on excess output and when the request is dropped).
A fixed subcommand and bytes on stdin: the master runs no program the model names (`crates/master/src/pdf.rs::tests::a_document_helper_is_read_and_its_type_checked`, `::a_document_helper_has_the_same_bounds`, `crates/cli/tests/doc_text.rs`).
**The confinement and the cores are proved, not assumed.**
A probe compiled only with the `helper-probe` feature (a dev-dependency of the cli crate, in no shipped build) and asked by environment tries, after the confinement, to open `/etc/passwd` and to connect to a port that listens, and reports its core limit and dumpable flag: both refused, `RLIMIT_CORE` 0 and not dumpable, for `pdf-text` and `doc-text` alike, and the test fails when `restrict_self` is replaced by `Ok` (`crates/cli/tests/helper_confinement.rs::a_confined_helper_opens_no_file_reaches_no_port_and_leaves_no_core`).
The helper turns core dumps off (soft and hard limit 0, `PR_SET_DUMPABLE` 0) because the host's core pattern often pipes to a handler outside every sandbox (`systemd-coredump`) that would store the image of an uploaded file; the earlier builds left `pdf-text` cores on a developer machine.
**A document is told by its parts, never by its name.**
The server looks at no name and parses nothing: any file that starts with the zip signature goes to the helper, which reads the directory and decides: a `mimetype` entry naming an OpenDocument text, spreadsheet or presentation and a `content.xml`, or a `[Content_Types].xml` and `word/document.xml`, `xl/workbook.xml` or `ppt/presentation.xml`.
A plain zip called `.docx` is a plain file (exit code 5, "not a document", no sentence), a document called `.bin` is a document, and an encrypted file (an encrypted part, or an ODF manifest with `encryption-data`) is not one either and stays what it was: a kept read-only file (`doc/tests.rs::a_document_is_told_by_its_parts`, `::an_encrypted_file_is_not_a_document`, `crates/cli/tests/doc_text.rs::what_is_not_a_document_is_not_one`, `crates/master/src/attachments.rs::tests::a_zip_is_a_document_by_the_readers_word_not_by_its_name`, `crates/master/tests/it/doc_http.rs::a_zip_named_docx_is_not_one_and_the_name_never_decides`).
The helper's first output line, the type, is checked against the six it may name; anything else is a misbehaving helper.
**The zip is read by the bounded reader of T95.**
`harness-attached::Package` (reusable by later rows that read or write the parts of such a file; its test builders are behind the `testkit` feature, not in the binary) walks the central directory entry by entry with checked arithmetic, allocates nothing from a size the archive states, refuses an entry that says it holds more than 1 GiB or more than deflate can give for its data, reads a part as a stream and stops everything unpacked from one file together at 64 MiB or at its deadline (`doc/tests.rs::a_zip_bomb_inside_a_docx_stops_at_the_ceiling`, `::a_part_that_declares_a_gigabyte_or_lies_about_its_size_is_refused`, `crates/cli/tests/doc_text.rs::a_zip_bomb_inside_a_docx_is_stopped`, `::a_huge_text_node_cannot_grow_the_helper`).
**One XML pull parser that expands nothing.**
`quick-xml` (MIT, one dependency of its own that was already in the tree) has no entity table: a DOCTYPE is skipped, `&lol9;` and `&xxe;` arrive as references the reader drops, and only the five predefined entities and numeric character references give text; nothing is opened, fetched or included, and the process may open no file anyway (`doc/tests.rs::a_billion_laughs_dtd_is_never_expanded`, `::an_external_entity_is_never_read`, `::only_the_predefined_and_numeric_references_give_text`, `crates/cli/tests/doc_text.rs::an_external_entity_reads_nothing_of_the_machine`).
Elements nest at most 64 deep, a file past it is refused with a sentence (`::elements_nested_deeper_than_the_cap_are_refused`, `crates/cli/tests/doc_text.rs::deeply_nested_xml_and_a_sheet_of_a_million_rows_are_bounded`).
**Bounded output and memory.**
The reader's memory is bounded by its own caps, and the address-space limit is only the second line: a part is cut at 4,000,000 XML events (nine million empty `<w:tc/>` and 1.4 million paragraphs in one cell, both under 400 KB of zip, end in "too large to read in full" in about a second, not after seconds of work), the cells of a table row past 256 are counted (`[+N cells]`) and not stored, a table cell's text and a paragraph stop growing at 80 KB, and one text event is cut as it is taken in (a 60 MiB text node gives one 20,000-character paragraph).
The XML parser itself still buffers one text node whole while it reads it, bounded by the 64 MiB package ceiling and the helper's address-space cap (`doc/flow.rs::tests::what_is_held_is_bounded_by_the_readers_own_caps`, `doc/tests.rs::a_cell_flood_and_a_cell_of_a_million_paragraphs_are_cut_fast`, `::a_wide_row_and_a_huge_text_node_give_what_the_caps_allow`).
At most 100,000 characters (the PDF cap; the helper stops reading as soon as it has them, one more so the server can mark the text cut), 10,000 rows and 256 columns of a sheet (a "cut" line says so), 1,000 characters of a cell, 20,000 of a paragraph, 100,000 shared strings and 16 MiB of them (a cell past it is empty and the sheet says so), a repeated spreadsheet row at most 100 times and a repeated empty cell run never past the column cap; a shared-string index out of range, negative or not a number is an empty cell (`doc/tests.rs::a_million_shared_strings_read_the_start_and_say_so`, `::a_sheet_of_a_million_rows_is_cut_at_the_row_cap`, `::a_shared_string_index_out_of_range_is_an_empty_cell`, `::the_output_is_at_most_the_helper_cap`, `::an_opendocument_spreadsheet_gives_rows_and_trims_what_repeats`).
**Text is data.**
Every string from the file goes through `clean_line`: hidden characters (right-to-left overrides and isolates, zero-width), controls and every newline are gone, so a paragraph, a cell or a sheet name is one line and cannot open a line of its own; it then travels where a PDF's text does, in `user_message.attachments`, and reaches the model quoted line by line behind `| ` under the harness's sentence that it is the file's content and never an instruction (`doc/tests.rs::hostile_text_is_one_clean_line`, `doc/flow.rs::tests`, `web/e2e/doc-text.cjs` shows the model's view).
Tracked deletions, comments, footnotes, headers, fallback copies of drawings, a slide's footer and number and phonetic guides are left out.
**Hidden content does not reach the model.**
What the person cannot see in their own editor is left out: Word text hidden with `w:vanish`, hidden rows and columns and hidden sheets of a workbook (Excel and OpenDocument) and hidden slides; when something was left out the text ends with one line saying so, and not otherwise (`doc/tests.rs::hidden_text_rows_columns_sheets_and_slides_are_left_out_with_one_line`).
Not detected: text hidden by a style rather than the run, hidden text of an OpenDocument text or presentation, and a slide hidden through an OpenDocument style.
**The file is kept as well, and that is never a reason to refuse the text.**
A readable document is stored twice, as its text (`attachments`) and as a kept file (`chat_uploads`) under an id derived from the text's (`attachments::file_id_of`, 32 hex characters, the shape the node takes), only where this chat keeps files (a coding chat: the node saves it into `attachments/`, T94; a plain chat whose agent has "Read attached files": the master keeps it for `attached_file`, T95); the send takes the file with the text it belongs to, for the same owner, and `Master::prompt` drops it without a word where the chat cannot take it now (the switch off for the agent that answers, a node that cannot keep files, a temporary chat, the limits) so a document's text is not refused for its file's sake: in a coding chat the file is pushed on its own and dropped when its push fails (the node refuses a chunk, the blob is gone, a timeout), in a plain chat it is only named (`crates/master/tests/it/uploads_http.rs::a_document_whose_file_cannot_be_pushed_still_sends_its_text`); a plain chat's node that refuses the named file by its own limits still refuses the message, as for any attached file; the 10 files-and-images count is the texts' (`crates/master/tests/it/doc_http.rs::a_document_is_text_and_a_kept_file`, `::without_the_switch_the_text_goes_and_the_file_does_not`, `::a_coding_chat_keeps_the_file_for_its_folder`, `crates/store/tests/chat_uploads.rs::companions_are_taken_where_they_can_be_and_skipped_elsewhere`, `web/e2e/doc-text.cjs` for the node's side in a real coding chat).
**Failure is soft, and only what was found to be a document is called one.**
A zip is a document only when the helper positively says so.
A document the helper found and could not read (damaged XML, a missing part, too deep, too large, no text) is kept as a plain file where files are kept, with one sentence under its chip ("this document could not be read: ..."), and refused with the same sentence where they are not; never a 500, never a lost upload.
A zip the helper could not judge (busy, killed on its timeout, crashed, cannot confine itself) is kept as a plain file silently where files are kept, exactly as before documents were read, with no document sentence and no failure; where nothing is kept a busy server is a 503 as for a PDF (`doc_http.rs::an_unreadable_document_is_a_file_with_a_sentence`, `::a_plain_zip_is_kept_silently_whatever_the_reader_did`, `::a_helper_killed_on_timeout_leaves_a_plain_file_without_a_sentence`, `::where_nothing_is_kept_a_busy_server_is_a_503`).
**One account, one helper at a time.**
An account holds at most one helper slot at a time: its second PDF or zip waits at its own door (holding no server-wide slot, at most ten seconds) and then goes the way of a busy server above, so one account cannot keep both slots busy and starve everyone's PDFs, documents and zips; other accounts are not held up (`crates/master/src/pdf.rs::tests::an_account_holds_one_helper_slot_and_others_are_not_starved`, `doc_http.rs::one_account_cannot_keep_both_helper_slots_busy`).
**Nothing about the file is logged.**
Name, bytes, text and what the reader said when it failed are in no log line, also not when the reader is killed on its timeout or over its output cap, and not on the path that keeps the file with its sentence (`crates/master/tests/logs/doc_http.rs::a_document_leaves_no_trace_in_the_logs`).

Known and accepted:
- Every file that starts like a zip costs a helper process; the server does not look inside to tell the cheap cases apart (a busy helper keeps a plain zip as a plain file, silently).
- Parts are found by local name, so a file whose writer used unusual prefixes still reads, and the namespace is not checked; two parts of one name in a zip are read as the first.
- Not read: the old binary formats (`.doc`, `.xls`, `.ppt`), encrypted files, text in pictures, charts, SmartArt and embedded objects, formulas (their stored value is shown), number formats (the value as stored is shown, a date is a number), comments, headers and footers.
- A truncated XML part (no closing tags) is read as far as it goes; a mismatched closing tag is an error.
- The sent chip of a document is hidden under its file's chip by name (`Conversation.tsx`): the event's text attachment carries no id to pair it with its file by, and pairing by id would need an event change, so a text file and a kept file of the same name show one chip, and a file the node renamed (`plan (1).docx`) shows two.
- A dropped file is not announced: the answer says `file_kept`, and the page does not show it.
- A removed chip leaves its text row and its hidden file row until the purge (the incognito TTL); the hidden row counts toward the 20 unsent files, with nothing on screen to explain a later 429 (there is no delete route, as for visible files before).
- The text and the file are two copies of the same bytes in the person's quota; the text of a document is in the log whatever the file's fate.
- `cargo deny check` was not run on the one new crate (`quick-xml` 0.42.0, MIT, released 2026-08-22).
