# T42

## Threat

An older build opens a database a newer build wrote (a downgrade, a node update rolled back, a copied data directory) and acts on it without what it cannot know: a newer column that restricts access is ignored, a newer table is never consulted, or the older build "repairs" the schema and the newer build can no longer open it

## Mitigation

Every database carries `PRAGMA user_version` (fix plan 4.3, `crates/store/src/migrate.rs`).
A build that finds a version above its own refuses to start with `<file> was written by a newer rizzy-harness (schema version N; this build knows up to M). It was not changed`, and the check runs before any pragma or statement writes, so the file stays byte-identical and the newer build still opens it; a negative version is refused the same way.
Pending migrations and the version bump are one `BEGIN IMMEDIATE` transaction, the version re-read under the write lock, with foreign keys off for its length (a table rebuilt the way SQLite documents it would otherwise cascade its DROP into every child row) and `PRAGMA foreign_key_check` required empty before the first step (a reference that already dangled is refused as such, naming both tables, not blamed on the migration: `a_reference_that_dangled_before_the_migration_is_named_as_such`) and again before the bump: a failing migration, a dangling reference, a full disk or a crash mid-migration leaves the file as it was.
A second opener waits for the file at most its busy timeout (5 s) and is then refused unchanged, saying another process holds the file, whether the lock hits the version read (a committing writer on a rollback-journal file), `BEGIN` or the commit (`a_database_held_by_another_writer_is_refused_as_busy_and_left_byte_identical`, `a_rollback_journal_file_held_by_a_committing_writer_is_refused_as_busy`); what keeps a second `serve` or `node` off the directory is the data directory lock (A.20), not this wait.
Tests: `store/tests/migrations.rs` (`a_database_from_a_newer_build_is_refused_and_left_byte_identical`, `a_failing_migration_leaves_the_file_byte_identical`, `a_table_rebuild_migration_keeps_the_rows_that_reference_the_table`, `a_migration_that_leaves_a_dangling_reference_fails_and_leaves_the_file_byte_identical`, `a_store_from_a_newer_build_is_refused_and_left_byte_identical` for `master.db`, `chat.db`, `node.db`), `memory/tests/schema.rs`.
**The version is trusted only with the schema** (review R43-2): a file at a version this build knows must have that version's recorded schema (`schema/<n>.sql`, without SQLite's own objects), and a migrated one must end with it before the bump, or it is refused with `<file> does not match schema version N (…). It was not changed`: a pre-release file whatever its version (an old-shaped version-0 file is not stamped 1), a `memory.db` copied in place of a `node.db` and the reverse, a hand-edited file (`a_store_whose_schema_is_not_its_versions_is_refused_and_left_byte_identical`, `an_unversioned_file_with_old_tables_is_refused_and_left_byte_identical`, `memory/tests/schema.rs`).
**The whole data directory is checked first** (review R43-3): `serve`, `node run` and `node join` read the version and schema of `master.db`, `chat.db`, `node.db` and `memory.db` through read-only connections right after taking the data directory lock, before anything is created, migrated or swept, so a newer file found last does not leave the ones before it migrated, and a crashed newer build's WAL is not checkpointed into its file (`cli/tests/schema_preflight.rs`, `the_preflight_leaves_a_crashed_newer_builds_wal_alone`).
The preflight does not change a database file; beside a WAL database SQLite's read-only connection leaves an empty `-wal` and a `-shm` (re-check D2, the CLI test's WAL case).
A file the read-only connection cannot judge because SQLite must first roll back a hot journal or recover a WAL (`SQLITE_READONLY_ROLLBACK`, `_RECOVERY`, `_CANTINIT`) is passed on: the real open recovers it and then applies the same version and schema checks (re-check D1: an interrupted first creation was refused on every start; `the_preflight_passes_on_an_interrupted_creation_and_the_real_open_recovers_it`, `serve_starts_on_a_data_directory_whose_first_creation_was_interrupted`).
For a newer build's file that recovery writes the file, but it is the recovery the newer build would make itself, and the file is then refused at its committed version (`a_newer_file_with_a_hot_journal_is_still_refused_by_the_real_open`).
A migration is logged before and after, naming the file and both versions (`a_real_migration_is_logged_before_and_after_and_a_creation_is_not`); a second opener that finds the file migrated under the write lock runs nothing (`a_file_migrated_by_another_process_while_this_one_waited_is_not_migrated_again`).
**Residual:** nothing-half-applied holds per file, not per data directory: if one database migrates and a later one then fails its migration (a full disk, a migration that trips on that file's data), the new build fails on every start and the previous build refuses the migrated file (the `Failed` message says so);
SQLite gives no atomicity across files in WAL mode, and a copy before migrating (fix plan 4.4) is what makes a failed upgrade reversible.
The recorded schema guards a released migration's tables, not its data statements: a backfill `UPDATE` or `INSERT` changed after release passes `check_recorded`, and only review catches it.
The preflight is the only read-only path: a direct `Store::open` of a newer WAL file still checkpoints it on close (same rows, other bytes).
The schema says which kind of file, not whose data (one node's `node.db` copied to another node opens); a node update rolled back after the new build migrated `node.db` leaves a node the previous build refuses to start (docs/node-update.md §6.3); a version-0 file that already has tables is adopted as version 1 only when its schema is exactly version 1's (a dev file from just before this change; `an_unversioned_file_with_exactly_version_1s_schema_is_adopted_as_version_1`), and is otherwise refused as not matching version 1 with the advice to remove the data directory, also where migration 1 would trip on the old tables (`an_unversioned_file_whose_tables_break_migration_1_is_refused_as_a_mismatch`).
