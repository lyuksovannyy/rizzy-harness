# T30

## Threat

A crash, `kill -9`, full disk or cancelled turn in the middle of `edit` or `write` leaves the user's file truncated or half-written, with nothing to restore it from if no checkpoint holds it (ADOPTION_PLAN A.8)

## Mitigation

`edit` and `write` replace files atomically (`tools/src/fs.rs`, `replace_with`), in the node process (not in `sandbox-exec`): the parent directory is opened once and every step is relative to it; the target must be absent or a regular file opened `O_WRONLY\|O_NOFOLLOW` (a symlink is refused, a read-only file stays unchanged); the bytes go to `.rizzy-harness-write.<128-bit random>.tmp` created `O_CREAT\|O_EXCL`, mode 0600, which is flushed, given the target's permission bits (new file: 0666 less the umask read from `/proc/self/status`), `fsync`ed and `renameat`ed over the target, then the directory is `fsync`ed; the temp file is unlinked on every error path (RAII guard) and the work runs in `spawn_blocking`, so a dropped turn does not stop it halfway.
Just before the rename the target is `fstatat`ed again without following links: a different inode, a symlink or a newly appeared file aborts with nothing replaced.
A directory the node cannot write is an error, never an in-place fallback.
Tests in `fs.rs` (`mod atomic`: a write failing halfway keeps the original byte-identical with no temp file; 0640 kept; symlink refused; link swapped in mid-write refused; new-file mode; read-only file and read-only directory refused).
**Residual:** the re-check and the rename are two syscalls, so a symlink swapped in between is *replaced* by the new file (never written through; the link's target is untouched); `edit` reads by path and writes by the directory handle, so a change between its read and its write is lost (staleness is T.2); setuid/setgid bits, ownership, hard links (split), extended attributes and ACLs, and a directory's default ACL for a new file are not kept; a `kill -9` between create and rename leaves a recognisable temp file.
