# T52

## Threat

**The context block is in the log** (ADOPTION_PLAN X.1): to keep the provider's cache across turns, what a turn sends besides the person's words (the repository's instruction files, the list of skills, the chat owner's memory facts, a project's brief, facts and board, the person's settings line, MCP notes) is now recorded in the session's log (`context_sent`) on the node and in the master's mirror, where before it was sent and dropped.
So the log holds text it did not hold: the owner's memory facts and project text at rest on the node's disk and the master's, a secret in an instruction file or a fact could be written there, a section could be large enough to fail its own append and wedge the chat, and a block that changes the bytes of an earlier message, or a forged one, could steer what later requests say

## Mitigation

**Written by the loop through the session's one writer**, only from what the node and the master gave the turn (never from model output), after the message and before any answer; a turn whose record cannot be appended ends there, as any failed append does.
**Scrubbed before it is sent:** every section passes the node's secret set first, as tool output does, so the message and its record are the same bytes and no secret reaches the model or the log (before X.1 the files and the master's context reached the model unscrubbed).
**Bounded:** each section is cut at 256 KiB (`context::SECTION_CAP`) before it is sent and recorded, far under the 4 MiB event limit, whatever a master sends; the caps where sections are made stay (instruction files 32 KiB, skills 8,000 bytes, memory 3,000 characters plus recall).
**Read paths:** the mirror's events are served only through `visible_session` (HTTP) and `may_see` (WebSocket), both `Principal::can_see`, so a chat's log, with the owner's facts in it, is the owner's alone in every workspace, for admins too (the server's API token, which sees every chat, sees these too, as it sees every message); search, titles, earlier-chats and routine reads select `user_message`, `assistant_message` and `history_summarized` by kind and never read it; the UI's fold ignores it (`view.rs`, `web/src/fold.ts`); a sub-agent's log holds its parent turn's context and belongs to the same owner.
**What is a section (reviews R4, F1):** every part of the master's context is a section of its own key, so the history holds only its current version: the chat owner's Personalisation, the fixed sentences of their reply choices and their personal instructions in their own words (`personal`, T74: not memory, so a turn without the master's context keeps it; the owner's settings whoever sends; absent for an agent whose switch is off and in an untrusted turn), each place's fact list with its header (`memory`, `workspace`, `project_memory`), what `remember` does in the chat (`remember`), the project's brief (`project`) and its board (`board`), which change rarely and are sent again only then (a moved card re-sends the board alone, a colleague's change to a team's shared memory that memory alone); and the parts that change with the message, each place's recall lines past its cap (`memory_recall`, `workspace_recall`, `project_recall`), the saved-memory counter with the notes on earlier `remember` calls (`memory_notes`) and a project chat's first-turn earlier chats (`earlier_chats`), which replace their earlier copy whenever they differ and leave the history, without a sentence, when a turn has none.
A turn where recall lines change therefore writes the cache from the previous opening, what `main` paid every turn before X.1. Only what is not derived from memory or project content is this turn's own for good (`turn`): the settings line (with the Profile's About you, T74), a `/skill` line, MCP notes, a "not read this turn" note.
**Callback turns and queued-only turns (reviews F2, M1, H1):** a callback turn is sent, by the master, the standing lists computed for the chat's agent and owner exactly as a person's turn of that agent reads them (`MasterContext::unattended`): when they did not change nothing is sent or withdrawn and its request extends the last one; a list switched off or changed is withdrawn or replaced as in a person's turn, with its recall lines and notes; the parts keyed on a message (recall lines, notes, earlier chats) and the `remember` line are not given and say nothing, so they stay where they are unless their place changed, and leaving them does not move the prefix.
Its grants stay withheld (`recall`, what `remember` may file).
An untrusted (webhook) turn reads no memory.
A turn that only reads queued messages is sent the master's context of the newest of them, which the node keeps in memory, only when that context was computed for the agent that runs the turn and the message was queued during the turn that just ended (otherwise, and after a restart, it is sent none); a turn with no context from the master withdraws every memory-derived section and keeps the brief and the board; each fact list's header says the bracketed ids are for `replaces` and `forget` only, never shown in an answer.
**Rebuild:** the opening is rendered from the recorded sections by the same code that sent it, without the standing sections a later record (or the turn being built) sent again or withdrew, so a memory-off agent (an `@mention`, the Agents-page switch, a team workspace where the person keeps memory out, an untrusted routine turn) reads none of the facts and a forgotten or corrected fact is gone from the next request (review R1, R2); a failed or timed-out read of the files or skills withdraws nothing and says so for that turn only (R3); in a sub-agent's session no earlier task counts as the person's words (R7); the block is capped at 1 MiB as rendered (R8); the frame is one paragraph of quoted lines under the harness's lead (T43), and the person's own words of an earlier message are read after it (`context::earlier_own_words`), so nothing in a block is URL provenance (T22) while the person's earlier words count again (the environment line had stopped them counting since PR 96).
Tests: `agent-native/tests/context_log.rs` (byte-for-byte over three turns with a restart between each; the cached prefix measured; unchanged, changed, withdrawn and returning sections; no withdrawal on a turn without the master's context; everything again after a summary, and after one mid-turn; a log without records; the cap; a secret; two sub-agents; a turn that only reads queued messages; earlier own words), `node/tests/repo_instructions.rs` (`a_file_changed_during_a_turn_waits_for_the_next_turn`), `agent-native/src/callback_tests.rs`, `core/tests/fold_fixture.rs` with `web/src/fold.test.ts`.
**Residual:** the owner's memory facts and project text sent to a chat stay in that chat's log on the node and the master until the chat is deleted, after the fact is forgotten or edited, the person leaves the workspace or a teammate deletes a project fact (they are no longer sent to the model; the model's earlier answers could quote them anyway); a callback turn reads the standing memory a person's turn of the chat's agent would, never more (it writes none and cannot recall); in a callback turn the last message's recall lines, notes and earlier-chats lines leave only with their list, so an older fact (one outside the carried list) forgotten after that message, or project memory switched off for a project that has no confirmed facts, is still in that callback turn's request and goes with the person's next message (it is text this agent was already sent in this chat; the master does not say which places a callback may read, only what their lists are); an earlier `recall` or `remember` tool result that quotes a fact stays in the history as a tool result after memory is switched off or the fact forgotten, like the model's own earlier answers; a node's operator could read them in transit before and can read them at rest now; in an agentic chat the master's line names the person and their zone and no clock (the node's environment line has the clock; review R10), in a plain chat it holds the clock to the minute; a section that keeps changing (recall that matches each message differently, a busy board) is sent in full each time it changes and stays in the history until the next summary.
