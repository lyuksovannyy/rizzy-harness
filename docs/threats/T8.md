# T8

## Threat

MITM on the node link

## Mitigation

WSS with the master's certificate pinned by fingerprint on the node (no CA, so a mis-issued certificate is not enough), and the node's Ed25519 key pinned on the master: the node signs a fresh master nonce bound to that fingerprint, so its signature cannot be replayed to or relayed through another endpoint.
The master authenticates only through TLS (it signs nothing itself).
Both directions are bounded queues with back-pressure, and the node times out connect and handshake (§3), so neither end can make the other buffer without limit or hang it.
A registered node cannot make the master store or list without limit either (Gate 3 review L-3): an event over `MAX_EVENT_BYTES` (4 MiB) is refused and freezes its session, the strings it supplies for the row are capped (title cut to 200 characters; `cwd`, model and agent id refused past 4096, 256 and 64 bytes), and session listings filter by owner in SQL instead of loading every account's rows (§3; `an_event_over_the_size_cap_is_refused`, `an_oversized_event_from_a_node_is_refused_and_freezes_the_chat`, `a_listing_of_one_owner_reads_only_their_rows`).
The master's certificate is made only when neither `keys/master-cert.der` nor `keys/master-key.der` exists; any other read error, or half a pair, stops the server with the path and the reason, because a new pair would silently break every node's pin (R.4, review N-4; `link/src/tls.rs` `an_unreadable_master_key_stops_instead_of_making_a_new_one`).
Residual: the board and project-memory pages still read every row to resolve card and proposal owners (bounded now by the caps); the event log itself grows as fast as a node writes in-order events (a quota per node is not built).
