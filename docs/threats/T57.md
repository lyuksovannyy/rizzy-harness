# T57

## Threat

An undo or rewind silently reverts work the turn did not do: two chats work in one folder (two people of a team, or one person with two chats), chat B changes a file while chat A's turn runs, and because a turn's checkpoints are snapshots of the whole folder, B's change is part of A's `after`;
A's undo passed the changed-since check (which looks only after the turn) and put the file back, B was not told, and the only copy was A's `before_restore` checkpoint, which B cannot reach (first live test with real models, 2026-11-15).
The same for a rewind, which also spans the time between A's turns, and for a chat deleted (or purged) after its work, whose log goes while its changes stay.
A prompt-injected agent in one chat could also try to use any such check to block another person's undo for good

## Mitigation

**An undo never silently reverts another chat's work** (`node/src/others.rs`, called from `Session::restore` before anything is written).
**The window** is the undone span: from the undone turn's `turn_started` (written before its `before` snapshot scans the folder; for a rewind, the first undone turn's) to the checkpoint of the state the undo expects (its `after`, or the latest state for a rewind: after it the changed-since check compares content); an interrupted restore has no such state and looks until now.
A call counts when it ran at any time in the window (started by its end, ended at its start or later), so a write that landed before the `after` snapshot counts even if its result was logged after.
**What counts**, from the logs of the other chats on the node whose folder overlaps the checkpoint's (and, of the undoing chat's own sub-agents, only the turns its `delegate` calls did not start: a person's message to a sub-agent's chat, a background sub-agent's work outside the chat's own turns; what a turn started by its call wrote is the turn's own; the delegation's first turn is the chat's first, which the node enforces: no other turn can be the first one of a sub-agent's chat, `Session::guard_first_turn`): files their `edit` and `write` calls wrote (`tool_call_finished.seen`) and files their own undos wrote are **certain**; a call of any tool not known to write nothing (a shell command, a sub-agent's merge, an MCP tool; unknown tools count as writing) makes the files its turn changed, by that turn's checkpoints in that chat's own store (paths mapped to this folder), **maybe**, or every file the undo writes when that turn has no checkpoints; a background command running in the window, and a **write tombstone** of a deleted chat overlapping it, make every file the undo writes maybe.
**What the undoing chat's own calls explain is dropped from every maybe set:** each `edit`/`write` records the hash of what it replaced (`FileSeen.base`, `""` for no file); a file whose `before` content is the first call's base, each result the next base, and the last result its `after` content, holds nothing foreign.
**A write tombstone** is written on the node in the same transaction that deletes a chat (a person's delete, or the incognito purge, which goes through it; an incognito chat cannot work in a folder anyway): the real path of the chat's folder and the time span of its file-changing calls, background commands and undos, nothing else (no id, title, text or file names); none for a chat that only read.
A tombstone is removed when an undo of that same folder finds it older than the oldest checkpoint kept there (no undo can reach before that); one for a folder with its own checkpoint store elsewhere stays until an undo there does (a few short rows).
Of the files the undo writes, any so named refuses the undo with nothing changed and nothing logged, naming the files and saying only "another chat" (no title, text, id or person: chats are private to their owner, and the node does not know owners), with its own sentence per kind (edits, commands, a background command, a chat deleted since), alongside the changed-since refusal when both apply.
The turn's diff view (X.12) names the same files before the click, certain and possible apart (`TurnDiff.others_wrote`, `others_may`).
**"Undo anyway" stays** (`force`), so no chat can block another's undo; a forced undo appends to each such chat a line naming the files attributed to it inside its own folder (or, when only "any file" applies to it, a sentence without a list), with nothing about the undoing chat, never naming files only the undoing chat's own chain explains, and then notes in the undoing chat that it put back another chat's files, saying "told" only for notes that were written.
Nothing is held in memory: it holds across a restart.
With one chat in a folder no log is read; measured at 22 ms per undo with one chat, 27 ms with a second chat of 300 turns that ended two hours earlier, 72 ms when all 300 ended within the hour (slow disk, `cargo test -p harness-node --test undo_other_chats cost -- --ignored`). Tests: `crates/node/tests/undo_other_chats.rs`, unit tests in `others.rs`.

## Column 4

The other chat cannot get its content back by itself: it is in the undoing chat's `before_restore` checkpoint, which only that chat reaches; its line says to make the changes again (its agent's `edit` guard also refuses to build on the stale picture, T45); a "put back this chat's version" action for it, limited to the named files and served from that snapshot, is the follow-up.
A crash between the restore's writes and those lines loses the lines.
The person's own edits during a turn are still the turn's (no per-write record).
A shell command of the other chat is attributed by its turn's whole span, so a file the undoing turn changed during that span with a shell command, or with a chain something else broke, is named too (a refusal the person passes with "Undo anyway"); a background command or a deleted chat names every file not explained.
Writers outside overlapping folders are not seen: a host-mode chat in a sibling folder writing here through an absolute path, or one allowed outside its workspace (`allow_outside_workspace`), and chats on other nodes sharing the folder over a network file system.
The window is by the node's wall clock (`ts_ms`): a clock step backwards can hide work from it (a node-wide monotonic mark would need every event to carry it, not done).
