# T29

## Threat

A script, or anyone who gets a copy of the one static API token, reads or drives every user's chats (an accepted gap against "chats are private to their owner, for admins too", A4 of the final review)

## Mitigation

**Not fixed; recorded.**
A request with `Authorization: Bearer <token>` that matches the 0600 `<data>/api-token` file becomes `Principal::api_token()`: `Role::Admin`, `can_agentic`, `user_id: None` (`auth.rs:121-128`, `:740-751`), and `can_see` is true for `user_id: None` (`auth.rs:137-143`).
So the token lists every chat (`list_sessions`, `http.rs:1062`), reads one and its events (`visible_session`, `http.rs:317-326`, used by `get_session`, `events`, `delete_session`), sends prompts (`prompt`, `http.rs:1314`), approves tool calls (`approval`, `http.rs:1435`), cancels, restores, and opens a WebSocket that streams any session (`ws.rs:190`, `may_see` at `:305`); routines, media, projects and artifacts use the same `can_see`.
Its agentic grant is unconditional and workspace checks treat it as owner (`workspaces.rs:312`), so approving a tool in someone's chat makes that person's node run it.
Every `require_admin` endpoint accepts it (`http.rs:295-301`): users, providers, nodes and join tokens, workspaces, storage, memory settings.
It has no password, so `change_password` refuses it (`http.rs:562-572`); the webhook handler never accepts it (`hooks.rs:19`).
The `Origin` rule does not apply: `needs_origin` is false whenever `Authorization: Bearer` is present (`auth.rs:804-820`) and `guard` lets it through without `Origin` (`:793-796`).
A given `Origin` is still checked against the allowlist, as is `Host`.
That is right for a non-cookie credential (a cross-site page cannot set `Authorization`, so there is nothing to forge), but it means the token is only as safe as its file and the hands holding it.
A bad `Bearer` is refused outright, not retried as a cookie.
At rest: `<data>/api-token`, mode 0600, checked at start (T26); 32 random bytes, constant-time compare.
It is never read from a URL (only the header), is in the redaction set for events and tool output (`cli/main.rs:244-248`), and the data directory is closed to sessions (T10); `rizzy-harness token` prints it (`cli/main.rs:864-868`, file path `:633-635`).
No per-request log line records which requests used it.
**Accepted until per-user, scoped tokens exist** (adoption plan T.5, after fix plan 4.1); scoping this one now would break the README's script uses.
**Operator, meanwhile:** treat the token as an admin password and as read access to every chat; do not give it to automation that needs one user's access; if no script needs it, do not print or copy it (the file is created at first start either way); rotate it by deleting `<data>/api-token` and restarting.
**Committed test for T.5:** user A's token cannot read user B's chat.
