# T82

## Threat

**A repository's own MCP servers** (ADOPTION_PLAN X.36, README "A repository's own servers (`.mcp.json`)", docs/projects.md; the owner, 2026-11-17: "threat those more as repo/project mcp", and a manual Reload instead of a file watcher): a project folder's `.mcp.json` names programs the node would start for chats there.
Anyone who can write the repository (its agents included) could make the node run a program; abuse cases: (a) the feature off, the file is read or a server of it starts; (b) the agent rewrites the file (another command, a new entry; a link, a FIFO, a huge file, a folder in its place) and its next turn, a new chat or a node restart starts the new text; (c) the file changes between the list a person saw and their click; (d) the person approves text they cannot fully see (a cut string, a line break, a hidden or direction character, padding: review of PR 150 H2, a 3,192-character argument shown as its first 2,048 ran a hidden `touch`); (e) one person's approval starts a server in another person's chat in the same folder; (f) a `host` chat starts one (**allowed by the owner's decision of 2026-11-20**: "if user selected host project workspace, why do we need to limit it? its his choice"; it was refused at first; what stays true there is under Residual); (g) `${HOME}`-style variables pull the node's environment into a server, an entry's `env` (`LD_PRELOAD`) reaches a process outside the sandbox (the guard, bubblewrap), or its values appear in a command line any local user can read (review M3); (h) an entry shadows a node.toml server by name or look-alike; (i) the approved copies are read or written from a chat's file view or shell (with the default `[sandbox] mode = "required"` Landlock keeps the data directory out of a sandbox chat's and a host chat's shell: `cli/tests/exec_modes.rs` `a_host_chats_shell_cannot_read_or_change_the_data_directory`; **the exception is `[sandbox] mode = "off"` with `[execution] host = true`**, where a host chat's shell is the node's own user with no file rule and reads and appends to `project-mcp.json` and lists the data directory (other people's chats, the master API token, the blobs, the keys): a forged approval written from such a chat started a server, after a node restart, in another person's sandbox chat; this predates X.36 (the store was writable there before) and is the property of that configuration, said in README and `docs/execution-modes.md`: use it only where everyone who may open a host chat is trusted like the node's owner; the node's start and `doctor` warn about the combination, `cli/tests/contain.rs` `doctor_warns_where_a_host_chat_can_reach_the_data_directory`); (j) repository values change other chats (review H1: added to the node-wide scrubber, values equal to event field names rewrote other users' `session_created` keys and the node did not start again); (k) a lying master; (l) a member who may not run agent chats there, another workspace's project, a project without a folder, a node away; (m) a 10 MB file, 10,000 entries, a storm of requests; (n) an approvals file the node cannot use

## Mitigation

**Off unless node.toml says `[mcp] project_servers = "ask"`** (`node/src/policy.rs` `McpPolicy`): off, the runtime has no `ProjectMcp` at all, no code path reads `.mcp.json`, `project.mcp` is refused and `project-mcp` is not announced (`off_reads_nothing_and_announces_nothing`: a FIFO at the file's name is never opened).
**A person's act, per person:** the master relays `project.mcp` (`user_id`, the project's `folder`, `List`/`Approve{name, digest}`/`Remove{name}`; nothing names a program) only on a person's HTTP call (`http/projects/mcp.rs`), for a member of the project's workspace who may run agent chats on its node (`folder::may_make_on`, the rule of the project's folder), never the API token; nothing a turn, tool or model does sends one.
The node checks the folder as a chat's (`check_cwd`), the user id's form (`valid_user_id`: ASCII letters, digits, `-`, `_`, at most 128), answers two requests at a time (also on a node that offers only host chats, which it refused until 2026-11-20) (the master 30 a minute per person and node, 2 in flight per person, 16 in all).
**The file** is opened without following a link (the folder `O_DIRECTORY | O_NOFOLLOW`, checked to be its canonical path through `/proc/self/fd`, then `openat(".mcp.json", O_NOFOLLOW | O_NONBLOCK)`, a regular file on the descriptor, at most 64 KiB), the standard shape, at most 32 entries (more: unreadable), 8 KiB of JSON, 64 arguments and 64 `env` names per entry; unsupported, never approvable: remote (`url`, `type` http/sse), `${`, a field other than `type: "stdio"`, `command`, `args`, `env`, an `env` name that is not a variable name or is `HARNESS_*`, a name outside `valid_mcp_server_name` (ASCII lowercase: no case or look-alike variant of a node.toml name); a name node.toml has is hidden, also when node.toml takes it after an approval.
**What is shown is what is hashed and runs** (review H2): an entry is approvable only if every string of it (command, each argument, each `env` name and value) would be shown whole and unchanged (`project_mcp::unshowable`): at most 512 characters each and 4 KiB together, **printable ASCII (0x21 to 0x7E) and single spaces only** (`harness_protocol::first_unshowable`; re-check of PR 150 NEW-1: U+00AD, U+034F, the Hangul fillers, U+2800, U+180E, variation selectors, stacked combining marks, Cyrillic look-alikes and every line break, control, hidden and direction character draw like other text or like nothing, and `--require ./saf<U+00AD>e.js` drew pixel-identical to `./safe.js` in the real page), no space at either end or two in a row, no empty argument; the reason names the first other character by its code point, never printing it; checked when the list is read and again at approve time (the approve reads the file again); the node sends those strings whole (`env` values too: repository content and part of what runs, `NODE_OPTIONS`/`LD_PRELOAD` making a harmless command repository code), the master passes the list whole or refuses it whole (`ProjectMcpList::showable`, shared by both: 64 entries of 64 parts, every entry string printable ASCII of at most 512 characters, so a lying or buggy node cannot show a look-alike), the page shows the command, each argument on its own line and each `NAME=value` as text, nothing joined, quoted or cut; an unsupported entry is shown with every non-ASCII character as its `\u{…}` escape, cut with a mark, at most 63 parts and a count of the rest, carries no digest, and its reason quotes at most 64 characters of the key it names, so no bad entry makes the master refuse the list (re-check NEW-2: a 499-character unknown key made a 583-character reason that blanked the person's whole list; `the_worst_entry_never_blanks_the_list`); notes and the file's state are cut to 480 characters.
**A stated limit:** honest non-ASCII paths and values cannot be approved in this version.
**Approval** is keyed (user id, the folder's real path, name) and holds the node's own copy (`project-mcp.json` in the data directory, 0600, written to a new file and renamed; read back only as a regular file of the node's user with no group or other bits): taken only if the file's entry still has the sha256 digest of exactly the strings shown (`a_change_between_the_list_and_the_click_is_refused`, `a_padded_command_line_cannot_be_approved`); at most 32 per person and folder and 1,000 per node;
Remove is always allowed, by the stored path when the folder is gone.
An approvals file the node cannot use fails closed and loud: nothing of it is taken, the log says why, approve and remove are refused naming the file, nothing is written over it; a remove whose write fails is refused and the approval stays (`an_unusable_store_refuses_approve_and_remove_and_is_not_overwritten`, `a_remove_that_cannot_be_saved_keeps_the_approval`).
**Whose chat:** `owner` on each turn command (`session.prompt`, `session.retry`, `session.callback`), set by the master from the chat's row in `send_command` whoever builds the command (`a_turn_carries_the_chats_owner` over HTTP for a prompt, `turn_owner_tests::every_turn_command_carries_the_owner` for all three), kept in the node's memory, never in an event (no schema change: the servers start lazily at a turn, which carries the owner; after a restart it is learned at the chat's next turn); a malformed one refuses the turn (`a_malformed_owner_on_a_turn_is_refused`); the node checks the id's form only, which account it names is the master's word.
**What runs is the copy:** each turn's table (`Session::sync_project_mcp`, before the loop loads its servers, and at once for every loaded chat of the folder after a person's request) gets the chat owner's approved copies for exactly the chat's folder (a sub-agent uses its chat's table, X.34 step C; none without an owner), less a name the node's last read of the file did not find (a person's request, or the one read per chat when its owner is first learned since the node started; never per turn; an unreadable file changes nothing), in a `host` chat as in a sandboxed one (since 2026-11-20; an entry with `env` values is not started there, and the chat is told which server and why: `mcp::start`, `env_values_are_shown_and_start_only_contained`); a changed entry runs its approved copy, a new one nothing (`the_approved_copy_runs_whatever_the_file_says_later`).
A server taken out of the table is stopped and never started again from it.
That holds also when the removal lands while it is starting: its stop order is reachable by the removal and by the chat's close from the moment it is spawned (`Slot::register`, under the lock `retire` takes), it is stopped through the same stop path as a published process (the guard confirms it in a sandbox chat), and the starter is told the server was removed, whatever way the start then ended, with nothing counted (`a_removal_stops_a_server_that_is_still_starting`, `a_start_that_fails_after_the_removal_is_told_as_a_removal`, `a_server_taken_out_while_it_starts_does_not_stay_up`, `a_removal_during_a_start_leaves_no_process_and_says_so`, `removals_racing_starts_leave_nothing_running`).
A call in flight when its server is removed, and every call after, is told that the server is no longer one of the chat's servers (the one in flight adds that whether it was carried out before the server was stopped is not known); the stop was ours, so it counts nothing against the restart limit and announces no restart, and a call made after the removal never reaches the process even in the instant before it dies (`a_call_in_flight_when_its_server_is_removed_gets_the_removal_answer`, `a_call_after_the_removal_never_reaches_the_server`).
A call that passed the removal check just before the removal can still be sent to the server that is being stopped, and the server may carry it out.
Everything of T47 holds: the chat's own `Confinement::shell`, the caps, the idle stop, one process per chat, every call `Mutating` and asked about in `ask` (the card says "from the repository's .mcp.json, as you approved it"), the Connectors switch, `deny_mcp_servers` and `denied_tools` by name.
**Environment:** less than `bash` gets: the core allow-list only (no `env_pass`, no `env_vars`); the entry's `env` values reach the server's own process alone (review M3): the node writes them to a 0600 file in the node-private folder of the server's request FIFO (`mcp::write_inner_env`), the guard takes it only from exactly `<its --mark temp root>/.mcp-<16 hex>/env` (a plain absolute path, no `..`), opening the root without following a link at its name and the folder and the file relative to it the same way, and only a regular file of its user with one link, mode 0600 and at most 64 KiB, checked on the opened descriptor before the name is removed; anything else refuses the server and removes nothing (re-check NEW-3: a path in the variable made the guard delete any file of the user and pass `/proc/self/environ`; no layer can set the variable today, every one drops `HARNESS_*`, so this is hardening; `guard::tests::the_env_file_is_taken_only_from_the_nodes_own_place`); it leaves the descriptor to bubblewrap, naming only its number (`guard::ENV_FILE_ENV`, `guard::INNER_ENV_FD`), and `sandbox-exec` reads it before it closes what it inherited, refuses any `HARNESS_*` or malformed name (`sandbox::parse_inner_env`, `the_inner_env_takes_no_harness_name_and_no_malformed_one`) and sets the values on its `exec` of the server only, after the confinement (`sandbox::take_inner_env`); a file a killed node left before its guard took it goes when the next start empties the temp root (`sandbox::reset_tmp`, `a_left_environment_file_goes_at_the_next_start`); the values are in no command line and on no process before the server's (`project_mcp_e2e`: no process of the machine has the value in its command line or environment but the server's own); an entry with values starts only contained (`env_values_are_shown_and_start_only_contained`): in a `host` chat, which has no bubblewrap, it is refused for now with words that say so (the values could reach only the server's own process through a process of ours before it, and no host form keeps them off it yet; the design note in `docs/projects.md`), while an entry without `env` starts.
**Repository values are not secrets** (review H1): they join no scrubber, node-wide or per chat, so they change no other chat's events (`repository_env_values_change_nobody_elses_events`: values equal to event field names and a common word, another user's events stay decodable and the node restarts); the harness writes them into no event, log or audit line, and only the asking person's answer carries them.
**The master** writes an audit line per approve and remove (user, project, node, server, outcome; never command or environment); the node writes one too.
**A lying master** (it chooses `owner` and `user_id`): it can approve, for any account id, an entry a `.mcp.json` inside the node's `workspace_roots` holds now, and name that account as a chat's owner, so the entry runs in that chat: nothing beyond what it could already do by creating a chat there and approving its `bash` calls in the same mode, and only where node.toml says `"ask"`; it cannot name a program, an entry not in the file or a folder outside the roots; in a host chat (made where node.toml offers `host`) the entry runs as the node's user, nothing beyond what it could already do by creating a host chat there and approving its `bash` calls.
Tests: `node/src/project_mcp.rs` (shape, reasons, digest, the display rules, links, FIFOs, folders, 10 MB, 10,000 entries, the store's mode, an unusable store, a failed remove), `node/tests/project_mcp.rs`, `tools/tests/mcp.rs` (`a_repositorys_servers_come_and_go_through_set_project`, `a_server_taken_out_while_it_starts_does_not_stay_up`, `a_call_in_flight_when_its_server_is_removed_gets_the_removal_answer`, `a_call_after_the_removal_never_reaches_the_server`, `a_removal_stops_a_server_that_is_still_starting`, `a_start_that_fails_after_the_removal_is_told_as_a_removal`, `a_removal_during_a_start_leaves_no_process_and_says_so`, `removals_racing_starts_leave_nothing_running`), `protocol/src/lib.rs` (`project_mcp_messages_name_no_program`), `master/tests/it/project_mcp_http.rs` (who may, what is sent, the owner on a turn, whole or refused, floods, audit), `cli/tests/project_mcp_e2e.rs` (real binary, real bubblewrap; a host chat's server, and what it leaves after a `kill -9` of the node), the host variants in `node/tests/project_mcp.rs` (`a_host_chat_starts_an_approved_repository_server`, `a_host_chat_keeps_every_rule_of_the_approval`: cases (b), (c), (e), (h) and the removal on a node that offers only host chats; `a_host_chats_repository_server_ends_with_its_chat_and_the_nodes_stop`), `web/src/components/projectmcp.test.tsx`.
**Residual:** **a `host` chat's repository server** (owner's decision of 2026-11-20) runs as the node's own user without the sandbox, with that user's whole reach, in the node's PID namespace, started through the chat's shell like node.toml's host servers (T47); an approval the person gives for a sandboxed chat therefore also covers their host chats on that node, and the page says so beside the approval where the node offers `host` (`web/src/components/ProjectMcp.tsx`); its stop (the chat's deletion, the node's stop, ten idle minutes) kills the server's own process group only: a process it detached (`setsid`, a double fork) is not reached and keeps running (`tools/tests/mcp.rs` `a_process_the_server_detached_survives_its_stop`), and after a `kill -9` of the node the server ends only if it stops when its input closes (`a_host_chat_runs_an_approved_repository_server_and_what_it_leaves`: one that reads its input ended, one that sleeps on stayed), nothing of ours reaps it (T47, C.11); entries with `env` values are not started in a host chat (step 2 of the owner's request: a design note, no code); the approval pins the command, its arguments and its environment, not the files they run: an approved `./tools/server.py` or `npx package` can be rewritten or republished without a question and then runs with the chat's sandbox, no more (the owner's accepted leftover); approvals are keyed by the folder's path, so another repository cloned at the same path inherits them (its approved copies run only for names still in its file; a same-named entry shows as changed and runs the old approved copy until someone approves or removes it), and a renamed folder orphans its approvals (not listed, still counted toward the 1,000; Remove by the old path works); a request on a stalled folder is answered after 10 s but holds a blocking thread and one of the node's two request slots until the read returns, and one person can hold both slots; the node's last read of a folder's file is in memory, so after a restart an entry gone from the file is noticed only at the chat's first turn or a person's list; an approval of an account later deleted stays on the node (it starts nothing: no chat of that account exists); a request that changes the table mid-turn fails that turn's held tools of a changed or removed server until the next turn; the master's `owner` is trusted for which account a chat belongs to (as for every chat command); a sub-agent's turn is not tested separately here (it takes its chat's table, X.34 step C).
