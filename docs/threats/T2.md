# T2

## Threat

Malicious website in the user's browser (CSRF, DNS rebinding, cross-site WS)

## Mitigation

Accounts with Argon2id passwords; the first (admin) account needs a one-time claim code from a 0600 file.
A login is two values (Gate 3 review P-1).
The `HttpOnly; SameSite=Strict` cookie holds a random 256-bit session id.
Browsers send a cookie to **every port** of its host (RFC 6265 §8.5; `SameSite` ignores the port), so another local server, such as one the agent started on `127.0.0.1:8000`, gets the cookie when the person opens it, and a non-browser client writes any `Origin` it likes.
The login therefore also has a random 256-bit **login key**, returned once in the body of the answer that made it (login, the claim, a password change).
The page keeps the key in `localStorage`, which is per origin with the port, and sends it as `x-harness-login` on every request.
A custom header also forces a CORS preflight on any cross-origin script, and the server answers none.
A WebSocket sends the key as its first message (`{"type":"login",…}`) within 5 s: nothing is subscribed or sent before it, and without it the socket is closed with 4401. Nothing about the cookie is looked up before the key arrives (R.4, fix review 2 R2-1): the upgrade is answered 101 for any cookie, live, dead or made up, and each ends the same way without the right key, so the cookie's holder learns nothing; a socket waiting for its key takes none of the user's 8 places (those are taken once the key is accepted; a ninth keyed socket is closed with 4429, one whose account must change its password with 4403), and the waiting ones are bounded apart, 64 in all, the oldest pushed out (1013, try again) rather than a new one refused, since a page sends its key at once.
The key is never put in the URL or a subprotocol.
Only the SHA-256 of each value is stored (`ui_sessions.token_hash`, `bind_hash`), so a leaked database does not leak logins. `authenticate` is one indexed lookup joined to `users`.
The key's hash is compared in constant time before the session is used or slid.
A missing, expired or disabled login, or a wrong or missing key, gets the same 401. Logout ends that login's row with the cookie alone (R.4, fix review 2 R2-3; before, only with the key, so a page that lost its key, storage cleared, could not end its login for 30 days): ending a login never harms its owner and the answer is the same whether the cookie was live, so the worst a holder of the cookie can do is sign the person out of that one login, which it can repeat only after they visit its page again.
What the browser fetches by itself (`<img>`, `<video>`, `<audio>`, `<a download>`, the thumbnail maker's elements) carries a **link** from `POST /api/links`. A link is a MAC, under a per-process key, over the login's cookie hash, an expiry 30 min out, and the exact path and query.
It works only with that login's cookie and only on the byte routes (media content and thumbnails, artifact downloads, previews and thumbnails; `auth/links.rs`).
It holds no secret of its own, and only paths are ever logged.
The engine favicon (`/api/favicon`, an `<img>`) is one of those byte routes since R.4 (R2-1): it used to take the cookie alone, which made the server fetch from the network for whoever held the cookie and told them whether the login was live.
Tests: `master/tests/logs/login_binding_http.rs` (`a_cookie_alone_takes_no_socket_place_and_learns_nothing`, `a_logout_with_the_cookie_alone_ends_that_login`), including the abuse case end to end (a second client that holds the cookie and forges `Origin` reads no events and answers no approval), and `media_http.rs` `an_element_fetches_by_link_and_the_cookie_alone_gets_nothing`; the web side in `web/src/api.test.ts`, `live.test.ts` and `lib/links.test.tsx`.
**Residuals:** (1) a script running in the harness's **own origin** would hold both values; this is why no model HTML is ever rendered (T3) and why the key is no worse kept in `localStorage` than in `sessionStorage`. (2) A local process can still hold many waiting sockets (each for at most 5 s, 64 in all) and so delay, not block, a new socket of the person's page; it needs no cookie for that, as with any connection flood (T21). (3) A playing `<video>` keeps the link it loaded with, so seeking more than 30 min later fails until the preview is reopened. (4) A holder of the cookie can sign the person out of that login (R2-3, above).
A session ends 30 days after its last use (the expiry is moved at most once a minute); logout deletes its row, and a password change or reset, disabling the account and deleting it delete all of the user's rows, so a copied cookie stops working at the next request; the same paths close every UI WebSocket opened with those rows at once (close code 4401; logout closes only that login's sockets).
Each socket is registered under its user with its session's SHA-256 (never the cookie) before its first login check, and revocation flips that socket's own flag after the rows are deleted, so a socket still upgrading during a logout is caught by one or the other; it is not a broadcast, so a lagging socket cannot skip it.
A socket also re-checks its login every 60 s and before every subscribe, read only (an open tab does not slide the expiry; only HTTP requests count as use), which covers expiry and disabled accounts; a store error closes it.
Client WS messages and frames are refused above 64 KiB by the WebSocket layer before buffering; a user (the API token counts as one) has at most 8 sockets, the 9th upgrade gets 429 (refused rather than closing the oldest, which would make two tabs evict each other forever).
API-token sockets have no login to end and live until they close; unknown usernames are verified against a dummy hash, under the same hash permit and throttle slot, so timing and status do not reveal them (login limits: T12).
A separate 256-bit API token (0600 file) serves scripts as `Bearer`.
Every request checks `Host` against an allowlist (anti-rebinding).
Any `Origin` sent must be exactly `scheme://host[:port]` of an allowed entry with that entry's scheme: the server's own (`https` with `--tls`), or the one an entry names (`--allowed-host https://chat.example` for a TLS proxy in front; `X-Forwarded-Proto` is never read), so `null`, another port or the other scheme are refused.
A cookie-authenticated (no `Bearer`) state-changing request (not GET/HEAD/OPTIONS) or WebSocket upgrade without `Origin` is refused (403 `origin required`); `Bearer` clients, cookie-less logins and webhooks need none (audit L6; `master/tests/it/hardening_http.rs`).
Token compared in constant time.
Every route answers 401 to a caller with no credentials, a wrong token or a made-up cookie, bar a public list of five (setup, login, logout, the incoming webhook with its own secret, and the WebSocket that authenticates by its first message): `master/tests/it/route_walk_http.rs` reads the route table from the source, so a new route cannot be missed, and fails on any other answer.
The caller is identified before anything of the request is read: every route but the public ones sits behind one route layer (`http/caller.rs` `identify`), which answers 401 before the handler's first extractor, so no path, query or body is parsed and no body is read for a caller who is nobody (before, 85 routes and the attachment upload's query answered 400, 413, 415 or 422 with the framework's text naming fields; `docs/auth-by-construction.md`).
An unread body is not waited for: a body that has already arrived whole is drained by its framing and the connection is kept; one that has not is not read, and the connection is closed after the 401; `Expect: 100-continue` gets the 401 and no `100 Continue` (`an_unauthenticated_upload_is_refused_unread`).
A drained body is never read as a request: a refused POST whose body is itself a request, with `Content-Length` or chunked framing, followed by a real pipelined request gets exactly two answers, and the inner request none (`a_refused_body_is_never_read_as_a_request`).
The layer checks a link's MAC before it reads the store, so a GET with a cookie and no key costs no store read unless it carries a valid link (`a_link_is_checked_before_the_store_is_read`).
The layer takes a link only on a GET or HEAD, and `ByteCaller` again (`a_link_counts_only_for_the_byte_routes`, `a_link_passes_the_byte_extractor_only_to_read`).
A deliberate change in which error wins: a handler converted to the extractors answers a signed-in caller who lacks the right (a member on an admin route, a login that must change its password) with 403 before its body is parsed, where the old order answered a bad body's 400 or 422 first (decision 2 of the design note).
Every handler on a private route takes one of the four extractors first (`Caller`, `User`, `Admin`, `ByteCaller`); `require`, `require_any`, `require_admin` and `require_bytes` are deleted, so no handler checks its caller by hand and a route cannot answer before the role is known (the one place a role is applied after the body is a chat approval's allow and the agent editor's `?scope=server`, with today's sentences). `member_walk_http.rs` walks every route as each kind of signed-in caller, pins the admin-only, any-login and byte routes read from the code, and `the_written_lists_hold_over_http` asks the server for what the written lists promise with a valid body for every body route (a member gets 403 on admin routes, a login that must change its password gets 403 "change your password first" everywhere but the any-login routes; mutations that narrow or widen a role fail it); `the_layer_answers_as_require_did` compares every answer with a frozen golden file of what `require*` answered before the layer (`tests/it/auth_golden.txt`, which cannot be regenerated). A must-change login cannot raise a chat's approval mode or step limit (`a_login_that_must_change_its_password_cannot_raise_the_mode` and `…_the_limit`). `projects/mcp.rs` approve and remove now answer 401 or 403 before validating the name and digest.
**Accepted (R.4)** from the Gate 3 reads: the page's `seen()` (`web/src/api.ts`) keeps a `login_key` from any JSON answer; only login, the claim and a password change return one today, and a route that echoed a node's JSON at top level would let that node sign the person out (fix review 2 N-1; it would change if such a route is added: then take the key only from those three calls).
The key's safety in `localStorage` rests on no model or node script ever running in the origin, residual (1) above, which the CSP backs (fix review 2 N-2).
Not observed in a real browser (no Playwright where it was built, R.2): that a browser sends the harness cookie to another local port, and that element links load and download as intended; the e2e scripts that log in or download were updated without being run.
A Playwright run with two listeners would settle the first.
**Accepted (R.4, fix review 6):** R4-2: a local process that opens 64 socket upgrades within the one round trip the page needs to send its key pushes the page's waiting socket out (1013) and the page reconnects; it needs no login, only a cookie-shaped header and a forged `Origin`, and keeping the page out means tens of thousands of upgrades a second on loopback, where no per-source limit can tell it from the page.
N-1: the socket's key check uses the login like an HTTP request, so it slides the login's expiry, once per connect (never per message or per re-check); an open tab therefore keeps its login alive only by reconnecting.
Either would change with a socket that carries the key in its upgrade request, which a browser cannot send.
