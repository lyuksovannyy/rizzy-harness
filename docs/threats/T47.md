# T47

## Threat

An MCP server (ADOPTION_PLAN X.3) is a program the harness did not write, started on the node for a chat: a prompt, a master, a repository's `.mcp.json` or `.codex/config.toml`, or an agent spec adds a server (code execution by configuration: DeepSeek's settings RPC); the server gets the node's environment and its provider keys (Oh My Pi, Pi, Cline, Warp inherit it); it runs outside the chat's sandbox or outlives the chat, the node's stop or a `kill -9`; it labels a destructive tool `readOnlyHint` to skip the approval (goose); it floods the node with one endless line, a huge listing or a huge result, hangs at start or in a call, or dies in a loop; one chat's server serves another user's chat

## Mitigation

Servers come only from `[mcp_servers.<name>]` in node.toml, read at the node's start (`tools/src/mcp.rs`, `node/src/policy.rs`): no protocol message, HTTP route, tool or file in a session folder names one, and a tool name no server of the chat lists is an unknown tool.
That holds by default; with node.toml `[mcp] project_servers = "ask"` a repository's `.mcp.json` entry runs too once a person approved it, as the node's own copy of it, never the file's text, and under every rule of this row (T82).
One process per agentic chat (never a sub-agent's: a sub-agent whose own agent may use MCP uses its chat's table, X.34 step C), started through the chat's own `Confinement::shell` like its `bash` (execution mode, folder, file view, network rule, guard) in the chat's own folder and temp folder whoever's turn or call starts it (`mcp::Home`, set by the node when it makes the table; a sub-agent's turn is offered nothing from a table without one), so a server never works in a sub-agent's copy of the folder: what a sub-agent does through a server is the chat's change, never covered by the sub-agent's merge-back or its report: a foreground run's is made inside the parent's turn and covered by that turn's checkpoint and Undo, a background run's wherever it lands (see the residual); only a run the node started for its parent's `delegate` call gets it (`RunningTurn::delegated_by`, a `Delegation` set in `start_child` and `start_continue` only, gone with the run's turn; `Session::chat_mcp`): a foreground run of its parent's running turn, and so on up to the root chat, or a background run of the root chat (X.24) and the foreground runs under it (the owner, 2026-11-18: "sub-agents allowed to use mcp depending on their own permissions"); a person's message or a retry in a sub-agent's chat gets none, also while the chat's own turn runs or the sub-agent's background run goes on (then it is refused: a sub-agent's chat takes no message while it works), and a callback never runs there (review of PR 149, H1); and neither does an agent the harness treats as read-only (`AgentSpec::changes_things`, T70) nor a plan-mode turn; a sub-agent's call goes through its own chat's approval path (its mode never above its parent's, its own card naming the server), the same caps per turn, and the same client: answers are matched to requests by id (`rmcp`), so sub-agents calling one process at once each get their own; a process that dies under several calls is one failure, counted once by its process number, and a caller that saw an old process fail never stops the one started since (review of PR 149, M2); a contained server reads its requests from a FIFO in a node-private folder outside every file view, which the guard opens without following a link, checks (a FIFO of the node's user), unlinks and hands to bubblewrap (`guard::STDIN_FIFO_ENV`, a `HARNESS_` name no `env_pass`/`env_vars` entry passes and server `env` may not set).
Environment: the core allow-list plus the server's `env_vars` (the node's deny-list wins: provider keys, `.env` names, `HARNESS_*`) and its `env` values, which are `Secret`s added to the node's scrubber.
The process is owned by one task and stopped when the chat is deleted, the node stops (waited for in `NodeRuntime::stop`), it is idle 10 minutes, a call times out or sends a message over 8 MiB, or the chat's table is dropped: in a sandbox chat through the guard channel, so everything it started ends with it; in a `host` chat by killing the server's own process group only, so a process it detached (`setsid`, a double fork) is not reached and stays (`tools/tests/mcp.rs` `a_process_the_server_detached_survives_its_stop`; the stop is not changed).
Every MCP tool is `ToolRisk::Mutating` (asked about in `ask`; `readOnlyHint` and the other annotations are never read); names are `mcp__<server>__<tool>` with a hash when cleaned or cut, server names without `__`.
Caps: 8 MiB per message (the read fails at once), 20 list pages, 1,000 listed tools, 40 tools and 64,000 bytes of tool text per chat, 8,000-byte schemas, 4,096-character descriptions, `startup_timeout_sec` and `tool_timeout_sec` (30 s / 300 s), 3 restarts in a row after failures (a successful call resets the count); a public name two servers would share is offered once, and server names ending in `_` or `-` are refused; two tools of ONE server whose names clean to the same public name (`a b` and `a_b_<its hash>`, review of PR 155) keep the first listed and leave the other out with a note: a server gains nothing by it but hiding its own other tool, since two servers' public names never meet (the server part, before the first `__`, is the server's own clean name and is never cut); `denied_tools` takes `mcp` (every MCP tool) and `mcp__<server>`, and a server it denies whole is not started; an agent with the tool no longer gets every server: a workspace can keep a server for some of its agents (X.34, T80), and for the others' turns it is neither started nor offered (`AgentSpec::deny_mcp_servers`, a deny list that names nothing to start); the approval card names the server and its own name of the tool; a workspace's custom connectors (T85) join a chat's MCP tools under these same caps, after the node's servers, which win a name, and the same rules of who is offered them, but run nothing on the node; notes (which can carry the end of a server's stderr) are scrubbed before they reach the model, and server-supplied names in them pass through `shown_name`; results are text only (other content named), cut to 30,000 characters, scrubbed and quoted like every tool result.
Tests: `tools/tests/mcp.rs`, `agent-native/tests/mcp.rs`, `node/tests/mcp.rs`, `node/tests/sub_agent_mcp.rs` (sub-agents: their own switch, the chat's folder, denials, read-only, plan mode, stop and deletion, parallel answers, caps; background runs: the same, a follow-up, the node's stop, a restart, the token cap, the same card as a foreground call's, and the two Undo cases below), `cli/tests/mcp_sandbox.rs`.
**Residual:** a background sub-agent's server calls (accepted by the owner on 2026-11-18) land in the chat's folder whenever its run makes them: one made while the chat's own next turn runs lies between that turn's snapshots, so that turn's checkpoint lists it and its Undo takes it back although that turn's agent did not make it; one made between the chat's turns is in no checkpoint and no Undo takes it back (`undo_of_the_chats_turn_takes_back_a_background_server_write_made_during_it`, `undo_never_takes_back_a_background_server_write_made_between_turns`); its card waits in its own chat with nobody watching until its wall-clock limit denies it (T72 (8)); a Stop ends its run and its call, but the server, which stays, may finish that call's work later, as for a foreground call; a grandchild with only `read` and MCP under a writing sub-agent changes the chat's folder through a server, although a sub-agent's own sub-agents may otherwise only read; under a foreground sub-agent it is inside the root turn, so that turn's checkpoint and Undo cover it, and under a background one it is a background run's change (in the turn running then, or in none); a writing sub-agent that changes one file both in its copy and through a server ends with the server's version and a refused merge-back, which its parent is told about; an agent with `read` and `mcp` whose servers are all denied to it still counts as one that changes things (plan mode refuses it although it can do nothing), as before; a sub-agent's call cancelled with its turn is dropped by the client (`notifications/cancelled`), but a server may finish the work after the parent turn's last checkpoint, as for the parent's own calls; one call that kills a server (a timeout, an over-cap message) fails the other sub-agents' calls to it at that moment; a node restart ends a sub-agent's call in flight with the node (its server is the chat's, started again by the next turn that offers it); a `host` chat's server, a repository's approved one included (T82, since 2026-11-20), can outlive a `kill -9` of the node (C.11): it ends if it stops when its input closes, and stays if not (`cli/tests/project_mcp_e2e.rs`); a server keeps state between calls, so one approved call can arm what a later call does, and it runs with the chat's folder read-write between calls without any approval (as the code of a program the node's admin installed); "for this turn" allows one exact call, not a server; no digest binds the approval or the start to the executable (a changed `npx` package runs as the old one did); sampling and elicitation are refused by the client library's defaults (`method not found`, decline), not by our code; the scrubber cannot catch an `env` value the server transforms before printing it, and it blanks every occurrence of an `env` value of 8 characters or more anywhere, so `env` is for secrets only; `rmcp` 3.8.0 has RUSTSEC-2026-0462 in its Streamable HTTP client, which this build does not enable: the pin must move to 3.9.0 or newer before an HTTP transport is.
