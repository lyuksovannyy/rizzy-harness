# T40

## Threat

A stuck or steered model repeats one call until the step cap: the same failing command, the same read, the same denied approval asked of the person again and again, spending the person's money and attention (T.1)

## Mitigation

The node's loop keeps a per-turn guard (`agent-native/src/repeat.rs`): the same call (`call_key`: tool, folder, canonical arguments) with the same result (a digest of `ok` and the logged output, less the harness's own tokens that differ on every run: the kept output's random `tool_output id=`, a stop's measured time) gets the harness's warning from the 2nd time, is not run the 5th (decided before approval and dispatch, so the person is not asked again and nothing starts), and a refused call asked for again in a later message (after the model was sent the refusal; the same call again in the refusing message is only refused again, T1-D2) ends the turn there: the rest of that message's calls are closed unrun and never offered for approval.
A change starts every count again, each call keeping its last result: a new successful result of a call made before in the turn (a poll that moved, so a wait between polls is not refused; a failure in new words restarts only its own count, so a failing runner that prints its time does not un-guard the read or the denied approval between its runs, T1-D1), the first successful run of a tool that changes things, a sub-agent that completed, a background end told at the step boundary; calls in between that change nothing do not break a count.
The model is told in `tool_call_finished.note`, a `[harness]` line placed after the result's escaped text (R-2), so tool output cannot forge it; it is its own message kind (`ChatMsg::CallNote`), so a callback turn's opening never takes it; the log rebuilds it byte for byte (the cache prefix does not move); the summariser's transcript carries it as a harness line.
Only digests are kept, and the notes hold no argument or output.
The state is the turn's alone, fed only what was logged; nothing the model writes is read as a switch.
The masked words are `harness_tools` constants that `bash` formats with, so they cannot drift apart.
A parallel batch of read-only calls (X.19) cannot run more calls than the guard allows in order: one call key at most once per batch, and a tool only while its identical-failure streak plus its calls in the batch stay under the second rule's refusal (`RepeatGuard::batchable`); its calls are admitted in call order before any runs and recorded in call order after, so the only difference from the order is stricter (a change made by an earlier call of the batch resets a later one's count from the next step); `agent-native/src/parallel_tests.rs`.
One behaviour in chats and routines; the thresholds are constants, not `node.toml` keys, and there is no switch to turn the guard off (owner, 2026-11-13); the note is for the model only, whether the UI shows it is a later web task.
Tests: `agent-native/src/repeat_tests.rs` (the real `bash` with filtering on, a failing runner whose text changes with a denied change between its runs, a failing build that moves after each edit, the same call twice in the refusing message, several calls a step, a completed and a failed sub-agent, a background end, a callback turn after a guard-ended turn), `agent-native/src/repeat.rs`.
**Residual:** a model that changes one byte of the call starts a new count; a program whose own output changes every run (a test runner's "finished in 0.03s") is a new result every time, so the same failing test run of most runners is not caught itself; a wait between runs of a failing check whose text changes is warned from its 2nd run and refused at its 5th (the note says to wait inside one command); a successful call whose result is new every run (a background start with a new id) restarts the others; `max_steps` stays the bound.
No test compacts mid-way through a callback turn with a call note before its trailing notes (the pop takes only `ChatMsg::Note`, by reading).
Review: T1-R1 to R6, T1-D1, D2.
