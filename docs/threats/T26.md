# T26

## Threat

Another local user reads a secret file the server uses (a restored backup, a copied `.env`, a key file with a loose umask) (audit L7)

## Mitigation

At start `serve` and `node run` refuse any secret file whose mode has group or other bits (`mode & 0o077`), before reading it, with the path, the mode and `chmod 600 <file>`: `secrets.toml`, `api-token`, `claim-code` (both in `load_or_create_secret`, so every reader), private keys in `keys/` (`*-key.der`, `node.key`) and the `.env` `serve` loads.
A symlink is judged by its target.
Files the harness writes are created 0600 by `open(mode)`, never chmod-ed afterwards; `secrets.toml`'s temp file is removed and created anew, so a stale one cannot keep a looser mode.
Unix only (other systems have no mode bits; nothing is checked there).
Tests: `cli/tests/data_dir.rs` (`open_secret_files_stop_the_server`), `auth.rs`, `secrets.rs`.
**Ownership** (R.4, review N-3): the same check refuses a secret file owned by another user, and the data directory is created 0700 (not created under the umask and chmod-ed after), refused when another user owns it, and made 0700 when it exists looser, a failing chmod stopping the start instead of being ignored (`secrets::check_data_dir`; tests `secrets.rs` `a_secret_file_of_another_user_is_refused`, `cli/tests/data_dir.rs` `a_data_dir_of_another_user_stops_the_server`).
**Residual:** `master.db` (chats, blob keys) is protected by the 0700 data directory only; `link::write_private` reuses a stale temp file's mode.
