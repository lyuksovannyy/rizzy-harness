# T10

## Threat

Another account reads or drives someone else's work

## Mitigation

Every session carries `owner_id`; REST and WS show a session only to its owner, admins included (server admins manage accounts, workspace admins and owners manage members and defaults; neither gets chats).
A workspace only groups chats: its mapping is master-side (never asserted by a node, T7) and is ignored once the owner leaves, so a chat cannot be planted in or stranded outside its owner's workspaces.
A chat's owner is the master's record too: no event from a node changes it once set, and a second `session_created` (which used to move a chat to the owner of the parent it named, or to nobody) is refused and freezes the chat (§3, Gate 3 review L-2; `the_row_is_set_at_seq_1_and_its_owner_never_changes`, `a_second_session_created_moves_nothing_and_freezes_the_chat`).
Only the API token, the machine owner's key on disk, sees all (an accepted gap until per-user tokens exist: T29).
**The data directory stays out of every session** (it holds the API token, the session keys, `secrets.toml` and `master.db` with everyone's chats): every node runtime protects its own data directory (for the embedded node, the master's), a session cwd that is inside it, equal to it or an ancestor of it (`$HOME` with the default `~/.local/share/rizzy-harness`) is refused at create and again before every turn and restore (sessions loaded from the log included), and `read`/`write`/`edit`/`outline`/`grep`/`glob` refuse any path whose real location (links and `..` resolved, a dangling link judged by its target) is inside it, `allow_outside_workspace` included; searches rooted above it skip it.
The API token is in the redaction set. bash and graphify cannot open the data directory: the sandbox grants nothing in it but the session's own temp folder (`<data>/sandbox-tmp/<session>`) and graphify's own output folder (T4).
Residual: on kernels before Landlock ABI 9 a command can reach pathname Unix sockets and through them start programs outside the sandbox (R2), which is why the embedded node stays admins-only by default (T11).
**Every chat has an owner and an end** (R.4, review P-6): a create records who asked for it (`create-intent:<id>` in the mirror's kv) before the node hears of it, so a `session_created` that comes after the ack, or after the ack timed out, is claimed for that person when it lands (and the claim drops another owner's parent, as on the usual path), instead of staying a chat only the API token can see; the intent is removed once the chat is claimed, or when the create was refused or never sent.
Deleting a user deletes every chat of theirs on the mirror (tombstoned) and on its node, at once or at the node's next hello.
**Deleting a chat deletes the chats of its sub-agents, at any depth, on the mirror and on their nodes, with the same `Delete` command.**
The chat goes first, through the one-chat path exactly as a chat with no sub-agents does (its `Delete` stops its turn; a refusal leaves it in place and is returned, and nothing below it has been touched), and the request is answered then.
The chats below are deleted in a task in the background: the deepest depth first, eight at a time (a slow node does not make anything last the sum), then a second listing with the same owner for chats added meanwhile (it finds a chat whose `session_created` reached the mirror before the chat's row was removed; one that lands after has no parent link and is not found).
A chat below always loses its mirror copy, whatever its node answers (done, away, silent, refusing); the tombstone makes the node be told again at its next hello or its next event of the chat (`redelete`, as for every deleted chat).
They are found from the master's mirror by `parent_id` and only when their `owner_id` is the deleted chat's at every depth (read once, before anything goes; the walk neither lists a chat of another owner nor goes through it), because a parent link rests on the node alone and a delete cannot be undone.
The listing is one scan and a walk in memory, 64 deep and 10,000 chats at most (past it one warning is logged; the second listing takes more, and a later delete the rest).
Every delete path goes through `Master::delete_session`: the person's, the account's, retention and the incognito purge.
Residuals: a master killed between the chat's delete and its sub-agents' leaves their chats behind, unreachable from the sidebar and visible to the API token, and nothing sweeps them at start (before, every delete left all of them); a node can name another chat of the same person on the same node as the parent of a chat that person just created, so deleting the first deletes the second (same node, same owner, and the node controls both chats anyway).**

An intent lives one hour (`CREATE_INTENT_TTL_MS`, far past the 15 s ack timeout): it is removed when its chat is claimed, when the create is refused or never sent, and otherwise by the next create after the hour, and an older one claims nothing (fix review 6 N-2; `a_create_intent_that_never_lands_is_removed_and_claims_nothing`).
Residual: a late chat is claimed but not linked into the project the create named.
Fix review 1's R3-1 (a node that acks before `session_created` kept a cross-owner parent in the row) is closed by the same path: the late claim runs `claim_session`, which drops it.
R3-2 (a node can make many tiny frozen placeholder rows, one refused first event each) is accepted: one small row per session id, bounded by the link's queue, and no worse than the node writing real sessions of its own; a per-node quota (T8) would bound both.
